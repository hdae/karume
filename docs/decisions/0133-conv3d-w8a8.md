## Context

The Wan2.2 VAE decoder spends 85% of its GPU time in `conv3d` (562 ms per next chunk on the RTX 3080 Ti; 31
chunks and 2.04× redundant pixels at 1280×704×121 give about 480 s for the VAE stage). The conv3d kernel is the f32
implicit GEMM of ADR 0118 and runs at 8.7 TFLOP/s — the level of this machine's f32 GEMM skeleton, so a better
address computation would gain little. The runtime's integer dot-product path (`linearCompute: "a8"`, ADR 0025)
runs 3–4× faster on the same machine, and the chunk graphs' 35 conv3d nodes all have `Cin` in {48, 256, 512, 1024}
(a multiple of 4) and `groups == 1`. The maintainer ruled on 2026-10-23 to build the conv3d counterpart of linear's
w8a8 (V-1 of the recon) before the larger decoder tile (V-2).

What makes conv3d different from linear: the activation side of the implicit GEMM is not a stored matrix. Column
`n` of `Xcol[K, N]` is the receptive field of output pixel `n`, gathered from `x[Cin, T, H, W]` per tap
`(kt, kh, kw)`, so one input pixel contributes to up to `Kt·Kh·Kw` output pixels. A per-token scale "over the im2col
row" would have to be recomputed per output pixel (the scale is not reusable across taps), or the input has to be
quantised once with a scale whose scope is reusable — one scale per input pixel over its channels.

## Decision

### 1. Scale per input pixel, integer dot product per tap, f32 flush at tap boundaries

The activation `x[Cin, T, H, W]` is quantised **once per input pixel over its `Cin` channels** (symmetric i8, the
rule of `quantize_rows`: `s = max(amax/127, tiny)`, closed at ±127). The reduction over `K = Cin·Kt·Kh·Kw` runs
**tap-major**: for each tap `τ = (kt, kh, kw)` in ascending order, the dot product over `Cin` is an exact `i32`
sum of the pixel's packed i8 channels against the weight's packed i8 channels, and the f32 accumulator takes it
with the pixel's scale:

```
accf = 0
for τ in taps (ascending kt, kh, kw):
    p    = input pixel of output pixel n under tap τ      (out of range → acci = 0 and s = 0)
    acci = Σ_{ci} xq[p, ci] · wq[co, ci, τ]               (exact i32, |acci| ≤ Cin·127·128)
    accf = fma(f32(acci), xs[p], accf)                     (one rounding per tap)
out[co, n] = fma(accf, wscale[co], bias[co])               (+ 1)
```

The form is w4a8's per-group flush (ADR 0076) with the roles swapped: there the scale that changes along K is
the weight's group scale and the per-row activation scale goes into the final fma; here the scale that changes
along K is the activation's pixel scale and the per-channel weight scale goes into the final fma. The rounding
count is `Kt·Kh·Kw + 1` (28 for the 3×3×3 layers, 2 for 1×1×1), independent of `Cin` and of the tile geometry.

Out-of-range taps (padding, the time edges) contribute exactly nothing: the B tile is zero-filled (`idot(0, x) == 0`)
and the scale used for that tap is `0.0`, so `fma(0, 0, accf) = accf` (a signed-zero flip when `accf` is −0 is
the only effect, and `===` comparison treats it as equal).

Rejected alternatives: (a) one scale per output pixel over the whole receptive field — exact single integer sum
and no weight reordering, but the B tile would read f32 and quantise on the fly (the same traffic as the f32
kernel, which is what the a8 path must cut), and the scale is 27× coarser; (b) a scale per input channel plane —
the scale changes inside the dot product at every element, so no packed integer dot product applies.

### 2. Contract class E — a TS mirror at atol = 0

The integer sums are exact, and the only floating-point operations are `f32(acci)`, `fma` per tap and the final
`fma` — the same operations as w4a8, so the TS mirror (`referenceConv3dI8a8`) reproduces the GPU bit for bit on
fused-fma implementations. The known 1-ULP deviation of non-fused `fma` (Metal — docs/known-issues.md) is inherited
from ADR 0025 unchanged. The mirror is a plain loop over `(co, n, τ, ci)` in the order above; it copies no tile
structure.

Because the per-pixel quantisation of x is the mirror of `quantize_rows` on the transposed layout, the tie-margin
caveat of ADR 0025 (GPU division may move `x/s` across a rounding boundary) applies as is: the kernel tests measure
the margin of their data before claiming atol = 0.

### 3. Activation quantisation reuses `quantize_rows` on a transposed copy

The path is three dispatches per conv3d node: ① a strided copy `x[Cin, P] → xt[P, Cin]` (P = T·H·W; the `strided`
kernel of ADR 0011 with permute strides), ② `quantize_rows(rows = P, dim = Cin)` → `xq[P, Cin/4]` words and
`xs[P]`, ③ the integer-dot-product GEMM. The transposed f32 copy is `4·Cin·P` bytes per node (16 MiB for the
largest layer) and is read once. ①② are temporaries closed inside the node (the arena invariant of ADR 0004).

Measured (the spike of decision 8): ① costs 0.2–3.1 ms per node against 5.6–11.9 ms for ③ on the three heavy
layers (20% of the path on the 256-channel layer at 128²), and on the 1×1×1 layers (1% of the decoder's work)
it exceeds the GEMM, so those nodes come out slower than the f32 path (3.2 ms against 2.5 ms). A fused
per-pixel quantiser that reads `x[Cin, P]` directly is the follow-up with the largest expected gain on this
path (Open points); it is not a precondition.

### 4. The weight is reordered to tap-major on the host at Session construction — no new storage form

The container keeps `[Cout, Cin, Kt, Kh, Kw]` i8 with one scale per output channel (the exporter's conv3d i8 of
ADR 0118). At upload, Session construction reorders the bytes of each output channel to `[Cout][Kt·Kh·Kw][Cin]`
(`reorderConv3dWeightTapMajor` — a permutation inside each row, so a piece of a row-split upload is reordered on
its own) and flags the resident record (`layout: "conv3d-tap-major"`); the kernel then reads one word per pack.
The set of weights to reorder is decided from the graph alone (`conv3dTapMajorInitializers` in plan.ts): i8
storage, consumed only at the weight slot of conv3d nodes that all pass the shape eligibility, not a graph
output. The recipe builder takes the w8a8 path exactly when the flag is set, and fails loudly if a flagged
weight reaches a node that is not eligible — the f32 kernel never reads a permuted weight. ADR 0024's "zero
reshapes" is about run time; this is a one-time CPU pass over the bytes, counted as decode time in the build
statistics.

Measured first (the spike of decision 8): reading the canonical layout in place — four byte gathers per word
at stride `Kt·Kh·Kw` — ran the 1024-channel 3×3×3 layer in 13.0 ms against 5.6 ms with the tap-major layout,
and the whole path at only ×1.1–1.2 over the f32 kernel; so the reorder is the decision, not an open point.

### 5. Geometry: the i8a8 default tile, no profile field yet

The kernel takes an `I8a8Geometry` (the shared tile arithmetic and inner-product loop of
src/kernels/i8a8-geometry.ts — the same single source as linear and fused attention) and runs the default of
linear (`tile128x64r8x8w8x16k16`, M = Cout rows, N = output pixels). The geometry is in the pipeline key. The
adapter profile has no conv3d field: adding one needs sweep cases of the decoder's shapes, which is a separate
sweep-and-register step (ADR 0115), not part of this change. The f32 conv3d keeps its own rule (ADR 0118
decision 1).

Eligibility (all required; otherwise the node runs the f32 implicit GEMM and the pipeline key shows it — ADR
0058): `convCompute: "a8"`, i8-resident weight, `groups == 1`, `Cin % 4 == 0`, `Cin ≤ 131,072` (the i32 bound per
tap, the same constant as ADR 0025's K limit). The v4 output store needs `P_out % 4 == 0` (the output is
`[Cout][P_out]`, so four consecutive pixels of one channel are one word); otherwise the scalar store.

### 6. A new Session option `convCompute: "a8"` and the preset token `conv8`

`SessionOptions.convCompute?: "f32" | "a8"` (default `"f32"` — the existing behaviour does not change by a byte;
ADR 0058). It is an axis of its own, not a widening of `linearCompute`: the DiT presets enable `linearCompute:
"a8"` for the transformer, and the VAE Session must be able to opt in independently (the Wan family hands the
VAE decoder Sessions their own options — today `{}`, tile-decode.ts). The hub manifest's `session` accepts the key
with the same closed vocabulary; the models' acceptance table lists it for the families that declare it.

Preset naming (ADR 0074): the token `conv8` means `convCompute: "a8"`, next to `a8` (linear) and `attn8`
(attention). Wan2.2 gains two presets: `i8` (reference — the transformer and the VAE decoder in i8 storage, empty
`session`; the control of the E2E difference floor) and `i8-a8-attn8-online-conv8` (practical). The base storage
is `i8` because the VAE roles are now i8 (the storage common to every role — ADR 0074 §1). The existing presets
are unchanged, and the default stays `f16+dit8-a8-attn8-online` until the A/B check and the visual check of
decision 8 pass.

### 7. The VAE decoder's i8 series comes from the exporter

`wan.export_vae` gains an i8 storage (`fake_quant_int8` with the exporter's default targets, which include
`nn.Conv3d` — one scale per output channel, the same quantiser as the DiT's `dit8`), written as a second series
of the two chunk graphs. Nothing in the runtime quantises weights at load time (the a8 contract of ADR 0025 is
"int8 activations against int8-resident weights", and this ADR keeps it).

### 8. Acceptance — spike first, then the Wan2.2 gates

1. Kernel: TS mirror at atol = 0 on the chunk graphs' shapes (reduced) and the edge shapes (`Cin % 16 ≠ 0`,
   `P_out % 4 ≠ 0`, padding on all three axes, stride and dilation ≠ 1, Kt ≠ Kh ≠ Kw), both integer dot-product
   variants (`dp4a` / emulated) bit-identical, the four-point check of ADR 0110 decision 3 as far as it applies to
   class E (mirror, fault injection of the tap order and of the zero fill).
2. Kill line (standalone timing, before any wiring beyond the kernel): below ×2.0 on
   `[1024,1024,3,3,3] → [1024,2,32,32]` against the f32 conv3d of the same shape, the work stops here and this ADR
   is rejected with the number. Expected ×3–4. **Result (2026-10-23, RTX 3080 Ti, Node + Dawn, min of 5 runs
   of one node, i8 weights on both paths)**: ×2.6 on that layer (15.3 → 5.8 ms, 9.9 TMAC/s), ×2.5 on
   `[512,512,3,3,3] → [512,4,64,64]` (24.6 → 9.7 ms), ×2.2 on `[256,256,3,3,3] → [256,4,128,128]` (33.3 →
   15.3 ms), ×0.8 on the 1×1×1 `[512,1024,1,1,1]` (2.5 → 3.2 ms — the transposed copy, decision 3). The line is
   passed; the f32 numbers of the two larger-N layers moved by up to ×1.6 between runs (the timing trap of
   this machine), the a8 numbers by less than 5%.
3. Wan2.2 (ADR 0110 §5): the census (every conv3d of the decoder on the a8 key), the difference floor against
   `i8`, the collapse ceiling of the relative RMS at the first chunk's output frame against `i8` (and recorded
   against `f16+dit8`), a sha256 row for the new preset, the VAE stage time at 1280×704×17 and ×121, and the
   maintainer's visual check (at least four seeds × two prompts). The default moves only on that ruling.

## Consequences

- One more Session option and one more preset token; the f32 conv3d path and every existing preset are
  byte-for-byte unchanged.
- The VAE decoder's int8 error compounds over the chunks through the causal cache; the A/B form measures it at
  the first chunk, the visual check over whole clips.
- The conv2d layers of the decoder (14% of its MACs — the 2D upsampling convolutions) are not covered; the same
  design applies to them (perf-ledger K-2) once conv3d is in.

## Alternatives considered

- Quantising the weights at Session construction instead of exporting an i8 series — rejected (decision 7):
  it would be a second quantiser whose values the exporter's goldens never saw, and the a8 contract is
  int8-resident weights.
- f16 compute for conv3d (`:c16`, V-3) — not exclusive in principle but it replaces the f32 multiply that this
  path removes, so it is not pursued alongside (recon §4).
- A larger decoder tile (V-2) — composes with this path and follows it (the maintainer's order).

## Open points

- A fused per-pixel quantiser that skips the transposed f32 copy (decision 3 — up to 20% of the path on the
  wide layers, and the whole loss on the 1×1×1 layers).
- A conv3d field in the geometry profile with sweep cases of the decoder's shapes (decision 5).
- The conv2d counterpart (K-2).

## Context

### Request

The maintainer asked to try Wan2.2 TI2V 5B (Alibaba's text / image-to-video model, Apache 2.0) before
MiniMax H3, including the w8a8 practical preset (i8 weights + 8-bit activations), with the
implementation delegated. Wan2.1 T2V 1.3B (ADR 0118), umT5 on the GPU (ADR 0119) and the w8a8
presets (ADR 0120) were done; this ADR puts the 5B on top of those parts.

### Terms introduced here

| Term                                 | Meaning                                                                                                                                                                                                                             |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TI2V                                 | text-image-to-video: one set of weights serves T2V (text only) and I2V (text + one first image)                                                                                                                                     |
| condition frame                      | in I2V, the first latent frame, replaced by the image latent; its tokens enter the DiT at t = 0 (upstream study §2.3)                                                                                                              |
| condition mask                       | DiT graph input `condition_mask [1,S,1]`: whether a token belongs to the condition frame. All false for T2V                                                                                                                         |
| two time inputs                      | DiT graph inputs `timesteps_proj` (generation t) and `timesteps_proj_condition` (condition t = 0). The time MLP runs twice with M = 1 (one row) and the condition mask selects the modulation (decision 3)                            |
| P                                    | tokens of the condition frame = (H/32)·(W/32); 880 at 1280×704                                                                                                                                                                      |
| patchify space                       | the space at the VAE 2.2 input and output where RGB 3 ch is folded 2×2 spatially into 12 ch; 8 px per latent, the same scale as the 2.1 pixel space                                                                                 |
| DupUp3D / AvgDown3D                  | VAE 2.2 shortcuts outside the residual: channel duplication + 3D depth-to-space (decoder); 3D space-to-depth + group mean (encoder) (upstream study §3.2)                                                                            |
| meta trace                           | export form of ADR 0119: torch.export traces the upstream on the weightless meta device; the linear weights are quantized to i8 per row chunk from the checkpoint and handed to emit as `fixed_weights`                            |
| layer-by-layer f64 reference         | CPU reference that reads the weights one block at a time and runs in f64 (decision 7)                                                                                                                                               |
| generation descriptor                | TS constants per generation for the values that differ between Wan2.1 and 2.2 and cannot be derived from the graph declarations: latent mean / std, accepted set, defaults, fps, the VAE `patch_size` (`WanGenerationDescriptor`) |
| i8 weights / linear dispatches       | the linear weights the container stores as i8 (307 in the 5B) / the linear dispatches of one pass that the census counts (310 in the 5B — the three time-MLP linears run twice, decision 3)                                        |

S, one pass, the reference and practical presets, r (normalized ratio), relRMS and `dit8` / `a8` /
`attn8` / `s16` are used as in ADR 0120.

### Findings of the investigation

- **The DiT is the Wan2.1 class with the same 825 tensors, only larger** (dim 3072, 24 heads × 128, 30
  layers, FFN 14336, in / out 48 ch, 4,999,787,712 parameters — upstream study §1). The forward
  differs in two points: the time is per token (`[B,S]`, modulation `[B,S,6,C]`), and there is no CLIP
  image encoder and no `k_img` / `v_img` (§2.1).
- **I2V replaces the first latent frame with the image latent and runs only those tokens at t = 0**
  (§2.3). t takes two values only, so running the MLP on two rows and selecting avoids the 1.87 GiB
  `e0` and about 1.8 T MAC per forward (§2.4).
- **The VAE is different** (Wan2.2-VAE, z_dim 48, compression 4×16×16, decoder 555,049,228 parameters =
  7.6× 2.1 — §3.1). Its new operations (DupUp3D, AvgDown3D, patchify / unpatchify, asymmetric zero
  padding) are all expressible with reshape / permute / expand / slice / pad / sum / mul of rank ≤ 4:
  **no new IR op** (gap study §2).
- **At equal pixels the token count is 1/4 of 2.1.** The official default 1280×704 × 121 frames gives
  S = 27,280 and 258.46 T MAC per forward (§4.4).
- **umT5 has the same weights as Wan2.1** (the Wan2.2 Diffusers bf16 is the round-to-nearest-even of
  the Wan2.1 f32 on all 242 tensors; the tokenizer sha matches — umT5 provenance study §0, upstream
  study §5). `karume-umt5-xxl` can be referenced across repositories as is.
- **The sampler code has zero diff to 2.1** (UniPC, 50 steps, guidance 5.0, shift 5.0, 24 fps, 121
  frames — §4.1). The official T2V accepts only 1280×704 / 704×1280 (`configs/__init__.py:46`).
- **The f16 DiT is 9,999,575,424 B (9.31 GiB)**; i8 linears alone give 5,012,178,432 B (4.67 GiB)
  (gap study §3). The official code runs the DiT under bf16 autocast; the weights are F32.
- **torch CPU linear splits the last bit between M = 1 and M rows of the same input** (max diff
  3.6e-7 to 1.9e-6; gap study §6.1). diffusers' `WanPipeline(expand_timesteps=True)` passes a `[1,S]`
  timestep, so its time MLP runs with M = S.
- **diffusers' 2.2 `tiled_decode` blends in the 12-ch patchify space and unpatchifies afterwards**
  (`autoencoder_kl_wan.py:1355-1401`); tile 256 px, stride 192 px by default.
- The independent verification corrected or added: the largest VAE intermediate at tile 16 is the
  padded CausalConv3d input `[1,512,6,130,130]` (207.7 MB), not 128 MiB; HF `vae/config.json`'s
  `clip_output` key is rejected by diffusers 0.39.0's `__init__` and is dropped when the config is
  passed directly; the official and diffusers I2V replacement forms were equal only by reading the
  code (later proven, addendum 2026-10-10); the tokenizer asset lives in the `karume-wan2.1`
  repository; the largest |w| of the small DiT tensors is 7.71 (within f16).

### Constraints

- Cross-cutting invariants: unsupported or unexpected input fails loudly; turning the sha check into
  a tolerance is prohibited (ADR 0106); runtime dependencies are Web standard APIs only; no module
  has side effects.
- The development machine at the time was the Intel Arc B570 (Deno, total allocation ceiling 9,600
  MiB, 2 GiB binding limit, device lost after a 5 s submit, delayed release after `destroy()`) with
  31 GiB of RAM. It was replaced on 2026-10-06 by an RTX 3080 Ti (12 GiB) with 64 GB of RAM (addendum
  2026-10-06); the B570 figures in this ADR are history. The GPU is shared with training.
- The 2.1 sha rows, bands and case ids do not change by a single bit (decision 10).

### Capacity and time estimates (history)

The pre-measurement extrapolations from 2.1 (gap study §3.2 / §4.2) put 832×480×81 within the B570
with 0.37–0.51 GiB margin and 1280×704×121 outside it, and estimated the host RAM of export and
reference (f64 of the whole 5B = 37.25 GiB, hence decision 7). All were replaced by measurements in
stages 0–10 (addenda below).

## Decision

### 1. The upstream is the Diffusers release pinned by commit SHA — Apache-2.0, only the transformer and the VAE are fetched

- Upstream: `Wan-AI/Wan2.2-TI2V-5B-Diffusers` @ `b8fff7315c768468a5333511427288870b2e9635` (license
  `apache-2.0`, not gated). The recipe's `SOURCES` has the row `ti2v-5b`
  (`tools/export-recipes/wan/sources.py`).
- Fetched: `transformer/` (19.99 GB) and `vae/` (2.82 GB), plus `scheduler/` (config only — the
  reference reads `flow_shift`) and the root `README.md` / `model_index.json` (license front matter,
  component index). `text_encoder/` and `tokenizer/` are not fetched (decision 9).
- `COMPONENTS` and `EXPECTED_PARAMETERS` become per-model tables. 5B expectations (sums of the
  safetensors header element counts): transformer 4,999,787,712; vae 704,688,668.
- diffusers stays at 0.39.0, the Wan recipe's pin (ADR 0118 decision 7); it has every TI2V branch.

Why: every Diffusers component is safetensors and maps onto the diffusers classes Karume already
patches (`WanTransformer3DModel` / `AutoencoderKLWan`); the official `WanModel` does not suit
torch.export and its VAE and T5 are pickled `.pth`. The DiT values match the official release
bit for bit (sampled), so the weight provenance does not change.

Protects: anyone builds the same reference from the same revision; only the needed components are
fetched.

### 2. Two presets — reference `f16+dit8` and practical `f16+dit8-a8-attn8-s16`; no `f16` preset

| Preset                  | `weights.transformer` | VAE (decoder first / next, encoder) | `session`                                                                       |
| ----------------------- | --------------------- | ----------------------------------- | ------------------------------------------------------------------------------- |
| `f16+dit8`              | `i8`                  | `f16`                               | empty (i8 weights, f32 compute) — the reference preset                         |
| `f16+dit8-a8-attn8-s16` | `i8`                  | `f16`                               | `linearCompute: "a8"`, `attentionCompute: "a8"`, `attentionScoreStorage: "f16"` |

- Preset grammar, the i8 scope (all DiT linear weights; bias / norm / `scale_shift_table` stay f32 as
  upstream; no calibration) and the three keys of the acceptance table `WAN_SESSION_POLICY` are as in
  ADR 0120 decisions 1 / 2 / 7. Both presets share one container `transformer/model.i8.krm`.
- Counts: 306 rank-2 linear weights (30 blocks × 10, `condition_embedder` 5, `proj_out` 1) plus the
  patch embedding that the recipe turns into a linear give **307 i8 weights**, as in 2.1. **One pass
  runs 310 linear dispatches**: decision 3 runs the three time-MLP linears twice on the same weights.
  The census counts dispatches (`WAN22_DIT_LINEARS` = 310 in
  `packages/models/tests/helpers/census-table.ts`).
- **No `f16` preset is built for now** (ruling 2 (a)). Shipped presets SHOULD be ones whose checks and
  sha rows the development machine can hold (re-graded 2026-10-18 to SHOULD: the RAM premise is gone
  with the 64 GB machine; an original-weights preset follows ADR 0128 decision 4 — best effort and
  opt-in, and for this upstream it means F32, not f16).
- The default preset was to be decided by the visual review of stage 7, with the reference preset as
  the provisional default until then (superseded by this ADR's addendum of 2026-10-06 and ADR 0128
  decision 1 on 2026-10-17: the maintainer's visual review of the practical preset alone made it the
  default on 2026-10-06; `WAN22_DEFAULT_QUANT` = `f16+dit8-a8-attn8-s16` in
  `tools/export-recipes/wan/distribution.py`). The maintainer's policy of 2026-10-04 — the default is
  the most practical preset today — leaves room to change course later (as in ADR 0120).
- **Every test case names its preset explicitly** (the lesson of ADR 0120's default switch): omitting
  `quant` is stopped by the type, so switching the default does not rewrite tests or sha rows.

Why: the f16 DiT (9.31 GiB) fits none of the B570 candidates and is borderline even on an RTX 5070 Ti
at 1280×704×121; exporting it needs either the RAM edge or widening `fixed_weights` to f16 in the
exporter core (`fixed_weights` takes i2 / i4 / i8 only — `tools/exporter/src/karume/emit.py:554-555`).
The reference preset is the partner of the self A/B difference floor (`referencePartnerOf` throws on
zero partners — ADR 0120 decision 1); GPU i8 dequantization matches the CPU expansion bit for bit
(ADR 0019), so the reference-path r check can use it.

Protects: the difference floor is never vacuous (the partner has the same weights — ADR 0110 decision
5 ②); a preset entering `defaultQuant` passed a quality review (ADR 0110 decision 8).

### 3. The DiT graph is I2V-capable from the start — two time inputs, a condition mask, `where`

- **Inputs**: the five Wan2.1 inputs (tokens, `timesteps_proj [1,256]`, context `[1,512,4096]`, two
  RoPE tables) plus `timesteps_proj_condition [1,256]` and `condition_mask [1,S,1]`. Token width 192
  (48 ch × 1×2×2).
- **In the graph**: the time MLP (`time_embedder` → SiLU → `time_proj`) runs **twice with M = 1**. Each
  modulation component (six per block, two in the head) is selected per token by
  `where(condition_mask, condition, generation)` into `[1,S,C]`; `[S,6,C]` is never built (1.87 GiB f32
  at S = 27,280). `where` broadcasts its three operands right-aligned.
- **Placement of `where`**: the patch writes each `where` immediately before its consumer (the
  pre-attention modulation, its residual gate, the pre-FFN modulation, the FFN gate, the head
  modulation). Building all six at the block head as upstream does would keep up to six `[1,S,C]`
  values alive across attention, because torch.export keeps the order. (Stage 1 measured: 182 `where`
  nodes, each consumed by the next node; stage 2 saw no capacity increment.)
- **T2V**: mask all false; `timesteps_proj_condition` gets the generation value. **I2V**: the first P
  tokens (the first latent frame — contiguous at the front by the token index `(f·H' + h)·W' + w`) are
  true and the condition t is 0.
- **The symbolic upper bound of S is 27,280** (1280×704×121; `SYM_MAX` in
  `tools/export-recipes/wan/ti2v_export_dit.py`). It only bounds torch.export's `Dim("S")`; IR symbols
  have no bounds and `requiredLimits` derive from resident memory only (ADR 0089 decision 3), so it
  does not affect admission.
- **The condition mask is a bool graph input** (IR semantic dtype bool, stored as u32 0 / 1 —
  `docs/ir-v2.md`).
- The recipe's configuration check (`_assert_supported_config` in `dit_patch.py`) passes because 2.2
  has `image_dim null`; the RoPE realification and the linear patch embedding carry no dimensions and
  apply as they are.

Why: the 5B DiT is not re-exported (CPU hours, new goldens) for I2V; goldens, sha rows and bands of
the T2V stages stay valid. **Not one call with M = 2**: torch CPU split the last bit between M = 1 and
M ≥ 2, and whether the GPU linear changes its reduction with M is unconfirmed; with M = 1 twice the
T2V generation row computes exactly as in Wan2.1, and `where` only selects.

Protects: T2V values computed in the Wan2.1 form; no new DiT container or goldens when I2V is added;
one symbol for the S-shaped graph (ADR 0034).

### 4. CPU comparison with upstream — T2V through the 1-D timestep path, I2V through per-token temb built with M = 1

The eager equivalence of the patch (MUST — the discipline of ADR 0118 decision 3, measured on the
real weights) has one counterpart per time representation:

| Path        | Counterpart                                                                                                                                                                                                                             | Expected            |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| T2V         | upstream `WanTransformer3DModel` called with a 1-D timestep (the `[B,6,C]` path, time MLP at M = 1) — the same counterpart as Wan2.1                                                                                                    | bit-identical       |
| I2V         | reference wrapper: upstream `condition_embedder` called twice with M = 1 (generation t and 0), per-token `temb [1,S,C]` and `timestep_proj [1,S,6,C]` built and passed to the upstream block (`temb.ndim == 4`) and head (`ndim == 3`) branches | bit-identical       |
| Observation | the 2-D timestep path (M = S linear) that diffusers' `WanPipeline(expand_timesteps=True)` / `WanImageToVideoPipeline` use                                                                                                               | recorded, not a check |

- The GPU r-check reference (decision 5) uses the same time representation.
- **Full-loop reference** (the two-step loops of stage 6 for T2V and stage 9 for I2V): the same time
  representation; the difference to diffusers' own pipeline (M = S) is an observation. The comparison
  of the GPU loop with the diffusers CPU f32 reference is opt-in (`KARUME_UPSTREAM_PARITY=1`), like the
  other families; the sha rows stay in the default lane (re-graded 2026-10-18: the same run's sha rows
  and wiring fault injections catch regressions; ADR 0129 addendum (2)). The band judgement is gated
  at the assertion (`packages/e2e/tests/e2e_wan_ti2v_pipeline_test.ts`,
  `e2e_wan_ti2v_i2v_pipeline_test.ts`, section "Default run vs opt-in upstream parity"): the reference
  cases still run by default for their sha rows, and the fault injections use the band only as the
  margin a wiring fault must exceed.
- Eager equivalence runs at S = 192 with the patched graph and upstream sharing one set of f32
  fake-quant weights.

Why: against the M = S path, the reduction difference of torch CPU linear (up to 1.9e-6) would mix
into the check and hide port errors. The I2V wrapper reuses the upstream block code, so the per-token
modulation formula is not re-transcribed.

Protects: "the port is correct" is stated as bit identity; the pipeline's M = S path stays an
observation.

### 5. Numeric baseline — the checks compare with f32 / f64 references on the same i8 fake-quant weights; the official bf16 is not a baseline

| Tier                       | Baseline                                                                                                              | Check                                                                                       |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Port (reference preset)    | CPU f64 / f32 reference (diffusers code in f32 / f64, i8 fake-quant weights, decision 4 time form)                     | normalized ratio r against f64 at S = 192 and full size (ADR 0118 decision 8, ADR 0120 decision 3) |
| Practical preset           | the reference preset on the same machine and the same i8 weights                                                      | self A/B check (ADR 0110 decision 5, ADR 0120 decision 4)                                   |
| Quality                    | the maintainer's visual review (seeds 42–45 × 3 prompts); also the quality ruling of the reference preset itself       | ruling (ADR 0058 addendum 2026-09-13)                                                       |
| Observation (not a check)  | weight-only i8 vs unquantized CPU f32 at S = 192, compared with the 1.3B measured the same way                         | recorded; above twice the 1.3B value, escalate before stage 2                               |

- The GPU r check of the port tier is opt-in (superseded by ADR 0129 addendum (2) on 2026-10-17: the
  port is proven when the family is implemented, later changes are caught by the sha rows and the
  self A/B checks; `describe.skipIf(!UPSTREAM_PARITY)` at
  `packages/e2e/tests/e2e_wan_ti2v_dit_test.ts:1997`, `:2106`, `:2218`).
- The official bf16 autocast run is neither a check nor a standing record.
- "Closest to the original weights" is not mistaken: the official run is f32 weights × bf16 compute,
  Karume's reference preset is i8 weights × f32 compute. Weight rounding is seen by the observation,
  compute rounding by the r check.
- S = 192 also uses the f64 reference and r, following the i8-series goldens (`wants_float64` in
  `export_dit.py`).

Why: WebGPU has neither bf16 nor f64 and Karume computes in f32; with bf16 as baseline, bf16's own
rounding would set the floor and no band could be justified. Diffusion trajectories diverge, so pixel
distance does not measure quality.

Protects: bands come from measurable error only; quality is judged by a human (ADR 0110 decision 8).

### 6. VAE 2.2 — existing ops, two chunk graphs, tile 16 latents / overlap 4 latents, blend in patchify space then unpatchify

- **No new IR op.** Unbatched `[C,T,H,W]` tensors (gap study §2.2): DupUp3D = duplication
  (`[Cin,1,THW]` → expand → reshape) + three rank-4 depth-to-space steps (the first chunk slices off the
  first `ft − 1` frames); AvgDown3D (encoder) = leading zero pad in time → space-to-depth → `sum(dim=1)`
  → `mul(1/4)` (`aten.mean.dim` has no exporter handler); ZeroPad2d((0,1,0,1)) via the existing `pad`;
  the mid single-head attention (D = 1024 decoder / 640 encoder) goes through the fused attention as in
  2.1.
- **Two decoder chunk graphs as in 2.1** (`vae_decoder_first` / `vae_decoder_next`): cache
  normalization (always 2 frames, zero init, update = last 2 frames of `cat(cache, x)`), hand-over in
  resident tensors and frame-only readback as in ADR 0118 decision 2. 32 caches; first has 30 (no
  `time_conv`).
- **The graph returns the 12-ch patchify space.** Unpatchify (`[12,T,h,w]` → `[3,T,2h,2w]`, channel
  order `(c, r, q)`) runs on the host.
- **Tiles**: 16 latents (256 px output), overlap 4 latents (64 px). Tile edges come from the opened
  asset's input shape. Tiles are the outer loop, chunks the inner. 1280×704 (latent 44×80) gives 4×7 =
  28 tiles.
- **Blending is done in the 12-ch patchify space and unpatchify follows the paste on the host**
  (diffusers' 2.2 order). The existing blend and paste (`vae-tiles.ts`) read the channel count from
  the graph declaration.
- **The overlap derives from output pixels**: 64 px ÷ spatial compression, where spatial compression
  = the graph's input / output spatial ratio (from the declaration; 8 for both generations) × the
  host unpatchify factor (`patch_size`: 1 for 2.1, 2 for 2.2 — not derivable from the graph, so held
  by the generation descriptor). 2.1: 8 × 1 → overlap 8; 2.2: 8 × 2 = 16 → overlap 4. The TS
  `wanVaeMinTileOverlap` (`vae-tiles.ts`) and Python `min_overlap_latent` (`vae_tiling.py`) implement
  it; the 2.1 plan and the 2.2 plan are frozen in tables on both sides.
- Latent de-normalization uses the 48 mean / std values (`WAN22_LATENTS_MEAN` / `WAN22_LATENTS_STD` in
  `latents.ts`), formula `latents / (1/std) + mean` as in 2.1.
- The 2.2 VAE patch shares the cache machinery and the pure rank-4 functions
  (`_shared/vae_rank4.py`) with 2.1 and adds the shortcuts and the exit.

Why: everything is data movement or elementwise within rank 4, so ADR 0059's entry check gives no
reason for an op. Tile 32 would cost 5.2 GiB of cache alone. Tile 16 / overlap 4 equals the diffusers
2.2 default (256 px, stride 192 px) and is baked into the distribution and the sha rows. Blending in
patchify space follows upstream; the value check's counterpart is Karume's own Python tile
reference, not diffusers' tiled decode (the placements already differ). With pixels as the source of
truth, a generation holds only the upstream fact `patch_size`.

Protects: values match the upstream causal decode; the asset is independent of resolution (ADR 0038
§4); the 2.1 tile plan and sha rows do not change.

### 7. Export — meta trace + i8 per row chunk + `fixed_weights` (no core change); the f64 reference becomes layer-by-layer, proven bit-identical on the 1.3B first

- **DiT i8 series**: the ADR 0119 meta-trace form. 307 linear weights go as `fixed_weights`; the f32
  rest (bias, norm, `scale_shift_table`) as is. The exporter core is unchanged.
- **f64 reference**: the whole-model `model.double()` of 2.1 needs 37.25 GiB for the 5B, so a
  layer-by-layer writer reads one block at a time from the series container
  (`tools/export-recipes/wan/dit_reference.py`).
  - It reads both the f16 and i8 series; the whole-model f64 path is not kept.
  - **Dequantization runs in f32 and then widens to f64** (the existing goldens applied fake-quant in
    f32 before `double()`).
  - It was first proven on the 1.3B: layer-by-layer f64 equals **every existing f64 golden of both
    series** bit for bit, then applied to the 5B.
  - The f64 path creates no other floating type (as in the umT5 layer-by-layer reference); the CPU
    forward runs under `sdpa_kernel([FLASH_ATTENTION])` (MATH would materialize S×S).
  - The f32 reference (the denominator of r) comes from the same writer, proven bit-identical to the
    upstream f32 eager at S = 192 (one writer only).
- **VAE series**: f16 (decoder first / next, encoder), checked for non-finite values after rounding.
- **Series names**: `wan2.2-ti2v-5b-i8-dyn` (transformer) and `wan2.2-ti2v-5b-f16-dyn` (the VAE graphs).

Why: the straightforward form would have peaked near 30 GiB; the meta-trace form passed for umT5 at
6.79 GiB. The 31 GiB RAM premise is gone since 2026-10-06, but one writer for both series keeps the
1.3B f16 goldens reproducible and there is no reason to restore the whole-model f64 path.

Protects: the reference rewrite provably keeps the reference values; the exporter core / recipe
boundary (ADR 0065).

### 11. I2V — diffusers-form conditioning, the official image preprocessing (ruling 3), encoder size handling decided at stage 9

- **Conditioning**: the `expand_timesteps` branch of diffusers' `WanImageToVideoPipeline`. Each step
  replaces only the first frame of the model input with `(1 − m)·cond + m·latents`; the scheduler
  advances the unreplaced latents; the latents are replaced once more before the VAE.
- **Reference-loop time**: the two-step reference runs this conditioning with the decision 4 time form;
  diffusers' own pipeline (M = S) is an observation.
- **Output size**: from the accepted set, the size closest to the image's aspect ratio (ties go to
  landscape; `selectWanI2vSize` in `i2v-preprocess.ts`). Explicit `width` / `height` must be in the set.
- **Image preprocessing** (ruling 3 (a)): LANCZOS resize to cover the chosen size
  (`scale = max(ow/iw, oh/ih)`) → center crop → `[-1, 1]` (official `textimage2video.py:462-477`). The
  input is RGB8; decoding is the caller's job. LANCZOS is a port of Pillow. The reference is taken by
  passing the host-cropped image to diffusers. A direct-resize option was added at stage 9b (`fit:
  "stretch"`; `"crop"` is the default).
- **VAE encoder**: one image = encode chunk 0 only (no `time_conv`, T = 1, no cache); patchify 3 → 12 ch
  on the host; the first 48 channels (mu) → `(mu − mean)·(1/std)`.
- **Stage order and release**: encoder → close the encoder sessions and wait for the release
  (`settleReleasedMemory` in `packages/models/src/session/settle-released-memory.ts`) → text → DiT →
  VAE decoder, so the DiT stage holds no encoder memory. The trigger was the B570's delayed release;
  the wait is kept as a cheap portability measure for browser devices.
- **Encoder size handling** in the order ① symbolic-length conv → ② one graph per accepted size → ③
  tiled encode (superseded by this ADR's addendum of 2026-10-09: the obstacle was the IR's dimension
  expressions, not conv; the encoder became three symbolic-length graphs around the mid attention).

Protects: the I2V loop is comparable with the diffusers reference; I2V does not change the T2V sha
rows; the I2V DiT stage fits in the same memory as T2V.

## Alternatives considered

- **Build an `f16` preset** (ruling 2 (b)) — did not fit the development machine; export needed the RAM
  edge or a core change (decision 2).
- **Expand the time MLP on the host to `[S,256]` with M = S** — about 1.8 T MAC per forward and a 1.87
  GiB `e0`.
- **Split the first P tokens by slice / cat** — needs a P symbol besides S (breaks ADR 0034).
- **One time-MLP call with M = 2** — CPU already split M = 1 and M = 2; revisit once the GPU linear is
  shown independent of M (open).
- **Two DiT graphs (T2V and I2V), or a T2V export redone at I2V** — re-export, new goldens, two
  containers.
- **The 2-D timestep (M = S) path as the eager counterpart** — reduction differences in the check.
- **The official bf16 run as baseline** — bf16 sets the floor; hours of CPU.
- **The official `Wan-AI/Wan2.2-TI2V-5B` format as upstream** — unsuitable for torch.export; pickle.
- **New ops for VAE 2.2 (rank-8 view / permute, `mean`)** — rank ≤ 4 existing ops suffice.
- **Tile 32** — 5.2 GiB of cache.
- **Blend in pixel space** — differs from upstream's patchify-space blending.
- **Keep the whole-model `model.double()` reference / write the 5B layer-by-layer reference without
  the 1.3B proof / an i8-only writer** — RAM; no proof of unchanged values; no way to rebuild the 1.3B
  f16 goldens.
- **Rebuild umT5 from 2.2's bf16 / move the tokenizer asset to `karume-umt5-xxl` / stamp the assets
  with the 2.2 pin** — two encoders; the asset path crosses repositories; false provenance.
- **Add a generation branch to `WanPipeline` / reuse `wan/1`** — acceptance would depend on the runtime
  generation; generations could be confused.
- **diffusers' direct resize as the only preprocessing** (ruling 3 (b)) — distorts the image (later
  added as the opt-in `fit: "stretch"`).
- **Accept 1280×704 × 121 from the start** (ruling 1 (b)) / **per-device acceptance by free VRAM** —
  regressions undetectable on the development machine at the time; comparing with free memory
  contradicts ADR 0070 decision 5 / ADR 0089.
- **Generalize the 2.1 path inside the VAE 2.2 stage** — a 2.1 regression would surface late and be
  misattributed.
- **Intermediate presets (`f16+dit8-a8`, …)** — review, sha-row and card cost per preset (ADR 0120).
- **Wan2.2 A14B (MoE) in the same ADR** — a different DiT (`transformer_2`, `boundary_ratio`); out of
  scope.

### Added complexity and future obstacles

- **Added**: two Wan classes over shared modules; 2.2 branches in the VAE patch (two shortcuts, 12-ch
  exit, encoder); two more DiT inputs; one layer-by-layer reference writer for both models and both
  series; one more lane.
- **Held back**: no new op, no runtime or exporter-core change; two presets; one DiT container including
  I2V; umT5 not re-exported; one overlap formula, with only `patch_size` per generation.
- **Possible obstacles**:
  1. A third Wan generation adds a descriptor; A14B (MoE) needs an expert switch in the shared loop

  2. Paths the sha rows do not cover (error messages, abort points) rely on host tests.
  3. The decoder weights are held twice (first / next, 2.07 GiB); sharing across graphs is perf-ledger
     K-79.
  4. Lengths above 57 frames are unsupported on the 10 GB class (decision 8).

there is no need to keep a non-official size. The stage-2 r check and the stage-5 tile reference stay
as size-independent numeric checks.

`ModelInputError`.

## Addendum (2026-10-11) — EXIF orientation is applied (ruling 40 replaces ruling 18)

- History: at stage 9c gpu-lab applied the orientation and the CLI example did not (like upstream
  `generate.py`); ruling 18 moved gpu-lab to `imageOrientation: "none"` (`552dac80`), but Chrome still
  applied the orientation with `"none"` (the spec renamed the old `"none"` to `"from-image"`).
- **Decision (ruling 40 = a, 2026-10-11)**, which a rebuilt browser application or CLI SHOULD follow
  (re-graded 2026-10-18 to SHOULD: the code it governed, `examples/wan` and `tools/gpu-lab`, was removed
  by ADR 0127 decision 5; the policy carries over to the rebuilt applications):
  - The orientation is **applied** by default, deliberately unlike upstream `generate.py`: a phone
    photo shown upright by its tag would otherwise generate sideways (ADR
    [0005](0005-verification.md) addendum 2026-10-11 — a better workaround becomes the default).
  - No "do not apply" option until there is demand; callers who want upstream's orientation rotate the
    pixels and strip the tag first.
  - Reading follows Chrome: JPEG — the first Exif APP1 before SOS; PNG — eXIf before IDAT (Chromium
    commit 694d9d3a, 2024-02); XMP `tiff:Orientation` alone is not read. IFD0 Orientation (SHORT, count
    1) values 1–8 are used; out-of-range values or broken EXIF mean orientation 1, not a failure
    (Skia's `SkExif::Parse` does the same). The eight transforms match Pillow's
    `ImageOps.exif_transpose` pixel for pixel.
  - `imageOrientation: "from-image"` is passed explicitly; `"none"` is not used because its meaning
    varies by version.
- The packages are unaffected: the public API takes a decoded `Rgb8Image`, and the I2V sha cases use
  the three `inputs/wan-i2v/*.png` images, which carry no eXIf chunk.

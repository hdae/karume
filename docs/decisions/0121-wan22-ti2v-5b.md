## Context

### 要望

利用者の要望は「MiniMax H3 の前に Wan 2.2 の TI2V 5B（Alibaba の text / image-to-video・Apache 2.0）を試す。w8a8
（重み i8 + 活性 8 bit の実用席）を含めて実装する。実装は Opus に委任」。Wan2.1 T2V 1.3B の受け入れ（ADR 0118）・umT5 の
GPU 化（ADR 0119）・w8a8 席（ADR 0120）は済んでいて、本 ADR はその部品の上に 2.2 の 5B を載せる設計を決める。

### 調査の結論（数値は調査の値）

- **DiT は Wan2.1 と同じクラス・同じ 825 テンソルで、寸法だけが大きい**（dim 3072・24 heads × 128・30 層・FFN 14336・in / out
  48 ch・4,999,787,712 パラメータ — 上流調査 §1）。forward の差は 2 点だけ: 時刻がトークンごと `[B,S]` になり変調が `[B,S,6,C]`
  になること、CLIP の画像エンコーダと `k_img` / `v_img` が無いこと（上流調査 §2.1）。
- **I2V は「先頭の潜在フレームを画像の潜在で置き換え、そのトークンだけ t = 0 にする」だけ**（上流調査 §2.3）。t の値は 2 種しか
  無いので、MLP を行 2 本で回して振り分ければ `e0` の 1.87 GiB と 1 forward あたり約 1.8 T MAC を避けられる（上流調査 §2.4）。
- **VAE は別物**（Wan2.2-VAE・z_dim 48・圧縮 4×16×16・decoder 555,049,228 パラメータ = 2.1 の 7.6 倍 — 上流調査 §3.1）。新しい演算
  （DupUp3D・AvgDown3D・patchify / unpatchify・非対称ゼロ詰め）は全て rank 4 以下の reshape / permute / expand / slice / pad / sum /
  mul で書け、**新しい IR op は要らない**（差分調査 §2）。
- **トークン数は同じ画素なら 2.1 の 1/4**。832×480・81 フレームで S = 8,190・1 forward 48.98 T MAC（2.1 の同条件の 0.35 倍）、公式の
  既定 1280×704・121 フレームで S = 27,280・258.46 T MAC（上流調査 §4.4）。
- **umT5 は Wan2.1 と同じ重み**。Wan2.2 Diffusers の bf16 は Wan2.1 の f32 を最近接偶数丸め（RNE）で bf16 にした値と全 242 本で
  ビット一致し、Wan2.1 の f32 は google/umt5-xxl の encoder と f32 で全要素ビット一致（umT5 出所調査 §0）。トークナイザも Diffusers 版の
  sha が 2.1 と一致（上流調査 §5）。**`karume-umt5-xxl` をそのまま越境参照できる**。
- **サンプラのコードは 2.1 と diff 0**（UniPC・50 steps・guide 5.0・shift 5.0・24 fps・121 フレーム — 上流調査 §4.1）。公式の i2v の
  docstring は「480p なら shift 3.0 を推奨」と書く（`textimage2video.py:439` — 上流調査 §4.1）。
- **公式は T2V の寸法を 1280×704 / 704×1280 の 2 つだけ受ける**（`configs/__init__.py:46` — 上流調査 §4.1）。832×480 は公式の対応寸法の
  外。
- **f16 の DiT は 9,999,575,424 B（9.31 GiB）で、B570 の Deno の天井 9.375 GiB（9,600 MiB）とほぼ同じ**（差分調査 §3）。Linear だけ i8 なら
  5,012,178,432 B（4.67 GiB）。
- **公式は DiT の forward を常に bf16 autocast で回す**（`--convert_model_dtype` が無くても `param_dtype=bf16` — `textimage2video.py:330`・
  `522`。上流調査「独立検証」）。重みは F32 で配られる（bf16 の拡張ではない — 上流調査 §1.2）。
- **torch CPU の Linear は、同じ行を M 本並べたときと M = 1 のときで最終ビットが割れる**（K 256 → N 3072・K 3072 → N 18432 の 2 形で
  M = 2〜8,190 のどれも不一致・最大差 3.6e-7〜1.9e-6・M 本の行どうしは全行一致 — 差分調査 §6.1 と「独立検証」の再実験）。diffusers の
  `WanPipeline(expand_timesteps=True)` は T2V でも `[1,S]` の timestep を渡すので、時刻の MLP は M = S で走る（上流調査 §7）。
- **2.2 の diffusers の `tiled_decode` は 12 ch の patchify 空間でブレンドしてから unpatchify する**（`autoencoder_kl_wan.py:1355-1401` —
  差分調査 §12）。既定はタイル 256 px・stride 192 px（`autoencoder_kl_wan.py:1076-1081`）。

### 独立検証で覆った・足された事実（設計に効くもの）

- **VAE 2.2（タイル 16）の最大の中間は 128 MiB ではない**: chunk 1 の最大は CausalConv3d の pad 後の入力 `[1,512,6,130,130]` = 51.9 M 要素
  （f32 207.7 MB）で、次が cache との cat `[1,512,5,128,128]` の 41.9 M（差分調査「独立検証」・refuted / 影響 low）。VAE 段の中間の見積り
  （0.5〜0.8 GiB）は根拠を測り直す（段 4 / 5）。
- **参照席 `f16+dit8` の diag と backing は 2.1 で一度も測られていない**。5B の参照席の容量は `f16` 席の係数 k を借りた仮定にすぎない（同）。
  段 2 で実測して置き換える。
- **束縛上限を超える S の境界**は FFN 中間が S ≥ 37,450・cross の S が S ≥ 43,691（差分調査本文の値から 1 ずつずれる・設計への影響なし）。
- **HF の `vae/config.json` の `clip_output` キー**は diffusers 0.39.0 の `__init__` が受けない（meta で組むと TypeError・`from_pretrained` では
  無視される）。export の台本が config を直接渡すときは除く（上流調査 §7・「独立検証」）。
- **既存の `vae-tiles.ts` のブレンドと貼り付けは patchify 空間でそのまま使える可能性がある**（2.2 の patchify 空間は潜在 1 あたり 8 px で 2.1 の
  画素空間と同じ縮尺）。逆に `WAN_VAE_MIN_TILE_OVERLAP = 8`（`packages/models/src/wan/vae-tiles.ts:58`）のままだと出力 128 px の重なりになる
  （差分調査「独立検証」）。
- **I2V の置き換えの 2 形**（公式 = 各 step の後に潜在を置き換える・diffusers = モデル入力だけ置き換えて最後に 1 回置き換える）が先頭フレーム
  以外で同値なのは、コードを読む限りの推測で実測は無い（上流調査「独立検証」）。
- **トークナイザ資産は `karume-wan2.1` リポの部品**（`karume-umt5-xxl` は資産を持たない）。umT5 の容器だけでなく資産の置き場も決める必要が
  ある（umT5 出所調査「独立検証」）。
- **DiT の小さいテンソルの |w| の最大は 7.71**（`blocks.29.attn1.norm_k`）。上流調査本文の「最大 0.25」は Linear の先頭だけの値（上流調査
  「独立検証」）。f16 の範囲内。

### 制約

- 横断の不変条件: 未対応・想定外は fail loudly・sha 門の tolerance 化は禁止（ADR 0106）・ランタイム依存は Web 標準 API だけ・全モジュール
  副作用ゼロ。
- B570（BMG G21・Linux xe・Deno）: 総確保の天井 9,600 MiB（9.375 GiB）・`maxStorageBufferBindingSize` 2,147,483,644 B・1 submit 5 s で
  device lost・`destroy()` の解放が次の device poll まで遅れる（ADR 0118 Context の制約・段 0）。
- 開発機の RAM は 31 GiB。この機の GPU は学習と共有している（GPU を長く使う段は使用中を確かめてから回す）。
- 2.1 の sha 行・帯・case id は 1 bit も変えない（本 ADR の共有モジュールの切り出しは 2.1 の値を保つ — 決定 10）。

## Decision

### 1. 上流は Diffusers 版を commit SHA で pin する — ライセンス Apache-2.0・取る重みは transformer と VAE だけ

- 上流: `Wan-AI/Wan2.2-TI2V-5B-Diffusers` @ `b8fff7315c768468a5333511427288870b2e9635`（上流調査 §6・license `apache-2.0`・gated なし）。
  recipe の `SOURCES` に配布形のモデル名 `ti2v-5b` の行を足す（今の表は `t2v-1.3b` 1 行 — `tools/export-recipes/wan/sources.py:54-63`）。
- 取得する重みは `transformer/` 5 本（19.99 GB）と `vae/`（2.82 GB）だけ。ほかに、2.1 の recipe と同じく `scheduler/`（config だけ — 参照は
  `scheduler.config.flow_shift` を読んで golden のメタに書く・`tools/export-recipes/wan/few_step_ref.py:272`）とリポ直下の `README.md` /
  `model_index.json`（ライセンスの front matter と部品の索引 — `sources.py:78`）を取る。`text_encoder/` と `tokenizer/` は取らない（決定 9 —
  umT5 は越境参照、トークナイザ資産は Wan2.1 の系列から写す）。
- 今の `COMPONENTS`（部品の取得の要否と理由 — `sources.py:66-72`）と `EXPECTED_PARAMETERS`（部品名をキーにした期待パラメータ数 —
  `sources.py:82-85`）は全モデル共通の表なので、**モデル名をキーにした表に分ける**。5B の期待値は safetensors のヘッダの要素数の和で、
  transformer 4,999,787,712・vae 704,688,668（decoder + `post_quant_conv` 555,051,580・encoder + `quant_conv` 149,637,088 — 本 ADR の改訂で
  pin のヘッダから集計）。
- diffusers は Wan の recipe が pin している 0.39.0 のまま（ADR 0118 決定 7）。0.39.0 は TI2V の分岐（トークンごとの timestep・`is_residual`・
  patchify）を全て持つ（上流調査 §7）。

なぜ:

- Diffusers 版は全部品が safetensors で、DiT / VAE とも Karume が既に切り出している diffusers のクラス（`WanTransformer3DModel` /
  `AutoencoderKLWan`）の分岐で表せる。公式形式の `WanModel` は torch.export に向かず（リスト入力・`grid_sizes.tolist()`・flash_attn の直呼び）、
  VAE と T5 は pickle の `.pth`（上流調査 §7 の比較表）。
- DiT の値は公式形式とビット一致（抜き取り — 上流調査 §1.2）なので、Diffusers 版を上流にしても重みの出所は変わらない。

守るもの: 誰でも同じ revision から同じ参照を作れること（ADR 0118 決定 5 の流儀）。取得量を必要な部品だけに保つこと。

### 2. 席は 2 つ — 参照席 `f16+dit8` と実用席 `f16+dit8-a8-attn8-s16`。f16 席は作らない。既定席は視認の段（段 7）で決める

| 席                      | `weights.transformer` | VAE（decoder first / next・encoder） | `session`                                                                       | 層     |
| ----------------------- | --------------------- | ------------------------------------ | ------------------------------------------------------------------------------- | ------ |
| `f16+dit8`              | `i8`                  | `f16`                                | 空（重みだけ i8・計算は f32）                                                   | 参照層 |
| `f16+dit8-a8-attn8-s16` | `i8`                  | `f16`                                | `linearCompute: "a8"`・`attentionCompute: "a8"`・`attentionScoreStorage: "f16"` | 実用層 |

- 席名の文法・i8 の範囲（DiT の linear の重み 307 本すべて・bias / norm / `scale_shift_table` は上流の f32 のまま・校正なし）・受理表
  `WAN_SESSION_POLICY` の 3 キーは ADR 0120 決定 1 / 2 / 7 と同じ。容器は 2 席で `transformer/model.i8.krm` 1 本を共有する。
- **本数の内訳**（pin の safetensors のヘッダを本 ADR の改訂で集計 — 上流調査 §1.2 の 306 と一致）: rank 2 の Linear の重みが 306 本（ブロック 30 ×
  10〈self 4・cross 4・FFN 2〉+ `condition_embedder` 5〈text 2・time 2・`time_proj` 1〉+ `proj_out` 1）。recipe が Linear に直す patch 埋め込み
  （`[3072,48,1,2,2]`）を足して **i8 の重みは 307 本**で、2.1 と同じ構成（ADR 0120 決定 2 の内訳と同じ）。**1 パスの linear の dispatch は 310 本**の
  見込み: 決定 3 で時刻の MLP（`time_embedder` の 2 本と `time_proj`）を M = 1 で 2 回回すので、同じ重みの linear のノードが 3 本増える（重みは
  307 本のまま — `fixed_weights` は消費者が複数の重みを受ける・`tools/exporter/src/karume/emit.py:543-547`）。census は dispatch を数える
  （`packages/models/tests/helpers/census-table.ts:328` の 2.1 の行 307 は dispatch の本数）ので、5B の行は 310 にする。段 1 で IR の linear の
  ノードを数えて確定する。
- **f16 席（`f16`）は作らない**（裁定 2）。
- **既定席**: manifest の `defaultQuant` は**段 7 の視認の結果で決める**（ADR 0110 決定 8 — `defaultQuant` に入れるときだけ品質裁定）。配布形を組むのは
  段 8 で、視認の後なので、最初から既定を焼く必要が無い。段 7 の視認は「参照席 vs 実用席」の比較に加えて、**参照席自身の品質裁定を兼ねる**
  （5B には f16 席が無く、元の重みとの視認の比較が他に無い。参照席は i8 の RTN〈最近接丸め〉・校正なしの席）。実用席が受かれば実用席を、
  実用席が落ちて参照席が受かれば参照席を既定にする。参照席自身が落ちたら既定を決めずに止め、裁定に上げる（i8 の範囲を狭める案と、
  裁定 2 の f16 席を見直す案を並べる）。利用者の方針（2026-10-04）: 既定は「今いちばん実用的な席」。将来「元の重みにいちばん近い席」を既定にする
  方針転換の余地は残す（ADR 0120 裁定 2026-10-04 の 4 と同じ）。
- **段 7 までの開発用**の系列とローカルミラーは、参照席を仮の既定にする。
- **テストのケースは全て席を明示する**（ADR 0120 追記「既定席の切り替え」の教訓 — 既定を切り替えたときに、席名を持たないケースが別の席の値で
  黙って回らないように、`quant` の省略を型で止める）。段 7 で既定が決まっても、テストと sha 行は焼き直さずに済む。

なぜ:

- f16 の DiT は重みだけで 9.31 GiB あり、B570 のどの候補にも入らない（差分調査 §3.2）。RTX 5070 Ti でも 1280×704×121 では境界（diag 13.80〜
  14.14 GiB）。開発機で一度も回らない席は門も sha 行も持てない。export も RAM の境界（20〜25 GiB の見込み）か、`fixed_weights` を f16 へ
  広げる exporter core の変更が要る（差分調査 §5.2 — `fixed_weights` は i2 / i4 / i8 だけ — `emit.py:549`）。
- 参照席は自機 A/B 門の床の相手として manifest に要る（`referencePartnerOf` は 0 個で throw — ADR 0120 決定 1）。GPU の i8 は要素ごとの逆量子化が
  CPU の展開とビット一致する（ADR 0019）ので、参照層の r 門は参照席で持てる（決定 5）。

- 既定を視認の段で決めるのは、`defaultQuant` に入る席は品質裁定を経ていなければならない（ADR 0110 決定 8）のに、5B では参照席の品質も
  まだ誰も見ていないため。2.1 の視認（ADR 0120）は f16 席が相手で、5B にはその相手が無い。

守るもの: 自機 A/B 門の床が恒真にならないこと（比較相手が同じ重み — ADR 0110 決定 5 ②）。開発機で全部の門と sha 行を持てる席だけを配ること。
`defaultQuant` に入る席が品質裁定を経ていること（ADR 0110 決定 8）。

### 3. DiT のグラフは最初から I2V 対応の 1 本 — 時刻入力 2 本・条件マスク・`where`

- **入力**: Wan2.1 の 5 本（トークン・`timesteps_proj [1,256]`・文脈 `[1,512,4096]`・RoPE の 2 本 — `ditContract` `packages/models/src/wan/pipeline.ts:865`）
  に、`timesteps_proj_condition [1,256]` と `condition_mask [1,S,1]` の 2 本を足す。トークン幅は 192（48 ch × 1×2×2）。
- **グラフの中**: 時刻の MLP（`time_embedder` → SiLU → `time_proj`）を **M = 1 で 2 回**回す（同じ重みの linear を 2 ノード — linear の dispatch は
  3 本増えて 310 本・決定 2）。変調の各成分（ブロックの 6 成分・head の 2 成分）を、使う場所で `where(condition_mask, 条件側, 生成側)` により
  `[1,S,C]` に選ぶ。`[S,6,C]` を一度に作らない（S = 27,280 で f32 1.87 GiB — 上流調査 §2.4）。`where` は条件と値の 3 者を右詰め broadcast する
  （`packages/runtime/src/ops/shapes.ts:309-313`）。
- **`where` の置き場所**: パッチは、各成分の `where` をその成分の消費（self-attention の前の変調・その残差のゲート・FFN の前の変調・FFN の
  ゲート・head の変調）の直前に書く。上流の順（ブロックの先頭で 6 成分をまとめて作る — `transformer_wan.py:469-484`）に倣って先頭で 6 本の
  `where` を作ると、torch.export はその順を保つので、最大 6 本の `[1,S,C]` が attention をまたいで生き、増分が約 3 倍になりうる（推測 —
  容量の表の注）。段 1 で IR を検査し、段 2 で diag の増分を記録する。
- **T2V**: 条件マスクは全て偽、`timesteps_proj_condition` には生成側と同じ値を渡す。
- **I2V**: 先頭 P トークン（先頭の潜在フレーム — トークン添字 `(f·H' + h)·W' + w` で先頭に連続して並ぶ・`dit-tokens.ts:15`）が真、条件側の t は 0。
- **S の記号の上限は最初から 27,280**（1280×704×121）。受理集合は TS のパイプラインが絞る（決定 8）。この上限は torch.export の `Dim("S")` にしか
  効かない（2.1 は `DIT_SYM_MAX = 32_760` — `tools/export-recipes/wan/export_dit.py:218`）。IR の記号は上下限を持たず（`ditContract` の注 —
  `packages/models/src/wan/pipeline.ts:860-861`）、`requiredLimits` は常駐分（重み・state）だけから導く（ADR 0089 決定 3）ので、上限が admission や
  計画に効いて B570 の受理に障ることは無い。
- **条件マスクの dtype は bool の入力**にする。IR の意味論 dtype は `f32 | i32 | bool` で、bool は u32 の 0 / 1 で格納され、グラフ入力の転送は 3 型とも
  できる（`packages/runtime/src/format/ir.ts:10`・`docs/ir-v2.md:174-177`）。段 1 で確かめるのは、exporter が bool のグラフ入力と `where` の条件を
  emit する経路だけ。
- recipe の構成の門（`_assert_supported_config` `tools/export-recipes/wan/dit_patch.py:234-244`）は `image_dim` / `added_kv_proj_dim` が None なら通り、
  2.2 は `image_dim null`（上流調査 §1.1）。RoPE の実数化・patch 埋め込みの Linear 化は寸法を持たないのでそのまま当たる（差分調査 §1.1）。

なぜ:

- 5B の DiT の再 export（CPU 数時間・golden の撮り直し）を I2V の段で起こさない（差分調査 §6.2）。T2V の段（1〜8）で作った golden・sha 行・
  帯がそのまま I2V の段でも有効になる。
- **M = 2 の 1 回にしない**: torch CPU では M = 1 と M ≥ 2 で linear の最終ビットが割れた（差分調査 §6.1）。GPU の linear が M で縮約の経路を
  変えるかは未確認（差分調査 §12）。M = 1 を 2 回にしておけば、T2V の生成側の行は Wan2.1 と同じ形の計算になり、`where` は選択なので値を
  変えない。
- 代わりの案（ホストで `[S,256]` に展開して M = S で回す・先頭 P トークンを slice / cat で分ける）は採らない（「採らなかった案」）。
- 費用（推測）: `where` を消費の直前に置けたとき、生きている `[S,dim]` が 2 本程度増え、backing は S = 8,190 で +0.19 GiB・S = 27,280 で +0.62 GiB。
  時間は要素ごとの演算で 1 パスの 1% 程度（差分調査 §6.2）。置き場所を誤ると S = 8,190 で約 +0.56 GiB になりうる（上の「`where` の置き場所」）。

守るもの: T2V の値を Wan2.1 と同じ形の計算のまま保つこと。I2V を足すときに DiT の容器と golden を作り直さないこと。S 形グラフの 1 シンボル
（ADR 0034）を保つこと。

### 4. 上流との CPU 照合の形 — T2V は 1 次元 timestep の経路、I2V は M = 1 で組んだトークンごとの temb を上流のブロックに渡す

パッチの eager 同値（MUST — ADR 0118 決定 3 の規律・実重みで実測）の相手を、時刻の表し方ごとに決める。

| 経路 | 相手                                                                                                                                                                                                                                                                                                                                                               | 期待                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------- |
| T2V  | 上流 `WanTransformer3DModel` を 1 次元の timestep（`[B,6,C]` の経路・時刻の MLP は M = 1）で呼んだ出力。Wan2.1 の eager 同値と同じ相手（`dit_patch.py:350-356` のラッパは上流の `[B,6,C]` 経路の逐語）                                                                                                                                                             | ビット一致             |
| I2V  | 参照ラッパ: 上流の `condition_embedder` を t の値ごとに M = 1 で 2 回呼び（生成側の t と 0）、トークンごとの `temb [1,S,C]` と `timestep_proj [1,S,6,C]` を組んで、上流のブロックの `temb.ndim == 4` の分岐（`transformer_wan.py:469-485`）と head の `ndim == 3` の分岐（`transformer_wan.py:704-708`）に渡した出力。ブロックと head は上流のコードがそのまま走る | ビット一致             |
| 観測 | diffusers の `WanPipeline(expand_timesteps=True)` / `WanImageToVideoPipeline` が渡す 2 次元 timestep（M = S の linear）の経路との差                                                                                                                                                                                                                                | 差を記録（門ではない） |

- GPU の r 門の参照（決定 5）も同じ時刻の表し方（M = 1 で 2 回）で採る。参照とグラフの意味論を揃えるため。
- **通しの参照**（段 6 の T2V・段 9 の I2V の 2 ステップのループ）も同じ時刻の表し方で採る。diffusers の `WanPipeline(expand_timesteps=True)` /
  `WanImageToVideoPipeline` をそのまま回した出力（M = S）との差は、観測として並べる（門ではない）。
- eager 同値は S = 192 で、パッチ後と上流が同じ f32 の fake-quant 重みの 1 本を共有する形で回す（RAM は f32 全量 18.63 GiB + 小さい活性 —
  段 0 で実測。載らなければブロック単位の同値に割る）。

なぜ:

- M = S の経路を相手にすると、torch CPU の linear の縮約の経路の差（最大差 1.9e-6）が門に混ざり、移植の誤りと区別できない。スレッド数への依存も
  未確認（6 スレッドだけ — 差分調査「独立検証」）。
- I2V の参照ラッパは上流のブロックのコードを使うので、「トークンごとの変調の式を書き写した」誤りを持ち込まない。時刻の MLP だけを M = 1 で
  回すのは、グラフと同じ意味論（決定 3）にするため。

守るもの: 「移植できた」をビット一致で言えること。上流の pipeline の M = S の経路は観測に留め、門を縮約の経路の差で汚さないこと。

### 5. 数値の基準 — 門は f32 / f64 の参照（同じ i8 の fake-quant 重み）。公式の bf16 は基準にしない

| 層                 | 基準                                                                                                                                               | 門の形                                                                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 移植（参照席）     | CPU の f64 / f32 参照（diffusers のコードを f32 / f64 で・重みは i8 の fake-quant・時刻は決定 4 の形）                                             | S = 192・S = 8,190 とも f64 参照と正規化比 r（i8 系列の前例 — ADR 0120 決定 3・`export_dit.py:144`・`324`。r は ADR 0118 決定 8・追記「段 3 の帰属」） |
| 実用（実用席）     | 同じ機・同じ i8 重みの参照席                                                                                                                       | 自機 A/B 門（ADR 0110 決定 5・ADR 0120 決定 4）                                                                                                        |
| 品質               | 利用者の視認（seed 42〜45 × プロンプト 3 本）。参照席自身の品質裁定を兼ねる（決定 2）                                                              | 裁定（ADR 0058 追記 2026-09-13）                                                                                                                       |
| 観測（門ではない） | 量子化なしの CPU f32 参照に対する、重みだけ i8 の CPU f32 参照の差（S = 192・max abs ÷ max ref）。比べる相手は 1.3B を同じ測り方で採った値（段 1） | results に記録。5B の値が 1.3B の値の 2 倍（目安）を超えたら、段 2 に進む前に裁定に上げる（下の箇条）                                                  |

- 公式の bf16 autocast の実行は門にも常設の記録にもしない。
- **観測の比べ方**: 2.1 の観測値（ADR 0120 追記「段 1 / 2 の結果」の 4.7e-2 / 1.5e-2）は f16 系列（f16 に丸めた重み）が相手で、量子化なしの
  f32 が相手の 5B とは測り方が違う。段 1 で 1.3B の値も量子化なしの f32 を相手に採り直し、同じ測り方で並べる。5B の値が 1.3B の 2 倍を超えたら
  （目安 — 寸法が違うので同じ値は期待しない）、段 2 に進む前に裁定に上げる。並べる案は「i8 の範囲を狭める（外れ値の大きい層を除く）」と
  「品質の判断を段 7 の視認に任せて進む」。視認が品質の正本で、観測は視認の前に大きな外れを拾うためのもの。
- 「元の重みにいちばん近い席」の意味を取り違えないために明記する: 公式は「f32 の重み × bf16 の計算」、Karume の参照席は「i8 の重み × f32 の計算」で、
  どちらも相手と同じではない。重みの丸めの影響は上の観測で、計算の丸めの影響は r 門で別々に見る。

なぜ:

- WebGPU に bf16 も f64 も無く、Karume の活性は f32（ADR 0118 決定 3）。bf16 の実行を基準にすると、bf16 自身の丸め誤差が床になって帯を決める根拠が
  無い（ADR 0119 決定 8 の「GPU i8 vs bf16 資産を門にしない」と同じ理屈）。
- 拡散の軌道は分岐するので、画素距離は品質を表さない（ADR 0120 採らなかった案「上流の bf16 実行との比較を門にする」）。CPU の bf16 で 5B の 50 ステップは
  数時間級（推測）。

- S = 192 も f64 参照と r にするのは、i8 系列の golden が全ケースで f64 の参照を持つ前例（`wants_float64` — `export_dit.py:319-324`）に揃えるため。
  f16 系列の S = 192 の「f32 参照に対する比」の形は、5B には f16 系列が無いので使わない。

守るもの: 門の帯を測れる誤差だけで決めること。品質の判断を人間の視認に置くこと（ADR 0110 決定 8）。

### 6. VAE 2.2 — 既存 op の組み合わせ・chunk グラフ 2 種・タイル 潜在 16 / 重なり 潜在 4・patchify 空間でブレンドしてから unpatchify

- **新しい IR op を足さない**。書き方は差分調査 §2.2 の表のとおり（テンソルは unbatched の `[C,T,H,W]`）:
  - DupUp3D: 複製（`[Cin,1,THW]` → expand → reshape）と、軸ごとに 3 段の depth-to-space（各段 rank 4）。最初の chunk は時間軸の slice で先頭
    `ft − 1` 枚を捨てる。up0 / up1（rep = 8）は 3D の最近傍 ×2 と同じ値で、中間の複製を作らない閉じた形を選んでよい。
  - AvgDown3D（encoder・I2V）: 時間の前ゼロ詰め → 軸ごとの space-to-depth → `sum(dim=1)` → `mul(1/4)`。`aten.mean.dim` は exporter にハンドラが
    無い（`tools/exporter/src/karume/aten_handlers.py:1429-1499` の表）ので recipe で書き換える。
  - ZeroPad2d((0,1,0,1)): 最終次元の pad と、`[C·T, H·W]` への reshape → pad → reshape（既存の `pad`）。
  - アップサンプルの conv2d は dim → dim（形が違うだけ）。mid の単一 head attention は D = 1024（decoder）/ 640（encoder）で、2.1 と同じ `[T,1,h·w,C]`
    の形で融合 attention に通す（D の上限の検査は無いが D = 1024 の実測は無い — 段 4 で確かめる）。
- **decoder の chunk グラフは 2.1 と同じ 2 種**（`vae_decoder_first` / `vae_decoder_next`）。cache の正規化（常に 2 フレーム・初期値ゼロ・更新は
  `cat(cache, x)` の末尾 2 フレーム）と常駐テンソルでの受け渡し・フレームだけを読み戻す経路は ADR 0118 決定 2 と追記「独立レビュー」の形のまま。
  cache の本数は 32 本（上流調査 §3.4）・first は `time_conv` の 2 本を除く見込み（段 4 で確定）。
- **出口は 12 ch の patchify 空間のまま返す**。unpatchify（`[12,T,h,w]` → `[3,T,2h,2w]`・チャネルの並び `(c, r, q)` — 上流調査 §3.5）はグラフに入れない。
- **タイル**: 潜在 16（出力 256 px）・重なり 潜在 4（出力 64 px）。タイル辺は開いた資産の入力形から導く（ADR 0118 決定 2 の流儀）。ループはタイルが外・
  chunk が内。832×480（潜在 30×52）は 3×4 = 12 枚、1280×704（潜在 44×80）は 4×7 = 28 枚（差分調査 §4.2）。
- **ブレンドは 12 ch の patchify 空間で行い、貼り合わせの後にホストで unpatchify する**（diffusers 2.2 の順序 — `autoencoder_kl_wan.py:1355-1401`）。
  既存のブレンドと貼り付け（`vae-tiles.ts`）を、チャネル数をグラフ宣言から読む形にして使う（`SAMPLE_CHANNELS = 3` の定数 — `vae-tiles.ts:50`・
  `vae-chunks.ts:55` を外す）。この一般化は 2.1 の経路に触るので、VAE 2.2 の段より前の段 3 で、2.1 のレーンの実走を緑の条件にして行う（決定 10）。
- **重なりの定数は出力画素から導く形へ直す**: 正本は出力 64 px で、潜在の重なり = 64 ÷ 空間の圧縮。**空間の圧縮 = グラフの入出力の空間比
  × ホストの unpatchify の倍率**と定義する。グラフの入出力の空間比はタイル辺の出力 ÷ 入力で、グラフ宣言から導く（2.1・2.2 とも 8 — 2.2 の
  グラフは patchify 空間を出すので潜在 1 あたり 8・差分調査「独立検証」）。unpatchify の倍率は上流の VAE の `patch_size`（2.1 は無し = 1・
  2.2 は 2 — diffusers も `config.patch_size` で同じ割り算をする・`autoencoder_kl_wan.py:1355-1361`）で、グラフから導けないので世代の記述子に
  持つ（決定 10）。2.1 は 8 × 1 = 8 → 潜在 8、2.2 は 8 × 2 = 16 → 潜在 4。圧縮をグラフの比だけで取ると 2.2 も 8 になり、重なりが潜在 8
  （128 px）になる — これを凍結表で防ぐ。2.1 の `WAN_VAE_MIN_TILE_OVERLAP = 8`（`vae-tiles.ts:58`）と Python 側 `MIN_OVERLAP_LATENT = 8`
  （`tools/export-recipes/wan/vae_tiling.py:82`）をこの式に置き換える（段 3）。2.1 の計画（12 枚・行 0 / 14 / 28・列 0 / 24 / 48 / 72）は不変で、
  Python / TS の凍結表で確かめる。2.2 の重なり 潜在 4 も凍結表で固定する（段 5）。
- 潜在の逆正規化は 48 値の mean / std（pin した `vae/config.json` — 上流調査 §3.1）を世代の記述子に持つ（2.1 の 16 値 `latents.ts:20`・`40` と並べる）。
  式は 2.1 と同じ `latents / (1/std) + mean` の逐語。
- 2.1 の VAE パッチは `is_residual` と `patch_size` を名指しで拒む（`tools/export-recipes/wan/vae_patch.py:113-119`）。2.2 のパッチは cache の仕組みと
  末端の純関数（`_shared/vae_rank4.py`）を共有し、ショートカットと出口を足す。

なぜ:

- 全てデータ移動か要素ごとの演算で、rank 4 以下に収まる（差分調査 §2）。op を足す理由（ADR 0059 の入場門）が無い。
- タイル 32 にすると cache だけで f32 1.74 GiB × 3 組 = 5.2 GiB になり、重みと合わせて B570 の余裕が消える（差分調査 §3.2）。潜在 16 / 重なり 4 は
  diffusers の 2.2 の既定（256 px・stride 192 px）と同じ大きさ。
- patchify 空間でブレンドするのは、上流の 2.2 の慣行（diffusers の `tiled_decode` — ブレンド幅も patchify 単位で 32）に揃える約束事。画素空間の
  ブレンドとは重みの粒度が違う（2×2 の画素が 1 つの重みを共有する）ので、どちらかに決めておく必要がある。値の門の相手は自前の Python の
  タイル参照で、diffusers のタイル decode ではない（Karume のタイル計画は重なり 4 以上を均等に配る形で、diffusers の固定 stride とは配置が
  既に違う — `autoencoder_kl_wan.py:1369-1383`）。patchify 空間は潜在 1 あたり 8 px で 2.1 の画素空間と同じ縮尺なので、既存のブレンドと貼り付けが
  チャネル数だけの一般化で使える（差分調査「独立検証」）。
- 重なりを潜在の定数のまま 2.2 に使うと出力 128 px になる（独立検証）。px を正本にすれば、重なりの値を世代ごとに持たずに済む（世代が持つのは
  上流の事実の `patch_size` だけ）。

守るもの: 上流の因果デコードと値が一致すること（cache の正規化の論証は 2.1 と同じ）。B570 で VAE 段が入ること。資産が解像度から独立すること
（ADR 0038 §4）。2.1 のタイル計画と sha 行を変えないこと。

### 7. export — meta trace + 行の塊ごとの i8 + `fixed_weights`（core の変更なし）。f64 参照は層逐次へ書き直し、1.3B で全体 f64 とのビット一致を確かめてから 5B に当てる

- **DiT の i8 系列**: ADR 0119 段 10b の形をそのまま当てる。trace は重みを持たない meta の上流で回し（グラフの JSON は実重みの export と同一）、
  linear 307 本は checkpoint から行の塊ごとに i8 にして `fixed_weights`（`emit.py:513-581`）で渡し、f32 の残り（bias・norm・`scale_shift_table`）は
  そのまま渡す。exporter core は変えない。
- **f64 参照**: 2.1 の f64 参照は f32 のモデルを読んで `model.double()` で全体を f64 にする（`tools/export-recipes/wan/export_dit.py:507`）。5B では
  37.25 GiB で載らないので、1 ブロックずつ系列の容器から重みを読む層逐次の書き手に置き換える（1 ブロック f64 1.22 GiB）。
  - **書き手は f16 / i8 の両系列を読む**。全体 f64 の経路は残さない（④）ので、1.3B の f16 系列の f64 golden（実寸の S = 14,040 / 32,760 —
    `wants_float64` は f16 系列では実寸のケースだけ・`export_dit.py:319-324`）もこの書き手が作る。
  - **逆量子化は f32 で行ってから f64 へ広げる**。既存の golden は、f32 のモデルに fake-quant を掛けてから `double()` した値（「丸めは f32 のうちに
    掛ける」— `export_dit.py:497-506`）。容器の `q × scale` を f64 で展開すると、この値とビットで割れる。f16 系列は f16 → f32 → f64 で、
    どちらの順でも値は同じ。
  - **手順**: まず 1.3B で、層逐次の f64 の出力が**両系列の既存の f64 golden の全ケース**とビット一致することを確かめる（f16 系列 = 実寸の
    S = 14,040 の 8 ケースと S = 32,760 の 8 ケース・i8 系列 = 小さい S の 9 ケース（S = 192 が 8 本・S = 128 が 1 本）と S = 14,040 の 8 ケース — `export_dit.py:259-292` の表）。
    一致してから 5B に当てる。
  - 書き下しは「f64 の経路で f64 以外の浮動小数を作らない」ことを縛る（umT5 の層逐次の前例 — `TorchDispatchMode`・ADR 0119 追記「段 10c の結果」）。
    diffusers の `_keep_in_fp32_modules`（`transformer_wan.py:549`）と RoPE の表の dtype の扱いに注意する。
  - CPU 参照の forward は `sdpa_kernel([FLASH_ATTENTION])` の下に置く（MATH に落ちると S×S を実体化して即 OOM — ADR 0118 追記「段 8 の計画」）。
  - f32 参照（r の分母）も同じ層逐次の書き手で採り、S = 192 で上流の f32 eager とビット一致を確かめる（書き手を 1 本に保つ）。
- **VAE の系列**: f16（decoder first / next・encoder）。VAE の重みを f16 に丸めて非有限が出ないことを export で確かめる（2.2 の VAE の重みの範囲は
  未確認）。HF の `vae/config.json` の `clip_output` は config を直接渡す経路で除く（独立検証）。
- **系列名**（ADR 0077 の接尾辞 `-dyn`）: `wan2.2-ti2v-5b-i8-dyn`（transformer）・`wan2.2-ti2v-5b-f16-dyn`（VAE の 3 グラフ・DiT を持たない）。

なぜ:

- 素直な形（f32 の全量を読む → fake-quant → export → emit）は umT5 で山 約 30.5 GiB の見込みだった。meta trace の形は core を変えずに山 6.79 GiB で
  通った前例がある（ADR 0119 追記「段 10b の結果」）。5B（4.99 B パラメータ）は umT5（5.68 B）より小さい。
- 層逐次の書き手は 31 GiB 機で他に手が無い（差分調査 §5）。1.3B で既存の golden とのビット一致を先に見れば、書き直しが参照の値を動かしていないことを
  5B の前に機械で言える。両系列の golden を相手にするのは、全体 f64 の経路を消した後も 1.3B の f16 系列の golden を作り直せる手を残すため。

守るもの: 31 GiB 機で export と参照が完走すること。参照の書き直しが参照の値を変えていないことを証拠で示すこと。exporter core と recipe の境界
（ADR 0065）。

### 8. 受理集合・既定値・fps

- **受理集合**（裁定 1 の推奨 a）: 832×480 / 480×832 × フレーム数 4n+1（5〜81）。既定は 832×480・81 フレーム。832×480×121 が B570 に入るかは段 2 で
  測り（diag だけ）、入るなら受理を広げるかを段 2 の結果で決める。公式の既定 1280×704 / 704×1280・121 フレームは段 10（利用者の RTX 5070 Ti の Chrome）
  で足す。
- **容量の閾値と、超えたときの手**（段 2 で判定・段 6 の前に確定）: 段 2 で S = 8,190 の diag を I2V 対応のグラフで両席とも測る。どちらかが
  **8.0 GiB を超えたら**（保守側は 8.0 + fdinfo − diag 1.14 ≈ 9.14 GiB で、天井の約 240 MiB 手前 — 容量の表の注）、受理するフレーム数の上限を下げる。
  新しい上限は、diag が 8.0 GiB 以下になる最大の 4n+1（65 フレーム = S 6,630・49 フレーム = S 5,070 の順に測る）で、既定のフレーム数もその上限に
  する。自機 A/B 門の長い側のケース（S = 8,190）とカード・受理集合の fixture も新しい上限へ移す。閾値の 8.0 GiB は B570 調査 §5 の「数百 MiB
  手前」を当てた目安で、段 2 の実測で変える根拠が出たら追記で開示する。
- **例外 — 1280×704 / 704×1280 系は「開発機の sha 行を持たない受理」**（段 10 で足す）。受理集合は機ごとではないので、受理に足すと B570 からも
  要求できる。この寸法は開発機で門も sha 行も持てない（容量の表 — 1280×704×81 の参照席は楽観側だけ入り、1280×704×121 は入らない）。
  **段 10 の着手条件**として、次の 2 点を決めて追記する:
  - **容量の admission**: admission は device の絶対上限（`maxBufferSize` / `maxStorageBufferBindingSize`）とだけ比べ、空き VRAM や確保の合計とは
    比べない（ADR 0089 決定 1 / 3・ADR 0070 決定 5）。1280×704 系の束縛は全て 2 GiB に収まる（FFN 中間 最大 1.46 GiB・スコアの行ブロック 最大
    1.96 GiB — 差分調査 §3.2）ので、B570 でも admission では拒まれない。総量の超過は errorScope で落ちる（fail loudly）。束縛上限の小さい
    adapter で計画時の preflight（ADR 0093 決定 5）が全件列挙で落とすことと、B570 級で総量の超過がどう見えるかを確かめ、limitations と
    カードに書く。
  - **1 submit の時間**: B570 では S ≥ 18,480 で裏付け前の 16 dispatch が 5 s を超えうる（容量と時間の見積り）。段 2 / 7 の 1 submit の実測から
    S = 18,480 / 27,280 へ外挿し、超えうるなら、submit を短くする runtime 側の手（別 ADR）と、B570 級での 1280×704 系を非対応として limitations と
    カードに書く手のどちらにするかを決める。
- **既定 shift**: 832×480 系は **3.0 で進め、段 7 の視認で確定する**（段 7 で shift 3.0 / 5.0 の対を見る）。3.0 は公式が 480p に勧める値（TI2V の
  i2v の docstring — `textimage2video.py:439`）で、Wan2.1 の 480p の既定も 3.0。2.2 の Diffusers 版の scheduler の config は 5.0 なので、参照は
  `flow_shift` を明示して採り、golden のメタに記録する（`few_step_ref.py:272` は config の値を書く）。1280×704 系の既定は段 10 で決める（公式・
  Diffusers 版とも 5.0）。shift は要求ごとに渡せる（`WanGenerateRequest.shift` — `pipeline.ts:416`）。
- **sha 行のケースは shift も明示する**（席の明示と同じ理屈 — 決定 2）。段 7 で既定の shift を変えても、既存の行を焼き直さずに済む。
- **step 数・guidance**: 50・5.0（公式・Diffusers 版の README と同じ — 上流調査 §4.1）。negative の既定は Wan2.1 と同じ公式の `sample_neg_prompt`
  （`shared_config.py:19` は 2.1 と同じ文面 — 上流調査 §4.1）。
- **fps は 24**（`wan_ti2v_5B.py:32`）。`GeneratedVideo`（今は fps を持たない — `pipeline.ts:321-325`）に `fps` を足し、各クラスが自分の世代の値
  （2.1 は 16・2.2 は 24）を入れる。fps は上流の事実でノブではないので manifest には入れない。
- **公式の対応寸法の外（480p）の品質は視認でしか決まらない**。公式の T2V は 1280×704 / 704×1280 だけを受け、480p は想定外。I2V の docstring は
  「480p なら shift 3.0」と書くので、480p で回す使い方そのものはある（上流調査 §4.1）。

なぜ:

- B570（開発機）で門と sha 行を全部持てるのは 832×480×81（S = 8,190）まで（容量の表）。公式の既定は B570 に入らない。
- 832×480×81 の余裕は、外挿と I2V の増分を入れると 0.37〜0.51 GiB で、見積りの誤差より薄い（容量の表の注）。閾値と手を実測の前に決めておけば、
  段 2 の結果を見てから基準を動かさずに済む。
- 1280×704 系を例外として明記するのは、機ごとの受理（空き VRAM で拒む）が ADR 0070 決定 5 / 0089 の「空き側と比べない」に反し、受理集合に
  入れた瞬間に B570 からも要求できるため。門の無い受理であることを隠さず、B570 での落ち方を着手前に決める。
- 既定 shift の良し悪しは視認でしか決まらない。材料の無い事前の裁定にせず、視認の段で対を見て決める。

守るもの: 受理する入力を、門と sha 行を持てる範囲に留めること（例外は 1280×704 系だけで、それを明記すること）。受理の外は fail loudly
（`ModelInputError`）。開発機の天井の手前で受理を止めること。

### 9. text 段 — umT5 は `karume-umt5-xxl` を越境参照。トークナイザ資産と埋め込み資産は Wan2.1 の系列からバイトそのまま写す

- **umT5**: `karume-umt5-xxl`（model `xxl`・pipeline `umt5-encoder/1`・quant `i8`）を `weights.text_encoder` で越境参照する（ADR 0119 追記「段 10d の設計」A /
  D と同じ形・全席の完全写像）。再 export しない。全席の `requiredLimits` は語彙埋め込み 1 バッファの 1,050,148,864 B を要求する（ADR 0119 追記
  「10d-1」）。
- **トークナイザ資産**（形式 `karume-wan-umt5-tokenizer/1`・Wan の前処理の表を束ねる — ADR 0119 追記「段 10d の設計」C）: `karume-wan2.2` の自前の資産に、
  系列 `wan2.1-umt5-tokenizer` の 1 本をバイトそのまま置く。
- **埋め込み資産**（事前計算の固定 4 プロンプト — ADR 0118 決定 4）: 同じくバイトそのまま置く。`textEncoder: "precomputed"` の経路（umT5 を取らない
  軽い使い方）を 2.2 でも保つ。
- **資産の出所の門**: 2 つの資産は出所として Wan2.1-T2V-1.3B-Diffusers の pin を名乗る。今の組み立ての門は出所を `SOURCES[model]` の pin と比べる
  （`tools/export-recipes/wan/distribution.py` の `assert_umt5_tokenizer` / `assert_text_embeds`）ので、2.2 では「text 段の資産の出所の pin」（= Wan2.1 Diffusers の
  pin）と比べる形に分ける。DiT / VAE の出所（2.2 の pin）とは別の欄にする。umT5 の容器の出所（今は Wan2.1 Diffusers の `text_encoder`・並行して起草中の
  ADR [0122](0122-umt5-upstream-and-compatible-encoders.md) は本家 google/umt5-xxl へ移す案）は `karume-umt5-xxl` 側の事実で、この欄とは独立に決まる。
- **カードと NOTICE の umT5 の書き方**は `karume-umt5-xxl` の出所の記述に揃える（0122 が採られれば、その決定 8 の「本家の encoder・2.2 の bf16 の
  `text_encoder` はその RNE 丸め」の形）。トークナイザは「Wan2.1 Diffusers の `tokenizer/` から変換・2.2 の `tokenizer/` と sha 一致」と書く。
- text 段のコード（`#encode` — `pipeline.ts:1523`・`textEncoder: "gpu" | "precomputed"`・`signal`）は共有モジュールへ切り出して 2.1 と 2.2 で使う（決定 10）。
  部品差し替え（`components.text_encoder` — 部品差し替え調査の要約 1）も 2.2 で同じく効く。
- 固定プロンプト（boxing-cats / ferret / cat-dog-baking + negative）は 2.1 と同じ。視認 A/B と sha 行のケースも同じ文面で持つ。

なぜ:

- umT5 は 2.1 と 2.2 で重みが同一（umT5 出所調査 §0）で、DiT の文脈入力の契約も同じ `[1,512,4096]`（上流調査 §1.1）。2.2 の Diffusers の bf16 から作り直すと
  i8 のバイトが変わり、同じ encoder が 2 本になる（差分調査 §7.2）。
- トークナイザ資産の形式は Wan の前処理（`prompt_clean`）の表を束ねた Wan 専用のもので、2.2 の前処理のソースも diff 0（上流調査 §5）。umT5 リポへ移すと
  資産の経路まで越境する（ADR 0119 追記「段 10d の設計」C）。2.2 は「Wan の別の世代」で、C が待つ「他の消費者」ではない。
- 埋め込み資産は umT5 の出力で、umT5 が同じなので 2.2 でも同じ値。作り直すと 2.2 の text_encoder（11.4 GB）の取得と CPU の bf16 forward が要るだけで値は
  変わらない見込み（RNE の一致 — 推測）。
- 出所の門を分けるのは、資産が本当の出所を名乗ったまま組み立ての門を通すため（出所を 2.2 の pin へ書き換えると、事実と違う provenance になる）。

守るもの: 1 つの encoder を 1 本の容器で共有すること（利用者の取得も 1 回）。資産の provenance が事実どおりであること。同じプロンプトが 2.1 と 2.2 で同じ id 列・
同じ埋め込みになること。

### 10. 配布形と公開 API — `karume-wan2.2` / `ti2v-5b`・`./wan` の中の別クラス・共有モジュールの切り出しは 2.1 の sha 行で確かめる

- **配布リポ**: `karume-wan2.2`・モデル `ti2v-5b`（ADR 0092 決定 1 / 2 — 家族 1 リポ・世代は別リポ。ADR 0118 決定 7 と `distribution.py:80` の予告どおり）。
  `WAN_SOURCES["wan2.2"]` は公開リポができる回に足す（ADR 0118 追記「段 7 の結果」）。リポ直下に `LICENSE.md` / `NOTICE.md`（ADR 0092 決定 7）。
- **配布の大きさ**（推測）: DiT i8 4.67 GiB + VAE decoder f16 2.07 GiB（first / next の 2 本 — 重みを跨いで共有する口は無い・ADR 0118 未解決「閉じた（段 4）」）+
  encoder f16 0.28 GiB + 資産 ≈ 7 GiB。umT5 5.3 GiB は越境参照。
- **pipeline 名**: `wan-ti2v` / major 1（2.1 は `wan` / 1 — `packages/models/src/wan/config.ts:30-31`）。VAE の mean / std・出口のチャネル・受理集合・既定・画像入力が
  違い、同じ `wan/1` を名乗ると読み手が世代を取り違えても通りうる（差分調査 §7.2）。
- **公開クラス**: `@karume/models` のサブパス `./wan` の中に別クラス（仮称 `WanTi2vPipeline`）を置き、barrel（`mod.ts`）にも出す。要求の型で I2V の画像入力を
  2.2 に限る。
- **共有モジュール**: text 段・DiT のループ（patchify → DiT → unpatchify → CFG → UniPC）・タイル decode を `pipeline.ts` から切り出し、2 つのクラスが使う。
  世代で違う値（決定 6 / 8 の mean / std・受理集合・既定・fps・VAE の `patch_size`）は世代の記述子に集め、グラフ宣言から導けるもの（潜在のチャネル数
  〈`WAN_PATCH.channels: 16` — `pipeline.ts:274-276`〉・出口のチャネル数・タイル辺・グラフの入出力の空間比）は導く。
- **切り出しと 2.1 の一般化は独立の段（段 3）にまとめる**: 共有モジュールの切り出しと、2.1 の経路の一般化（チャネル数をグラフ宣言から読む・
  重なりを px から導く式〈TS / Python〉・タイルの計画・`GeneratedVideo.fps`）を、VAE 2.2 の段（段 4）より前の 1 つの段で行う。2.2 のコードは入れない。
  **緑の条件は、`deno task test:models:wan`（2.1 のレーン）を B570 で実走して、2.1 の既存の sha 行・帯・case id が全て一致すること**。Python 側は、
  2.1 のタイル計画の凍結表が不変で、1.3B の krm・golden がバイト不変（safetensors はテンソルで比べる — ADR 0118 段 8 の結果）。
- **以後も、2.1 の経路に触るコミットは同じ条件**（2.1 のレーンを B570 で実走して全て一致）。共有モジュールへの I2V の条件づけの追加（段 9）や、
  2.1 と共有する recipe（`dit_patch.py` / `vae_patch.py` / `vae_tiling.py` / `_shared/vae_rank4.py`）の変更が当たる。recipe だけの変更は、1.3B の
  krm・golden のバイト不変で代える（GPU を使わない）。
- **テストのレーン**: 2.2 のテストは名前に `wan_ti2v` を含め、別レーン `test:models:wan-ti2v`（`deno test -A 'packages/models/tests/*wan_ti2v*_test.ts'`）
  に置く。`wan_ti2v` を含む名前は今の `test:models:wan` の glob `'packages/models/tests/*wan*_test.ts'`（`deno.json:35`）にも一致するので、
  **`test:models:wan` に `--ignore='packages/models/tests/*wan_ti2v*'` を足す**。レーンの被覆の門（`packages/runtime/tests/verify_lanes_test.ts`）は
  `--ignore=` を解析でき、系列レーンどうしの重複を許す（同 `:9-10`・`:190-201`）ので、ignore を忘れても赤にならない。ignore が無いと、2.1 の
  無害を確かめるレーンが 5B の e2e まで走らせる。レーンの追加と ignore は段 1 で行い、被覆の門を緑にする（レーンは空を許さない — 同 `:11-12`）。

なぜ:

- 別クラスにすれば、型で I2V の入力と 24 fps・既定 81 フレームを 2.2 に結び付けられる。同じクラスに世代の分岐を入れると、受理の判定が実行時の世代に依存する。
- 2.1 の sha 行は「切り出しで値が動いたら赤」を機械で言える既存の検出器で、新しいテストを書かずに無害を示せる。
- 切り出しと一般化を VAE 2.2 の段より前の 1 段にまとめるのは、2.1 の経路を変えるコミットと 2.2 を足すコミットを分けるため。一般化を VAE 2.2 の段で
  行い安全網を後ろの段に置くと、退行が出ても見えるのが遅れ、原因を切り出しと一般化のどちらに帰すかを取り違える。

守るもの: 公開面を必要最小に保つこと（ADR 0008）。2.1 の値を 1 bit も変えないこと。2.1 の経路を変えたコミットごとに、その無害を機械で示すこと。

### 11. I2V — 条件づけは diffusers の形・画像の前処理は公式の挙動（裁定 3）・encoder の寸法の扱いは段 9 の最初に決める

- **条件づけ**: diffusers の `WanImageToVideoPipeline` の `expand_timesteps` 分岐の形を採る（参照が diffusers なので）。各 step でモデル入力の先頭フレームだけを
  `(1 − m)·cond + m·latents` で置き換え、スケジューラは置き換えない潜在で進め、最後に 1 回置き換えてから VAE へ渡す（`pipeline_wan_i2v.py:760-767`・`816-817`）。
  公式の形（各 step の後に置き換える）との差は段 9 の CPU 2 ステップで記録する（同値は推測 — 独立検証）。
- **参照ループの時刻**: 2 ステップの通しの参照は、この条件づけを決定 4 の時刻の形（時刻の MLP を M = 1 で 2 回）で回す。diffusers の pipeline
  そのもの（M = S）との差は観測として並べる（決定 4）。
- **出力寸法**: 受理集合（決定 8）の中から、画像の縦横比に最も近い寸法を選ぶ（同点は横長）。`width` / `height` を明示したときは受理集合の中であること。
- **画像の前処理**（裁定 3 の推奨 a）: 選んだ寸法を覆う側へ LANCZOS でリサイズ（`scale = max(ow/iw, oh/ih)`）→ 中央クロップ → `[-1, 1]`
  （公式 `textimage2video.py:462-477`）。入力は RGB8（decode は Karume の責務外 — `packages/models/src/image/preprocess.ts:6-9`）。
  - LANCZOS を `preprocess.ts` に足す（今は bilinear / bicubic — Pillow の `ImagingResample` と同じ分離型で、2 パスの間で uint8 へ丸め直す既存の規律に従う）。
  - 参照は、ホストで切った画像を diffusers に渡して採る（diffusers の前処理は直接リサイズで公式と違う — 上流調査 §4.3）。
- **VAE encoder**: 画像 1 枚 = encode の chunk 0 だけなので、`time_conv` 無し・T = 1・cache 無しのグラフ 1 本（上流調査 §9）。patchify（3 → 12 ch）はホスト。
  出力の前半 48 ch（mu）→ `(mu − mean)·(1/std)`（48 値）。
- **段の順と解放**: I2V の生成は「encoder → encoder のセッションを畳む → text → DiT → VAE decoder」の順に回し、DiT の段に encoder の重み
  （f16 0.28 GiB）と活性を残さない。DiT の段の余裕は 0.4〜0.8 GiB しか無い（容量の表）。2.1 の各段もセッションを段ごとに畳んでいて
  （`pipeline.ts:1572-1577`・`1669-1676`・`1732-1741`）、同じ形に倣う。B570 は `destroy()` の解放が次の device poll まで遅れる（制約）ので、
  畳んだ後に解放を待つ。段 9 で VRAM の山を段ごとに記録する。
- **encoder の寸法の扱い**（段 9 の最初に決める・推奨の順）: ① conv2d / conv3d を記号長の空間で受けられるか（runtime の shape 規則 `ops/shapes.ts:672-728`
  は数値の長さで式を立てる — 未確認）を確かめ、通れば寸法から独立した 1 本 ② 通らなければ受理寸法ごとのグラフ（受理集合が有限の間 — ADR 0038 §4 の
  「資産は解像度から独立」からの逸脱として開示）③ タイル encode（上流の非タイルとは近似の差）。1280×704 の 1 枚でも最大中間 36.2 M 要素（145 MB）で、
  容量の理由でタイルにする必要は無い（上流調査 §3.4）。

なぜ:

- 条件づけを参照と同じ形にすれば、2 ステップの通しを帯で照合できる。
- 受理集合が有限の間、出力寸法を画像から自由に選ぶ公式の `best_output_size` は使えない（選ばれる寸法の門と sha 行を持てない）。

守るもの: I2V の通しを diffusers の参照と照合できること。T2V の sha 行を I2V の追加で変えないこと。I2V の DiT の段が T2V と同じ容量で入ること。

### 12. GPU と CPU の段の運用

- GPU を長く使う段（2〜7・9）は GPU のロックで 1 本ずつ直列に回し、順序はメインが決める。この機の GPU は学習と共有なので、回す前に使用中を確かめる
  （使用中なら待つ・CPU の段は進めてよい）。
- 確保が最大のものを先頭に置く（B570 の `destroy()` の解放遅れで、後ろに置いた大きい確保が OOM になった前例 — ADR 0118 段 8 の結果）。
- CPU の長い作業（golden の採取・層逐次の参照）は他の重い CPU 作業と同居させない（RSS）。

守るもの: GPU の測定どうしが干渉しないこと。学習の邪魔をしないこと。

### 13. 段の分割と実装の進め方

11 段（段 0〜10）に分ける（「検収」節の表）。**2.1 の実行経路（TS）の変更は段 3 に集め、T2V を段 8 で一度閉じてから I2V（段 9）に入る**（2.1 と共有する recipe だけの変更は段 0 / 1 / 4 にもあり、1.3B の容器と golden のバイト不変で確かめる — 決定 10）。

- 実装は Opus へ委任する（段ごとの契約: 目的・出力・境界・仕様一式）。
- worktree はリポ外に作る（例 `~/workspace/karume-wt-wan22`）。リポ内に置くと fmt / lint / test が worktree 側のファイルを誤拾いする（CLAUDE.md）。
- GPU の段の実走・帯の確定・sha 行の `write` はメイン側で直列に行う。

守るもの: 各段を単独で検収できること。T2V の成果を I2V の作業で壊さないこと。

## 採らなかった案

- **f16 席を足す**（裁定 2 の b）— B570 に入らず、門も sha 行も持てない。export も RAM の境界か core の変更が要る（決定 2）。
- **時刻の MLP をホストで `[S,256]` に展開して M = S で回す** — `time_projection` だけで 1 forward 約 1.8 T MAC・`e0` が f32 1.87 GiB（上流調査 §2.4）。
- **先頭 P トークンを slice / cat で分ける** — S のほかに P の記号が要り、S 形グラフの 1 シンボル（ADR 0034）から外れる（差分調査 §6.2）。
- **時刻の MLP を M = 2 の 1 回にまとめる** — M = 1 と M = 2 で linear の縮約の経路が違えば、T2V の値が「I2V 対応のグラフ」と「2.1 型のグラフ」で割れる。
  CPU では実際に割れた（決定 3）。GPU の linear が M で経路を変えないと確かめられたら見直せる（未解決）。
- **T2V 用と I2V 用に DiT のグラフを 2 本持つ / T2V だけで export して I2V の段で作り直す** — 5B の再 export（CPU 数時間）と golden の撮り直しが要り、容器も
  2 本になる（決定 3）。
- **上流の pipeline の 2 次元 timestep（M = S）の経路を eager 同値の相手にする** — linear の縮約の経路の差が門に混ざる（決定 4）。
- **公式の bf16 実行を数値の基準にする** — bf16 自身の誤差が床になる。CPU で数時間級（決定 5）。
- **公式形式（`Wan-AI/Wan2.2-TI2V-5B`）を上流にする** — `WanModel` は torch.export に向かず、VAE と T5 は pickle（決定 1）。
- **VAE 2.2 のために op を足す（rank 8 の view / permute・`mean`）** — 全て rank 4 以下の既存 op で書ける（決定 6）。
- **VAE のタイルを潜在 32 にする** — cache だけで 5.2 GiB になり、B570 の余裕が消える（決定 6）。
- **画素空間でブレンドする（タイルごとに unpatchify してから貼る）** — 上流の 2.2 の慣行（patchify 空間でブレンド）と重みの粒度が違う。patchify
  空間なら既存のブレンドがチャネル数だけの一般化で使える（決定 6）。
- **f64 参照を全体 `model.double()` のまま使う** — 37.25 GiB で 31 GiB 機に載らない（決定 7）。
- **5B の f64 参照を、1.3B での一致確認なしに層逐次で書く** — 書き直しが参照の値を動かしていないことを示せない（決定 7）。
- **umT5 を 2.2 の Diffusers の bf16 から作り直す** — i8 のバイトが変わり、同じ encoder が 2 本になる（決定 9）。
- **トークナイザ資産を `karume-umt5-xxl` へ移す** — 資産の経路まで越境し、2.1 の配布形も焼き直しになる。資産は Wan の前処理を束ねた Wan 専用の形（決定 9）。
- **資産の出所を 2.2 の pin へ書き換えて置く** — provenance が事実と違う（決定 9）。
- **2.1 の `WanPipeline` に世代の分岐を足して 1 クラスにする** — 受理の判定が実行時の世代に依存し、型で I2V の入力を 2.2 に限れない（決定 10）。
- **pipeline 名を 2.1 と同じ `wan/1` にする** — 世代の取り違えが通りうる（決定 10）。
- **I2V の画像の前処理を diffusers の直接リサイズにする**（裁定 3 の b）— 形が歪む。公式の挙動と違う（決定 11）。
- **最初から 1280×704・121 を受理する**（裁定 1 の b）— 開発機で回らず、回帰を開発機で検出できない（決定 8）。
- **1280×704 系を機ごとの受理にする（空き VRAM や機の種別で admission が拒む）** — admission は device の絶対上限とだけ比べ、空き側とは比べない
  （ADR 0070 決定 5・ADR 0089）。当て推量の閾値は健全な環境で誤拒否を作る（決定 8）。
- **832×480 系の既定 shift を事前の裁定で決める** — 良し悪しは視認でしか決まらず、材料の無い a / b になる。3.0 で進め、段 7 の視認で対を見て
  確定する（決定 8）。
- **一般化（チャネル数・重なりの式・タイルの計画）を VAE 2.2 の段で行い、2.1 のレーンの確かめを切り出しの段だけに置く** — 2.1 の退行が後ろの段まで
  見えず、原因を取り違える（決定 10）。
- **層逐次の f64 の書き手を i8 系列だけにする** — 全体 f64 の経路を消すと 1.3B の f16 系列の f64 golden を作る手が無くなる（決定 7）。
- **中間の席（`f16+dit8-a8` など）を置く** — 視認・sha 行・カードの費用が席の数だけ増える（ADR 0120 決定 1 と同じ理由）。
- **Wan2.2 の A14B（MoE の 2 専門家）を同じ ADR に含める** — 5B とは DiT の構成が違う（Diffusers 版の `transformer_2` と `boundary_ratio` が 5B では null —
  上流調査 §7）。範囲外。

## Consequences

- runtime と exporter core は変わらない見込み（新しい op・カーネル・キーが無い — 差分調査 §1.1）。既存の codegen スナップショットは不変。
- 2.1 は値が 1 bit も変わらない（共有モジュールの切り出し・重なりの定数の式化・`GeneratedVideo.fps` の追加のあとも、2.1 の sha 行・帯・case id・タイル計画が一致）。
  `GeneratedVideo` に `fps` が増えるのは公開面の追加（未リリースなので形は変わってよい）。
- `@karume/models/wan` に別クラスが増える。pipeline 名 `wan-ti2v/1` が増える。
- 配布形 `models/karume-wan2.2/`（約 7 GiB・umT5 は越境参照）が増える。
- 生成 1 本の所要は B570 の実用席・832×480×81 で約 29 分（DiT 約 18 分 + VAE 約 11 分 — 推測）。VAE が生成の約 4 割を占める（差分調査 §0）。

### ② 検証計画

- **移植の門（参照層）**: eager 同値（決定 4・ビット一致）→ S = 192 と S = 8,190 の f64 参照と正規化比 r の帯（決定用 6 本〈T2V の形 3 + I2V の形 3〉の
  最悪 × 5・受入れは別ケース・故障注入が帯の外）。VAE は cache の正規化だけの形が上流の非タイル `_decode` とビット一致 → GPU の chunk 列の帯 →
  タイルの縮退門の Uint32 一致。
- **実用層**: 自機 A/B 門（床・上限 = 実測 × 2・census〈linear の dispatch 310 本〉・決定性・故障注入）を S = 3,510（33 フレーム）と S = 8,190（81 フレーム —
  決定 8 の閾値で上限を下げたらその S）で持つ（attention a8 の誤差は行の長さ N で増える — ADR 0120 決定 4）。
- **退行**: sha 行（ADR 0106・環境キー別）。既定レーンは 2 ステップ × 33 フレーム × 2 席（参照行 / 実用行 — ADR 0110 決定 7）、81 フレーム・50 ステップは
  opt-in（`KARUME_WAN_FULL_PIPELINE=1` と同じ扱い）。ケースは席と shift を明示する（決定 2 / 8）。2.1 の sha 行は、段 3 と以後の 2.1 の経路に触る
  コミットの無害の検出器を兼ねる（2.1 のレーンを B570 で実走 — 決定 10）。
- **品質**: 利用者の視認 A/B（参照席 12 本 vs 実用席 12 本・seed 42〜45 × 固定プロンプト 3 本・832×480×81・50 ステップ）。参照席自身の品質裁定を兼ね
  （決定 2）、実用席の shift 5.0 の 12 本を足して既定 shift を決める（決定 8）。I2V は段 9 で別に持つ。
- **各段の後**: 変更した範囲のレーン（`test:models:wan` / `test:models:wan-ti2v`）と両方の `uv run pytest`。段 8（T2V を閉じる）と段 9 の後はフル `deno task verify`。

### ③ 段の分解

「検収」節の表（段 0〜10）。依存: 0 → 1 → 2、3 → 4 → 5、1 → 4、2・5 → 6 → 7 → 8 → 9 → 10。段 3（2.1 だけの変更）は 5B に依らないので、段 0〜2 と
並行できる（GPU は直列）。段 4 は段 1・3 の後なら段 2 と並行できる。

### ④ 足される複雑さと将来の障害の自己評価

- **増えるもの**: Wan のクラスが 2 つになり、text 段・DiT のループ・タイル decode が共有モジュールになる。VAE のパッチに 2.2 の分岐（ショートカット 2 種・
  出口 12 ch・encoder）が入る。DiT のグラフ入力が 2 本増える。層逐次の参照の書き手が 1 本増える（1.3B と 5B・f16 と i8 の両系列で共有するので、全体
  f64 の経路は残さない）。テストのレーンが 1 本増え、2.1 のレーンに ignore が 1 つ増える。
- **抑えたもの**: 新しい op・runtime の変更・exporter core の変更は無い。席は 2 つ。DiT の容器は I2V を含めて 1 本。umT5 は再 export しない。重なりは
  式 1 本で、世代が持つのは上流の事実の `patch_size` だけ。
- **将来の障害になりうるもの**:
  1. 世代の記述子に値を集めるので、Wan の 3 世代目が来たときは記述子を足す形になる。2.2 の A14B（MoE）は DiT のループが 2 専門家の切り替えを持つので、
     共有のループに分岐が要る（範囲外 — その時に別 ADR）。
  2. 共有モジュールの切り出しと一般化は 2.1 の振る舞いを変えうる。段 3 と以後の 2.1 の経路に触るコミットごとに 2.1 の sha 行で機械的に検出する
     （決定 10）が、sha 行が覆わない経路（エラー文言・中断の位置）はホストテストに頼る。2.1 のレーンの実走（約 48 分）がそのたびに要る。
  3. VAE の decoder の重みを first / next で 2 本持つ（2.07 GiB）形は 2.2 で重くなる。グラフを跨ぐ重みの共有の口は無く、作るなら runtime の別起票（ADR 0118
     未解決）。
  4. 1280×704 系は「開発機の sha 行を持たない受理」（決定 8 の例外）で、門は RTX の Chrome の実走に頼る。その寸法の回帰は開発機で検出できず、
     B570 から要求されたときの落ち方（総量の超過・1 submit の時間）は段 10 の着手条件で決める。
  5. I2V の encoder を受理寸法ごとのグラフにする場合（決定 11 の ②）、受理寸法を増やすたびに encoder の容器が増える。
  6. 832×480×81 の容量の余裕は薄い（0.37〜0.51 GiB の見込み）。決定 8 の閾値で受理するフレーム数の上限を下げると、最初の版の最長の動画が
     81 フレームより短くなる。

### 費用とリスク

- **CPU**: 1.3B での層逐次の検証は両系列の f64 golden の全ケースで、f16 系列の S = 14,040 の 8 ケース（f64 約 370 s — ADR 0118 追記「段 3 の結果」）と
  S = 32,760 の 8 ケース（約 1,505 s — ADR 0118 段 8）・i8 系列の S = 14,040 の 8 ケース・小さい S の 9 ケース（S = 192 が 8 本・S = 128 が 1 本）（秒単位）で、合わせて約 5 時間（推測・
  層逐次の読み直しを除く）。5B の S = 192 の golden（分単位）・S = 8,190 の golden 10 本（約 2.2 時間 + 層逐次の読み直し — 推測）。
- **GPU**: r 門と A/B 門は 1 回数分。視認 A/B 24 本は参照席 約 46 分 × 12 + 実用席 約 29 分 × 12 ≈ 15 時間、shift 5.0 の 12 本（実用席）を足して
  約 21 時間（推測）。2.1 のレーンの再走は 1 回 約 48 分（ADR 0118 追記「レビュー 2 本の消化」の 48 分 32 秒）で、段 3 と以後の 2.1 の経路に触る
  コミットごとに要る。
- **取得**: 上流 22.8 GB（transformer 19.99 + VAE 2.82）。

リスク:

1. **attention a8 の誤差と N**: 2.1 の実用席の step 1 relRMS は N = 14,040 で 1.07e-1、N = 32,760 で 2.10e-1（ADR 0120 段 4）。832×480×81 の N = 8,190 は
   2.1 で受け入れた N の内側だが、head 24・dim 3072 の別モデルで、2.1 の視認の結果をそのまま移せない。1280×704×121 の N = 27,280 は B570 で A/B 門を回せない。
2. **I2V の条件トークンと attention a8**: t = 0 の条件トークンは鋭い attention の行を作りうる（推測）。③PV の行 scale 1/127 固定で質量が消える形（ADR 0030 決定 6）が
   条件の忠実さに効くかは未知。段 9 で I2V の A/B 門と視認を別に持つ。
3. **参照席の帯（K-75）**: GPU の f32 GEMM の K 縮約の誤差は K とともに大きい（2.1 の FFN 下り K = 8960 で CPU f32 の 11〜14 倍 — ADR 0118 追記「段 3 の帰属」）。
   5B の FFN 下りは K = 14336 で、r の帯は 2.1 より広くなりうる。帯は実測から導く。
4. **容量の余裕が薄い**: 参照席の diag は 2.1 で測られていない（独立検証）。S = 8,190 は k の較正範囲の外で、外挿と I2V の増分を入れると余裕は
   0.37〜0.51 GiB（容量の表の注）。段 2 の diag が 8.0 GiB を超えたら、受理するフレーム数の上限を下げる（決定 8）。
5. **VAE 段の中間**: 最大の中間の根拠が覆った（207.7 MB）。cache との cat がグラフの中にある形なら、見積り 4.2〜4.5 GiB を測り直す（段 4 / 5）。
6. **480p の品質**: 公式の T2V の対応寸法の外。視認でしか決まらない（決定 8）。参照席の品質も視認でしか決まらない（決定 2）。
7. **diffusers の I2V の読み込み**: `WanImageToVideoPipeline.from_pretrained("Wan-AI/Wan2.2-TI2V-5B-Diffusers")` が通るかは未実行（上流調査 §10）。段 9 の最初に
   確かめる。
8. **export の RAM**: eager 同値の門は f32 全量（18.63 GiB）を持つ。他の重い CPU 作業と同居させない。段 0 で実測する。
9. **1280×704 系の B570 での落ち方**: 受理集合は機ごとではないので、段 10 の後は B570 からも要求できる。admission は拒まず（束縛は全て 2 GiB 以内）、
   総量の超過か 1 submit の 5 s 超え（device lost）で落ちうる。段 10 の着手条件で扱いを決める（決定 8）。

## 裁定

利用者に判断を仰ぐ点（推奨案つき）。832×480 系の既定 shift は裁定にせず、3.0 で進めて段 7 の視認で shift 3.0 / 5.0 の対を見て決める（決定 8 — 良し悪しは
視認でしか決まらず、材料の無い事前の a / b にしない）。

1. **受理する解像度とフレーム数**。開発機（B570）で全部の検証と sha 行を持てるのは 832×480・81 フレームまで。公式の既定 1280×704・121 フレームは開発機に
   入らない（容量の表）。
   - a. 832×480 / 480×832・4n+1 の 5〜81 フレームで始める（既定 81 フレーム = 24 fps で約 3.4 秒）。832×480×121 が開発機に入るかは段 2 で測る。81 フレームの
     余裕は薄く、段 2 の diag が 8.0 GiB を超えたら上限を 65 / 49 フレームへ下げる（決定 8）。1280×704・121 フレームは最後の段 10 で、利用者の RTX 5070 Ti
     の Chrome の実走で、「開発機の sha 行を持たない受理」として足す（B570 からも要求できるので、落ち方を段 10 の前に決める）。何が変わるか: 最初の版で
     作れる動画は 480p・最長 3.4 秒（上限を下げたらそれより短い）。守るもの: 退行を開発機で毎回検出できること。
   - b. 最初から 1280×704・121 フレームを受理に入れる。何が変わるか: 公式どおりの 720p・5 秒の動画が最初から作れる。守るもの: 公式の想定どおりの品質。
     ただし開発機では回らず、検収は RTX の実走（DiT だけで 40〜80 分 — 推測）に頼り、退行を開発機で検出できない。
   - **推奨 a**。理由: 門と sha 行を開発機で持てる。公式の対応寸法の外（480p）の品質は視認でしか決まらないので、段 7 の視認で確かめる。公式の I2V の
     docstring は 480p で回す使い方を想定している（shift 3.0 の推奨）。
2. **f16 席（元の f32 の重みを f16 に丸めた席）を作るか**。f16 の DiT は 9.31 GiB で開発機に載らず、RTX 5070 Ti でも 1280×704・121 フレームでは境界。
   - a. 作らない（参照席 `f16+dit8` と実用席の 2 つ）。何が変わるか: 利用者が選べる席は「重み i8・計算 f32」と「重み i8・活性 8 bit」の 2 つ。元の重みに
     いちばん近い席は参照席が担い、その品質は段 7 の視認で裁定する（決定 2）。守るもの: 配る席が全て開発機で検証されていること。
   - b. VRAM の大きい機のために作る。何が変わるか: 16 GB を超える GPU の利用者は丸めの少ない重みで回せる。ただし開発機では一度も回らず門も sha 行も無い席を
     配ることになり、export も RAM の境界か exporter core の変更が要る。
   - **推奨 a**。理由: 検証できない席を配らない。必要になったら、VRAM の大きい機での実測を材料に足せる。段 7 の視認で参照席自身が落ちたら、この裁定を
     見直す材料にする（決定 2）。
3. **I2V で画像の縦横比が出力と違うときの扱い**（段 9 で効く）。
   - a. はみ出しを切る（公式 — 覆う側へリサイズして中央クロップ）。何が変わるか: 縦横比は保たれるが、画像の端が欠ける。
   - b. 引き伸ばす（diffusers — 指定寸法へ直接リサイズ）。何が変わるか: 画像の全体が残るが、形が歪む。
   - **推奨 a**（公式の挙動）。理由: 歪んだ先頭フレームから動画を作ると、全フレームが歪んだまま動く。参照は、ホストで切った画像を diffusers に渡して採る。

## 裁定（2026-10-04・利用者）

1. **受理する解像度とフレーム数 = まず開発機で回せる解像度とフレーム数で作って試す**。利用者の意見: 解像度を保ってフレーム数を落とす形で
   入るなら、その方が安定しそう。開発機に入るトークン数の予算（S = 8,190 前後 — 容量の表）の配分は 2 通りある:
   公式の解像度 1280×704 系を 33 フレームまで（潜在 9 フレーム × 880 トークン = S 7,920・24 fps で約 1.4 秒）と、832×480 系を
   81 フレームまで（潜在 21 フレーム × 390 トークン = S 8,190・約 3.4 秒）。どちらを主にするか（両方を受理して視認で比べるか）は
   確認中で、決まったら決定 8 を追記で改める。段 0 / 1 はこの配分に依らない（実寸の golden の形を決めるのは段 2）。
2. **f16 席 = 今は作らない（a）**。後で f16 などの席を足す方針 — 開発機で動かなくても、重みは用意しておきたい（backlog に起票）。
   後で足すときの材料: f16 の export は RAM の境界か exporter core の変更が要る（決定 7）・開発機では門も sha 行も持てない。
3. **I2V の縦横比 = まず公式の挙動（a — 覆う側へリサイズして中央クロップ）**。利用者の要望: 選べるようにしたい。直接リサイズ
   （diffusers の挙動）を選ぶ口の形は段 9 で決める。

## 未解決

- **実測で置き換える数値**: 容量と時間の見積りの表の全部（参照席の diag は 2.1 でも未測・S = 8,190 は k の較正範囲の外）・VAE 段の中間・取得量・CPU 参照の
  所要。段 0〜7 の実測で置き換える。
- **容量の閾値 8.0 GiB**: B570 調査 §5 の「数百 MiB 手前」を当てた目安。段 2 の実測で変える根拠が出たら追記で開示する（決定 8）。
- **I2V 対応の増分**: `where` の置き場所で +0.19〜+0.56 GiB（推測）。段 1 の IR の検査と段 2 の diag で確かめる（決定 3）。
- **GPU の linear が M で縮約の経路を変えるか**: 変えないなら時刻の MLP を M = 2 の 1 回にまとめられる（差分調査 §12）。今は M = 1 × 2 で問題が無いので急がない。
- **AvgDown3D の和の順**: 4 要素の和の順が torch CPU の `mean` と Karume の `sum` で同じか（段 9 — encoder は帯で受ける）。
- **VAE の mid の attention（D = 1024）**: 融合 attention が実寸で通すか（段 4）。
- **I2V の encoder の寸法の扱い**: 記号長の conv の可否（段 9 の最初）。受理寸法ごとのグラフにするなら ADR 0038 §4 からの逸脱を追記で開示する。
- **公式と diffusers の I2V の置き換えの同値**: 推測のまま（段 9 で CPU の差を記録）。
- **832×480×121 の受理**: 段 2 の diag で決める。
- **832×480 系の既定 shift と既定席**: 段 7 の視認で決める（決定 2 / 8）。
- **1280×704 系の B570 での扱い**: 容量の admission と 1 submit の時間。段 10 の着手条件（決定 8）。
- **1280×704 系の既定 shift**: 段 10 で決める。寸法ごとに既定を変えるなら `pipelineConfig` の形が変わる（1 値 → 寸法の表）。
- **RTX の Chrome での実用席の速度と VRAM**: 2.1 でも未実走。段 10 で初めて分かる。
- **umT5 の部品差し替え**（コミュニティの追加学習版など）: 2.2 でも 2.1 と同じ `components.text_encoder` の席で効くが、bf16 の入力経路・出所の扱い・トークナイザの
  同一性の検査は部品差し替えの別の作業（部品差し替え調査 §3）。本 ADR では扱わない。
- **ADR 0122 との順序**: 0122（umT5 の出所を本家へ）が採られると `karume-umt5-xxl` の系列名と provenance が変わり、2.1 と 2.2 の配布形は越境参照の
  実 SHA で焼き直す。本 ADR の段 8 のローカルミラーは、その時点の `karume-umt5-xxl` のミラーを参照して組む（仮の SHA — ADR 0119 追記「段 10d の設計」E）。
- **1 パスの時間の内訳**: Wan の op 別の時間の記録は無い。速度の候補（adaLN / rope の融合・VAE の重みの共有）は perf-ledger に回す。

## 追記（2026-10-04）: 裁定 1 の確定 — 2 つの配分を両方受理して試す

- **利用者の裁定**: 公式の解像度を保ってフレーム数を絞る配分と、832×480 系の配分の両方を試す。
- **決定 8 の改訂**: 受理集合は 832×480 / 480×832 の 4n+1・5〜81 フレーム（S ≤ 8,190）と、1280×704 / 704×1280 の 4n+1・5〜33 フレーム
  （潜在 9 フレーム × 880 トークン = S ≤ 7,920）。どちらの上限も段 2 の実測で確定する（diag が 8.0 GiB を超えたら上限を下げる規則を両方に当てる）。
  既定の寸法とフレーム数は、段 7 の視認で両方を見てから決める。
- **段への影響**: 段 2 の実寸の golden と r 門は 2 つの形（潜在 `[48,21,30,52]` と `[48,9,44,80]`）で持つ。段 5 のタイル計画の凍結・段 6 の sha 行・

- **費用（推測）**: 段 2 の CPU の参照と GPU の門、段 6〜7 の GPU 時間が約 1.5〜2 倍。

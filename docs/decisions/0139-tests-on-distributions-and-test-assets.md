## Context

The real-weight tests read their containers and goldens from `outputs/series/`, the exporter's output (195 GiB on the
development machine on 2026-11-02, next to 125 GiB of distribution mirrors under `models/`). Every model therefore
costs its disk twice, and a series has to be kept for as long as any test reads it.

The recon of 2026-11-02 (eight read-only legs over every test that names a series) established:

- Every series container that has a distribution counterpart is byte-identical to it: the parts' sizes and sha256
  match the mirror's `karume.json` (moss, wan / umt5, irodori / dacvae, birefnet / lucida / depth-anything / siglip2,
  sbv2 front and voice, deberta's sbv2 22-layer encoder, gemma4 product and drafter, gemma4-qat). Only the names and
  the layout differ: `<series>/<component>/model-N-of-M.krm` becomes `<model>/<graph>/model.<dtype>-N-of-M.krm`, and
  parts shared between models move to `shared/` (ADR 0041 decision 9). A mirror container is therefore opened
  through its manifest, not by "representative path plus numbering".
- A sha256 row depends only on output bytes, so with the same session options it holds on the mirror as it held on
  the series.
- The goldens — `io.*` and the other recipe outputs (CPU references, latents, prompt embeddings, PLE probes) — are not
  part of any distribution (`dist.py` keeps them out by design). There are 1,134 such files, 30.6 GiB, 26.2 GiB
  unique by content. Default lanes read them as torch comparisons, as inputs, and as existence conditions.
- Some series graphs are not shipped (gemma4's one-shot and decode graphs, sbv2's dp / flow / dec and f32 storage,
  deberta's 24-layer and 2-layer encoders, anima's retired f16 / bf16 and i4-dyn series), and three families have no
  distribution at all (EmbeddingGemma, MiniCPM5, the vowel detector). Wan2.1 has a local mirror that is not
  published.
- Distribution assembly reads the series (`dist.py --series`), so rebuilding a distribution needs its series.

Keeping goldens only on the machine that exported them also left a gap: on a new machine there is no torch
comparison until every model is exported again.

## Decision

1. **Default lanes open real-weight containers only from the distribution mirrors** (`models/<repo>/`), through the
   manifest (`karume.json` → selection → `container.parts`), which also checks the two documents' sha256 that the
   series path never checked. An unpublished family reads its local mirror built by `dist.py` (Wan2.1). Files that a
   distribution already carries (tokenizers, Wan's text embeddings) are read from the distribution, not from a
   golden copy.
2. **Test assets that no distribution carries live in a private Hugging Face dataset, `hdae/karume-test-assets`**,
   fetched into the local root `outputs/test-assets/` — the dataset root and the local root have the same layout,
   one folder per kind of asset:
   - `goldens/<series>/<path>` — recipe outputs (torch references, inputs captured from upstream), each at the same
     relative path it has under `outputs/series/` (containers never);
   - `corpus/` — test inputs made by this project and frozen by hand, which cannot be regenerated byte for byte:
     `corpus/anima/` (the four 1024² Anima images of `outputs/misc/corpus/`, the inputs of the real-image checks
     and of the birefnet / depth-anything / siglip2 goldens) and `corpus/wan-i2v/` (the three image-to-video
     condition images of `inputs/wan-i2v/`, pinned by sha256 in `wan.export_vae_encoder.IMAGES`; frame 0 of this
     project's own Wan2.1 seed-42 review clips — no upstream repository carries them).

   The local root is a cache: deleting it loses nothing that a fetch does not restore. A new kind of asset gets its
   own top-level folder.
3. **The dataset is pinned.** A tracked file holds the dataset repository and its commit SHA; the fetch command
   downloads that revision and records it in `outputs/test-assets/.revision` only after the download completes. A change
   that needs new or changed goldens uploads them first and moves the pin in the same commit as the tests that read
   them.
4. **Which goldens are uploaded**: the non-container files that a default-lane or opt-in parity test of a family with a
   distribution reads — at directory granularity where a test reads a whole directory. Not uploaded: containers,
   files the distribution already carries, goldens no test reads (for example `gemma4-e4b-decode`), and the goldens
   of implementation-time tests (decision 6).
5. **The assets gate moves from the series root to the test-asset root.** It is red when `outputs/test-assets/` is
   absent or its `.revision` differs from the pin; the opt-out stays `KARUME_ALLOW_NO_ASSETS=1`. A partial fetch
   (`--include`) writes no `.revision`. A default-lane case whose test asset is absent FAILs when the root holds a
   complete fetch of the pin (the dataset lacks a file the tests read) and SKIPs explicitly otherwise; a missing
   mirror, or a sibling mirror it references, is a SKIP (the distribution gate owns that red). The series-graph table
   (`series-graphs.ts`) is retired; the graph-name check moves to the distribution gate, which checks every
   model × quant × graph that a manifest declares (parts present with their declared sizes, the container's graph
   name equal to the weights key), not only the default selection.
6. **Implementation-time checks read series behind `KARUME_SERIES=1`** and SKIP explicitly without it: tests of
   graphs that are not shipped, and of families with no distribution (MiniCPM5, the vowel detector; EmbeddingGemma
   until its distribution is published — Rulings D2). Their goldens stay in their series; they are regenerated by
   exporting again.
7. **sha256 case IDs are frozen strings.** IDs that spell a series name (birefnet's `<series>/<photo>`,
   siglip2-golden, qwen3_5) stay as they are; no row is rewritten for the move.
8. **Series are transient.** Adding or re-exporting a model is: export → implementation-time checks → assemble the
   distribution → publish → upload the goldens and move the pin → record sha rows → the series may be deleted.
   Rebuilding a distribution or regenerating a golden exports again.
9. **Access.** The dataset is private; it is read and written with the project account's token (`Karume Release`,
   the everyday token — the release runbook's token step). The personal account's `Karume Gated Read` cannot be
   granted access to it and is used only to fetch gated upstream models. Before anyone else is given access, the licences of
   the upstream models whose outputs the goldens contain are checked.

## Rulings (2026-11-02)

- D1 — goldens: the maintainer proposed a private HF dataset instead of the recommended "tracked small fixtures, the
  rest opt-in" or a local-only golden root. Chosen because it keeps today's default checks unchanged, makes the
  goldens re-obtainable, and gives a new machine its torch comparison without exporting again.
- D2 — families without a published distribution: EmbeddingGemma gets a published distribution; MiniCPM5 and the
  vowel detector move to the implementation-time checks; Wan2.1 reads its local mirror.
- The vowel detector's training checkpoint (`inputs/vowel-detector/`) is not uploaded; the Anima corpus and the
  image-to-video images are (maintainer, 2026-11-02). The dataset is named for test assets in general, with one folder
  per kind, because the corpus is not a golden (maintainer, 2026-11-02).

## Consequences

- Disk: the series (195 GiB) are no longer needed by the default lanes; the test-asset root is about 26 GiB at most and
  can be fetched per family. Each model's weights are kept once, in `models/`.
- New machine: fetch the distributions and the test assets, then `KARUME_REFERENCE=write` records its sha rows after the
  torch comparisons (`KARUME_UPSTREAM_PARITY=1`) have passed on that machine.
- The upload and the pin are one more step per model (decision 8), and the dataset counts against the account's
  private storage quota.
- Tests that read a golden only as an existence condition are untied from it while they are migrated.
- ADR 0129 decision 3's assets gate and ADR 0005's addendum of 2026-09-05 are amended to decision 5; `assets-layout`
  gains the test-asset root (and loses `outputs/misc/corpus/` and `inputs/wan-i2v/`); the release runbook gains the fetch.

## Staging

1. This ADR; the golden file list (decision 4) from the recon's per-test classification.
2. Create the dataset, upload, pin; the fetch command; the gates of decision 5.
3. Shared test helpers: one mirror-root resolver and one manifest-based component opener.
4. Families, one commit each, each family lane green with no `KARUME_REFERENCE` write or rewrite: vision →
   sbv2 / deberta → irodori → gemma4 → moss / qwen3_5 → wan / umt5 → anima.
5. Python: the cases that check distribution assets read `models/`; golden cases stay opt-in.
6. Full verify; then the series are deleted with the maintainer's confirmation.
7. EmbeddingGemma's distribution (a recipe pipeline, publication) as its own step.

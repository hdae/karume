## Context

ユーザー裁定（2026-08-04）: **本機で時間の勝ちが無くても f16 計算変種は実装して通す**。
動機はブラウザ / FP16:FP32 = 2:1 の GPU で速くなる可能性（本機 GA102 は 1:1 で ALU 利得
ゼロ — recon §1.4）。**量子化バリアント（w8 / w8a8）と同様、f16 計算も明示 opt-in を維持**
する。#28 と違い、マイクロベンチは**配線の門ではなく記録**。

## Decision

1. **feature 配線**: `AcquireGpuOptions.shaderF16?: boolean`。**`undefined` = 要求しない** —
   `gpuTiming` の三値 auto と既定の意味が違う。f16 計算は数値を変えるので、アダプタの能力で
   有効・無効が決まると「機械を替えたら黙って出力が変わる」ことになる（auto 禁止）。判定は
   純関数 `planShaderF16Feature`、有効判定は `GpuContext.shaderF16Enabled`（features から導出）。
2. **実走カナリア**: `shaderF16: true` の acquireGpu は、既知解を返す極小 f16 カーネルを
   1 dispatch 実走して突合する。**feature の列挙は「動く」の証拠にならない**
   （denoland/deno#23125 = `enable f16` シェーダが警告なく出力全 0 の open バグ）。検査は
   **実行時の値を f16 共有タイルへ通す**形が主 — 下記「知見」のコンパイラ恒等消去のため、
   定数式やレジスタ往復の検査では丸めの実在を確かめられない。
3. **変種の形**: gemm 骨格（packages/runtime/src/kernels/gemm.ts）の **f16 タイル・累積 f32**。丸め列の正本は
   `GemmCompute` の doc — ①丸めは共有タイルへ書く 1 箇所 ②拡幅はレジスタロード時 1 回
   （MAC ごとの変換禁止）③累積 f32 ④出力 f32（唯一の例外 = 融合 attention の S は f16 で
   受け渡し、**transient 半減** 1,073.7→536.9MB @1024px）。キー語彙は `:c16`（格納 `:wf16`
   と別語 — 両方同時に立つ組み合わせがある）。配線は **attention 3 カーネル + linear** のみ
   （3 カーネルは S の格納形を共有するため**同時に**切り替わる）。matmul / bmm / conv 族は
   結ばない — 実測の傾向（GEMM は f16 タイルで負ける）から優先度は低い。
4. **ノブ**: `SessionOptions.attentionCompute?: "f32" | "f16"` 新設・`linearCompute` に
   `"f16"` を追加。既定はどちらも `"f32"`（MUST — 既存 PNG sha256 門と tolerance を壊さない）。
   **w8a16（i8 重み × f16 計算）は実装しない** — ALU 1:1 の機では速度案として不成立
   （dp4a を捨てて共有バイトだけ半減）。品質フォールバック枠としての需要が出たら別 ADR。
   ADR 0025 参照節の「shader-f16 と合流」予告は**この決定で却下側に確定**。組は
   codegen（CodegenError）/ encode（ExecutionError）/ デモ CLI の 3 段で fail loudly。
5. **数値契約 = atol=0**: **f16 変種の出力 ≡ 入力を f16 に丸めた f32 変種の出力**（縮約順序・
   丸め列とも同一なのでビット単位一致）。オラクルは「ホストが丸め（`roundToF16` =
   `Math.f16round`）だけを担い、f32 の縮約は既存 f32 カーネル自身に任せる」合成 —
   CPU で f32 縮約を書き直すと WGSL の FFMA 融合・`exp` 実装のドライバ裁量ぶん割れるため。
   正本 = packages/runtime/tests/gpu_f16_compute_test.ts（実 GPU 13 形状で全ビット一致を実測・恒真化対策に
   「f32 変種と**違う**こと」も毎ケース確認）。
6. **E2E は判別帯 3 層**（packages/runtime/tests/e2e_anima_f16compute_test.ts）: 上限（実測の約 1.6 倍）+
   **下限の床**（step1 noise 1e-3 — f32 経路への沈黙フォールバックは誤差が**小さく**なる
   ので上限だけでは検出できない）+ 診断キー検査（f16 キーの dispatch 本数 = census・
   f32 キー 0 本）。tolerance は本波の素の実測から導出（既存 41 定数・スナップショット
   74 本・PNG 門とも不変）。torch 側に f16 計算の鏡像は作れない（タイル形・縮約順序が違う）
   ため、数値契約の本体は決定 5 の atol=0 が担う。

## 実測（2026-08-04・RTX 3080 Ti / Deno 2.9.4）

- **マイクロベンチ（実形状: attention B·H16/M=N=4096/D128・linear M4096/N2048/K2048 wf16・
  同一 submit 交互・6 ラウンド中央値 — 門ではなく記録・2 回実測〈実装レッグ / メイン再実行 =
  熱状態違い〉)**: attention_qk **0.91〜0.92×** / attention_stats **1.45〜1.58×** /
  attention_pv **0.97×** / linear(wf16) **0.91〜0.92×**。attention 3 段合計 0.97〜0.98×
  （行統計の勝ちが GEMM 2 本の負けをほぼ相殺）。**本機に時間の勝ちは無い** — GEMM は
  バイト半減でも遅くなる = 律速は共有帯域でなく命令発行（recon §3.2 の読みを支持。拡幅
  命令ぶんの純損）。勝つのは帯域律速のカーネルだけ（stats）。
- **1024px 同一セッション順次比較**（turbo・f16 系列・seed 42・f32 計算 → 両方 f16 の順）:
  DiT GPU **5,992 → 6,541ms/step（0.92×）**〈linear 4,382→4,875ms 73→75% / qk+pv
  1,328→1,400ms〉・denoise 65.4 → 66.2s・**全体 77.8 → 77.7s（同着 — 差はロード/VAE/熱に
  埋没）**。設計上確実な利得は S transient 半減（1,073.7 → 536.9MB）のみ。nvidia-smi 2s
  サンプリングの見かけピークは 7,875 → 5,703MiB だが、粗いサンプリングはロード時スパイクを
  取り逃がすので **VRAM の主張は S transient の設計値までに留める**。
- **E2E 判別帯の実測**（512px turbo 10 step・atol=rtol=0 の素の実測）: step1 noise
  f16 計算 4.943e-3 vs f32 計算 7.725e-5（**64 倍の判別帯** — 床 1e-3）。誤差は約 1.8 倍/step
  で単調増幅し step10 noise 1.577（|ref| 上端 4.97 と同桁 = step10 は粗い門）。
  段①（f16 計算を掛けない）は f32 計算と 4 桁一致。
- **既定経路の不変**: PNG sha256 門 2 系列とも完全一致（512/wf16 seed42 `20990ae4…`・
  1024/wi8 seed42 `ce6c950f…` — 変種追加の前後でビット同一）・WGSL スナップショット 74 本
  バイト不変・既存 tolerance 変更ゼロ。
- verify **616 passed / 0 failed / 2 ignored**（ignored = f32 系列 DiT 天井の既存 2 本）。

## 検出限界・知見（このタスクで確定）

- **レジスタ上の `f32→f16→f32` 往復は本環境のコンパイラに恒等として消される**（故障注入で
  実測: 累積への往復挿入が出力を 1 ビットも変えない）。**丸めは f16 の「格納」を経由する形
  でしか保証できない** — 本実装が共有タイルの**要素型**で丸めるのはこの性質に乗っている。
  「レジスタで丸める」設計だったら、数値が f32 と同一のまま「f16 で動いている」と誤認する
  沈黙故障になっていた。カナリアが共有タイル経由なのも同じ理由。
- 丸め位置の誤り（タイル充填で丸めない等）のうち**コンパイラに消される形**は数値に出ない —
  検出器は WGSL スナップショットのみ（#28 の「述語の誤りは数値で検出不能」と同型）。
  一方「タイルを f32 のまま残す」変異は 5 門が赤（オラクル不一致 + assertDiffers +
  スナップショット + 構造検査）— 契約時の予測「数値で検出不能」は**外れ**（良い方に）。
- `Math.f16round` とビット実装（double→f32→f16）は **f32 で表せない double で割れる**
  （二重丸め: 65519.999 は前者 65504 / 後者 Inf）。カーネルが丸めるのは常に f32 の値なので
  契約には無影響だが、オラクル実装を差し替えるときの罠として記録。
- 判別帯 E2E の床（下限）は w8a8 E2E に無い新設計 — opt-in の**失効**（f32 への沈黙
  フォールバック）は誤差を小さくする向きなので、上限だけの検定では原理的に検出できない。

## Consequences

- f16 計算変種が全環境で選択可能になった（feature + カナリアを通る環境のみ・opt-in）。
  本機での価値は **S transient 半減**のみで時間は 0.92〜0.98×。ブラウザ / FP16 2:1 GPU での
  実測は持っていない（そこで勝つ可能性が実装動機 — ユーザー裁定）。
- 帯域律速カーネルは f16 で素直に勝つ（stats 1.58×）— recon 案 γ（中間バッファの f16 化 =
  非 GEMM 系の帯域半減）が次の候補として実測の裏付きを得た。着手は別裁定。
- 既定経路は 1 バイト・1 ビットも変わっていない（スナップショット / PNG 門 / 既存 tolerance
  で三重に機械確認）。

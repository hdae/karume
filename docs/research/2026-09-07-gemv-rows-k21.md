# 2026-09-07 — 小 M の linear を GEMV 族へ（行ブロック変種 — perf-ledger K-21 / ADR 0082 追記 5）

> 時点スナップショット（2026-09-07・RTX 3080 Ti / Deno 2.9 / Linux / Vulkan）。採否の記録は
> [perf-ledger](../perf-ledger.md) K-21、設計の正本は [ADR 0082](../decisions/0082-linear-gemv-decode.md)
> 追記 5。生データと harness は `outputs/bench/karume-gemma4/2026-09-07_k21-gemv-rows/`（git 追跡外）。

## 0. 目的と結論

M（1 回の linear に入る行数 = token 数）が 2 以上になると linear は既定の GEMM 骨格（幾何 M16N16）に
落ち、gemma4 E2B の 276 本で **M に無関係な固定費 65〜67 ms** を払っていた
（[research 2026-09-07 §7.2](2026-09-07-codex-perf-review-followup.md)）。M=1 専用だった GEMV 族
（ADR 0082）を **1 スレッド = 1 列 × `rows` 行**の行ブロック変種で M ≤ 64 へ広げ、
**既定経路と u32 完全一致（出力 f32 のビット列を整数として比較）のまま** census 加重で
M=8 ×6.0・M=32 ×3.1・M=64 ×2.6 を得た（§3）。`rows` は (格納, m, n) の純関数で選ぶ（§4）。
生成テキストの量がそのままシェーダのコンパイル費になる（§6）ので、行数の天井は実行時間の最適
（512 要素/語）ではなく **256 要素/語**（i4 8 行 / i8 16 行）に置き、逆量子化を行間で共有する形で
テキストを縮めた — 初回ターンのコンパイル合計 ≈ 1.3 s → ≈ 150 ms。

## 1. 方法（スパイク — リポ非改変の raw WebGPU harness）

- 形: gemma4 E2B decode の op census（`tools/opbench census`）が数えた linear 13 形（i4 12 形 = 276 本・
  i8 の lm_head 1 本）を**本数で加重**。重み・活性・bias・scale は乱数（値は性能に効かない。
  一致検査には対称パターンを避ける意味で乱数が都合よい）。
- 変種: `cols ∈ {16, 32, 64}` × 先読み `unroll ∈ {2, 4}` × `rows ∈ {1, 2, 4, 8, 16, 32}` × 生成形
  （行ごとに M=1 と同じ字面 / 逆量子化を `let` に巻き上げ / 行ループを WGSL の `for` に畳む /
  先読みをレジスタ回転で行う）× M ∈ {1, 2, 4, 8, 16, 32}（後段で 33 / 48 / 64）。基準 = リポの
  `linearWgsl`（幾何 M16N16）を同じバッファで走らせた値。
- 計測: 1 pass = 同じ dispatch 8 本（重みは 16 本まで複製した別領域を回して L2 の温まりを避ける）・
  pass 境界の timestamp-query で ns / dispatch・reps 5 の中央値。**同じ submit に基準と全変種を同居**させ、
  rep ごとに順序を回転。submit 先頭に ≥ 8〜30 ms のスピンアップ pass を置く（置かないと GPU が
  アイドル 210 MHz から立ち上がる途中で最初の pass が 2〜15 倍遅く出る — sweep2 で観測。§7）。
- 一致検査: 全 (変種, M, 形) で行ブロック出力と GEMM 出力を全要素 u32 比較。
- コンパイル: `createShaderModule` + `getCompilationInfo`（naga の解析・検証）と
  `createComputePipeline`（ドライバ）を分けて初回の所要を採る（§6）。

## 2. 一致（ビット同一の実測命題）

**掃引 3 / 4 / 6 / 7 / 8 の全 (変種, M, 形) 6422 組が u32 完全一致・不一致 0。** 行ブロック変種は
1 出力要素あたりの縮約順（語昇順 × 成分昇順 × バイト昇順 × 下位→上位 nibble）と積の対応
（x の要素 × その要素の逆量子化値 `f32(q) * scale`）を M=1 変種と同一に保つ。逆量子化した f32 を
`let` に置いて行間で共有する形（採用 — §6）も、行ごとに乗算を書き直す形も、行ループを `for` に
畳む形も、先読みをレジスタ回転にした形も、全て一致した — 変わるのは担当割りと共通部分式の
置き方だけで、丸め点は動かない。

## 4. 機序と選択規則（`linearGemvRowsForShape`）

表 B の並びは 2 つの力で説明がつく:

1. **並列度**: スレッド数 = 出力列 n × y タイル数 `ceil(m / rows)`。これが **≈16K を下回る間は**、
   行を 1 スレッドに畳む（`rows` を増やす）より y タイルを増やして並列度を買う方が速い。
   タイル間の重みの読み直しは同じ dispatch 内で L2 が吸う（n=256 の形は M=32 でも `rows = 1`）。
2. **転送量**: 16K を超えた先は重みの読み直しが効き、`rows` を増やす方が速い（lm_head の n=262,144
   は `rows = M`）。ただし 1 スレッドが語 1 本あたりに抱える要素数 `rows × 刻み` には天井があり、
   実行時間では 512（i4 16 行 / i8 32 行 — その上は行ごとの x の quad 読みとアキュムレータの
   レジスタ圧で遅い。i4 の r32 は r16 の 1.5〜2 倍遅い）、**コンパイル費では 256**（§6）。

規則 = 「m 以下の最大 2 冪（天井 256 / 刻み の内側）から始め、`n · ceil(m / rows) ≥ 16384` に届くまで
半分にする（届かなければ 1）」。目標 16384 と天井 256 の 2 定数で表 B を再現し、`cols = 32 /
unroll = 4` は M=1 の既定のまま（c16 / c64 が勝つ形は小さな n の数 % だけ）。候補にした
「M だけの表（≤4→r1 / ≤16→r2 / ≤64→r4）」は i8 で oracle の 2〜3 倍、i4 の M=32 で +15% 遅い。
目標 16384 は参照 device（RTX 3080 Ti・80 SM）の飽和点で、可搬な最適値ではない
（[limitations](../limitations.md)）。

## 7. 計測の落とし穴（記録）

- **クロックの立ち上がり**: アイドルの GPU（210 MHz）に短い submit を投げると、最初の pass が
  2〜15 倍遅く出る（同じ submit の後ろの pass ほど速い）。基準を先頭に置いた素朴な掃引は基準を
  不利に見せる。対策 = submit 先頭のスピンアップ pass + rep ごとの順序回転。研究 2026-08-30 §7.3 の
  「1 dispatch ずつフェンスして測ると床に埋もれる」と並ぶ、カーネル単体 A/B の 2 つ目の罠。
- 掃引ごとの絶対値の差（§3）。同じ submit 内の倍率だけを採否に使う。
- コンパイル時間の単発計測は前後の非同期処理に引きずられて 2 倍程度ぶれる（表は代表値）。

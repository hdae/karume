## §0 要約

- gemma4 decode の lm_head（`model.lm_head.weight` i8 [262,144 × 1,536]・出力チャネルごと scale・M=1）を GEMM
  骨格（`linear:v2:f32:reg16x16r1x4w4v4:wi8`）から GEMV 族（`linear_gemv:v1:f32:c32u4:wi8`）へ移した。
- 単体（`opbench single`・heater 込み・min）: **5.317 → 1.056 ms/node（×5.03）**。kill 線 ×1.3 を超えて採用。
- 実走 ABBA（同一セッション・A B B A）: decode GPU **22.83 / 21.84 → 17.48 / 17.02 ms/token（−21〜−24%）**、
  lm_head キー 5.31〜5.51 → 1.10 ms、壁（prefill + 29 token）**3,513 / 3,606 → 3,401 / 3,432 ms（−3.2〜−4.8%）**。
- 数値契約は既定経路とビット同一（u32 完全一致門 6 形 + gemma4 golden 厳密一致 3 ケース × 16 step）。

## §1 実装（ADR 0082 の族に格納の軸を足す）

- 1 語 `vec4<u32>` が運ぶ要素数 = i4 32 / i8 16（`linearGemvUnit(storage)` — 門とカーネルが同じ導出点を読む）。
- i8 の復元は既定経路の `dequant4`（`vec4<f32>(unpack4xI8(w)) * scale`）と同じ字面
  `f32(q) * wscale_v` の要素ごと乗算で、scale は出力チャネルごと 1 本を縮約の外で 1 度だけ束ねる
  （`weightScaleWgsl("i8", "col")` — gemm.ts と同じ生成部品）。積和 `acc = acc + x * (f32(q) * wscale_v)`・
  k 昇順の逐次（語昇順 × 成分 x→w × レーン x→w）・bias は最後に 1 度。
- 門（recipe-builder `#buildLinear`）: `m === 1 && i8 && f32 && v4 && k % 16 === 0`。i8 は group を持たない
  ので group 条件は無い。`n % 4 != 0` と `k % 16 != 0` は既定経路のまま（実測の範囲に留める — ADR 0082 決定 4）。
- 変種の既定は i4 と同じ c32 u4。i4 の生成 WGSL はバイト不変（スナップショット緑）。decode の GEMV dispatch
  は 276 → 277 本（`e2e_gemma4_greedy_test.ts` の期待値を更新）。

## §2 単体（`opbench single --op linear`・gemma4 decode census・13 形）

| 形（lm_head）           | before（GEMM 骨格） | after（GEMV c32u4） |    比 |
| ----------------------- | ------------------: | ------------------: | ----: |
| n 262,144 × k 1,536・i8 |            5.317 ms |        **1.056 ms** | ×5.03 |

i4 12 形の加重は 9.21 → 8.93 ms（同じコード・ノイズ帯）。帯域で見ると 384 MiB ÷ 1.056 ms = **381 GB/s**
（理論 912 の 42%・i4 GEMV の 12 形と同じ「n/32 workgroup × k 逐次」の構造で、k=1,536 は短い側）。

変種の掃引（`defaultLinearGemvVariant` を一時的に書き換えて同じ行を採取・既定は最良点）:

| 変種  |   ms/node | 変種   | ms/node |
| ----- | --------: | ------ | ------: |
| c32u4 | **1.056** | c32u8  |   1.295 |
| c32u2 |     1.535 | c64u4  |   1.904 |
| c64u8 |     1.849 | c128u4 |   2.631 |
|       |           | c256u4 |   2.613 |

cols を増やすほど遅い（n = 262,144 では c32 で 8,192 workgroup が立ち、それ以上まとめる利得が無い）。
先読み 4 語が最良で、2 でも 8 でも落ちる。

## §3 実走 ABBA（gemma4 chat 1 ターン・A = `4e42e7e` の worktree・B = `5ddd186`）

| 量                                  |          A（前） |              B（後） |
| ----------------------------------- | ---------------: | -------------------: |
| decode GPU / token（15 run 平均）   | 22.83 / 21.84 ms | **17.48 / 17.02 ms** |
| うち lm_head（`wi8` キー）          |   5.51 / 5.31 ms |       1.10 / 1.10 ms |
| decode dispatch / token             |            1,373 |                1,373 |
| prefill の lm_head（M=1 の最終行）  |   4.83 / 4.92 ms |       0.98 / 1.19 ms |
| 壁（prefill + 29 token・load 除く） | 3,513 / 3,606 ms | **3,401 / 3,432 ms** |

壁の差 −110〜−170 ms は 29 token × ≈5 ms と整合する（decode の壁 ≈32.5 ms/token → ≈27 ms/token）。
B の 2 本目は prefill が 522.8 ms（1 本目 361.9）と外れており、全 GPU 778 ms はその影響（decode 側は 17.02
で安定）。

## §4 残り（decode GPU ≈17 ms/token の内訳・2 本目の B run）

linear_gemv i4 276 本 ≈9.7 ms（57%）/ lm_head 1.1 ms（6%）/ attention_state_* ≈2.4 ms / rms_norm ≈1.5 ms /
要素ごと ≈1.4 ms / strided ≈0.9 ms。次の候補は i4 GEMV の down-proj（k=12,288・157 µs/dispatch・加重の 35%）と
①QK（K-14）— どちらも「k 方向が 1 スレッド逐次」の構造で、縮約順を変えずに割る手は無い（ADR 0082 決定 5 の
split-K は不採用）ため、opt-in 席（`stateAttentionReduce: "parallel"` と同型）の設計になる。

## §5 未検証

> 7.1.10）/ Mesa ANV 25.0.7 / Deno 2.9.6。GPU は空き（busy 1%）の状態で測った。時刻は UTC。

# B570 の Deno の総確保の天井と申告予算（ADR 0118 検収 段 0）

## 1. 目的

ADR [0118](../decisions/0118-wan21-video-generation.md) の検収 段 0。Deno の GPU バッファの総確保は、ドライバが
`VK_EXT_memory_budget` で申告する予算（heapBudget）の 97% で頭打ちになる（limitations「Deno では GPUBuffer の
総確保がドライバ申告予算の 97% で頭打ちになる」節）。B570 ではこの申告予算が未測だった。ADR の「所要とメモリの
見積り」節は、RTX 3080 Ti の前例（申告予算が総量の 61%）を当てると 97% の線は約 5.9 GiB で、DiT 段の約 5.7 GiB は
境界に来ると見ていた。ここではその線を実測し、DiT 段・VAE 段の見積りと並べる。

## 2. 測り方

- 道具: `tools/diag/hold-vram.ts <MiB>`。256 MiB の STORAGE バッファを順に `createBuffer` し（最後の 1 本は端数）、
  1 本ごとに out-of-memory の errorScope を見る。全部通れば `<MiB>MiB を N 本の GPUBuffer で保持中。` を出して
  保持し続ける。途中で落ちれば `<確保済み>MiB まで確保して力尽きた: not enough memory left` で終了する。submit は
  出さないので、99% の線（device lost）は踏まない。
- コマンド: `timeout 40s deno run -A tools/diag/hold-vram.ts <MiB>`。timeout は保持を解放するためだけに使う。
- 判定の基準: 「保持中」の行が出てから timeout（終了コード 124）で止まった試行を**通過**とする。「力尽きた」の
  行で終了コード 1 になった試行を**失敗**とする。どちらの文言も出ない試行は無かった。
- 天井の詰め方: 通過した最大の総量と、失敗した最小の総量で挟む。失敗した試行はどれも 9,472 MiB まで確保した後の
  最後の 1 本で落ちたので、最後の 1 本の大きさ（128 / 160 / 192 / 256 MiB）を変えて挟みを詰めた。
- 回数: 独立に 3 系列（系列の間に 40〜50 秒空けた）。各試行の間は 5 秒以上空けた。各系列の前に
  `outputs/diag/gpu-busy.zsh 5` で busy 1% を、`ps -eo args | grep -c '[h]old-vram'` で 0 を確かめた。
- 申告予算の直接読み: runtime には予算の値を読む口が無い（`packages/runtime/src/gpu/headroom.ts` の
  `fitsHeadroom` は「入るか / 入らないか」の試し確保だけで、空き容量を値として出すことは ADR 0070 決定 5 が
  禁じている）。代わりに `vulkaninfo` の `VkPhysicalDeviceMemoryProperties` で heap 0 の size / budget を読んだ。
  さらに、別プロセスで hold-vram に 8,192 MiB / 9,472 MiB を保持させた状態で `vulkaninfo` を読み、他プロセスの
  使用量で予算がどう動くかを見た。

## 4. ADR 0118 の見積りとの比較

天井は保守側の 9,600 MiB（9.38 GiB）で比べる。見積りは全て ADR の「所要とメモリの見積り」節の推測値。

| 段                                | 見積り                 | 天井との差（余裕）    | 判定     |
| --------------------------------- | ---------------------- | --------------------- | -------- |
| DiT 段（33 フレーム）             | 約 5.7 GiB = 5,837 MiB | 3,763 MiB（3.67 GiB） | 入る     |
| VAE 段（33 フレーム・タイル 32）  | 約 2.0 GiB = 2,048 MiB | 7,552 MiB（7.38 GiB） | 入る     |
| DiT 段 + VAE 段が同時に居る（33） | 約 7.7 GiB = 7,885 MiB | 1,715 MiB（1.67 GiB） | 入る     |
| DiT 段（81 フレーム）             | 約 7.6 GiB = 7,782 MiB | 1,818 MiB（1.78 GiB） | 入る     |
| DiT 段（81）+ VAE 段が同時に居る  | 約 9.6 GiB = 9,830 MiB | −230 MiB              | 入らない |

- 事実: B570 の天井は 9,600〜9,631 MiB で、ADR が前例から置いた「約 5.9 GiB」より 3.5 GiB 高い。3 系列で揺れは
  無かった。
- 推測: 見積りが当たっていれば、33 フレームは DiT 段・VAE 段とも、両方が同時に居ても入る。段 3 の前に手を
  決める必要は無い。
- 推測: 81 フレームは DiT 段単独なら余裕 1.8 GiB で入るが、DiT 段の確保を持ったまま VAE 段へ進むと天井を
  230 MiB 越える。段 6 の「DiT → VAE の切り替えで足りなければ解放待ちを入れる」がそのまま要る形になる
  （81 フレームの VAE 段も 2.0 GiB と置いた — ADR の 2.0 GiB は 33 フレームの値）。

## 5. 所見

- 事実: B570（Mesa ANV）の申告予算は RTX 3080 Ti（NVIDIA）のように総量の 6 割で止まらない。空きの時に
  vulkaninfo が読む budget は総量の 89.8% だが、これは使用量 0 のプロセスから見た値で、天井の基準ではない。
- 推測（3-3 と Mesa の式から）: Mesa の budget は「自プロセスの使用量 + 空き × 0.9」で、自分が確保するほど
  空きは減るが自分の使用量が足される。だから天井は「空きの時の budget × 0.97」（8,859 MiB）では決まらない。
  9,472 MiB を確保した時点の Deno 自身の budget は 9,472 + 431 = 9,903 MiB と読め、97% の線は 9,606 MiB になる。
  これは 3-1 の挟み（9,600 は通過・9,632 は失敗）と合う。
- 事実: 他プロセスの VRAM の使用量は budget を直接減らす（8,192 MiB を別プロセスが持つと、vulkaninfo の
  budget は 9,133 → 1,583 MiB）。この開発機の GPU は学習と共有しているので、学習が VRAM を持っている間は
  天井がその分下がる。今回の値は GPU が空いている時の値。
- 事実: hold-vram のプロセスは、確保したバッファより 197 MiB 多く空きを減らす（8,192 / 9,472 の両方で同じ）。
  中身は未特定（推測: Deno / wgpu の device・コンテキスト側の確保）。
- 推測: 99% の線（device lost）は submit / poll で判定される。同じ式に当てると、自分の使用量が 9.6 GiB の時に
  空きが約 108 MiB を切ると踏む。hold-vram は submit を出さないので、この線は今回測っていない。実際の
  パイプラインは `writeBuffer` の staging も VRAM の heap 0 に置く（ReBAR）ので、段 3 / 5 / 6 のピークは天井から
  数百 MiB 手前で見るのが安全。
- 測れなかった点: runtime から申告予算の値を直接読む口は無い（vulkaninfo で代替した）。99% の線・Chrome
  （Dawn）の天井・学習と共有している時の天井は測っていない。

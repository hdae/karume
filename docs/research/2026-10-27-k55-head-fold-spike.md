# K-55: folding the GQA query heads of one kv plane in the states-form decode attention

Question: does one workgroup handling the F query heads that share a kv plane (reading each K / V element once for
all F heads) speed up the decode kernels ①′ QK, ③′ PV and the sliding fused stats + PV, while staying
bit-identical to the current kernels? Answer: yes for the full-layer ①′ QK; on the PV side the gain is the
unrolled KV loop, not the fold.

## 3. Bit identity

### 3.1 The contract the variants keep

Per output element the variants keep the current expression and order. QK: lane `l` sums `acc + (q·scale)·kd`
with `kd = k·scale` for `d = l, l + 16, …` ascending, then the stride 8 → 4 → 2 → 1 tree. PV: lane `l` sums
`acc + (exp(s − amax)·inv)·v` for `cl = l, l + 16, …` ascending, then the same tree. The fused statistics keep the
256 flat lanes, the `nan_max` loop, the 128 → 1 trees, the `maximum != neg_inf` guards and `1/Σ`. Only the mapping
changes: how many chains a thread runs (F heads; a batch of columns), where partial sums live, which thread writes
(lane f writes head f) and the workgroup shape. The write predicates are the current ones. The kv plane of a
folded group is that of its first head `z = workgroup_id.z · F` (`z / kv_repeat`, the product's shared head → kv plane
fragment), with F | r.

The identity rests on the backend compiling the same expression the same way (for example contracting `acc + a·b`
into an FMA in both kernels). It was observed on this driver for every variant; WGSL does not guarantee it, so the
product carries a word-for-word GPU gate to run on each backend (§6).

### 3.2 Spike (`spike/bitcheck.ts`, `spike/fault.ts`)

Each case runs the current kernel and every variant on the same device buffers; output buffers are pre-filled with
a NaN sentinel, so words a kernel must not write are compared too; all words are compared as u32. PV and fused
kernels are checked on S from the current ①′ + ② and on a synthetic S (−inf outside the predicate, an all-−inf
valid row, leftovers of `1e30` beyond live, NaN and +inf in single rows). Cases: E2B / E4B × full / sliding ×
P ∈ {1, 15, 16, 17, 511, 512, 513, 1024, 4000, 16000} × six (M, Q, rows_block, row_offset) row shapes × finite /
non-finite inputs.

Result: **440 cases, 72,232 comparisons, 0 mismatching words, 0 device errors.** Order-only mutants of the same
kernels do mismatch (P = 4000, M = 1):

| Mutant | full (E2B) | sliding (E2B) |
| --- | --- | --- |
| QK F8: `(q·s)·(k·s)` → `q·(s·(k·s))` on head 3 | 2,854 of 32,048 words | 342 of 4,096 |
| QK F4: tree of head 0 → sequential sum of the 16 lanes | 5,472 of 32,048 | 694 of 4,096 |
| PV F8: head 5 `(exp·inv)·v` → `exp·(inv·v)` | 381 of 4,096 | 182 of 2,048 |
| fused F2: head 1 exp-sum tree → sequential sum | — | 1,024 of 2,048 |

### 3.3 Independent check (`check/bitcheck2.ts`, `check/probe.ts`, `check/retime.mjs`)

Inputs the spike did not use: another generator and seeds, subnormals, signed zeros, magnitudes whose sum overflows
or cancels depending on the order, many distinct NaN payloads, ±inf pairs, the MiniCPM5 shape (r = 8 with two kv
planes), sliding row blocks with `row_offset > 0`, and a row block with no valid row. **350 cases, 104,552
comparisons, 1,926,431,872 words, 0 mismatching, 0 device errors.** The sensitivity probe ran order-only mutants
(a reassociated QK product, two PV terms swapped) on the same inputs. They mismatch in every input mode except two:
the NaN-payload mode, where the affected outputs are NaN and NaN words are canonical, and the PV kernels on the
chained S of the "huge" mode (speculation: S so large that the probabilities are one-hot, so the order cannot
round). In those two modes the gate checks the classes of the words, not their rounding.

The re-timing (`check/retime.txt`) recomputed every pooled median and ratio from the raw samples of the two final
runs: all 30,800 samples on the 1,024 ns grid, the per-run ratios agree, and the ratios above are reproduced.

### 3.4 Caveats

- NaN payloads cannot be told apart on this driver: every NaN in the probe's outputs came out as `0x7fffffff` (one
  distinct word per output), so "the same NaN" means the same NaN class, not the same payload.
- Subnormals cannot be told apart either: no output word was subnormal in the subnormal mode, consistent with
  flush-to-zero on this driver (observed by the independent check; not isolated), so orderings that differ only in
  the subnormal range are not distinguished.
- L2 is cold in the timing (the 32 MiB flush before every pass). In the product the KV of a layer is next read one
  token later, so it is cold as well, but S and q are warm there; the product also runs these dispatches inside 7
  passes per token rather than one pass each (speculation: small differences only).
- B > 1 and r = 1 were not compared in the spike. The product gate (§6) runs B = 2 for every shape and r = 1 shapes
  for ③′ and the fused kernel; the fold itself is selected only on the measured classes (§4.3), all GQA.
- One backend only (Dawn / Vulkan / NVIDIA) for §3.2–§6. The identity was checked afterwards on D3D12 in Chrome on
  the RTX 5070 Ti (§6.1: the E4B fold differs there); not on D3D12 under Node + Dawn, nor on Metal.
  `gpu_state_attention_fold_test.ts` (§6), or the browser runbook in a browser, must pass on each of them before a
  release relies on the identity there.
- E4B at P = 8,192: run 1 sat in the slow mode of this machine for that case (current 324.6 vs 256.0 µs in run 2,
  every configuration raised alike); the pooled median lies between the two.

### 4.2 Full-layer ③′ PV and the sliding kernels

E2B ③′ PV: current 31.7 / 56.3 / 103.4 / 201.7 / 370.2 µs at P = 1K / 2K / 4K / 8K / 16K; the unrolled one-head
kernel with 8 depth values per workgroup (`F1 x8 u8`) ×1.94 / ×2.20 / ×2.46 / ×2.63 / ×2.74; with the current
16 × 16 workgroup and 4 columns per batch (`F1 x16 u4`) ×1.82 / ×2.12 / ×2.35 / ×2.49 / ×2.67; the fold with F = 2,
4 depth values per workgroup and 8 per batch ×1.82 / ×2.12 / ×2.40 / ×2.66 / ×2.88. Against the unrolled one-head
kernel the folds add at most ×1.05 (E2B) / ×1.07 (E4B) at 16K and ×0.96–1.03 at P ≤ 8K (spike RESULTS §8).

Sliding layers (constant in P): fused stats + PV current 22.5 µs, `F1 x16 u8` 13.3 (×1.69), F2 ×1.57, F4 ×1.38,
F8 ×1.05–1.10; ①′ QK folds ×0.89–1.07. The null pass (fixed cost of one timed pass) is 4.1–5.1 µs, so the sliding
kernels are 10–18 µs of work.

Why the PV fold does not pay (speculation consistent with the numbers): the head workgroups of a depth slice run at
the same time and read the same V rows, so most re-reads already hit L2; the PV chains are long (`live / 16`
dependent adds per lane and head) and fixed in number, so F heads per thread divide the thread count by F and leave
the GPU latency-bound. The loop as written also issued one V load per dependent step, which the unroll fixes. The QK
chains are short (D / 16 = 32 steps) and there are `⌈live / 8⌉ × H / F` workgroups, so the fold keeps enough
parallelism and removes 7/8 of the K traffic (for E2B 8 × 32.8 MB (P = 16,000) per layer, which does not fit the 6 MB
L2).

above 16,000 was not timed.

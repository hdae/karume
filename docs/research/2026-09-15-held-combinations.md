# Gemma E2Bの保留候補を組み合わせた再検証

利用者の依頼に従い、[attention融合](2026-09-15-attention-fusion.md)の後、過去に保留・不採用となった候補を現行実装へ載せ直して比較した。
数値の正本は[結果JSON](2026-09-15-held-combinations-results.json)。生データ・候補コード・準備スクリプトは各専用ディレクトリへ保存し、旧実験を上書きしていない。
attentionを追加したコードの基準は`b9d41ef`。以下の候補を製品コードへまとめて入れたわけではない。

## 比較の条件と限界

通常Gemma 4 E2Bと固定mobile QAT E2B、同じ変換資産・英語/日本語の2入力、64トークン、温度0。
f32計算、並列GEMV（行列・ベクトル積）、dense chunk64、capacity128、RMS→add融合、attentionの`parallel-fused`を基準にした。
投入上限は基準768。変更する候補だけ2048とした。初回応答までの時間（TTFT）はdecodeのtok/sに含めない。
各ロード・入力につき初回と追加暖機を除き、本計測3回の中央値を取る。表はさらに全ロード・入力の中央値。

最初の3走行は探索用。候補順を反転した各2ロードで比較した。
初回走行の終盤には短いCPU静的集計が重なり、探索中の連続走行ではGPUの温度制限によるクロック低下を観測した（600標本中102件でsoftware thermal slowdownが有効）。
数％の差をそのまま採用根拠とせず、後段の比較では各ロード前に75℃以下かつsoftware thermal slowdownが無効となるまで待った。
基準・候補を各4ロードし、順序を反転、500ms間隔で温度・クロック・制限理由を記録した。
ファン・クロック・電力設定は変更していない。外れた試料も生データに残し、都合のよい試料だけを選び直していない。

通常のpermute別名化と現在の並列GEMVを維持し、古いrecipe全体を戻して比較していない。
RMSのworkgroup融合とsubgroup融合、境界探索の方式など、同じ演算に対する排他的方式は別構成にした。
「最大併用」はここで列挙した互いに併用できる候補の集合であり、全ての幾何・探索方法の直積を網羅したという意味ではない。
別モデル向けのDiT/drafter候補や、今回既に単独比較したattention共有配列は最大併用へ含めていない。

重み転置の実験用の試作は、通常版277コピー・1,341,063,168 B（1,278.94 MiB）、QAT215コピー・379,060,224 B（361.5 MiB）を追加する。
元の重みはprefill/embedding用に保持する。GPU処理をrecipe導出中に行う実験用の実装なので、速度が良くてもそのまま製品へ移植する設計ではない。

norm/rmsSrqはさらにRMS→SRQ、linearはnormへlinear→SRQを追加する。
stack2048は投入上限、stackL8はさらにI4配分、allLayout/allBoth/allはさらに重み転置を含む。

## 温度を管理した再測定と採否

通常版は基準/legacyをABBA+BAAB、QATは基準/norm/linear/linearOnly/linearFastを往復2巡し、各構成4ロード。
計280生成。ロード前は全て75℃以下、計測中の採取点は63〜85℃で、software/hardware thermal slowdownの表示はともに0件だった
（全1,047標本、うち本計測の生成時間内220標本）。500ms未満の状態やGPU内部の全ての制限要因を否定するものではない。

| モデル | 構成       |   tok/s | 基準との差 |
| ------ | ---------- | ------: | ---------: |
| 通常   | base       | 114.650 |     +0.00% |
| 通常   | legacy     | 115.713 |     +0.93% |
| QAT    | base       |  94.623 |     +0.00% |
| QAT    | norm       |  97.065 |     +2.58% |
| QAT    | linearFast |  99.810 |     +5.48% |
| QAT    | linearOnly |  99.174 |     +4.81% |
| QAT    | linear     | 102.958 |     +8.81% |

全280生成が同じモデル・入力の基準とtoken/stop/text一致。
QATの入力・ロード別中央値の範囲は、基準94.199〜95.368、linearFast99.057〜100.143、linear102.190〜103.618 tok/sだった。
通常版の基準113.167〜116.215とlegacy114.545〜117.297は範囲が重なる。
通常版の約0.9%では複数の専用融合を追加する根拠として弱く、legacyの製品化は保留。
QATはlinear→SRQ単独でも約4.8%、融合内の探索展開を含め約5.5%、軽い融合の併用では約8.8%改善した。
過去の逐次GEMVでの見送りを現在の並列GEMVへそのまま適用せず、linear→SRQを次の製品化候補へ戻す。
併用全体と単独との差を全て「相互作用による増幅」とは呼ばない。独立した小改善の和も含み、全要因の直交実験ではない。

大きな最大併用は、最後にlinear→SRQも加えるとQATのsubgroup側で約4.9%改善したが、軽いworkgroup併用の方が速かった。
通常版では最大併用が約15〜16%遅く、QATもlinear→SRQを入れる前は約7〜9%遅い。
起動回数を減らすことと、投入の遅延・各カーネルの負荷・重みの読み方を同時に変えることを区別する。
重み転置・大きいI4のL8・投入2048を一括採用しない。

4走行の計920生成は同じ構成内で出力が安定。
うちsubgroupを含むQATの80生成は基準と異なるが、今回の英語/日本語の短文に明らかな崩れは見られなかった。
残る840生成はモデル・入力ごとに基準と一致。これは広い品質評価の代用ではなく、出力差だけを不採用理由にもしていない。

## GPU時間の帰属

通常のバッチ境界を保ったnative pass timestamp。各生成の最後の63 decodeについて、
1トークン3 passの和の中央値を取った。queryのresolve/mapは生成計時後。
各構成1回のprofileなので、繰返しの速度評価は前節を正本にする。

| QAT構成    | 起動回数/token | GPU ms/token |
| ---------- | -------------: | -----------: |
| base       |           1376 |     7.327744 |
| norm       |           1221 |     7.254016 |
| linear     |            946 |     6.747136 |
| linearOnly |           1101 |     6.909952 |
| linearFast |           1101 |     6.829056 |

linear→SRQは275起動/token、RMS→RoPEは50、GELU→mulは35、RMS→SRQは70を削減した。
元の3 pass/tokenは全構成で維持。GPU時間の短縮は壁時計の改善を裏付けるが、その差をCPU単独の費用と見なさない。
dispatchごとにpassを分けた別profileは演算の調査用で、その合計を通常生成のGPU時間へ使わない。
この診断の35生成も全て基準とtoken/stop/text一致した。

## 数値検査とattentionの追加掃引

- RMS→SRQはD1536/2560、M1/4/17、広い・小さい値・非有限、強制grid-strideを含む48条件で融合前と一致した。
  比較相手のSRQも探索展開版。有限はu32、非有限はNaN分類で検査した。
- linear→SRQの初回270条件も、探索展開版SRQとのu32比較。
  JSのscaleリテラルが厳密なf32ではなく事前検査で拒否された初回実行は不合格として保存し、
  新規ディレクトリでMath.froundした入力へ直した。製品のscale検査を緩めていない。
- 追加360条件では、融合内だけ探索を展開した候補を**元の非融合linear＋元の二分探索SRQ**と比較。
  INT2/4/8、Kの短い形/1536、L2/4/8/16/32、M1/4/8、
  全128閾値の前/一致/後×正負、広い値・NaN/Infを含む。有限u32・NaN分類が全条件で一致した。
  最初の比較用import mapがSRQも置換する点と区別し、この最後の比較は独立SRQを置換していない。
- attentionの幅16/32/128を、D256/512、過去長31/95/511/1023、full/slidingの16形状で追加掃引した。
  独立f64参照との最大絶対差は幅32で2.384185791015625e-7、幅128で5.960464477539062e-7（許容5e-6）。
  元の幅16融合に対する時間比の中央値は1.0813 / 2.0607。幅32は16形状中5形状で速く、幅128は0形状。
  幅32/128は加算順も変わる。全体で追加する根拠がなく、製品は幅16を維持する。

準備時の型・private helper・fusion counter不足はGPU実行前に失敗し、新しい専用ディレクトリで修正した。
数値検査の失敗を成功に数えたり、準備失敗後に旧候補を走らせたりしていない。
温度集計の初版は集計JSONのgenerations件数を生成配列と誤認して失敗した。生データは変更せず、配列を持つ走行JSONだけを読む集計へ修正した。

## 次の実装単位

今回製品へ追加済みなのは別コミットのattention融合だけ。ここで試した組合せは実験用の試作のままで、既定・quant・公開APIは変更していない。
次はlinear→SRQを独立した任意指定として整理する。順序は次の通り。

1. 現在の並列GEMVと同じ縮約を使い、最後の出力処理だけ固定SRQへつなぐ。
   実験用のWGSL文字列置換を製品化せず、キー・uniform・丸め障壁・境界探索を型のある共通生成へ整理する。
2. 融合の計画には常駐重みの格納情報だけを渡す。scaleは既存バッファを借り、GPU転置や新しい重みコピーを作らない。
   private/隣接/同形状、検収済みparallel形状・M≤8・f32計算に絞り、参照経路と不正設定の拒否を維持する。
3. 適用/非適用、重みscaleの借用寿命、元のSRQ oracle、MTPのverify行0/decode一致、
   製品経路の生成比較を行い、ADRと明示フラグを追加する。広い併用の既定化は一緒にしない。
4. M2はまず現在の比較画面のattention80生成で検収する。
   linear→SRQの製品実装後に必要な比較だけを画面初期選択へ反映する。今回の最大併用を全パターンで利用者へ再依頼しない。

M2・長文・E4B・他LLMでの速度や品質は今回の実測から結論しない。
gate/up入力共有などの新候補は、この独立融合の検収後に費用を測る。
再開時は本節とbacklogを読む。実験のGPUジョブは全て終了済み。実験のprepare/run/source/log/raw hashは結果JSONの各ディレクトリを辿る。

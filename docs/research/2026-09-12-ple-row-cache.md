# Gemma の PLE 行キャッシュと初回応答の改善

## M2 の利用者実測

[保存した集計と生成列](2026-09-12-m2-browser-speed-results.json)に、通常E2Bのみの初回提出と、通常/QATを含む再提出を保存した。
元JSONは `outputs/bench/karume/2026-09-12_m2-prefill-attribution-jz9xnvbz/m2-{normal|normal-qat}.json`。
集計に元ファイルのSHA256、全反復の計測値・生成列hash、最初の生成列を持つ。
実行コードは両提出とも `0adfa5a` の同じbrowser bundleで、改善前の実測である。
JSONが公開するGPU情報は `apple / metal-3`。M2という機種名は利用者の申告による。

再提出の値は暖機後3回の中央値。生成速度は最初のtokenを除いたdecode、TTFTは最初の非停止tokenまで。

| モデル   | engine          | 英語 tok/s | 日本語 tok/s | 英語 TTFT ms | 日本語 TTFT ms |
| -------- | --------------- | ---------: | -----------: | -----------: | -------------: |
| 通常 E2B | karume          |      20.02 |        19.08 |        451.9 |          734.1 |
| 通常 E2B | Transformers.js |       8.92 |         8.87 |        275.1 |          383.7 |
| QAT E2B  | karume          |      20.12 |        20.21 |        520.8 |          875.2 |
| QAT E2B  | Transformers.js |      10.08 |        10.01 |        760.9 |          906.6 |

再提出の40生成は各条件の反復間で一致し、通常版の生成列は前の提出とも両エンジンで一致した。
保存済みRTXとの照合では、通常版karumeと両ONNXの生成列は一致した。karume QATは英語23token目、
日本語36token目から異なった。これは行キャッシュ導入前の同じbundle同士の差であり、今回の変更による退行ではない。
過去にCPU/GPUの行列縮約がSRQ境界をまたぐ差は確認済みだが、このM2/RTX差の原因まで同じとは断定しない。
ただしTransformers.jsの通常版は前回約19 tok/sから約9 tok/sへ変動した。karumeも前回約21.4〜21.7から低下している。
原因はこのJSONだけでは帰属できず、今回の比率を安定した「エンジン間の2倍差」とは扱わない。
量子化・演算精度などの条件差は[ブラウザ比較の記録](2026-09-12-browser-llm-speed.md#実行条件とモデル差)のとおり残る。

## RTX / Chrome での費用の分解

専用実験 `outputs/bench/karume/2026-09-12_m2-prefill-attribution-jz9xnvbz/`。
製品を変更せず、実験内でSession.runとHTTP読取りの前後を測った。公開pipelineと同じ入力を使い、各入力の生成数は1。
5反復の最後3回の中央値。通常の壁時計計測とGPU timestamp計測は別実行である。
LinuxのChromeは前の比較と同じXvfb上のheaded実行・NVIDIA f16実験フラグ付き。M2の費用内訳ではない。

| モデル   | 入力          | TTFT ms | 入力準備 ms | HTTP読取り区間 ms | Session.run ms |
| -------- | ------------- | ------: | ----------: | ----------------: | -------------: |
| 通常 E2B | 英語31token   |   114.4 |        72.9 |              72.4 |           40.9 |
| 通常 E2B | 日本語37token |   137.0 |        74.1 |              73.4 |           62.8 |
| QAT E2B  | 英語31token   |   109.3 |        66.7 |              66.0 |           42.0 |
| QAT E2B  | 日本語37token |   142.4 |        69.3 |              68.6 |           70.8 |

HTTP読取り区間は最初の発行から最後の完了までで、入力準備に含まれる。中央値どうしを足して厳密な総和とはしない。
sequence準備は約0.4〜0.5 ms、run後の選択・配送は約0.5〜0.6 ms。
既定のPLEは小さい入力を行読みするため、暖機しても英語52 / 日本語64要求を毎回発行していた。
QATは値のbyte数が減っても同じ2区間を読む。GPUだけでなく、この往復にも固定費が残る。
GPU timestampでは行列演算が大きいが、dispatchごとにpassを分ける観測値なので壁時計と直接合算しない。

## 候補と採用する変更

候補実験は `outputs/bench/karume/2026-09-12_prefill-candidates-sp5bluff/`。
基準、細かい入力バケット、256行の試作キャッシュ、逆順の基準で、計48生成のtoken列が一致した。

- バケット候補は既存の指定口に `[8,16,24,32,40,48,56]` を渡した。日本語37tokenを64行から40行に縮めると、
  通常版の最後の反復のTTFTは130.3→109.4 ms、QATは134.0→121.1 msになった。
  既定バケットを変更したわけではない。追加の形が計画キャッシュと初回コンパイルに与える影響・M2の選択は未検収で、今回の製品変更には含めない。
- 試作キャッシュはf32行を256行保持し、同じ入力の最後の反復で通常版のTTFTが106.5→36.7 / 130.3→59.5 msになった。
  これは反復のほぼ全行がhitする条件で、一般入力の期待値ではない。試作のメモリ構成は製品へそのまま採用しない。
- 製品は量子化値とscaleをそのまま保持し、全量shard常駐後の既存予算の空きだけを使う。
  最大256行、予算0で無効、全量shard優先。逆量子化は既存の2段丸めを通す。
  E2Bの最大payloadは通常2,329,600 B / QAT1,182,720 B。追加のGPU常駐や予算引数は無い。

上限の補助確認では、保存済みの入力・生成token列をCPUのPLE loaderへ再生した。GPU速度の測定ではない。
未使用6入力の行読取り数は次のとおり。256→512行では上限メモリが倍になる一方、追加で省ける読取りは少なかった。
この入力集合では256行を維持する根拠になるが、あらゆる長文に最適な上限とは主張しない。
生データは `outputs/bench/karume/2026-09-12_ple-cache-capacity-5a72_z_e/result.json`、SHAと集計は比較JSONにも保存した。

| 上限行数 | 通常 E2B | QAT E2B |
| -------: | -------: | ------: |
|        0 |      504 |     512 |
|       64 |      292 |     291 |
|      128 |      266 |     257 |
|      256 |      237 |     236 |
|      512 |      234 |     236 |

詳細な契約は[ADR 0085の追記](../decisions/0085-ple-host-gather.md)。
内部診断 `residentBytes` は行の保持分も数える。読取り方針を検証する既存テストの期待byte数だけをこの新しい勘定へ更新し、
読み回数・区間・上限・bit一致の検査は維持した。性能低下や数値差を隠す許容値変更はしていない。

## 製品候補の検収

正本は[比較JSON](2026-09-12-ple-row-cache-results.json)。通常/QAT E2BはChromeとDenoでABBA、
通常/QAT E4BはChromeで候補→基準の順に比較した。各pipelineは固定英語・日本語を各3回暖機し、
その後に未使用の英語3・日本語3プロンプトを1回ずつ生成する。最大64token、容量128、chunk64、温度0。
重み・グラフ・既定バケット・GPUカーネルは変更していない。

全20実行・240生成について、120組の基準/候補がtoken列と停止結果で一致した。配送数は55 / 60 / 64token。
同じ入力の反復とは別に、下表は未使用6入力の中央値を比較する。E2Bの「再比較」は逆順側の組で、外れ値を除外していない。

| Chrome | 通常 E2B | 再比較   |       88.4 → 63.2 |          49.74 → 54.36 |

Chromeでは未使用6入力のHTTP要求合計が通常E2Bで1,008→474、QAT E2Bで1,024→472へ減った。
同じ文章を再実行しなくても共通tokenの重みは再利用できる。Denoの位置読取りは元から小さく、全体速度はほぼ中立。
E4Bは1組なので、E2Bほど反復の確かさはない。M2・CacheStorageのBlob経路・長文・MTPの改善幅は未計測。
先頭の生成はshader/JSの暖機状況も異なり、キャッシュ変更で必ず速くなるとは主張しない。

生データの専用ディレクトリは以下。

- `outputs/bench/karume/2026-09-12_ple-row-cache-abba-pvkp9pvo/`: Chrome E2B ABBA。
  この台本のE4Bは通常版の配布先がE2Bのみだったためモデル選択段で拒否され、E4Bの計測値は作らなかった。
- `outputs/bench/karume/2026-09-12_ple-row-cache-e4b-2uouigrk/`: 正しいE4B配布先での追試。
  通常E4Bのモデル参照symlinkは、実験サーバーにその既知の参照先だけを明示して配信した。
  製品のパス越境拒否は変更していない。
- `outputs/bench/karume/2026-09-12_ple-row-cache-deno-0rjvbvyv/`: Deno E2B ABBA。
- `outputs/bench/karume/2026-09-12_ple-row-cache-product-1v6tm8g0/`: 変更前PLE、集計スクリプト、重点検証。

CPU重点検証は **34 passed（38 steps）/ 0 failed、147 ms**（`focused-v3.log`）。
256行の上限、LRU、既存予算の残り・予算0、全量予約中の並行行読み、破棄・中断・値/scaleの失敗を検査した。
I2/I4は固定CPU参照のu32列をそのまま比較し、cache hitにも同じ期待値を使った。
初回検証の失敗は、内部診断の保持byte数に行が含まれるようになった差である。新しいbyte勘定へ期待値を更新し、
既存の読取り位置・回数・数値検査は弱めていない。

全体検証はGPUベンチと全ての実験サーバーを停止してから実施し、**2,936 passed（771 steps）/ 0 failed / 5 ignored、24分53秒**で成功した。
正本は `outputs/bench/karume/2026-09-12_ple-row-cache-verify-b49feca6/verify.log`。
最終コードのbrowser bundleを再作成し、比較に使ったbundleとbyte単位で同一であることも確認した（同ディレクトリの `bundle-verification.json`）。
実測ファイル・生成列のhashと文書リンクも照合済み。改善後のM2は、サーバーを再起動して同じ `deno task bench:llm-browser` で追試できる。

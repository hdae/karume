# 大きいI4行列のレーン数変更を見送る

## 判断

通常Gemma E2BのI4 group32・N12288/K1536だけ、1出力を分担するレーン数を4から8へ増やす案を比較した。
暖機後decodeは112.090→100.056 tok/s、約10.74%遅く、ABBAの2組とも低下したため不採用とする。
製品のカーネル・API・quant・既定設定は変更しない。QATの対応行列はINT2であり、この変更の対象外。
前回の[単体配置探索](2026-09-13-gemv-subgroup.md#候補と単体検査)から残っていた、この形状の全体比較を閉じる。
同じ候補をM2へ追試依頼する段階には進めない。他の配置すべてが無効という判断ではない。

集計と各ロードの実測・入力元SHAは[保存JSON](2026-09-14-i4-lane-results.json)。

## 条件と隔離

基点は`f2e3985`。現行`loadKarume`を実験ディレクトリへ写し、絶対importにした。
候補は`linear-gemv.ts`の形状表の1項目だけをL8へ変えたコピーをimport mapで解決する。
両bundleは同じloaderを使い、実際に解決したレーン数をmetadataへ記録して4/8をassertした。
共有メモリによる既存parallelのまま、subgroup値交換は使わない。既存資産・追跡コードは上書きしていない。

通常E2B、量子化`i4-gemvpar`、f32、英語31入力token・日本語37入力token、容量128、64生成、温度0。
chunk64・dense buckets・RMS→add融合・RMS workgroup・投入上限768を固定。
ロード順はL4→L8→L8→L4を2回、各ロードで各入力2暖機＋本計測3回、計80生成。
各入力・ロードの3回中央値を取り、方式ごとに8中央値をまとめた。

| 比較                 |            L4 |            L8 |   L8/L4 |
| -------------------- | ------------: | ------------: | ------: |
| 80生成の暖機後decode | 112.090 tok/s | 100.056 tok/s | 0.89264 |
| 前半ABBA             | 112.651 tok/s | 100.056 tok/s | 0.88819 |
| 後半ABBA             | 111.603 tok/s | 100.259 tok/s | 0.89835 |

## GPU時間への帰属

別走行で英語をABBA、各ロード3暖機後に無計測→通常pass→無計測→dispatch分割→無計測を実施した。
外付け計器はtimestamp-queryを要求し、実験コピーの`gpuTimingEnabled`をfalseにして通常GPU greedy経路を維持した。
計32生成。時間の読戻しは生成の計時終了後。通常passは191本からprefill先頭2本を除いた189本を63 decodeへ集計する。

| 計器                                     |                 L4 |                 L8 |
| ---------------------------------------- | -----------------: | -----------------: |
| 通常passのGPU時間/token（2ロード中央値） |           6.499 ms |           7.128 ms |
| decodeのdispatch数/token                 |              1,024 |              1,024 |
| 対象dispatchのGPU時間（ロード別中央値）  | 26.624 / 27.648 µs | 43.008 / 43.008 µs |
| 対象dispatch数/token                     |                 40 |                 40 |
| 対象workgroups                           |                384 |                768 |

処理数は同じで、変えた行列のdispatchが遅くなり、通常passの総GPU時間も増えた。
GPU側の配置変更が遅化に寄与することは実測で裏付けられた。キャッシュ・占有率などハードウェア内部の原因は未特定。
dispatchを別passに分ける計器は生成自体を遅くするため、その総和を通常実行の内訳率として扱わない。
wall時間との差も、すべてTypeScript処理とは呼ばない。

単体も同じ合成入力でL4/L8を交互に測り直した。各timestampの直前に32dispatchの非計測passを置き、
計測passも32dispatch、4暖機後ABBA×4。24.576→42.688 µsで全体実測と同じ傾向だった。
前回の25形状探索のL4約198.6 µsは再現しなかった。以前と今回の走行は条件・時刻が違い、その差の原因を暖機不足と断定しない。
前回の絶対時間の比較だけを採用根拠にしない。

## 数値と検証範囲

Denoの実GPUでI4 g32、N36の短K/端列と実形状N12288/K1536、L4/8/16、M1/4/8を検査した。
36条件・483,444要素は既存GEMM許容帯に収まり、最大絶対誤差は約4.50e-7。
同じレーン数のM1/4/8先頭行はu32一致し、未使用行のsentinelは維持した。
実形状M1のL8はL4と12,288要素中10,351要素の下位bitが異なる。最大絶対誤差はL4約4.50e-7、L8約2.20e-7。
加算順を変えるため、L4/L8のビット一致を主張しない。

全体80生成とプロファイル32生成、計112生成はtoken列・停止token・文章が入力ごとにすべて一致。
これは広い品質評価や実モデルMTPの検収ではない。L16は数値検査のみで全体性能は測っていない。
単体速度JSONの`maxError: 0`はFP64参照を省いた旧ハーネス欄であり、誤差ゼロの意味ではない。
FP64誤差の正本は別の`numeric.checks`に保存した。

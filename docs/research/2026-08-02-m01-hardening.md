## M0.1 差分への再レビュー（3 レンズ + 敵対検証）と修正

指摘 14 件（major 2・minor 5・info 7）、major 相当 2 件を敵対検証し**いずれも holds**:

1. **失敗経路の残 pending がロック外・errorScope ゼロ本で submit される**（実 GPU 実測）—
   エンコード途中の throw で残った dispatch が arena.destroy → flush で流れ、並行 Session の
   スコープに誤帰属する。→ `SubmitScheduler.discard()` 新設（失敗した run の残骸は submit
   しない。discard-or-flush before destroy）。1a09dfd。
2. **Session.run × ロックの結線が無アンカー**（検証者が複製リポジトリでラップ素通し化 →
   全テスト緑を実証）→ faulty 側が**先に push し先に pop** する決定的構成で結線回帰を追加
   （逆順では再現しない — 検証者が初回構成を撤回して特定）。1a09dfd。

他の修正: 不変条件を「run が GPU 操作を発行するのは自分のロック区間内のみ」へ単純化
（readback / arena.destroy をロック内へ。1a09dfd）/ 未使用グラフ入力の dtype を列挙門に追加
（`RuntimeSupport.io` 軸）+ 違反列挙の宣言単位化（6ae4b80）/ withValidationScope の pop
rejection ガードと `pendingLostListeners` 診断（d33522e）。

**修正しない裁定 3 件**: ① create の popFailureScopes reject 経路（pop は device 消失後も
null resolve — m0-review の refuted 実測に基づき到達不能。投機的ハンドリングはしない）
② 契約表→RUNTIME_SUPPORT 導出テストの自己比較性（導出の脱落検出の価値は残る）
③ resolvedShape の単体テスト（module-local の 5 行に export-for-test は不釣合）。

**設計裁定**: assertRuntimeSupport と plan 層 validateGraphContracts の検査重複は許容 —
両者とも `src/ops.ts` の契約表から導出され正本は一本（container.ts の NOTE 参照）。
withScopeLock の再入検出は実装しない — 保持中フラグでは正当な待ち行列と区別できず、
async 跨ぎの実行コンテキスト追跡は ADR 0002（Web 標準のみ）下に純粋な手段が無い
（device.ts の不変条件 doc 参照）。

## 公開面の変化（M0 比）

- 同一 device 上の複数 Session の run が丸ごと直列化（[limitations.md](../limitations.md)）
- `GpuContext` は型のみ公開（構築は `acquireGpu` のみ）
- `SubmitStats` に `measuredCount` / `pendingMeasurements` / `discardedDispatches` 追加、
  `measuredMs` は直近 32 件に有界化
- dtype / attrs / 格納 / 転送の capability 違反は `createSession` が `ContainerError` で全件列挙
- `RunArena` の retain は「定義ぶんの 1 + uses」（diagnostics の peak/alloc が正確化）

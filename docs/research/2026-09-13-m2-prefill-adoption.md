## 日本語入力のTTFT

以下は並列加算を指定した結果。各設定の本計測3回の中央値を取り、範囲は往路/復路の2値を示す。
信頼区間ではない。時間短縮率は往路同士・復路同士の標準との比較である。

| モデル  | 標準A (ms)    | 少数追加B (ms) | 細分化C (ms)  | Cの時間短縮  |
| ------- | ------------- | -------------- | ------------- | ------------ |
| 通常E2B | 671.82–672.23 | 508.69–509.10  | 446.16–446.30 | 33.57–33.63% |
| QAT E2B | 804.65–805.56 | 607.46–615.27  | 524.67–532.29 | 33.85–34.87% |

日本語37 tokenの物理行数はA64/B48/C40。計算する余分な行を減らした効果はRTX・M2で同じ方向だった。
英語31 tokenは全候補32行で、並列加算の通常版ではA370.82–373.40 ms/C376.37–376.89 msと小さく悪化し、
QATではA424.17–427.31 ms/C414.01–416.96 msと小さく改善した。英語の物理形は変わらず、バケットによる高速化とは帰属しない。

## decode速度と実行順

| エンジン・設定     | 通常E2B 英語/日本語 (tok/s) | QAT E2B 英語/日本語 (tok/s) |
| ------------------ | --------------------------- | --------------------------- |
| Karume並列・標準   | 25.84–26.59 / 25.60–25.71   | 26.54–26.71 / 26.64–26.69   |
| Karume並列・細分化 | 25.14–25.53 / 25.55–25.71   | 26.67–26.88 / 26.73–26.89   |
| Transformers.js    | 9.28 / 8.94                 | 10.17 / 10.16               |

バケット細分化はdecode高速化として採用するものではない。
特に通常版の逐次加算は、標準の往路/復路で英語26.08→21.21 tok/s、同じ32行のTTFTも341.68→370.35 msへ変動した。
加算方式は逐次6設定を終えてから並列6設定を走らせるため、この全組み合わせ走行だけからGEMV並列化の厳密な倍率を求めない。
通常版の読み込みも最初の3設定で2.84–3.93秒、その後の9設定で8.60–10.15秒へ増えた（保存用JSONの`timeline`）。
以前のM2計測より並列時の絶対速度も低い。熱・電源・メモリ圧・他の処理の影響は候補だが、
JSONには温度・クロック・メモリ使用量がなく原因を確定できない。読み込み時間自体はdecode tok/sに含まれない。
Transformers.jsも後の時間帯で実行され、Karumeとは配布重み・演算精度・キャッシュ構成が異なる。上表は今回の実用構成の速度である。

## 採否と初期選択

採用するのはブラウザ比較のchunk64での細分化。標準と同じ出力を維持し、日本語TTFTに約34%の利得がある。
長いchunk・複数容量のキャッシュ不足は[RTX負荷検証](2026-09-13-prefill-buckets.md#長いchunk容量切り替え)で確認済みのため、
`GEMMA4_CHUNK_BUCKETS`、CLI、モデル・runtimeの既定、cache上限は変更しない。
URLや`runBenchmark`でバケット指定を省略した場合も従来どおり標準を使う。

利用者の依頼に従い、画面の初期選択を次のdecode最適化の基準へ合わせる。

- モデル: 両方
- 比較対象: karume
- 行列計算: 並列加算を指定
- 入力バケット: 細分化

`deno task bench:llm-browser` の後、Chromeで開いて開始するだけで2設定・20生成を実行する。
全組み合わせや参照経路は手動で選べる。次の候補を追試してもらう際には、その候補と基準の比較を初期選択へ反映する。
この運用をAGENTS.mdにも記録する。基準の保存のためだけに今回と同じ260生成を取り直す必要はない。

次は正規化周辺とRMS→SRQ融合の候補を調べる。広い入力長分布への既定採用、長い生成・品質、Chromeの起動時Instance消失は未完。

# 融合 attention op のノード内一時を見積りに数える前後の表（ADR 0124 決定 7）

> 時点スナップショット（2026-10-11）— 見積り（`estimateGraphMemory` / `PreparedModel.estimate`）に融合 attention op（states 欄なし）の
> ノード内一時を数える変更が、既存の呼び手の数字をどれだけ動かすか。GPU 不要の計算値で、実測ではない。

## 手法

- 同じ台本を 2 つのコードで回した。前 = ブランチ `wip/d6` の `fe00f66b`（予算のノブまで — 融合 attention op の一時は数えない）。
  後 = その上に ADR 0124 決定 7 の勘定を足したコード（このファイルの次のコミット）。
- device の上限は開発機（RTX 3080 Ti・Vulkan）の値を渡した: `maxStorageBufferBindingSize` 2,147,483,644 B・`maxBufferSize` 1 TiB
  （記録値 — [research 2026-10-02](2026-10-02-video-gen-recon.md) の「実測値」の行）。`maxBufferSize` はこの表の数には効かない
  （どの領域もそれを下回る）。Anima の段の見積り（`packages/models/src/anima/pipeline.ts` の `stageNeed`）が渡すのも、この 2 つの上限と束縛だけ。
- 容器: Anima は `outputs/series/anima-f16/` の `text_encoder` / `text_conditioner` / `vae_decoder`（配布形の `vae_decoder` と入力の形も
  attention の本数も同じことを確かめた）。Gemma は配布形 `models/karume-gemma4/e2b/` の `model` / `drafter`。Wan2.2 は
  `outputs/series/wan2.2-ti2v-5b-i8-dyn/transformer`。
- 「融合 attention op」は op が `attention` で states 欄が空のノード。states 形（ADR 0067）と分解 attention の行ブロック
  （ADR 0060・`bmm` の 9 ノード窓）は、変更の前から勘定に入っている。

## 既存の呼び手の前後

単位はバイト。`workspaceBytes` は中間（ノード出力とノード内一時）の領域の総和、`peakAccountedBytes` は重み + 保持集合の上限。Anima の
`stageNeed` は `peakAccountedBytes` + 最大 part の staging + 512 MiB なので、差は `peakAccountedBytes` の差と同じ。

| 呼び手                                      | 対象（束縛）                       | 融合 attention op | 前 `workspaceBytes` | 後 `workspaceBytes` | 前 → 後 `peakAccountedBytes` |
| ------------------------------------------- | ---------------------------------- | ----------------: | ------------------: | ------------------: | ---------------------------- |
| Anima `stageNeed`（text 段の前の量り）      | `text_encoder`（`T` = 24）         |                 0 |           1,698,048 |           1,698,048 | 1,462,263,812 → 同じ         |
| 同上                                        | `text_encoder`（`T` = 512）        |                 0 |          51,904,512 |          51,904,512 | 1,462,263,812 → 同じ         |
| 同上                                        | `text_conditioner`（24 / 24）      |                 0 |           1,105,920 |           1,105,920 | 538,134,532 → 同じ           |
| 同上                                        | `text_conditioner`（512 / 512）    |                 0 |          46,661,632 |          46,661,632 | 538,134,532 → 同じ           |
| Anima `stageNeed`（VAE 段の前の量り）       | `vae_decoder`（静的形 — 潜在 64²） |                 1 |         629,145,600 |         629,145,600 | 683,175,064 → 同じ           |
| Gemma `estimateSessionMemory`               | `model`・`drafter`                 |                 0 |                   — |                   — | 変わらない（下の注）         |
| Gemma の PLE（`ple-gpu.ts`）・greedy の出力 | 構築したグラフ                     |                 0 |                   — |                   — | 変わらない（下の注）         |
| runtime の見積りのテスト（既存のケース）    | `estimate_test` ほかの fixture     |                 0 |                   — |                   — | 期待値は全て不変             |

- **Anima の text 段は動かない**。`text_encoder` / `text_conditioner` に `attention` op は 1 本も無い（attention は `bmm` と `softmax` の
  分解形で出ている — `text_encoder` は `bmm` 56 本・`softmax` 28 本、`text_conditioner` は 24 本・12 本。本数を数えた結果）。
- **Anima の VAE も動かない**。mid block の attention は融合 attention op 1 本（q / k / v とも `[1,1,4096,384]`）で、S は
  1 × 4,096 × 4,096 × 4 = 67,108,864 B・行統計は 32,768 B。後の勘定でこの一時は数えられるが、first-fit の配置が既存の領域の中に
  収めるので、領域の総和は 1 バイトも増えない（このグラフの最大のノード出力は 201,326,592 B）。設計 v2 が書いた「Anima の VAE 段の
  必要量の見積りが増える公算」（推測）は、この形では外れた。先回りの退避（常駐 DiT を畳む判断）の入力は変わらない。
- **Gemma は構造上動かない**。`model` の attention 35 本・`drafter` の 12 本は全て states 形で、融合 attention op は 0 本。PLE と
  greedy の出力のグラフ（`embedding` / `mul` / `topk`）は attention を持たない。
- **runtime の見積りのテスト**は、既存のケースの fixture（`gpu_estimate_test` の states 形・分解の行ブロックを含む）に融合 attention op を
  持たないので期待値は動かない。後のコードで、GPU を使わない runtime と models のテストを既存の期待値のまま回して緑だった
  （GPU を使うテストは GPU が空いていなかったので、この時点では回していない）。

## 参考: Wan2.2 の DiT（呼び手ではない — Wan の pipeline は見積りを呼ばない）

ノブの効き目を読み込みの前に知る手段として、Wan2.2 TI2V-5B の DiT（i8 の系列・融合 attention op 60 本 = self 30 + cross 30）を
同じ上限で見積った。席の束は `EstimateOptions` に渡した（参照席 = 省略・実用席 = `attentionCompute: "a8"` +
`attentionScoreStorage: "f16"`）。単位はバイト。

- 前のコードでは、融合 attention op の S を数えないので席にも予算にも依らず同じ値だった（予算が効くのは states 形と分解の行ブロック
  だけで、この DiT はどちらも持たない）。
- 後の実用席・121 フレーム・予算なしの 6,019,073,792 B（5.61 GiB）は、開発機の Deno で測った backing 5.97 GiB
  （ADR 0121 追記「開発機の 1280×704×121」）に近づいた（前は 3.54 GiB）。見積りは他の融合（`silu` など）が畳む中間を融合前の列で
  数えるので、実測とは原理的に一致しない（`unaccounted` の 1 項目め）。
- 後の値は予算に単調でない形がある: 実用席・121 フレームで 512 MiB が 4,116,457,472 B、256 MiB が 4,252,639,232 B。参照席の
  1 GiB と 512 MiB は同じ値になる。理由は調べていない（推測: S が小さくなると、最大の中間が FFN の側へ移り、first-fit の領域の
  割れ方が変わる）。実寸の backing（段 4b で測る）が同じ形になるかは、実行が同じ配置関数を使うので同じになる見込み（推測）。
- 予算をかけた後の値は予算なし以下だった（この表の 12 組の範囲で）。同じ値になったのは 17 フレームの実用席の 1 GiB だけで、
  S 1 枚が 1 GiB に収まり枚数が 1 のまま変わらない形（それ以外の 11 組は小さい）。

## §1 F-01 — 観測席の phase（性能変更なし）

`tools/opbench/graph.ts` は通知の回数だけで `prefill` / `decode-n` を決めていた。850 token（chunk 768 で 2 本）+
`maxNewTokens: 1` では decode run が 0 本なのに 2 本目の prefill が `decode-1`（dispatch 1478・349 ms）として記録され、
既定の突合（`--runs decode`）に prefill が混ざっていた。修正後は `prefill-1` / `prefill-2`・decode 0 件。併せて、停止
token を引いた最後の decode run（`token` イベントを伴わない）も通知するようにした — 通知数 = `tokens − 1 + prefill chunk 数`
（chat 1 ターン eos・tokens 12 で 12 通 = 式どおり）。**過去の research の decode 平均は停止 run を含まない**ので、以後の
opbench 値と厳密には比較できない（増分 1 本）。

## §4 PLE — 実利用では既定予算が働き集合を覆えない → 行読み

### §4.1 自然文の実測（配布既定の sampler・seed 固定・2 ターン × 200 token・`fromAssets` + ローカル読み）

| ターン           |     壁 | shard 読み | 読み時間 |
| ---------------- | -----: | ---------: | -------: |

### §4.4 行読み後の再測（models の行読み — commit `feat(models)!: PLE の読み口を handle へ`）

同一機・seed 42・既定予算 506 MiB・`fromAssets` + ローカル読み（seek）・`ulimit -n 1024` 配下。

| 経路               |   壁（2 ターン計） | shard 全量読み |         行読み | 備考                                                                              |
| ------------------ | -----------------: | -------------: | -------------: | --------------------------------------------------------------------------------- |
| 従来（range 無し） |             59.5 s | 137 回・43.2 s |              — | §4.1 と同じ                                                                       |
| 行読み（seek）     | **12.1 s（−80%）** |   1 回・328 ms | 718 本・191 ms | turn 1 = 5.84 s・全量 0 / turn 2 = 6.30 s・全量 1（prefill の 32 行以上の shard） |

- 行読みの同時発行は 16 本のプール（1 read = 1 fd の取得元で 768 行 chunk が fd 上限 1024 を踏まない）: 上限無しはピーク
  768 fd・1,200 行で EMFILE、16 ではピーク 16 fd・768 行 53 ms / 1,200 行 72 ms。
- ビット一致: PLE 突合門（torch 厳密一致・29 の相異なる id）を全量経路と行読み経路の両方で通し、経路間も u32 一致。交差 parity
  3 ケース × K=16 は golden 一致（gather 50 回に対し shard 全量取得 1 回 — 従来 9 回）。
- ブラウザの HF 経路は取得層 0.8.0（`openHfFile`）の公開（同日）を受けて hub が追従した（cost = blob → seek / stream → scan）。

## §5 F-02 — prefill の M バケット

### §5.1 実測（wall・timing off・PLE 全常駐・chat 1 ターン + 1 token 生成・capacity 2048・梯子 5 種を A B C D E E D C B A × 3 = 各 9 点の中央値 ms）

|                             prompt token | none（768） | [32,64,128,256,512] | [32,128] | [64,256] | [128] |
| ---------------------------------------: | ----------: | ------------------: | -------: | -------: | ----: |
|            20（+ テンプレ ≈ 30 行 → 32） |         434 |             **129** |      127 |      168 |   189 |
|                60（≈ 70 行 → 128 / 256） |         415 |             **188** |      194 |      309 |   190 |
|              120（≈ 130 行 → 256 / 768） |         410 |             **305** |      451 |      298 |   455 |
|              300（≈ 310 行 → 512 / 768） |         411 |                 550 |      445 |      453 |   455 |
| 850（2 chunk・末尾 ≈ 92 行 → 128 / 256） |         882 |             **746** |      737 |      861 |   801 |

範囲（min〜max）は none 20 token で 385〜817（初回の外れ値）・他は概ね中央値 ±15%。

### §5.2 所見

- 短い発話（chat の 2 ターン目以降が典型）の壁が 434 → 129 ms（−70%）— Codex の実測（chunk 32 で 385 → 106 ms）と整合。
- **512 バケットは 768 より遅い**（310 行で 550 vs 411 ms）。GEMM の幾何は M ≤ 512 で `M64N32`、それより上で
  `reg128x128` に切り替わる（`gemm-geometry.ts`）ので、512 行の小タイルは 768 行の大タイルに負ける。256（M64N32）は
  130 行で 305 ms と 768 形（410 ms）より速いので梯子に残す。**既定 = [32, 64, 128, 256]**。
- 768 形へ落ちる prompt（130 行 → [32,128] の 451 ms・310 行 → 445〜455 ms）が none（410 ms）より 10% ほど遅く見えるのは、
  直前の別 M の run で slot backing が退役し 768 形を作り直す費用（limitations「prefill バケット」の 2 → 3 回/ターン）を
  含むため。多ターンの実運用では毎ターン decode 形との切替があるので、none にも同じ費用が乗る。
- 65〜512 の帯の GEMM 幾何（K-13 が Anima / SBV2 の掃引で選んだ `M64N32`）が gemma4 の prefill にも最適かは未測定
  （512 行で `reg128x128` を使う選択肢は別の研究）。

## §6 K-17 / F-05 — GPU 側の 2 件（Codex 実測の転記）

- K-17（③′ の `exp` を深さ方向で共有）: `lid.x == 0` が `p` を workgroup memory へ置く案は barrier 2 本 / 反復で **2.0〜2.14 倍
  遅い**（P=16383 / D512 で 0.373 → 0.796 ms）、別 dispatch で S を P に変換する案は同速（0.373 → 0.373）。両案とも u32 一致。
  不採用（perf-ledger K-17 ❌）。subgroup 系は Deno の adapter が feature を出さず未測定。
- F-05（マスクで全域が無効な QK タイルの K 反復を 0 に）: 単体 −7〜35%・S 全語一致、実グラフ（850 token・M768）で QK
  −21% だが**全 GPU −0.59%**（721.1 → 716.9 ms・範囲が重なる）。ビット同一の候補として保留（perf-ledger K-19 🚧）。

## §7 MTP（Gemma 4 drafter）の採算実測 — E-0 フェンス床（2026-09-07・追記中）

| 計測（submit 1 回・GPU の仕事はほぼ空）                    | Chrome 152 / macOS（Metal・ユーザー実機・300 回中央値） | Deno + wgpu / RTX 3080 Ti（research 2026-08-30） |
| ---------------------------------------------------------- | ------------------------------------------------------: | -----------------------------------------------: |
| A: submit → `onSubmittedWorkDone`                          |                                                 0.20 ms |                                                — |
| B: submit + copy 4 B → `mapAsync`（karume の decode の形） |                                 **0.30 ms**（p90 0.30） |                                          ≈ 11 ms |

→ ブラウザでは 2F ≈ 0.5 ms で無視できる。フェンス床 11 ms は Deno + wgpu 固有の問題（MTP と独立に起票の価値がある）。

### §7.1 E-1 — 受理数 E[a]（transformers 5.14.1・BF16 target + 公式 drafter・greedy・200 token・RTX 3080 Ti / CUDA）

| prompt（P）                                    |  k=2 |  k=4 |  k=6 |  k=8 | 位置 1 の受理率 |
| ---------------------------------------------- | ---: | ---: | ---: | ---: | --------------: |
| (a) 自由文（物語・P=33）                       | 0.54 | 0.58 | 0.55 | 0.51 |      0.39〜0.44 |
| (b) 対話 2 ターン目（要約 + 語彙・P=461）      | 0.57 | 0.64 | 0.65 | 0.78 |      0.37〜0.42 |
| (c) 長文脈の抽出的要約（README 3 本・P=4,414） | 1.31 | 1.46 | 1.49 | 2.16 |      0.55〜0.78 |

- 分布は 0 に寄る（0 受理率 0.53〜0.64・中央値 0〜2）。自由文は k を増やしても E[a] が伸びない（HF 壁時計でも k=2 で 1.10×・k=8 で 0.73×）。
- centroid 疎 softmax（efficient embedder）を切っても受理数は同一（k=2 でラウンド列まで一致）— karume が topk を export できない件は受理率に効かない。
- **投機ありの出力は 1 行 decode の greedy と一致しない**（24 条件中 1 条件のみ一致）: target 側の M 行まとめ forward が 1 行ずつと argmax 反転を起こす（teacher forcing で初分岐位置を 1 対 1 に同定）。
- i4 の karume と BF16 の同一 prefix 次 token argmax 一致率は 75.5 / 78.4 / 84.0% → i4 target では E[a] がさらに下がる、と**この時点では見た**（→ 翌日の E-4 [research 2026-09-08](2026-09-08-mtp-ea-i4-target.md) で反証: i4 と同値の重みで測った E[a] は BF16 と同等以上）。生データ: `outputs/bench/karume-gemma4/2026-09-07_mtp-experiments/e1/`。

### §7.2 E-2 — 検証 run の時間 T(M)（Deno・e2b i4・`chunkBuckets` に小さい値を渡すだけ・中央値 ms）

| P                | M=1（decode） |         M=2 |          M=4 |          M=8 |         M=16 |
| ---------------- | ------------: | ----------: | -----------: | -----------: | -----------: |
| ≈14,700 GPU / 壁 |   21.5 / 34.0 | 81.9 / 98.8 | 86.7 / 107.5 | 99.2 / 122.3 | 92.7 / 111.3 |
| 256 GPU / 壁     |   15.0 / 26.8 | 71.1 / 85.2 |  71.8 / 86.1 |  73.0 / 87.6 |  74.1 / 88.7 |

- **支配項は attention ではなく linear**: M=1 は GEMV 族（ADR 0082）で 276 本 9.99 ms、M ≥ 2 は GEMM 経路に落ちて 64.9〜67.1 ms の**行数にほぼ無関係な固定費**（M=2 と M=16 で +3.4%）。T(k+1)/T(1) は GPU で ×3.8〜4.9。
- **M が run ごとに変わると slot backing（容量 1）が作り直され +37〜42 ms/run**（`planBacking.buildCount` が切替 run でだけ +1）。交互 1↔8 の 1 サイクル実測 224.8 ms。この費用は通常の chat でも prefill 形 ↔ decode 形の切替で毎ターン払っている（下の所見）。
- M=8 は谷の底で M=16 へ pad する方が速い（長文脈 attention −29%）。F = 壁 − GPU = 11.8〜12.5 ms（既存の床と一致）。

### §7.3 E-3 — draft k 段を 1 グラフに畳んだ drafter の時間 D（使い捨てグラフ・乱数重み・正しさ不問）

| P      | k=1 壁 / GPU | k=6 壁 / GPU | 1 段あたり GPU |
| ------ | -----------: | -----------: | -------------: |

### §7.4 予測倍率と判定

予測倍率 = (E[a] + 1)·T(1) / (2F + T(k+1) + D)。T(k+1) と D の壁は F を含む。

| 条件（P≈14.7K・k=6・verify M=8）                                 |    分子 (E[a]+1)·T(1) |                    分母 |  予測倍率 |
| ---------------------------------------------------------------- | --------------------: | ----------------------: | --------: |
| Deno・自由文（E[a]+1 = 1.55）                                    |               52.7 ms | 122.3 + 26.4 = 148.7 ms | **0.35×** |
| Deno・長文脈要約（2.49）                                         |               84.7 ms |                148.7 ms | **0.57×** |
| ブラウザ相当（F ≈ 0.5 ms を差し引き）・長文脈                    | 2.49 × 22.0 = 54.8 ms |  99.7 + 16.8 = 116.5 ms | **0.47×** |
| 仮に M ≤ 16 の linear が GEMV 族相当（65 → 11 ms）・長文脈・Deno |               84.7 ms |   68.5 + 26.4 = 94.9 ms |     0.89× |

- **K1（予測 < 1.5×）と K3（T(k+1)/T(1) = 3.3〜3.6 > 1.5）が成立** → MTP は parked。小 M の linear を直しても E2B の受理数（自由文 0.5・長文脈 1.5〜2.2）では 1× に届かない。
- ブラウザ（F ≈ 0.5 ms）では通常 decode の水増しが消えるぶん、投機側はむしろ不利になる。
- 復活条件: ①M ≤ 16 の linear が GEMV 族相当になる ②対象ワークロードで E[a] ≥ 2（長文脈・抽出的）③drafter は別 Session（M 切替の罰を避ける）。E4B / 12B は受理率が高い報告があるが配布対象外。

### §7.5 副産物（MTP と独立に効く所見）

- **M ∈ [2, 16]（と恐らく 32 まで）の linear が GEMV 族の 6.5 倍遅い**（同じ重みを読んで 10 → 65 ms）。短い chat ターンのバケット prefill（M=32）の壁 129 ms の大半がこれで、GEMV 族の小 M 拡張は TTFT にそのまま効く。
- **prefill 形 ↔ decode 形の切替で slot backing の作り直しが +37〜42 ms/run**。通常の chat は毎ターン 2 回（bucket → decode → 次ターン）払う ≈ 80 ms。generation 形の backing を複数保持（バイト予算つき）すれば消える。
- Deno のフェンス床 11.5 ms（H-2）はブラウザ（0.3 ms）に無い Deno + wgpu 固有の費用。

## §1 F-01 — 観測席の phase（性能変更なし）

`tools/opbench/graph.ts` は通知の回数だけで `prefill` / `decode-n` を決めていた。850 token（chunk 768 で 2 本）+
`maxNewTokens: 1` では decode run が 0 本なのに 2 本目の prefill が `decode-1`（dispatch 1478・349 ms）として記録され、
既定の突合（`--runs decode`）に prefill が混ざっていた。修正後は `prefill-1` / `prefill-2`・decode 0 件。併せて、停止
token を引いた最後の decode run（`token` イベントを伴わない）も通知するようにした — 通知数 = `tokens − 1 + prefill chunk 数`
（chat 1 ターン eos・tokens 12 で 12 通 = 式どおり）。**過去の research の decode 平均は停止 run を含まない**ので、以後の
opbench 値と厳密には比較できない（増分 1 本）。

## §2 F-04 — sampler の top-k を有界 heap へ

V = 262,144・ABBA 各 6 点の中央値（ms・挿入配列 → heap）。出力（候補列・確率・RNG 消費順）は全 28 条件で完全一致。

| 分布       |        k=64 |      k=1024 |                          k=1025 |      k=4096 |
| ---------- | ----------: | ----------: | ------------------------------: | ----------: |
| 一様乱数   | 0.99 → 0.55 | 3.31 → 1.04 | 84.7 → 1.03（旧は全語彙ソート） | 27.2 → 3.09 |
| 正規分布風 | 0.99 → 0.39 |           — |                               — | 27.5 → 3.07 |
| 昇順       | 21.4 → 9.34 |  241 → 19.7 | 12.5 → 21.9（旧は全語彙ソート） |  941 → 22.3 |
| 同値 8 種  | 0.90 → 0.37 |    1.44 → — |                     38.6 → 1.47 | 10.4 → 1.61 |

heap が全条件で勝ったので挿入配列と `SELECTION_LIMIT`（1024）を撤去した（定常相の足切り `logits[token] <= logits[root]` が
同値の密な入力で挿入形に負けないための要）。topP だけの指定は全語彙ソートのまま（backlog）。

## §3 F-03 — PLE gather の hit 先行と重複 id の複写

実資産 e2b（9 shard × 253 MB・既定予算 = 最大 shard 2 本）。

| 計測                                                |         変更前 |         変更後 |
| --------------------------------------------------- | -------------: | -------------: |

## §4 PLE — 実利用では既定予算が働き集合を覆えない → 行読み

### §4.1 自然文の実測（配布既定の sampler・seed 固定・2 ターン × 200 token・`fromAssets` + ローカル読み）

| ターン           |     壁 | shard 読み | 読み時間 |
| ---------------- | -----: | ---------: | -------: |
| 1（物語 300 語） | 31.7 s |      75 回 |   23.3 s |
| 2（要約 + 語彙） | 26.7 s |      62 回 |   18.7 s |

生成 token は 9 shard 中 8 本に散る（shard 1 が 64%・9 が 17%・2 が 10%・残り 6 本に 10%）。LRU 2 本では 1 token ごとに
253 MB（約 300 ms）の読みが走る — p99 ではなく p50 の問題。

### §4.2 方針のオフライン比較（同じ id 列・読み時間は 300 ms / 265 MB で換算・2 ターン 400 token 合計）

| 方針                                               |     shard 読み |                          推定読み時間 |
| -------------------------------------------------- | -------------: | ------------------------------------: |
| 現行（予算 2 本・LRU）                             |            131 |                                37.5 s |
| 行キャッシュ 16 MiB を追加                         |             71 | 20 s（初出 token の miss は減らない） |
| 予算 4 本（約 1 GB）                               |             33 |                                 9.4 s |
| 予算 = 全量（2.4 GB RAM）                          |              9 |                     2.6 s（初回のみ） |
| **1 id の gather は行だけ読む**（予算 2 本のまま） | 5 + 行読み 207 |                              約 1.5 s |
| shard 細分化 36 MB × 64 本（再 export）+ LRU       |             69 |                                 2.8 s |

### §4.3 読み口の実測（行読みの成立条件）

| 環境                                                   | 手段                                        |                    1 行 8,960 B | 備考                                                        |
| ------------------------------------------------------ | ------------------------------------------- | ------------------------------: | ----------------------------------------------------------- |
| Chrome 152 / macOS（ユーザー実機・256 MiB 合成 shard） | `cache.match(Range)`                        |                               — | **200 全量**（Range は無視・Accept-Ranges の有無に依らず）  |
| 同上                                                   | `response.blob()` → `slice().arrayBuffer()` |                     0.1〜0.3 ms | blob() 0.2〜0.9 ms（遅延・コピー無し）・bytes 一致          |
| 同上                                                   | 本文ストリームの読み飛ばし                  |                        1〜99 ms | offset 比例                                                 |

| Deno 2.9（CacheStorage）                               | `response.blob()`                           |           326 ms + RSS +517 MiB | **全量を読み込む**（遅延ではない）。以後の slice は 0.05 ms |
| Deno 2.9（CacheStorage）                               | 本文ストリームの読み飛ばし                  |                 17 / 51 / 76 ms | offset 1 MB / 128 MB / 256 MB                               |

§4.4 に追記する。

### §4.4 行読み後の再測（models の行読み — commit `feat(models)!: PLE の読み口を handle へ`）

同一機・seed 42・既定予算 506 MiB・`fromAssets` + ローカル読み（seek）・`ulimit -n 1024` 配下。

| 経路               |   壁（2 ターン計） | shard 全量読み |         行読み | 備考                                                                              |
| ------------------ | -----------------: | -------------: | -------------: | --------------------------------------------------------------------------------- |
| 従来（range 無し） |             59.5 s | 137 回・43.2 s |              — | §4.1 と同じ                                                                       |
| 行読み（seek）     | **12.1 s（−80%）** |   1 回・328 ms | 718 本・191 ms | turn 1 = 5.84 s・全量 0 / turn 2 = 6.30 s・全量 1（prefill の 32 行以上の shard） |

- 行読みの同時発行は 16 本のプール（1 read = 1 fd の取得元で 768 行 chunk が fd 上限 1024 を踏まない）: 上限無しはピーク
  768 fd・1,200 行で EMFILE、16 ではピーク 16 fd・768 行 53 ms / 1,200 行 72 ms。
- ビット一致: PLE 突合門（torch 厳密一致・29 の相異なる id）を全量経路と行読み経路の両方で通し、経路間も u32 一致。交差 parity
  3 ケース × K=16 は golden 一致（gather 50 回に対し shard 全量取得 1 回 — 従来 9 回）。
- ブラウザの HF 経路は取得層 0.8.0（`openHfFile`）の公開後に hub が追従するまで従来どおり（backlog）。

## §5 F-02 — prefill の M バケット

### §5.1 実測（wall・timing off・PLE 全常駐・chat 1 ターン + 1 token 生成・capacity 2048・梯子 5 種を A B C D E E D C B A × 3 = 各 9 点の中央値 ms）

|                             prompt token | none（768） | [32,64,128,256,512] | [32,128] | [64,256] | [128] |
| ---------------------------------------: | ----------: | ------------------: | -------: | -------: | ----: |
|            20（+ テンプレ ≈ 30 行 → 32） |         434 |             **129** |      127 |      168 |   189 |
|                60（≈ 70 行 → 128 / 256） |         415 |             **188** |      194 |      309 |   190 |
|              120（≈ 130 行 → 256 / 768） |         410 |             **305** |      451 |      298 |   455 |
|              300（≈ 310 行 → 512 / 768） |         411 |                 550 |      445 |      453 |   455 |
| 850（2 chunk・末尾 ≈ 92 行 → 128 / 256） |         882 |             **746** |      737 |      861 |   801 |

範囲（min〜max）は none 20 token で 385〜817（初回の外れ値）・他は概ね中央値 ±15%。

### §5.2 所見

- 短い発話（chat の 2 ターン目以降が典型）の壁が 434 → 129 ms（−70%）— Codex の実測（chunk 32 で 385 → 106 ms）と整合。
- **512 バケットは 768 より遅い**（310 行で 550 vs 411 ms）。GEMM の幾何は M ≤ 512 で `M64N32`、それより上で
  `reg128x128` に切り替わる（`gemm-geometry.ts`）ので、512 行の小タイルは 768 行の大タイルに負ける。256（M64N32）は
  130 行で 305 ms と 768 形（410 ms）より速いので梯子に残す。**既定 = [32, 64, 128, 256]**。
- 768 形へ落ちる prompt（130 行 → [32,128] の 451 ms・310 行 → 445〜455 ms）が none（410 ms）より 10% ほど遅く見えるのは、
  直前の別 M の run で slot backing が退役し 768 形を作り直す費用（limitations「prefill バケット」の 2 → 3 回/ターン）を
  含むため。多ターンの実運用では毎ターン decode 形との切替があるので、none にも同じ費用が乗る。
- 65〜512 の帯の GEMM 幾何（K-13 が Anima / SBV2 の掃引で選んだ `M64N32`）が gemma4 の prefill にも最適かは未測定
  （512 行で `reg128x128` を使う選択肢は別の研究）。

## §6 K-17 / F-05 — GPU 側の 2 件（Codex 実測の転記）

- K-17（③′ の `exp` を深さ方向で共有）: `lid.x == 0` が `p` を workgroup memory へ置く案は barrier 2 本 / 反復で **2.0〜2.14 倍
  遅い**（P=16383 / D512 で 0.373 → 0.796 ms）、別 dispatch で S を P に変換する案は同速（0.373 → 0.373）。両案とも u32 一致。
  不採用（perf-ledger K-17 ❌）。subgroup 系は Deno の adapter が feature を出さず未測定。
- F-05（マスクで全域が無効な QK タイルの K 反復を 0 に）: 単体 −7〜35%・S 全語一致、実グラフ（850 token・M768）で QK
  −21% だが**全 GPU −0.59%**（721.1 → 716.9 ms・範囲が重なる）。ビット同一の候補として保留（perf-ledger K-19 🚧）。

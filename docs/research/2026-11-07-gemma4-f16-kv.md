> This document is a point-in-time snapshot (2026-11-07) of the f16 full-layer KV on Gemma 4 (K-100, ADR
> [0143](../decisions/0143-f16-full-state-storage.md)): its effect on the numbers, memory and decode speed on the maintainer's
> RTX 3080 Ti under Node + Dawn. It is not a design source of truth. Chrome was not run. The harness and the raw records are
> local and untracked (`outputs/diag/f16-kv-spike-2026-11-06/`).

# Gemma 4: the f16 full-layer KV

## 1. Summary

- Rounding the full-layer KV to f16 is well under the existing distance between Karume and torch: KL at most 2.07e-7 on E2B
  and 5.61e-4 on 12B, against baselines of 7.0e-4 and 8.7e-3, with top-1 unchanged on every compared row (§2).
- Karume's greedy tokens were the same with and without f16 in every arm here, up to P ≈ 127K on E2B and P ≈ 62K on 12B
  (§3).
- **12B decodes faster at long context, which the ledger did not expect**: about 4% at P ≈ 16K, 13% at P ≈ 32K and 22% at
  P ≈ 62K. E2B does not: 6% slower at P ≈ 32K and no measurable difference at P ≈ 127K. The cause is not known (§3).
- The estimate drops by exactly the slots' half: 12B 16 KiB per position, E2B 6 KiB (§4).
- `capacity: "fit"` on this 12 GB card moves 12B from 32,768 to 65,536 and leaves E2B at 131,072 (§4).

## 2. The numbers

Torch against torch: upstream's forward with the full-attention KV stored as f16 once a chunk has run, cut at Karume's chunk
boundaries, compared with the same forward in f32. The only difference is the store, so this bounds the effect of the
rounding itself, not Karume's implementation of it. Karume's implementation is pinned separately, at atol = 0 against an f32
kernel over a slot rounded on the host (`packages/runtime/tests/gpu_state_kv16_test.ts`,
`packages/runtime/tests/gpu_full_state_storage_test.ts`).

| Check | E2B (P up to 31,488) | 12B (P = 31,762, retrieval prompt) |
| ----- | -------------------- | ---------------------------------- |
| Rows compared | 42 | 126 |
| Top-1 agreement | 42 of 42 | 1.0 on every position bucket |
| KL, largest | 2.07e-7 | 5.61e-4 |
| KL, median | 1.81e-8 | at most 8e-6 per position bucket |
| Baseline: Karume f32 against torch f32, largest KL ([research](2026-11-06-gemma4-long-context-quality.md)) | 7.0e-4 | 8.7e-3 |
| Largest \|k\| / \|v\| in the store | 1.12 / 22.1 | 1.41 / 21.6 |
| Greedy decode | not run | 85 of 85 tokens the same, 8 of 8 facts in both, decode KL about 0 |

The largest values are far below f16's limit of 65,504. On the tie and overflow cases `1 + 2⁻¹¹`, `1 + 3·2⁻¹¹`, 65,520 and
65,519, torch's `half()` gave `[1.0, 1.001953125, inf, 65504.0]`: ties to even, overflow at 65,520.

## 3. Decode speed

Quant `i4-fast`, greedy, 64 tokens, one process per arm, the GPU cooled to 60 °C between arms. The sets at P ≈ 1K to 32K ran in
ABBA order over two rounds; P ≈ 62K ran one round. The values are the median wall ms per token of each chat, so four per arm
over two rounds.

| Model, P | f32 | f16 | f16 against f32 |
| -------- | --- | --- | --------------- |
| 12B, 973 | 21.9, 21.4, 22.2, 22.3 | 22.4, 22.2, 22.4, 22.1 | about +1% |
| 12B, 15,994 | 36.4, 36.2, 36.5, 36.1 | 34.8, 34.7, 34.8, 34.7 | about −4% |
| 12B, 31,978 | 49.8, 49.8, 50.6, 48.4 | 41.2, 43.9, 42.7, 44.3 | about −13% |
| 12B, 61,943 (one round) | 78.0, 79.3 | 61.4, 62.0 | about −22% |
| E2B, 31,974 (the warm chat only) | 11.2, 11.5 | 12.0, 12.1 | about +6% |
| E2B, 126,947 (the warm chat only) | 26.2, 27.0 | 26.2, 27.4 | none |

E2B's first chat has cold host PLE blocks (43–64 ms per token in both arms), so only its warm chat is listed. GPU busy time
moves with the wall in every row. Prefill does not change on 12B (about 2.4 / 51 / 111 / 250 s). E2B's prefill is too noisy to
compare: 82–118 s at P ≈ 32K and 284–395 s at P ≈ 127K, overlapping in both arms.

**Why 12B gains is not known.** The fused stats + PV is not the cause: a full slot's column limit is its capacity, so at these
capacities f32 does not fuse full slots either. Read volume alone does not explain it: E2B at P ≈ 127K reads about as many
bytes per token as 12B at P ≈ 47K and shows no gain. Pressure on the 12 GB of VRAM is a candidate (12B's peak is 10–11 GiB
here), and only a card with more memory can separate it [speculation]. The ledger's reason for expecting no gain, that decode
is latency-bound (L-10), therefore does not hold on 12B on this machine.

**Combinations.** All with the same token hash as the arm without them.

| Arm | Decode wall ms per token, warm chat | Without it |
| --- | ----------------------------------- | ---------- |
| 12B f16, P = 973, `decodeAhead: 4` | 22.3 | 27.2, 27.3 |
| 12B f16, P = 31,978, `decodeAhead: 4` | 44.5 | 47.4, 51.4 |

`speculative: "always"` on 12B at P = 973 ran in both storages with the same tokens and the same speculation counters (86
drafted, 33 accepted, 63 delivered), at 39.9–45.1 ms per token in f16 and 43.7–44.4 in f32.

Estimated peak in MiB (`estimateSessionMemory`), and what `fitCapacity()` picked on the RTX 3080 Ti (12 GB, shared with the
display).

| 12B, 4,096 | 8,159 | 8,095 | 64 |
| 12B, 16,384 | 9,119 | 8,863 | 256 |
| 12B, 32,768 | 10,399 | 9,887 | 512 |
| 12B, 65,536 | 11,423 | 10,399 | 1,024 |
| E2B, 32,768 | 2,642 | 2,450 | 192 |
| E2B, 131,072 | 4,562 | 3,794 | 768 |

| Model | `fitCapacity()` f32 | `fitCapacity()` f16 |
| ----- | ------------------- | ------------------- |
| 12B | 32,768 | 65,536 |

12B at capacity 65,536 also ran in f32 when asked for explicitly (P ≈ 62K, above), so f16 does not make that run possible on
this card; it moves what `fit` is willing to pick.

## 5. What this does not cover

- Chrome and D3D12. The reader and the append have not run outside Dawn on Vulkan; the Playground's `/kernel-check` page has
  the `state-kv16` check for that.
- KL above P ≈ 32K, and retrieval above it with f16. The tokens were compared up to the P above, not the distributions.
- E4B, and the regular lines (`karume-gemma4`). Only the q4_0 QAT line's 12B and E2B on `i4-fast` were measured.
- Any machine other than this one, so the speed gain on 12B may not carry over.

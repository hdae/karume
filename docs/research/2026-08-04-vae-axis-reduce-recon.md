# 隣接① recon — VAE decoder の reduce に軸指定を持たせて permute を消す（2026-08-04）

> NOTE: 時点スナップショット。文中のパス・コマンド・コミットハッシュは記録当時のリポジトリ構成に基づく。

> 読み取り専用レッグ。**リポジトリは 1 バイトも変更していない**（作業物は scratchpad の
> `r19/` 配下のみ）。**GPU は 1 回も走らせていない**（並走レッグが専有中 — 契約）。
> 数値は ①既存の per-key 実測 JSON からの転記、②IR を `openModel`+`planGraph` で読んだ
> 実カウント、③それらから組んだ帯域モデルの**試算**、の 3 種で、区別して書く。
> 「プロトタイプ」= 参考元の先行実験プロジェクト（固有名・実パスは書かない）。

---

## 0. 要旨

1. **タスク前提の訂正（事実）**: 犯人は `group_norm` ではない。**`QwenImageRMS_norm` =
   チャネル軸の L2 正規化**（`x / clamp_min(sqrt(Σ_c x²), 1e-12)`）で、permute を入れているのは
   ランタイムではなく**エクスポータ**である。正本は
   `tools/exporter/karume/patch_anima.py:147-158` の `_l2_normalize_channels`
   ——「IR の `sum` は最終次元専業なので、チャネル方向の L2 は permute で最終次元へ持ってくる
   以外に表現が無い」とコメントに明記されている。タスクの機序仮説（縮約軸を permute で
   最終次元へ持ち上げるレイアウト戦略が原因）は**当たっている**。名前だけが違う。
2. **帰属は完全に閉じた**（IR ↔ 実測 dispatch/workgroup が全 14 キーで**厳密一致**、§2）。
   VAE decoder 1024px の `strided` 71 dispatch のうち **60（要素の 81.95%・非コアレス分の
   98.97%）が norm の permute 対**、`reduce` 30 dispatch は **30/30 が norm**。
   タスクが挙げた 228.02ms のうち **220.4〜221.5ms（96.7〜97.1%）が norm 帰属**。
3. **norm 全体は VAE GPU の 19.2%**（246.1ms / 1,282.50ms）で、**dispatch は 210/395 = 53.2%**。
4. **推奨 = 案 A**: `sum`（reduce 族）に `dim` attr を足し、**非最終軸専用の reduce カーネル
   変種**を新設する。permute 対は IR から丸ごと消える。期待 **−208〜214ms（VAE GPU −16.2〜
   16.7%）・dispatch −60**。**既定経路（最終次元 reduce）は 1 バイトも触らない**。
5. **ビット同一は成立する**（本 recon の最重要成果）。現行カーネルの縮約順序は
   「256 レーン grid-stride + 256 幅の**ビット反転**二分木」で、これを**1 スレッドの
   carry-stack で厳密再現できる**ことを記号式で確認した（dim = 1〜512 の 21 ケースで
   式が完全一致 — §5.2）。**PNG sha256 門はビット同一のまま通る**のが期待値。
6. **工数 M**（TS 5 ファイル + Python 4 ファイル + 契約表 + 資産再 emit 20 秒 + テスト）。
   **縮退点つき**: carry-stack が実 GPU で破れたら「現行カーネルのアドレス式だけ変える」
   案 A1 へ落ちる（**構成上ビット同一が自明**・利得は −100〜135ms に減）。
7. **壁時計への効きは小さい**（1024px turbo 全体 27.4s に対し **−0.22〜0.26s = −0.8〜0.9%**）。
   VAE decode が全体の 6% しかないため。**GPU 時間ではなく「非コアレスの構造的根絶」と
   「dispatch −60」に価値を置くかどうか**が裁定の軸。

### 2.1 norm（`QwenImageRMS_norm`）の展開形

IR ノード #2〜#9 が 1 個目の実体（以降 30 回反復。`patch_anima.py:161-172` の `_rms_norm_forward`
→ `_l2_normalize_channels`）:

```
#2 permute [0,2,3,1]  [1,384,128,128] → [1,128,128,384]      ← 縮約軸を最終次元へ
#3 mul     (x, x)                                            ← 二乗
#4 sum                [1,128,128,384] → [1,128,128]           ← 最終次元 reduce
#5 sqrt / #6 clamp_min(1e-12) / #7 reshape（別名・unsqueeze）
#8 div     [1,128,128,384] / [1,128,128,1]
#9 permute [0,3,1,2]  → [1,384,128,128]                       ← 元のレイアウトへ戻す
```

**30 実体 × 7 dispatch = 210 dispatch = VAE 全 dispatch の 53.2%**（別名 reshape 30 本は除く）。

### 2.2 strided 71 ノードの内訳（1024px・書き込み要素数）

| 内訳                            | ノード |        write 要素 |      % | 読みのコアレス性                                                    |
| ------------------------------- | -----: | ----------------: | -----: | ------------------------------------------------------------------- |
| **norm の permute `[0,2,3,1]`** | **30** |     1,214,251,008 | 40.98% | **非コアレス**（最内軸の src stride = H·W = 16,384 要素 = 65,536B） |
| **norm の permute `[0,3,1,2]`** | **30** |     1,214,251,008 | 40.98% | **非コアレス**（同 stride = C = 384 要素 = 1,536B）                 |
| upsample の `expand`（×2 複製） |      6 |       490,733,568 | 16.56% | コアレス（stride 0 か最内 stride 1）                                |
| attention の qkv レイアウト     |      5 |        44,040,192 |  1.49% | 混在（permute 2 本が非コアレス）                                    |
| **計**                          | **71** | **2,963,275,776** |   100% |                                                                     |

> 非コアレス性の根拠は codegen そのもの: `src/codegen/strided.ts:64-105` — 出力は常に連続で
> `out[i] = src[src_index]`、src 側だけが stride で読まれる。上の 2 本は最内出力軸に対する
> src stride が 32B セクタを大きく跨ぐ。

### 2.3 reduce 30 ノードの形（**縮約長が workgroup 幅より短い**）

| rows      | dim（縮約長） | ノード |   read 要素 |
| --------- | ------------: | -----: | ----------: |
| 16,384    |       **384** |     11 |  69,206,016 |
| 65,536    |       **192** |      1 |  12,582,912 |
| 65,536    |       **384** |      5 | 125,829,120 |
| 262,144   |       **192** |      6 | 301,989,888 |
| 1,048,576 |        **96** |      7 | 704,643,072 |

`dim` は 96 / 192 / 384 の 3 種で、**うち 58% の要素が dim=96**。workgroup 幅 256 に対し
dim=96 では **256 レーン中 160 が identity しか持たない**まま 8 段のバリア木を回す。

**これが「reduce が 124 GB/s しか出ない」機序**（doc §3.1 の「dim=128 の行縮約」は概算で、
実際は 96/192/384）。決定的な証拠 = **単価が解像度不変**:

- 1024px: 39.39ms / 1,214,251,008 要素 = **32.44 ps/要素**
- 512px : 9.80ms / 303,562,752 要素 = **32.28 ps/要素**

キャッシュ律速なら working set が 4 倍違えば単価が動く。動かない = **バリア/占有率律速**。

## 5. 設計 3 案

### 案 A（推奨）— reduce 族に `dim` attr を足し、非最終軸専用のカーネル変種を新設

**IR は変わる**（タスクの「IR 不変」という想定は**成立しない** — §7 の逸脱①）。
permute を出すのはエクスポータなので、`sum` が軸を持たない限りエクスポータは permute を
出し続ける。ランタイムだけの改修では消せない。

#### 変更後の IR（norm 1 実体）

```
mul  (x, x)                [1,384,128,128]          ← permute 消滅
sum  attrs={"dim":1}       [1,384,128,128] → [1,128,128]
sqrt / clamp_min           [1,128,128]              ← キー・shape とも現行と同一
reshape（別名）            → [1,1,128,128]
div  (x, norm)             [1,384,128,128] / [1,1,128,128]   ← r4・キー現行と同一
```

**変わるキーは `strided`（−60 dispatch）と `reduce`（新変種）だけ**。
`ew:mul:r4` / `ew:div:r4` / `ew:sqrt:r3` / `ew:clamp_min:r3` は **キーも shape も不変**。

#### A3（本命）— コアレス「1 スレッド = 1 出力」+ **ビット反転 carry-stack**

- スレッド t ↔ 出力要素（= (h,w) 平面の 1 点）。ループは縮約軸 c を進む。
  **同一 workgroup の隣接スレッドは連続アドレスを読む → 完全コアレス**、`workgroupBarrier` ゼロ。
- **縮約順序は現行と厳密一致**（§5.2 で記号検証）。
- 期待コスト: read 4.857GB + write 0.038GB がコアレス →
  **5.57ms（879 GB/s）〜6.99ms（700 GB/s）**。余裕を見て **6〜10ms**。

#### A1（縮退点）— 現行カーネルのアドレス式だけ軸対応にする

- `x[base + i]` → `x[base + i*axisStride]`。**レーン ↔ 要素の対応も木の形も 1 段も動かないので
  ビット同一が構成上自明**。工事は params に 2 語足すだけ。
- ただし読みが非コアレスのまま → 期待 **85〜103ms**（試算・§3.1 の単価より）。

#### 期待利得（1024px・**試算**）

| 置換対象        |   現行 ms |     A3 後 |          削減 |       A1 後 |                削減 |
| --------------- | --------: | --------: | ------------: | ----------: | ------------------: |
| norm permute 対 |     181.0 |         0 |    **−181.0** |           0 |          **−181.0** |
| reduce sum      |      39.4 |     6〜10 |   **−29〜33** |     85〜103 | **+46〜64**（悪化） |
| **計**          | **220.4** | **6〜10** | **−210〜214** | **85〜103** |       **−117〜135** |

- VAE GPU 1,282.50 → **A3: 1,068〜1,072ms（−16.4〜16.7%）** / A1: 1,147〜1,165ms（−9.1〜10.5%）。
- **dispatch 395 → 335（−15.2%）**。VAE decode の非 GPU 分は本 run で
  1,736.7ms(壁) − 1,325.6ms(GPU) − 85.3ms(ロード) = **325.8ms / 395 dispatch ≈ 0.82ms/dispatch**
  （DiT の 0.21ms/dispatch より高い — readback 等を含むので上界）。
  → 非 GPU 側 **−13〜49ms（推測・幅が広い）**。
- **512px**: 同構造で VAE GPU 305.97 → 約 **−52ms（−17%）**。
- **壁時計 1024px turbo 10 step（全体 27.4s）: −0.22〜0.26s = −0.8〜0.9%**。
  512px（15.6s）: −0.06s = −0.4%。**正直に言って壁時計は小さい**。
- **transient メモリは概ね不変**（§6.4）。

### 案 B — 融合 op `channel_l2_norm`（`x → x/clamp_min(sqrt(Σ_axis x²),eps)`）を新設

- ACTIVE_DESIGN の「カスタムカーネル機構: まず **C = ランタイム内蔵の融合 op を
  最適化が必要な処理に足す**」方針そのもの。layer_norm / rms_norm（ADR 0012 / 0017）の先例あり。
- 1 カーネル 2 パス（Σx² → 割り算）: read 2× + write 1× = 14.57GB コアレス →
  **17〜21ms**。置換対象は permute 対 + mul + sum + sqrt + clamp_min + div = **246.1ms**。
  → **−225〜229ms（VAE GPU −17.5〜17.9%）**、**dispatch −180（395→215・−45.6%）**。
- **A3 との差は GPU で +15ms・dispatch で +120**。dispatch −120 の非 GPU 効果（推測
  −25〜98ms）を入れると壁時計差は −0.03〜0.11s。
- 追加コスト: 語彙に 1 op 恒久追加（`docs/op-vocabulary.md`・契約 4 点セット・
  CPU 参照・op-contracts.json・gridstride/full-write ハーネス・スナップショット）+
  **単一モデル専用の op**（「単一用途の抽象を作らない」規律との緊張）。
- 縮約順序のビット同一要件は A と同じ（融合しても Σ の順序は再現が要る）。
- **工数 L**。

### 案 C（却下） — ADR 0011「案 A: strided 融合読み」の部分適用（IR 不変・再 emit 不要）

- executor が `permute` を消費側カーネルへ融合する。**IR も資産も変えなくて済む**のが唯一の利点。
- **却下理由**: この permute は**消費者が 2 つ**（`mul` と `div`）ある。片方に融合しても
  permute は実体化され続ける。両方へ融合すると今度は `mul`/`div` の出力が HWC 順になり、
  後段の `div`→`permute_back` を strided **書き**へ融合する連鎖が要る = 案 A より工事が
  大きく、しかも「IR は最終次元 reduce だと言っているのに実行は違う」状態が残る
  （根治ではなく執行時パターンマッチ = 症状対処）。
- 派生の「`permute → row_reduce` の peephole を planGraph に置く」も、**この permute には
  他の消費者があるので発火しない**（発火しても permute は消えない）。

## 5.2 ビット同一の検証（本 recon の最重要成果・**自分の初案を反証した**）

### 反証した初案

最初「現行の 256 幅ツリーは隣接ペアの平衡二分木なので、1 スレッドの素朴な carry-stack
（2 進カウンタ）で再現できる」と考えた。**記号式で比較して反証した**（`r19/tree.mjs`）:

```
dim=3   現行 : ((x0+x2)+x1)
        素朴 : ((x0+x1)+x2)      ← 不一致
```

機序: 現行の木は `scratch[lid] += scratch[lid+stride]`（stride = 128→64→…→1）なので、
最初に組むペアは (0,128)・(1,129)… で、**葉の順序がビット反転**している。
「隣接ペア木」という私の思い込みが誤りだった。

### 採用形（検証済み）

**`slot[i] = Σ_k x[i+256k]`（k 昇順・左結合）を、`i` を `reverseBits8` の順に carry-stack へ
push する** と、現行の木と**記号式が完全一致**する（`r19/tree2.mjs`・
dim ∈ {1,2,3,5,7,31,32,63,64,96,97,127,128,192,224,255,256,257,384,511,512} の 21 ケースで
`ALL IDENTICAL`）。

```
dim=384 の先頭（両者一致）: (((((((((x0+x256)+x128)+((x64+x320)+x192))+(((x32+x288)+x160)+…
```

WGSL 実装の骨格（**設計案** — 実装はしていない）:

```wgsl
var acc: array<f32, 9>;                 // 全て 0.0 で初期化
for (var m = 0u; m < 256u; m = m + 1u) {
  let i = reverseBits(m) >> 24u;        // WGSL 組込み
  var v = 0.0;                          // i >= dim の slot は identity
  var c = i;
  while (c < dim) { v = v + x[base + c * axisStride]; c = c + 256u; }
  var k = 0u;
  while ((m & (1u << k)) != 0u) { v = acc[k] + v; k = k + 1u; }   // 木は「先 + 後」
  acc[k] = v;
}
out[row] = acc[8];                      // 256 回 push 後は acc[8] のみ有効
```

- ALU は 1 出力あたり固定 256 反復（うち `i >= dim` は**メモリを触らない**）。
  最大の dim=96 段でも追加 ALU は総計 2G 命令級 = **1ms 未満**（推測・帯域 5.6ms に対し無視できる）。
- `+0.0` の畳み込みは**していない**（現行カーネルも identity `0.0` を実際に足すので、
  `-0.0 + 0.0 = +0.0` の 1 例外まで同じ挙動になる）。

### 帰結（数値契約）

| 対象                                   | 判定                                                                                                              |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **GPU 出力の PNG sha256 門（2 系列）** | **ビット同一のまま通るのが期待値**（破れたら設計前提の破れ — ADR 0023 / 0024 / 0028 / 0031 と同じ流儀）           |
| `mul` / `div` / `sqrt` / `clamp_min`   | 各要素の演算・被演算数が 1 対 1 で同じ → **要素ごとビット同一**（レイアウトが変わるだけ）                         |
| 既定経路（最終次元 reduce）            | **カーネル・キー・WGSL バイト列とも無変更**（別変種として足す）→ DeBERTa / SBV2 / DiT は完全に無影響              |
| torch 由来 golden（`io.case*`）        | **ulp 級で動く**（torch 側も `sum(dim=1)` と `permute+sum(dim=-1)` で縮約順序が違う）→ **tolerance 再実測が必須** |
| `--verify vae_decoder`（現行 9.34e-6） | 同上で再実測（値はほぼ動かない見込み — **推測**）                                                                 |

> **検出限界（先に書いておく）**: 「軸 reduce 変種が実は 1 本も走らずキー既定へ縮退した」
> 形は、**IR に permute が無いので数値が壊れて loud に落ちる**（ADR 0030 決定 5 型の沈黙縮退は
> **起きない**）。逆に、carry-stack の順序が現行と違ってしまう誤りは **PNG sha256 と
> atol=0 パリティテストの 2 本でしか捕まらない**（値としては数 ulp なので tolerance は素通りする）。

## 7. リスク・逸脱・未確定

### 7.1 タスク前提からの逸脱（3 件）

1. **「group_norm」→ 実際は `QwenImageRMS_norm`（チャネル軸 L2 正規化）**。機序の仮説
   （縮約軸を permute で最終次元へ持ち上げるレイアウト戦略が原因）は正しい。
2. **「IR 不変」→ 不成立**。permute を出しているのはエクスポータ

   残り 6.5〜7.6ms（upsample の expand・attention の qkv レイアウト）は本タスクで動かせない。

## 8. 推奨と裁定材料

### 推奨 = **案 A（A3 直行・A1 縮退点つき）**

根拠:

1. **根治である。** ADR 0011 が「IR 語彙を変えずに実行戦略の差し替えだけで到達できる
   upgrade path」として先送りした非コアレス問題の、**実測で最大の単一発生源**
   （VAE 非コアレストラフィックの 98.97%）を構造ごと消す。案 C（融合読み）のような
   執行時パターンマッチではなく、**IR が意図（軸 1 の縮約）をそのまま書ける**ようになる。
2. **既定経路がバイト不変で、ビット同一が設計として成立する。** 最終次元 reduce の
   カーネル・キー・WGSL は 1 バイトも動かない（DeBERTa / SBV2 / DiT は無影響）。
   VAE 側も縮約順序を厳密再現できることを**記号式で確認済み**（§5.2）→
   **PNG sha256 門 2 系列がビット同一のまま通る**。この門を再利用できるのは
   ADR 0022 / 0023 / 0024 / 0028 / 0031 と同じ、このプロジェクトで最も信頼された検証形。
3. **利得 / 工事 比が案 B より良い。** 案 B（融合 op）は GPU で +15ms・dispatch で
   +120 を上積みするが、**単一モデル専用の op を語彙へ恒久追加**する（契約 4 点セット・
   CPU 参照・op-vocabulary 台帳・ハーネス）。案 A は**汎用能力**（非最終軸 reduce）を足すだけで、
   将来の NCHW 系モデル（group_norm / BN 統計）にそのまま効く。
4. **再 emit が実質無コスト**。実測で `sum` を含む実モデルは **VAE decoder だけ**
   （他 11 グラフは 0 本）。emit は 10.4s ×2。

### 「軽ければ即着手 / 重ければ tiling の後」への直答

**S ではない（M）。** ただし M の中では軽い側で、危険な部分（数値契約）は
§5.2 で先に潰してある。判断材料を並べると:

- **即着手を支持する材料**: ①既定経路バイト不変 + PNG 門ビット同一で回帰リスクが極小
  ②再 emit が VAE 2 本 20 秒 ③#21（VAE tiling）と**直交**（tiling は解像度分割で
  norm の軸は動かない → tiling 後も同じ比率で効くし、tiling 実装の前に dispatch が
  60 本減っているほうが tiling 側の見通しが良い）④隣接②（非 GPU 固定費）に
  dispatch −60 で寄与。
- **後回しを支持する材料**: ①**壁時計 −0.8%** は 1024px turbo 27.4s に対し 0.22s で、
  ユーザー体感には出ない ②メモリ利得ゼロ = 2048px / 天井の話には効かない
  ③#21 の固定タイル VAE（工数 S〜M）のほうが「できないことをできるようにする」利得。

**私の推奨は「#21 VAE tiling を先に、案 A はその直後」**。理由は、案 A の価値は
GPU 時間 −16% という**比率**であって壁時計ではなく、tiling で VAE の実行形が変わっても
案 A の設計（軸 reduce）はそのまま通用する = **急ぐ理由が無い**から。逆に tiling は
「2048px を通せるか」という**能力**の話で、案 A で作った dispatch 削減はそこでも効く。
ただし ①〜④ の即着手材料も実在するので、**メインが「軽い工事を挟んで勢いを維持したい」
と判断するなら先行させても矛盾は無い**（どちらの順でも後戻りは発生しない）。

# Gemma E2Bの入力バケットとキャッシュ

2026-09-13時点の調査・実測スナップショット。継続候補はH-23、数値と生データの所在はこの記録と付属JSONを参照する。

## 目的と測定条件

入力の処理（prefill）では、実際の入力より大きい行数の計算形へ切り上げる。
37 tokenの日本語入力を64行から40行へ縮め、最初のtokenまでの時間（TTFT）を減らす候補を調べた。
生成中の1 tokenずつの計算（decode）の高速化とは分けて扱う。

既存の `chunkBuckets` 指定を使い、重み・カーネル・キャッシュ上限を変えずに比較する。
通常/QAT E2Bの配布形は `i4-gemvpar` 採用時に新規作成したもの。全比較でGEMV並列加算を明示する。
通常版は `outputs/bench/karume/2026-09-13_quant-distributions-nqqe9kt9/karume-gemma4/`、
QATは `outputs/bench/karume/2026-09-13_quant-qat-family-7zrm_ov9/karume-gemma4-qat/`。
元のローカル配布資産は上書きしていない。

実行環境はRTX 3080 Ti、headless Chrome 153、Vulkan。M2の実測ではない。
Linuxの起動フラグは各 `run-browser.mjs` と結果JSONに記録する。
GPU参照を保持する実験台本を使用した。以前のInstance消失は根因未確定で、製品側の修正とは扱わない。

| 呼称        | chunk未満へ絞る前のバケット                |
| ----------- | ------------------------------------------ |
| A: 標準     | 4, 8, 32, 64, 128, 256                     |
| B: 少数追加 | 4, 8, 16, 32, 48, 64, 128, 256             |
| C: 細分化   | 4, 8, 16, 24, 32, 40, 48, 56, 64, 128, 256 |

通常版のchunk既定は768、QATの最大chunkは128。ブラウザ比較画面は64で固定する。
バケットはchunk未満に限り、論理長1はdecode形、該当バケットがなければchunk全体を使う。
契約は[ADR 0066](../decisions/0066-generation-context-state-slots.md)を参照する。

## chunk64の初期比較

生データ: `outputs/bench/karume/2026-09-13_prefill-bucket-retained-mu2itm1h/`。
`RESULTS.md`、`summary.json`、`probe-v2.ts`、各設定JSONに条件・値・SHAを保存した。
最初の台本 `2026-09-13_prefill-bucket-survey-_s_ei117/` は生成前にGPU Instanceエラーで終了し、
別の専用ディレクトリで参照保持後に成功した。失敗した記録も残している。

通常/QAT、容量128/8192、A/B/CをABC→CBAの順に計24設定。
各設定は英語31・日本語37 tokenと8種類の合成入力長を3周、最大32 token生成した。
720生成すべてで、対応する標準設定とtoken ID・停止理由が一致し、反復の不一致もなかった。

日本語入力の後半2周のTTFT中央値。範囲は往路と復路の値であり、信頼区間ではない。

| 容量 | モデル | A (ms)      | B (ms)      | C (ms)      | Cの時間短縮 |
| ---- | ------ | ----------- | ----------- | ----------- | ----------- |
| 128  | 通常   | 57.45–60.20 | 45.80–47.45 | 40.05–41.00 | 30.3–31.9%  |
| 128  | QAT    | 61.95–62.00 | 47.75–48.10 | 41.20–42.70 | 31.1–33.5%  |
| 8192 | 通常   | 67.40–67.85 | 54.25–59.10 | 45.10–47.45 | 30.1–33.1%  |
| 8192 | QAT    | 63.60–67.85 | 52.45–55.80 | 45.65–47.00 | 26.1–32.7%  |

英語入力は全候補で32行になり、安定した利得はない。
Cの計算用バッファ保持量は容量128で67.54/82.23 MiB（通常/QAT）、
容量8192で124.41/126.01 MiB。重み・KVキャッシュはこの値に含めない。

最初の計算計画ミスは一時バッファで実行し、最初の計画ヒットで再利用バッファを構築する。
そのため「一度生成した」だけでは暖機が完了しない形がある。
上表の英語・日本語の後半2周では計画ミス・バッファ構築が0であることを確認した。
合成入力の一部は2周目まで構築が残るため、全入力を一律に2周目から定常と呼ばない。
3周目では全設定の構築が0だった。

温度・クロックは途中から423標本を保存した（70–94°C、SM 210–1905 MHz、アイドルを含む）。
往復で改善方向は揃うが、小さい差の精密な推定には使わない。
診断コールバックを付けた計測なので、診断なしのブラウザUIのdecode速度と混ぜない。

## 長いchunk・容量切り替え

生データ: `outputs/bench/karume/2026-09-13_prefill-cache-stress-p02h3vvi/`。
コードは `6aae325` の固定バンドル。計測開始後のブラウザUI変更を含めない。
通常chunk768/QAT chunk128、容量8192単独と1024/8192交互を比較する。
英語・日本語に合成長4/7/13/20/41/49/57/95/129/257/769を加え、各設定4周、最大8 token。
A/B/Cを往復して24設定、1,872生成。後半2周を集計対象とするが、計画ミスや構築が残る場合は定常値とは扱わない。

計算計画は最大12個、計算用バッファは既定256 MiBの別々のLRU（最近使ったものを残すキャッシュ）である。
保持契約は[ADR 0095](../decisions/0095-plan-backing-budget.md)を参照する。
容量も計画キーに含まれる。Cは通常chunk768で13形になり、一容量でも全形を保持できない。
一方、大きいchunkのバッファは単体で予算を使い切り、A/Bでも小さい形の再構築が起きうる。
上限を引き上げる変更は、この実験には含めない。

1,872生成で標準とのtoken ID・停止理由の不一致0、反復の不一致0、容量間の不一致0。
これは短いgreedy生成の検査であり、一般のlogits一致や広い品質評価ではない。

後半2周×往復の各一巡について、TTFTの合計を示す。容量単独は13生成、交互は26生成の合計。
範囲には全標本を含め、外れ値を除外しない。decode時間は含めない。

| 容量          | モデル | A (ms/巡) | B (ms/巡) | C (ms/巡) | A/B/Cの計画ミス (回/巡) |
| ------------- | ------ | --------- | --------- | --------- | ----------------------- |
| 8192          | 通常   | 1514–1608 | 1507–1565 | 1688–1731 | 0 / 0 / 12              |
| 8192          | QAT    | 1619–2122 | 1577–1650 | 1575–1611 | 0 / 0 / 0               |
| 1024/8192交互 | 通常   | 3660–3762 | 3862–4011 | 3818–3953 | 10 / 18 / 24            |
| 1024/8192交互 | QAT    | 3552–3701 | 4101–4190 | 4440–4590 | 0 / 10 / 20             |

- 通常版chunk768のCは、一容量でもprefill 14回のうち12回が計画ミス。
  Bでは短い日本語入力のTTFTは改善しても、一巡全体では小さい差に留まる。
  最大の計算用バッファは全候補335.25 MiBで、256 MiB予算を超える単体形を保持した後に他形を作り直す。
  一容量の後半各巡の構築はA/B/Cで10/12/2回。Cの構築数が少ないのは、計画ミスで一時バッファを使うためであり、改善を意味しない。
- QATの一容量では全候補の計画ミス・構築は0。最大保持量はA/B/Cで107.79/136.15/189.23 MiB。
  交互容量では標準の12形が収まるのに対し、B/Cはあふれる。Cの一巡合計は往復の対応比較で約23〜27%悪化した。
- 温度581標本は54–94°C、SM 210–1935 MHz（アイドルを含む）。往復は熱や実行順の影響を観測するためであり、
  バケット数以外の影響を完全には排除しない。後半にも計画ミスが残るため「十分に暖機すれば全て解消」とは扱わない。

以上から、全chunk・複数容量向けの既定バケット変更は採用しない。
chunk64の固定容量での利得をM2でも評価できるように、比較画面への追加に留める。
キャッシュ上限の拡大は別のメモリ評価を要するため、この変更では行わない。

## 投機デコードの確認

通常版E2B、chunk64/容量128とchunk768/容量1024、GEMV逐次/並列、A/B/Cを比較。
各設定で非投機と常時投機（k=3）を4入力×3周、最大32 token生成した。
計288生成で標準の非投機とのtoken ID・停止理由が一致し、投機あり/なし・反復とも不一致0。
verifyの論理行数は4が1,476回、終端付近の1/2/3が各36回だった。
物理行数はdraftが0なら1、それ以外はk+1=4を維持する。
7 token入力を含み、8行prefillも通す。GEMV逐次と並列の間の一致は要求しない。
既存のverify行0/decodeのu32一致の門は、全体テストで別に維持する。

- `outputs/bench/karume/2026-09-13_prefill-mtp-_x2qbgjm/`: chunk64の144生成。
  chunk768は台本の容量128がchunk未満だったため、生成前に正しく拒否された。
- `outputs/bench/karume/2026-09-13_prefill-mtp-wide-a9c4dk_f/`: 容量1024に直した残り144生成と統合 `summary.json`。
  前走と結果を上書きせず、モデル側の拒否条件も変更していない。

この台本はABC順の数値検収であり、MTP速度の採否に使う往復比較ではない。
QATには投機を追加していない。

## ブラウザの比較設定

[比較画面の説明](../../tools/llm-speed/browser/README.md#prefill-bucket-experiment)を追加した。
標準/少数追加/細分化と、ABC→CBAの往復を選べる。各設定を別iframeで実行し、
選択した `prefillBuckets` と実際の `chunkBuckets` を表・JSONへ記録する。
既存のGEMV比較とは独立し、両方を比較すると1モデル12回の読み込みになる。
Transformers.jsにはバケット設定を適用せず、1モデル1回のまま。

M2での手順:

```sh
deno task bench:llm-browser
```

Chromeでlocalhost:8787を開き、モデル「両方」、比較対象「karume」、
行列計算「並列加算を指定」、入力バケット「3種類を往復比較」を選ぶ。
初回・暖機後TTFT・decode tok/s・出力IDを分けて比較し、JSONを保存する。
古いローカル配布形でも明示した並列加算が優先される。既存モデル資産の更新は不要。

## 採否と残件

- 採用: 比較画面の入力バケット指定と往復実行。標準の既定値・モデル・runtimeには変更しない。
- 不採用: 全chunk/容量向けのバケット細分化と、利得を作るためのキャッシュ上限拡大。
- 未検収: M2のTTFT/メモリ、実際の対話の入力長分布、長い生成と広い品質評価。
  既存のlogits/bit同一性を、今回の短いtoken一致だけから一般化しない。
- 次: M2結果でchunk64の用途限定採用を判断。decodeは下記のCPU計測から融合を優先し、GPU常駐PLEの転送削減は別に帰属する。H-23のTTFT改善と分けて追う。

## 次のdecode調査に向けたCPU計測

層別埋め込み（PLE）の量子化行キャッシュが効いた後も、各gatherはCPUで値を展開している。
この費用を `outputs/bench/karume/2026-09-13_cpu-ple-cost-9ajm68w2/` で測った。
AMD Ryzen 5 5600 / Deno 2.9.6で実際のPLE資産を読み、各入力を事前取得・100回暖機してから500回ずつ計測した。
通常E2BはI8、QAT E2BはI4、QAT E4BはI2。7入力形×3モデルの10,500標本で計測中の追加I/Oは0。
値展開と出力配列確保を含むgather全体であり、初回読み取り・GPU転送・モデル推論は含まない。

| モデル  | decode 1行 p50/p95 (ms) | verify 4行 p50 (ms) | 日本語40/64行 p50 (ms) |
| ------- | ----------------------- | ------------------- | ---------------------- |
| 通常E2B | 0.02070 / 0.03174       | 0.03461             | 0.54925 / 0.62014      |
| QAT E2B | 0.03251 / 0.03354       | 0.09455             | 0.97405 / 1.27504      |
| QAT E4B | 0.04659 / 0.04994       | 0.13871             | 1.46176 / 1.53806      |

このDenoの暖機後decodeではCPU展開が小さいため、F32行キャッシュやPLE全表のGPU常駐化を先行実装しない。
Chrome/M2のgather費用、キャッシュが外れる頻度、GPUへの書き込み費用はこの実験では未測定。
以前のChromeで見えた壁時間とGPU時間の差を全てPLEへ帰属させることもできない。
次は通常版の正規化周辺とQATのRMS→SRQ融合を全体比較で調べる。個別dispatch時間の和を速度予測に使わない。

全表を常駐させる場合の値とscaleの容量は通常E2B 2,275 MiB / QAT E2B 1,155 MiB / QAT E4B 714 MiB。
これは実際のindexからの計算で、メモリ使用量の実測ではない。GPU行キャッシュの場合も、
複数sequence・MTP・追い出し時の参照寿命を先に設計する必要がある。
コード上の調査と容量計算は `outputs/bench/karume/2026-09-13_decode-next-scope-bwkzatw_/`、
CPUの全標本・台本・環境は上記専用ディレクトリ、要約と元JSONのSHAは保存用集計JSONの `cpuPleCost` に残す。

## 何を測ったか

- **3 系列 × part 長 3 通り × 取得元 3 通り × 3 回の中央値**。系列と取得元（cold / warm / local）の定義は
  前回と同じ — gemma4 e2b `i4-fast` / irodori v4.1-small `i8-a8` / anima turbo-v1.1
  `f16+dit8-a8-attn8-s16`。cold / warm は Deno の HF 経由で hub の取得面は **scan 型**（part を 1 度に
  読んで保持枠に置き、block を切り出す）、local は `denoDirectory` で **seek 型**（block ごとに位置読み）。
- **part 長 {256, 512, 1024} MiB**: 256 は `models/` のミラーそのもの。512 / 1024 は旧 `karume/4` ミラー
  （`~/workspace/karume-models-v4/`）から `karume migrate --part-bytes` で `outputs/dist-partlen/` へ
  焼き直した。**irodori は重みの最大 part が 350.6 MiB** なので、512 と 1024 は同じ割れ方になる
  （宣言の最大 part が両方 350.6 MiB — 2 行は同じ配布形の繰り返し測定として読む）。
- **3 段の実装**（どれも同じ 27 構成を回した）:
  - **M0** = 基準（段 3d のまま）。
  - **M1** = 候補 3 — hub の scan 型の切り出しを `slice()`（写し）から保持枠の器の view（`subarray()`）へ。
  - **M2** = 候補 3 + 候補 2(c) — Session 構築が part の block を 1 本読んでは上げて手放す
    （`WeightBatch.items` の lazy 化・フェンスは part ごと 1 回のまま）。
  - 候補 1（取得層の `readFile` に器を渡して使い回す）は測っていない（読み取り ⑤）。
- **数値**: `external`（V8 が抱える ArrayBuffer の実勢 — 50 ms 標本化の最大値・load / run の区切りは前回と
  同じ）、VmHWM、load / run の ms。50 ms 標本化は block 単位の短い山を取りこぼしうるので VmHWM を併記する。
- **宣言だけで閉じる見積り**（container-v1 §11）: 最大 block は 3 系列とも 32.0 MiB。最大 part は表の
  括弧内。

## 読み取り

1. **ピークは part 長にほぼ比例して伸びる（M0）**。scan 型（cold）は gemma4 load 1,287 / 1,543 / 2,058・
   anima run 1,261 / 1,907 / 3,194、seek 型（local）は gemma4 load 775 / 1,143 / 1,515・anima run
   679 / 1,143 / 1,876（part 長 256 / 512 / 1024）。最大 part に対する倍率は、大づかみに **scan 型 ≈ part × 3・
   seek 型 ≈ part × 1.5〜2**（どちらも約）。幅を正確に書くと scan 型は約 2.0〜5.0 倍（part 512 以上に限ると
   約 2.0〜3.7 倍 — irodori 約 3.3・gemma4 約 3.0 / 2.0・anima 約 3.7 / 3.1）、seek 型は約 1.1〜3.0 倍
   （part 512 以上で約 1.1〜2.2 倍）。part 256 で倍率が高いのは、part に比例しない分（GC を待つ前の器・
   part 以外の確保）が相対的に効くためと読む（**推測**）。irodori の local が 393 / 394 と動かないのは、dit の
   重み 350.6 MiB が part 256 でも 2 本にしか割れず、2 本が同時に生きれば part 長に依らず同じ量になるため
   （**推測**）。
2. **候補 3（view）は scan 型を下げ、seek 型は動かさない（M0 → M1）**。part 512 以上の cold で、VmHWM は
   irodori 1,729 → 1,285（part 約 1.3 本ぶん）・gemma4 2,555 → 1,509（約 2.0 本）/ 3,069 → 1,979（約 1.1 本）・
   anima 2,842 → 2,145（約 1.4 本）/ 3,760 → 2,760（約 1.0 本）下がった。external では irodori run
   1,157 → 744（約 1.2 本）・gemma4 load 1,543 → 1,033（約 1.0 本）/ 2,058 → 1,516（約 0.5 本）・anima run
   1,907 → 1,741（約 0.3 本）/ 3,194 → 2,305（約 0.9 本）。part 256 では効きが揃わない（irodori run
   777 → 583 は約 0.76 本ぶん下がり、gemma4 warm load も 1,287 → 785 と下がったが、anima warm run
   1,261 → 1,247・gemma4 cold load 1,287 → 1,282 はほぼ動かない）。local の変化は約 7% 以内（最大は gemma4 part 512 の load 1,143 → 1,058）。
   副次効果として scan 型の時間も縮んだ（part ぶんの写しが消えたためと読む — **推測**）— anima cold run 7,518 → 6,123 ms・
   irodori cold run 5,777 → 5,409 ms・gemma4 warm load 3,186 → 2,598 ms（part 256）。
3. **候補 2(c)（lazy）は seek 型を「block 1 本 + 展開席」まで下げ、part 長に依らなくする（M1 → M2）**。
   anima local run 679 / 1,143 / 1,876（M0）→ **75 / 102 / 75**、gemma4 local load 775 / 1,143 / 1,515 →
   **108 / 139 / 138**、irodori local run 393 → **71**（512 / 1024 は 394 → 92 / 71）。VmHWM も part 長に
   依らなくなった（anima 988 / 1,451 / 2,254 → 484 / 479 / 476・irodori 907 / 892 / 930 → 541 / 544 / 576・
   gemma4 1,428 / 1,899 / 2,234 → 1,181 / 1,217 / 1,148）。残る 71〜139 MiB は item 1 本（最大 block
   32.0 MiB + 同乗 scale + 展開席の f32 展開結果）と固定分の桁である（内訳は切り分けていない）。scan 型は M1 からほぼ動かない（irodori run 744 / 744・
   gemma4 load 1,032 / 1,515・anima run 1,741 / 2,245 — part 512 / 1024）。scan 型の block は hub の保持枠の
   view なので、items を lazy にしても上限は **hub の保持枠 1 本**（+ GC を待つ前の器）が決める。
   - wgpu の staging（フェンスまで part ぶん残る — ADR 0108 決定 9）について: staging が part ぶんホストの RSS に
     積まれるなら、local の VmHWM は part 長 256 → 1024 で伸びるはずだが、M2 では 484 / 479 / 476（anima）と
     平らだった。この機（Arc B570 / Deno 2.9.6）では staging が part 長に比例してホスト RSS に乗る形は
     観測されない（**読み** — 機序は未確認）。part より細かい予算ごとのフェンスを足す理由は出なかった。
4. **gemma4 の run 時間が M2 で +0.14〜+0.55 s 伸びた**（local 820 / 854 / 908 → 1,367 / 1,360 / 1,267 ms・
   cold / warm は +0.14〜+0.29 s）。cold / warm は M1 の時点で既に +0.10〜+0.21 s 伸びており（851 → 993 ms
   など）、local は M1 では動かず M2 で伸びた。gemma4 の run は `fromPretrained` が組み終えた Session での
   最小の生成 1 回で、重みの供給は run の窓に入らない。Session 構築を run に含む irodori / anima の run ms は
   M2 でほぼ動かないか縮んでいる（irodori local 5,694 → 5,604 ms・anima local 8,169 → 7,314 ms〈part 1024〉
   など）。例外は anima part 256 の local で 6,770 → 6,960 ms（M1 は 6,684）と約 3〜4% 伸びたが、gemma4 local の
   伸び（約 40〜67%）より 1 桁小さい。なので供給経路そのものの遅れではない読みである。**原因は未切り分け**（**推測**: load で出た不要物の GC が run
   の窓へずれた / host PLE の行読みの経路の変化 — どちらも未測）。
5. **候補 1（器の使い回し）は採らない**。理由は 4 点:
   - 単独の削減（part を読み替えるたびの新規確保 1 本 = part 1 本）は、候補 3 の削減と同じかそれ以下。
   - 候補 3 と組むと器の view が hub の外（runtime の重み・資産の読み・`graphBytes`）へ出る。器の上書きを
     跨いで view が生きる経路があるので、runtime 公開型 `BlockSource` の寿命契約を「借用 → 返却」に変える
     破壊的変更が要る（3 と衝突する）。
   - 取得層（`@hdae/fetch-cache`）は同じ器の並行使用を入口で拒むので、scan 型の読みを直列化する必要がある。
     gemma4 の PLE の行読み（16 本並行）が 1 本ずつになる。
   - 器は取得面の寿命いっぱい最大 part 長で居座り、gemma4 の host PLE の decode 中の常駐が約 +224 MiB
     増える見込み（**推測**・未実測）。

   なお M2 の scan − local は part 256 で irodori 約 2.0 本（582 − 71）・gemma4 約 2.6 本（warm load
   785 − 108）・anima 約 4.2 本（1,139 − 75）ぶん残っており、監査の段階で置いた候補 1 の追加実測の起動
   条件「part 256 で 0.75 本以上残る」には数値上当たる。採らない判断は上の費用と衝突に拠るもので、残りの扱いは
   ⑦の Range 取得の論点へ回す。
6. **既定 part 長は 256 MiB のまま**。M2 の後、seek 型は part 長に依らない（③）が、scan 型（Deno の HF 経由）
   はおおむね part 長とともに伸びる — M2 の cold で anima run 1,139 / 1,741 / 2,245・irodori run 582 / 744。
   gemma4 load は 1,038 / 1,032 / 1,515 で、256 → 512 では伸びていない（part 256 の cold だけ高い形 — 残った問い）。既定を上げて得るのは part 本数（ADR 0108 決定 6 の R2）だけで、gemma4 e2b の
   `model` 容器は 256 で 83 part・512 で 79 part・1024 で 78 part と、ほとんど減らない（区間読みの資産 =
   PLE は 1 block = 1 part の専用 part なので、part 長を上げても本数が減らない）。
7. **段 6 の Range 取得の前倒し条件への含意**。前倒しの条件は「cold のピークが『part 長 + 重ね合わせ』を
   超える」こと（ADR 0109 決定 7）。段 2 の時点では超過の原因を保持の重複（写し・part 単位の items）と読み、
   Range ではなく段 3 の候補で閉じるとした（ADR 0108 追記 3 の 10）。3e でその重複は消えた（②③）が、scan 型の
   cold は M2 でも part 長 + 最大 block（256 + 32）を上回る（irodori run 582・gemma4 load 1,038・anima run
   1,139）。残りは保持枠 1 本と GC を待つ前の器で、原因は **part 単位の全量読みそのもの**、つまり取得の粒度に
   移った。条件は形式上成り立ったままである。GC を待つ器の積み上がりを消す手は候補 1 だが、それでも part 1 本は
   残る。part 長に依らない形へ下げる手は Range 取得（block 単位の区間取得）に限られる。影響するのは Deno の HF 経由（取得層の戦略 "stream"）だけで、local と、ブラウザ
   （戦略 "blob" = seek 型 — Chrome は未実測）は既に block 粒度に収まる。前倒しするかは本記録では判断しない。

## 残った問い

- gemma4 の run 時間の伸び（④）の帰属。
- scan 型で GC を待つ器の本数は宣言から閉じない — M2 の part 256 で anima が最大 part の約 4.4 本
  （run 1,139 MiB）。container-v1 §11 が置いていた「part の境界では GC まで 2 part」は、この構成では実測を下回る
  見積りだった（§11 は実測の幅〈最大 part の約 1.5〜4.4 本〉へ改めた）。
- gemma4 part 256 の cold だけ load が warm より高い（M2 で 1,038 / 785 — part 512 / 1024 では cold ≈ warm）。
  cold の取得相の山かどうかは未切り分け。
- ブラウザ（Chrome）での実測は未。

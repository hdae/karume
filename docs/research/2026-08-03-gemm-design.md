## 1. プロトタイプ 4×4+vec4 の構造（写し）

プロトタイプは **GEMM 3 op（matmul / bmm / linear）が 1 本の共通シェーダ骨格を共有**する形で、
骨格関数が「head / prologue / fillA / fillB / store」の 5 断片を差し込む。レジスタブロッキング
本体（内積ループ）はその骨格 1 箇所にしか存在しない。

### 1.1 タイル・スレッド・共有メモリ

| 項目                   | 値                                                  | 備考                                                |
| ---------------------- | --------------------------------------------------- | --------------------------------------------------- |
| 出力タイル             | 64×64                                               | `GEMM_TILE = 64`（dispatch は `ceil(dim/64)`）      |
| workgroup              | 16×16 = **256 スレッド**                            | `WG = GEMM_TILE / REG = 16`。現行 Karume と同数     |
| 1 スレッドの出力       | **4×4**（`acc: array<vec4<f32>, 4>` = 16 レジスタ） | `REG = 4`                                           |
| K タイル               | **16**（`TILE_K`）                                  | 現行 Karume の 16×16 と同じ K 刻み                  |
| 共有 A タイル          | `sa: array<f32, 64*16>` = 4,096 B                   | スカラ格納（行 = m 方向）                           |
| 共有 B タイル          | `sb: array<vec4<f32>, 16*16>` = 4,096 B             | **列方向を vec4 に束ねた [k][列 quad]**             |
| 共有合計               | **8,192 B / WG**                                    | `maxComputeWorkgroupStorageSize` 既定 16,384 の内側 |
| K タイルあたり quad 数 | `K_QUADS = TILE_K / REG = 4`                        | A 充填の割当（64 行 × 4 quad = 256 = スレッド数）   |

### 1.2 内側ループ（vec4 の使い回し＝この設計の全て）

```
for (kk in 0..TILE_K) {          // 16 回
  let bv = sb[kk * WG + lid.x];  // 共有から vec4 を 1 回だけロード
  for (i in 0..REG) {            // 4 回（成分は vec4 演算で自動 4 並列）
    acc[i] = acc[i] + sa[(lid.y*REG + i) * TILE_K + kk] * bv;
  }
}
```

- 共有ロード **5 回**（B の vec4 1 + A のスカラ 4）に対し **16 MAC**。現行 16×16 は
  共有ロード 2 回に対し 1 MAC（`src/kernels/matmul.ts:63`）なので、共有帯域あたりの演算密度が
  **6.4 倍**。これが 2.50× の出所で、vec4 のグローバル読み書きが更に 3.07× まで押し上げる。
- **縮約は k 昇順の逐次のまま**（外側 t が K タイル昇順、内側 kk が 0→15 昇順）。
  現行 Karume の `for (i = 0..16)`（`matmul.ts:62-64` / `linear.ts:93-95` / `bmm.ts:69-71`）と
  **加算順序が完全に一致する**。ここが後述 §4 の tolerance 設計の土台。

### 1.3 充填（fill）とスレッド割当

- **A タイル**（= linear の x・matmul/bmm の a。どれも `[m,k]` 行優先 f32）:
  `ar = tid / K_QUADS`（0..63 = タイル内行）、`aq = tid % K_QUADS`（0..3 = k quad）。
  v4 なら `a[base + arow*k4 + ak4]` を **vec4 で 1 回読み**、`sa` へ 4 スカラに撒く。
  範囲外は 0 で埋める（内積に寄与しないので K タイル端数も結果不変）。
- **B タイル（matmul / bmm）**: b は `[k,n]` 行優先なので**列方向がそのまま vec4**。
  `bk = tid / WG`（0..15 = K タイル内行）、`bcq = tid % WG`（0..15 = 列 quad）。
  v4 は `b[base + brow*n4 + bc4]` を vec4 で 1 回。スカラ版は 4 成分を個別に境界検査して詰める。
- **B タイル（linear）**: W は `[n,k]` で連続方向が k。1 スレッドが **k 連続 4 要素を読み**、
  **共有メモリ側で転置して置く**（`sb[(wq*REG + q)*WG + wc/REG][wc%REG] = bt[q]`）。
  `wc = tid / K_QUADS`（0..63 = タイル内の出力チャネル）、`wq = tid % K_QUADS`（k quad）。
  → 内積ループを 3 op で共有できるのは、この**共有メモリ上の転置**のおかげ。
- **境界処理**: 充填は 0 埋め、書き出しは `orow < m` と（v4 は `ocq < n4`、スカラは `col < n`）で
  ガード。v4 経路は `K%4==0` が前提なので、`wk0 < k` が成り立てば 4 要素とも範囲内
  （`wk0` は 4 の倍数・`k` も 4 の倍数）。

### 1.4 K/N%4 条件の判定場所

- 判定関数は **カーネル側**（`gemmUsesVec4(k, n) = k%4===0 && n%4===0`）に置き、
  **executor の encode 時に shape から評価**して `v4: boolean` を WGSL 生成関数とキー生成関数の
  両方へ渡す。プロトタイプの dispatch は 3 op とも
  `const v4 = gemmUsesVec4(k, n); dispatch(kkey(v4), () => kwgsl(v4), ...)` の形。
- キーは `matmul:f32:reg64x64v4:v1` / `bmm:f32:reg64x64:v1` / `linear:wi8:reg64x64v4:v1` のように
  **v4 フラグを含む**（= 形状から導いた 1 ビットがキーに載る）。
- 条件が両方必要な理由: dense 側は a が `[m,k]`（k%4）、b が `[k,n]`（n%4）、c が `[m,n]`（n%4）。
  linear 側は x が `[m,k]`（k%4）、out が `[m,n]`（n%4）、W が `[n,k]`（k%4 で行頭が quad 境界）。

### 1.5 プロトタイプと Karume の**重み格納の差分**（ここが移植の主戦場）

| 論点               | プロトタイプ                                                                                                               | Karume                                                                                                                                                           | 帰結                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| f16                | `enable f16` + `array<f16>` 直読み。ただし **vec4\<f16\> のストレージ配列は使わず 4 スカラで読む**（移植リスク回避と明記） | `array<u32>` + `unpack2x16float`（feature 依存ゼロ・ADR 0018、`weight-storage.ts:70-77`）                                                                        | Karume は **2 要素 pack**。v4 では **u32 を 2 語読んで vec4 を組む**（§2.3）                                           |
| i8                 | `array<u32>` + `unpack4xI8`。**scale は縮約の外**で出力チャネルごとに 1 回（`acc[i] * sv + biasv`）                        | **scale は要素ごと**（`f32(unpack4xI8(...)[i&3]) * scale`、ADR 0019 の中核決定・`weight-storage.ts:83-85`）                                                      | **プロトタイプ形を写してはならない**。§2.4 で per-element を保ったまま vec4 化する                                     |
| bias               | wf16 では `array<f16>`（`f32(bias[…])` でキャスト）                                                                        | **bias は常に f32**（ADR 0006 / `linear.ts:60`）                                                                                                                 | Karume 側が単純。キャスト不要                                                                                          |
| 重み格納の生成部品 | 各 WGSL 生成関数に分岐が散る                                                                                               | `weight-storage.ts` 1 本に集約（5 op 共有・`:20-23` にバイト不変 MUST）                                                                                          | v4 用の読み出しは**この共有部品を拡張**して足す（§2.2）                                                                |
| 生成の共有         | 3 op が 1 テンプレートを共有                                                                                               | 3 ファイル独立。`linear.ts:13-14` と `bmm.ts:7-9` に「共通化するな」MUST（matmul 側にはこの MUST は無く、`matmul.ts:3-5` が「perf で差し替える」と予告している） | この MUST の趣旨は「既存の生成バイト列を動かすな」。3 本を**同時に別キーへ改版する**今回は前提が消える（§2.1・要裁定） |

## 2. Karume への写像

### 2.1 モジュール構成（3 op × 重み格納 3 変種 × v4/scalar）

- **`src/kernels/gemm.ts` を新設**し、プロトタイプと同じ 5 断片差し込み型のテンプレートを置く。
  `matmul.ts` / `bmm.ts` / `linear.ts` は薄い呼び出し側（キー・タイル定数・params）に痩せる。
- 既存の「共通化禁止」MUST 2 箇所（`src/kernels/linear.ts:13-14` / `src/kernels/bmm.ts:7-9`）は
  **文言ごと書き換える**（黙って破らない）。理由: あの MUST は「既存の生成バイト列と
  スナップショットを動かすな」が目的で、今回は 3 本とも WGSL が総取り替え＋キーを v2 へ
  改版するため保護対象が存在しない。むしろ**内積ループの正本を 1 箇所に保つ**方が
  「同じ縮約順序」という不変条件を機械的に守れる。
- 生成物の総数: matmul 2 / bmm 2 / linear 3 変種 × 2 = 6 → **合計 10 本**
  （現行 5 本: `tests/fixtures/wgsl/{matmul,bmm,linear,linear_wf16,linear_wi8}.wgsl`）。

キー（`src/gpu/pipeline-cache.ts:1-11` の決定性 MUST に従い、同一キー ⇔ 同一バイト列）:

```
matmul:v2:f32:reg64x64[v4]
bmm:v2:f32:reg64x64[v4]
linear:v2:f32:reg64x64[v4][:wf16|:wi8]
```

`v1 → v2` の改版は `conv1d:v2`（`src/kernels/conv1d.ts:52-53`）で確立済みの流儀。
`weightKeyPart`（`weight-storage.ts:38-39`）は f32 で空文字という規約をそのまま使う。

### 2.2 `weight-storage.ts` の拡張（3 点・既存 4 op のバイト不変を維持）

現行の生成部品はスカラ 1 要素前提（`weightRead` は `dequant(i)` / `dequant(i, scale)` を返す・
`weight-storage.ts:112-122`）。v4 経路には **quad 読み**が要る:

1. `weightArrayType` に **quad 版**を足す: f32 は `vec4<f32>`、f16 / i8 は `u32` のまま
   （pack 済みなので配列型は変わらない）。
2. `weightLoaderWgsl` に **`dequant4` を出す版**を足す。
   **MUST: 既存の呼び出し側（conv1d / conv2d / conv_transpose1d / embedding）には
   `dequant4` を出さない**。無条件に足すと `weight-storage.ts:20-23` のバイト不変 MUST が
   壊れ、`tests/fixtures/wgsl/conv*.wgsl` / `embedding*.wgsl` 6 本が一斉に動く。
   → 引数（`quad: boolean` など）で明示的に opt-in させ、既定は現行と 1 バイトも変えない。
3. `weightRead4`（quad 読み式）を足す。f32 は `w[i >> 2u]`（vec4 配列の quad 添字）、
   f16 / i8 は `dequant4(i)` / `dequant4(i, scale)`。

### 2.3 f16（2 要素 pack）の vec4 化

v4 経路では読み出す平坦添字 `i` が **4 の倍数**であることが保証される
（linear の B 充填では `i = wcol*k + wk0`、`k%4==0` かつ `wk0` は 4 の倍数）。したがって
4 要素はちょうど **u32 2 語**に収まり、語をまたがない:

```wgsl
// MUST: i は 4 の倍数（v4 経路からのみ呼ぶ）。行頭が語境界に来ることに依存しているのではなく、
// 平坦添字が 4 の倍数であることに依存している — ADR 0018 の偶奇の罠とは別物。
fn dequant4(i: u32) -> vec4<f32> {
  let lo = unpack2x16float(w[i >> 1u]);
  let hi = unpack2x16float(w[(i >> 1u) + 1u]);
  return vec4<f32>(lo.x, lo.y, hi.x, hi.y);
}
```

- 読み出し命令は 4 → **2**。プロトタイプは「16bit ベクトル配列は移植リスクだけが残る」として
  vec4\<f16\> を避けたが、Karume は元々 u32 束縛なのでこの論点自体が消える。
- **スカラ経路（k%4≠0）は現行 `dequant(i)` をそのまま使う**。ADR 0018 の「平坦添字の偶奇で
  対を選ぶ」MUST と、その唯一の検出器（行長が 2 の倍数でないテスト）は無傷。

### 2.4 i8（4 要素 pack）の vec4 化 — **ADR 0019 の per-element scale を保つ**

`unpack4xI8` は元々 4 要素単位なので **vec4 との相性は 3 変種中で最良**:
1 語 = 4 バイトのロードで vec4 が 1 本できる（f32 の 16 バイトに対し 1/4 の帯域）。

```wgsl
// MUST: i は 4 の倍数（v4 経路からのみ呼ぶ）。語をまたぐと 4 要素が別行に散る。
fn dequant4(i: u32, scale: f32) -> vec4<f32> {
  return vec4<f32>(unpack4xI8(w[i >> 2u])) * scale;
}
```

- **ビット一致の議論**: `vec4 * scalar` は WGSL の成分ごと f32 乗算なので、
  各成分は `f32(q_j) * s` — 現行スカラ経路 `f32(unpack4xI8(w[i>>2])[i&3]) * scale`
  （`weight-storage.ts:83-85`）と**同一の演算・同一の丸め**。
  → **ADR 0019 の「scale は要素ごと」（`docs/decisions/0019-i8-weight-execution.md:28-35`）は
  vec4 化しても維持される。ADR 0019 の改訂は不要**。
- **プロトタイプ形（`acc[i] * sv + biasv` の縮約外 scale）を写すと ADR 0019 の改訂 +
  tolerance 再導出が発火する**（同 ADR `:33-35` / `:69-70` が明示条件）。今回は採らない。
- **scale の読み出し位置が現行と変わる**: 現行は `col`（= 出力列を担当する自分のスレッド）で
  1 回読む（`linear.ts:72`、`weightScaleWgsl(weight, "col", "  ")`）。新カーネルでは
  **B タイルを充填するスレッドの担当チャネル `wcol`** が正しい引数。
  `wcol = wid.x*64 + tid/4` は K タイルループ不変なので、**ループの外で 1 回**束縛する
  （ADR 0019 の「ループ不変巻き上げ」規律そのまま）。
  → `weightScaleWgsl(weight, "wcol", "  ")` を `main` 冒頭に置く。
  端タイルで `wcol >= n` になりうるが、WGSL の境界付きアクセスで安全、かつ読んだ値は
  `wcol < n` のときしか `sb` に載らない（現行 `linear.ts:22-24` と同じ論法）。

### 2.5 3 カーネルの断片（差し込み表）

| op     | head（束縛）                                | prologue                                    | fillA                  | fillB                       | store                                       |
| ------ | ------------------------------------------- | ------------------------------------------- | ---------------------- | --------------------------- | ------------------------------------------- |
| matmul | dims / a / b / c                            | v4 のとき `k4`,`n4`                         | 共通（`a`, base 無し） | dense（`b`, base 無し）     | dense（base 無し）                          |
| bmm    | 同上                                        | `k4`,`n4` + `abase/bbase/cbase = wid.z * …` | 共通（`a`, `abase +`） | dense（`b`, `bbase +`）     | dense（`cbase +`）                          |
| linear | dims / x / w / bias / out（+ i8 は wscale） | `k4`,`n4` + i8 の `wscale_v`                | 共通（`x`, base 無し） | **linear 専用（転置撒き）** | linear（bias 加算・i8 は既に dequant 済み） |

- **束縛番号は現行のまま**: linear は 0=dims / 1=x / 2=w / 3=bias / 4=out / 5=wscale
  （`linear.ts:43` の `LINEAR_SCALE_BINDING = 5` と `executor.ts:1216-1221` の対応を維持）。
- **バッチのオフセットは quad 単位で計算する**（v4 のとき `abase = wid.z * m * k4` であって
  `m * k` ではない）。ここは新設の失敗モード — §4.4 の故障注入の主対象。
- **bias の vec4**: Karume の bias は常に f32 なので
  `let biasv = vec4<f32>(bias[oc], bias[oc+1u], bias[oc+2u], bias[oc+3u]);`（キャスト不要）。
  `n%4==0` かつ `ocq < n4` なので `oc+3 < n` が保証される。
- **`dims.batch` の扱い（要裁定）**: 現行 bmm の uniform は 4 語 `{batch,m,n,k}` だが
  **WGSL 本体は `dims.batch` を一度も読んでいない**（`src/kernels/bmm.ts:26-31` で宣言、
  `:47` 以降は `wid.z` から導出）。プロトタイプは 3 語 `{m,n,k}` で統一している。
  改版のついでに 3 語へ揃えるか、`bmmParams` のテスト（`tests/codegen_wgsl_test.ts:584,591,965`）
  ごと現状維持にするかは裁定事項（§7 Q3）。

### 2.6 executor / dispatch の変更

```ts
// #encodeMatmul（executor.ts:1096-1122）/ #encodeBmm（:1128-1156）/ #encodeLinear（:1196-1230）
const v4 = gemmUsesVec4(k, n);
const key = matmulKey(v4); // linear は linearKey(weightStorage, v4)
const pipeline = await this.#state.cache.get(key, matmulWgsl(v4));
this.#state.scheduler.dispatch(pipeline, bindGroup, [
  tiledWorkgroups(n, GEMM_TILE, limit, where), // GEMM_TILE = 64（16 から変更）
  tiledWorkgroups(m, GEMM_TILE, limit, where),
  1, // bmm は tiledWorkgroups(batch, 1, …)
], key);
```

- `tiledWorkgroups`（`src/codegen/dispatch.ts:24-37`）の **fail loudly 不変条件はそのまま**。
  タイル辺が 16→64 になるので、`DispatchLimitError` に当たる閾値が **4 倍緩む**
  （副次的な改善。縮退させない設計は不変）。
- **params は変更不要**: `matmulParams` / `linearParams` は `{m,n,k}` を 16 バイトに詰めており
  （`matmul.ts:77-88` / `linear.ts:108-119`）、新カーネルも同じ uniform を読む。
- **vec4 束縛のバイト整列**: `array<vec4<f32>>` を束縛するバッファは 16 バイトの倍数が要る。
  v4 条件（`k%4==0 && n%4==0`）から a/x（m·k）・b（k·n）・out（m·n）はいずれも要素数が 4 の倍数
  → バイト数が 16 の倍数。アリーナは 4 バイト整列でぴったり配る
  （`src/gpu/arena.ts:41-52`「要求より大きいバッファを配らない」）ので過不足なし。
  なお **これらのカーネルは `arrayLength()` を使わない**ので、同 MUST の本来の懸念
  （要素数が静かに変わる）には触れない。
- `scheduler.dispatch` の第 4 引数（キー）は ADR 0021 の集計単位。**キー名が変わるので
  perf 比較表は前後で名前対応を作る必要がある**（§5）。

### 2.7 レジスタ配列のアンロールについて（リスクと選択肢）

`acc: array<vec4<f32>, 4>` を `for (i)` で動的添字するのは、ドライバがループを展開して
初めてレジスタに載る。展開されなければローカルメモリに溢れて 2.50×/3.07× は出ない。
プロトタイプの実測はこの**ループ形のまま**取られているので、まずは**ループ形をそのまま写す**
（実測が付いている形から離れない）。数値が伸びなかった場合の第 1 候補として、
Karume は WGSL を TS で生成しているので **codegen 時に 4 本へ展開する**手が無料で取れる
（成分 x/y/z/w の展開はプロトタイプも codegen 時にやっている）。

## 3. フォールバック構造（K/N が 4 の倍数でない場合）

### 3.1 候補と評価

| 案                            | 内容                                                                                              | 評価                                                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **A（推奨・プロトタイプ形）** | 同じレジスタブロッキング構造のまま**スカラ読み書き**へ落ちる変種を持ち、`v4` フラグでキーを分ける | 端数形状でも **2.50×**。生成の骨格は共有なので縮約順序が構造的に一致。生成物 5→10 本                                |
| B（パディング）               | K/N を 4 の倍数へゼロ詰めして常に v4                                                              | 重み・活性の**レイアウトを全域で変える**。full-write 不変条件・別名化・プール寸法・エクスポータ契約に波及。**却下** |
| C（16×16 残置）               | 端数形状は現行カーネルへ                                                                          | 端数が 1.00× に落ちる。かつ**構造の違う 2 本**（縮約順序は同じだが実装が別系統）を永久に保守する。A に劣る          |

**推奨は A**。B は blast radius が桁違い（不変条件を 3 本壊す）、C は A の下位互換。

### 3.2 キーが形状依存になることの影響

- **決定性は崩れない**。`pipeline-cache.ts:1-11` の MUST は「同一キー ⇔ 同一 WGSL バイト列」で
  あって「キーが形状に依存しないこと」ではない。`v4` は shape → `{true,false}` の写像なので
  同一キーには常に同一バイト列が対応する。
- **前例あり**: `elementwiseKey` は既に `r${rank}`（形状由来）をキーに載せている
  （`src/codegen/elementwise.ts:360-363`。fixture 名 `elementwise_add_r3.wgsl` がその現れ）。
  `reduceKey` は `from>to`（`src/codegen/reduce.ts:108-111`）。**キーが形状の関数であること自体は
  既存の設計語彙**で、今回は新規則ではない。
- **キャッシュ効率**: 増えるのは **1 op あたり高々 2 倍**（有限・形状の連続値ではなく 1 ビット）。
  実グラフでは片方しか踏まないのが普通（Anima DiT の hidden 1024 / FFN 幅 / head dim はいずれも
  4 の倍数なので v4 側のみ）。**混在するグラフでのみ**両方が乗る。
  → 「どのモデルが scalar 側を踏むか」は**未計測**（SBV2 系は幅が 4 の倍数でない層がありうる）。
  実装波で `diagnostics()` のパイプラインキー集合を 1 回見れば確定する。
- **スナップショット**: `tests/fixtures/wgsl/` に 5 本追加（`*_v4.wgsl`）+ 既存 5 本を差し替え。
  `tests/codegen_wgsl_test.ts:125-126,146,151` の表と `:201-214` のキー一意性検査に
  v4 側を機械的に足す（`WEIGHT_STORAGES` × `[false,true]` の直積で回すのが漏れない）。

## 4. 正しさの検証計画

### 4.1 まず「縮約順序は変わらない」を主張として立て、反証しにいく

**重要な訂正**: タスク前提の「縮約順序が変わる = 既存 golden / E2E の数値が動く」は、
実装を読む限り **成り立たない見込み**である。

- 現行 16×16 と新 64×64 は **K タイル幅がどちらも 16**、外側 t が昇順、内側が 0→15 昇順で、
  **1 出力要素あたりの加算順序が完全に一致**する（`matmul.ts:62-64` ⇔ §1.2）。
- 積の値も同一（f32 の x·w。i8 の dequant は §2.4 で成分ごと同値、f16 は同じ `unpack2x16float`）。
- プロトタイプ側の記録も、同じ置換（16×16 → レジスタ 4×4+vec4）で
  **「数値は完全に同一 — 刷新前とビット単位で同じ結果」**と実測している。

残る唯一のリスクは **fma 収縮の差**（スカラ `acc = acc + a*b` と vec4 `acc[i] = acc[i] + sa*bv` で
ドライバの融合判断が変わる可能性。WGSL は融合を規定しない）。

**手順**:

1. **仮説検定を先に置く**: 実装直後に `atol=rtol=0` の素の突合を、既存 E2E の全系列で 1 巡回す。
   対象 = `tests/e2e_golden_test.ts`（tiny 5 本）/ `e2e_deberta_test.ts` /
   `e2e_sbv2_test.ts`（dp / front / flow / dec / voice）/ `e2e_anima_test.ts`（f32・f16 系列）/
   `e2e_anima_i8_test.ts` / `e2e_anima_1024_test.ts` / `e2e_anima_turbo_test.ts`。
2. **全て 0 なら tolerance は 1 つも触らない**。代わりに「ビット一致を実測で確認した」旨を
   ADR / ACTIVE_DESIGN に記録する（後続が「動いたはず」と誤読しないため）。
3. **動いた場合のみ再導出**。既存規律（`tests/e2e_anima_test.ts:183`）どおり
   `atol=rtol=0` の素の突合 → **実測最悪の 5〜10 倍**。
   **系列間・解像度間の流用は禁止**（`e2e_anima_1024_test.ts:63-64,84-89` が明示。
   f16 系列の値を i8 系列へ、512px の値を 1024px へ持ち込まない）。
   動いた場合、`e2e_anima_turbo_test.ts` の**累積表**（`.claude/ACTIVE_DESIGN.md:258-262`:
   1.75×/step で単調累積）も採り直しの対象になる — 入口の誤差が変われば到達点も変わる。
4. **`gpu_ops_test.ts` は検出器にならない**ことを明記しておく: CPU 参照は f64 で積んで
   1 回だけ丸める（`src/reference/ops.ts:6`）ため GPU 側の縮約順序変化に鈍感で、
   突合は `DEFAULT_TOLERANCE`（atol 1e-5 / rtol 1e-3・`src/reference/allclose.ts:27`）。
   **ビット一致の検出は E2E の `atol=rtol=0` 実測でしか取れない**。

### 4.2 full-write 不変条件の維持

- 新カーネルの書き出しは `orow < m`（+ 列ガード）だけで、`ceil(m/64) × ceil(n/64)` タイルが
  出力の全要素をちょうど 1 回ずつ覆う（v4 は `n%4==0` なので quad の端数なし）。bmm は z 軸が
  全バッチを覆う。**構造上 full-write は保たれる**が、guard 式が現行より複雑なので
  **`tests/gpu_full_write_test.ts` に GEMM 3 op を足す**（現行は cat / pad / flip /
  conv_transpose1d のみ・同ファイル `:1-15`）。毒値バッファ再利用の仕掛けはそのまま使える。
- 併せて「1 workgroup = 1 タイルで全域を覆う／縮退させない」MUST
  （`matmul.ts:6-9` / `bmm.ts:10-12` / `linear.ts:15-17`）はタイル辺だけ 64 に書き換えて維持。

### 4.3 縮退ハーネスの扱い（タスク前提の訂正）

- タスクの「縮退ハーネス（tests/gpu_gridstride_test.ts）に新カーネルは必ず載せる規約」は
  **GEMM には適用されない**。同ファイル `:665-667` に
  「**linear はタイル固定で grid-stride を謳わないのでこのハーネスの対象外**」と明記があり、
  matmul / bmm も同じ理由で載っていない（MUST の本文 `:7-9` も「grid-stride を謳う全カーネル族」）。
  タイル系カーネルを縮退ハーネスに載せるのは**カテゴリ違い**で、載せれば「タイルが欠落して
  出力が未書き込みで残る」＝ハーネスが赤くなるのが正しい振る舞い。
- **タイル系の等価な安全網は 2 本**: ① `tiledWorkgroups` の fail loudly
  （`src/codegen/dispatch.ts:29-36`。タイル辺 64 に変わっても壁は残る）
  ② `gpu_full_write_test.ts` の毒値注入（§4.2 で GEMM を追加）。
- 加えて **`gpu_ops_test.ts` にタイル境界ケースを増設**（現行のケースはタイル 16 前提で、
  タイル 64 では `[7,5]×[5,3]` などが全て「1 タイル未満」に潰れる）。

### 4.4 故障注入の候補（各項目に「どの誤りを、どのケースだけが検出するか」を対で持つ）

| # | 注入する誤り                                                                    | 検出するケース（v4 側 / scalar 側）                                                                                                                                                                                 |
| - | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① | **バッチ base を quad 単位でなく要素単位で計算**（`wid.z*m*k` vs `wid.z*m*k4`） | bmm・**batch ≥ 2 かつ B/M/K/N を全て違う長さ**（`[3,68,20]×[3,20,12]`）。batch=1 では踏まない。既存 BMM_CASES（`tests/gpu_ops_test.ts:402-437`）は B/M/K/N を違えているが**タイル 16 前提**なので寸法を 64 系へ更新 |

## 5. 性能の検証計画

- **測定器**: `examples/anima/main.ts` の時間 JSON に載る `gpuTimingByGraph`
  （グラフ別 × パイプラインキー別・ADR 0021 / `examples/anima/main.ts:437,633` /
  `examples/anima/README.md:45-47`）。
- **条件**: 前提となった内訳と同じ 2 点 —
  ① `--resolution 512 --dit f16`（linear 89% / bmm 9%）
  ② `--resolution 1024 --dit i8`（linear 75% / bmm 23%）。seed / steps / cfg は固定。
- **熱の扱い（MUST）**: `docs/research/2026-08-03-demo-w8-perf-recon.md:62-67` の実測
  （時間比とクロック比が 4 走行とも一致・`r(step時間, clocks.sm) = −0.92〜−0.99`・
  冷機 45℃ 対照で Σ(ms×MHz) 差 0.1%）に従い、**十分な冷機を揃えるか ms×MHz で正規化**する。
  各条件 4 走行。
- **報告する量（両方）**: ① キー別の **share**（内訳が本当に動いたか）
  ② **絶対値**（ns 合計と s/step。share は分母が動くので単独では読めない）。
  キー名が `…tile16` → `…reg64x64[v4]` に変わるので **前後の名前対応表**を添える。
- **反証可能な事前予測**（Amdahl・GEMM が一律 3.07× と仮定）:

  | 条件                                 | linear のみ置換                | linear+bmm+matmul 置換         |
  | ------------------------------------ | ------------------------------ | ------------------------------ |
  | 512px / wf16（linear 89% / bmm 9%）  | 1/(0.11+0.89/3.07) = **2.50×** | 1/(0.02+0.98/3.07) = **2.95×** |
  | 1024px / wi8（linear 75% / bmm 23%） | 1/(0.25+0.75/3.07) = **2.02×** | 1/(0.02+0.98/3.07) = **2.95×** |

  プロトタイプは実形状で**ベンチ（3.07×）より伸びた**（512px 3.45→0.979 s/step = 3.5×）ので、
  上表は下限側の見積り。**実測が 1.8× を下回ったら原因調査**（共有メモリのバンク衝突・
  小 M 形状での占有率・レジスタ溢れ）に入る合図とする。
- **やらないこと**: 単体 GEMM マイクロベンチの新設。プロトタイプの実測表が
  `demo-w8-perf-recon.md:14-22` に恒久記録されており、Karume 側で測るべきは
  「実グラフで share がどう動くか」。

## 6. 段階分割案

### 案 A（推奨・**検証軸**で切る 2 波）

- **波1 — codegen + 結線（3 op 同時）**
  1. `src/kernels/gemm.ts` 新設（テンプレート・`GEMM_TILE`・`gemmUsesVec4`）
  2. `weight-storage.ts` の 3 点拡張（§2.2。**既存 4 op のバイト不変を先にテストで固定**）
  3. `matmul.ts` / `bmm.ts` / `linear.ts` を薄い呼び出し側へ（キー v2・MUST コメント書き換え）
  4. `executor.ts` の 3 encode（v4 判定・`GEMM_TILE`・キー渡し）
  5. スナップショット 10 本 + キー一意性 + `gemmUsesVec4` 単体 + タイル辺の文字列固定
  6. `gpu_ops_test.ts` のタイル境界ケース増設（§4.4 の ①〜⑦）+ `gpu_full_write_test.ts` に GEMM 追加
  - **検証**: `deno task verify` 緑 + 実 GPU の op テスト緑。
- **波2 — 数値と性能の実測**
  1. 全 E2E を `atol=rtol=0` で 1 巡（§4.1 手順 1）→ ビット一致なら tolerance 無変更
  2. 動いた分だけ再導出（系列ごと・流用禁止）
  3. `gpuTimingByGraph` 前後比較（§5）
  4. ADR 0022（新設）+ ACTIVE_DESIGN の decisions-in-flight 更新 + recon への実測追記
  - **検証**: E2E 全緑 + 性能表。

**この切り方の理由**: 3 op はテンプレート共有なので実装を分けると同じ骨格を 2 度書くことになる。
一方「コードが動く」と「数値契約と性能が期待どおり」は別種の検証で、間に切れ目を入れる価値がある。
波1 が赤いまま波2 の実測に入る事故も防げる。

### 案 B（**op 軸**で切る 2 波 — 波1 が大きすぎた場合の退避）

- **波1 = linear のみ**（89% / 75% を単独で取る。`weight-storage.ts` を触る唯一の op なので
  リスクの大半がここに集中する）→ **波2 = bmm / matmul**（f32 のみ・2 変種ずつ）。
- 欠点: テンプレートを linear 専用で書いてから dense 用に一般化するので構造が 2 度動く。
  利点: 波1 の tolerance 実測結果（ビット一致か否か）を波2 の設計に反映できる。

### どちらでも守る切れ目

- **`weight-storage.ts` の拡張は独立コミット**にし、その時点で
  「conv1d / conv2d / conv_transpose1d / embedding の fixture 6 本がバイト不変」を緑で示す。
- **tolerance の変更は独立コミット**（実測値と導出根拠を doc コメントに埋めるのが既存規律）。

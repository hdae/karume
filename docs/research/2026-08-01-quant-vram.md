# 量子化と VRAM 削減の実態確認（2026-08-01）

> NOTE: 時点スナップショット。文中のパス・コマンド・コミットハッシュは記録当時のリポジトリ構成に基づく。

ADR [0006](../decisions/0006-quantization.md) の「VRAM への効果」節の根拠調査
（プロトタイプの実装・実測記録の読解）。パスは断りなければプロトタイプの
リポジトリ内相対パス。

## 結論

1. **適格重みは圧縮格納のまま GPU に載る**（f16 ≈1/2・i8 ≈1/4 + scale 小バッファ）。
   dequant はカーネル内（i8: `unpack4xI8`、f16: f16 ストレージ読み → f32 キャスト）。
   適格外はアップロード時に CPU で f32 展開され、VRAM 削減はゼロ（配信サイズのみ縮む）。
2. **Anima の VRAM 削減（ピーク 15,690 → 12,483 MiB、−3.2GB）は w8(i8) によるもの**。
   attention 融合が下げたのは中間バッファ会計（2,214.6 → 302.0MB）であり、実測ピークは
   DiT ロード時 = 重み側。バッファプール改善を単離した VRAM 実測は存在しない。
3. f16 は降格バグ（適格 0.0MB / CPU 展開 3,731.5MB / GPU 実サイズ 7,463MB）により
   Anima では実質無効だった。i8 が無傷だったのは **i8 の重みスロット定義が bias を
   含まない**構造のため（Karume 0006 の「bias 常時 f32」はこの一般化）。
   i8 化の対象は DiT の Linear 454 本のみで、VAE・テキスト層は f16 のまま。

## 主な根拠（プロトタイプ内 file:line）

- 圧縮のまま確保・転送: `packages` 本体 `src/runtime/executor.ts:1006-1014`（i8、
  4byte 境界 pad のみ）/ `:1030-1039`（f16）/ `:1048-1052`（payload.byteLength で確保）。
  適格外の CPU 展開: `:1021` / `:1041`（実体 `src/format/safetensors.ts:238` 以降）。
- カーネル内 dequant: `src/kernels/gemm.ts:141-155`（`unpack4xI8`）、scale 適用は縮約の
  外で 1 回 `:195-219`。conv1d 系は `src/kernels/indexing.ts:70-82` / `:185-195`。
- i8 スロットが bias を含まない: `src/runtime/executor.ts:481-489`（対して f16 は
  `:470-478` で bias を含む — 降格バグの根）。
- i8 の VRAM 実測表: `docs/research/2026-08-01-webgpu-vram-release.md:105-138`
  （DiT ファイル 3,918→1,967MB / 常駐 5,181→3,320MB / ピーク −3,207MiB）。
- f16 降格バグ: `docs/known-issues.md:7-24`（修正後予測 7,463→3,731MB は
  `docs/roadmap.md:37-40`）。

## 注意（推測・未検証）

- 重みバッファ差（≈5.5GB）と観測ピーク差（≈3.4GB）が閉じない。f16 側が VRAM 上限の
  96% に張り付いた飽和等の仮説はあるが**未検証**。
- −3.2GB は「壊れた f16」比。公平な比較は f16 修正後の再測が必要（プロトタイプ側の
  記録自身が同旨を注記）。
- conv2d の w8 変種は未実装（VAE は f16 頼み）。conv 主体モデルの VRAM 削減幅は
  Karume で conv 系 w8 を実装するかどうかに依存する。

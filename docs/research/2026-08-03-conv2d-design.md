## 0. 結論（先出し）

- **推奨は候補 (i) implicit GEMM**（`src/kernels/gemm.ts` の 64×64 / 4×4 / vec4 骨格を
  そのまま流用し、B タイル充填だけを x の暗黙 gather に差し替える）。
- 決め手は性能ではなく**縮約順序が現行カーネルと厳密に一致する**こと。
  ADR 0022 と同じく **tolerance を 1 つも動かさず、PNG sha256 ビット一致を受け入れゲートに
  できる**（唯一の例外は符号付きゼロ — §5.3）。
- 期待値: 1024px の conv2d **15.18s → 1.7〜3.0s（5〜9×）**。VAE 16.3s → 2.5〜3.8s、
  総壁時計 85.9s → **73〜74s（−14〜15%）**。512px は 1.73s → 0.4〜0.7s（総 26.1s → 25.1s）。
  上限は「同一マシン・同一骨格の GEMM 実測 3,320 GFLOP/s」で決まる（§2.3）。
- (ii) 共有メモリ直接タイルは有力な次点だが**縮約順序の正本が 2 本に割れる**のが致命的。
  (iii) im2col は `maxStorageBufferBindingSize` を単一バッファで超えるため構造的に不可。
  (iv) Winograd は**算術そのものが変わる**ため tolerance 全面再導出 + PNG ビット一致という
  最強の回帰検出器の喪失と引き換えになり、この段階では割に合わない。

## 1. conv2d 形状 census（IR 実測）

### 1.1 conv2d が出るグラフ

全 `models/**/model.safetensors` を走査した結果、**conv2d は VAE decoder にしか無い**。

| グラフ                                              | ノード数    | conv 族                           |
| --------------------------------------------------- | ----------- | --------------------------------- |
| anima / anima-f16 / anima-f16-1024 の `vae_decoder` | 455         | **conv2d 37**                     |
| anima 系 `transformer`（DiT）                       | 3,904       | **なし**                          |
| anima 系 `text_encoder` / `text_conditioner`        | 1,769 / 613 | なし                              |
| deberta full-24layer                                | 1,230       | conv1d 1                          |
| sbv2 dec / flow / front / voice / dp                | 246〜1,836  | conv1d 4〜245・conv_transpose1d 5 |

- **DiT の patchify は conv2d ではない**。IR の先頭は `cat → reshape → permute → …` の
  レイアウト連鎖で、埋め込みは `p_model_patch_embed_proj_weight [2048, 68]` の **linear** に
  落ちている（= ADR 0022 の GEMM 置換で既に高速化済み）。**この設計の適用先は VAE decoder 1 本**。
- conv1d / conv_transpose1d は別カーネル・別グラフで、本設計の影響を受けない。

### 1.2 conv2d 37 ノードの内訳（512 系列 / 1024 系列は解像度が 2 倍で同型）

37 ノード・**14 種の異形**。属性は全ノードで `stride=[1,1] / dilation=[1,1] / groups=1`、
カーネルは **3×3 padding=[1,1] が 34 本・1×1 padding=[0,0] が 3 本**。
**stride>1 / dilation>1 / groups>1 は 1 本も無い**。

- 全形状で **Wout ∈ {64, 128, 256, 512, 1024} = 4 の倍数**。

## 2. 現行カーネルの構造と実測効率

### 2.1 構造（`src/kernels/conv2d.ts`）

- **1 スレッド = 1 出力要素**の直接畳み込み・`@workgroup_size(256)`・`gid.x` の grid-stride
  （`gridStrideWorkgroups`）。
- ループ形は `for ic_rel { for kh { if(iy 範囲外) continue; for kw { if(ix 範囲内) acc += x·w } } }`。
  **padding 域は加算せず読み飛ばす**（0 を足さないことで丸めの並びを固定 — 同ファイルの MUST）。
- `acc` は **`bias[oc]` で初期化**してから縮約に入る（bias-first）。
- 共有メモリ **不使用**。重み再利用ゼロ、x 再利用は L1/L2 頼み。
- 重み読みは `weightRead`（f32 直添字 / f16 `unpack2x16float` + `select` / i8 `unpack4xI8` +
  要素ごと scale）で、**MAC 1 回ごとに展開が走る**。
- 縮約順序 = `(ic, kh, kw)` 昇順 = **平坦 k 添字の昇順**（この事実が §5 の土台）。

### 2.2 パイプラインキー別の実測（`turbo-*-seed42.json`）

VAE decoder（1 decode ぶん、404 dispatch）:

| key                                                                          |                         1024px |                         512px |
| ---------------------------------------------------------------------------- | -----------------------------: | ----------------------------: |
| **`conv2d:v1:f32:direct:wg256:wf16`**                                        | **15.180 s（95.9%）/ 37 disp** | **1.725 s（95.5%）/ 37 disp** |
| `strided:v1:f32:r4:wg256`                                                    |                   0.303 s / 78 |                  0.040 s / 78 |
| `bmm:v2:f32:reg64x64v4`                                                      |                    0.138 s / 2 |                   0.006 s / 2 |
| `reduce:v2:sum` + `ew:mul/div/sigmoid/add/sqrt/clamp_min`（group norm 相当） |                  0.207 s / 286 |                 0.036 s / 286 |
| `softmax:v1`                                                                 |                    0.005 s / 1 |                   0.000 s / 1 |
| **VAE GPU 合計**                                                             |                   **15.833 s** |                   **1.807 s** |

参考（同 run の DiT・1 forward ぶん）: `linear:…:wi8` 4.097s / `bmm` 1.302s → ×10 step で
41.0s / 13.0s。`ditMs 63.9s + vaeMs 16.3s = totalMs 85.9s`。
**VAE 系列は 512/1024 とも重み f16**（i8 化は transformer のみ — ADR 0019）なので、
両系列の conv2d は**同一の WGSL**で比較できる。

### 2.3 効率の見積もり

|                                                            |                       1024px |      512px |
| ---------------------------------------------------------- | ---------------------------: | ---------: |
| FLOP                                                       |                    4,297.9 G |  1,074.5 G |
| 実測時間                                                   |                     15.180 s |    1.725 s |
| **実効 GFLOP/s**                                           |                      **283** |    **623** |
| 参考: **同一マシン・同一 run の DiT GEMM 実測**（§2.3 注） | **linear 3,318 / bmm 3,325** |       同左 |
| 対 GEMM 比                                                 |                     **8.5%** |      18.8% |
| 最小メモリ traffic（x + out + 重みを 1 回ずつ）            |                     11.67 GB |    2.95 GB |
| 同 traffic に必要な帯域                                    |                 **0.8 GB/s** |   1.7 GB/s |
| 素朴カーネルの x 読み総量（キャッシュ 0 と仮定）           |                      8.60 TB |    2.15 TB |
| 同上に必要な帯域                                           |                     566 GB/s | 1,246 GB/s |

> **§2.3 注 — 比較の基準線**: 同じ `turbo-i8-1024-seed42.json` の `transformer` 側で
> linear 4.097s / bmm 1.302s（1 forward）。同じ IR から MAC を数えると
> linear 6,796 G MAC = 13,592 GFLOP・bmm 2,165 G MAC = 4,329 GFLOP なので、
> **linear 3,318 GFLOP/s・bmm 3,325 GFLOP/s**。ADR 0022 の 64×64/4×4/vec4 骨格が
> **この実測マシン（RTX 3080 Ti・Deno 2.9.4 / wgpu 29.0.1 — limitations.md）で
> 実際に出している値**であり、上限見積もりはこれを使う。
> プロトタイプの 10,754 GFLOP/s は**別世代 GPU（Chrome / Blackwell）の値**なので、
> Karume の見積もりの基準にしてはならない（3.2 倍ずれる）。

読み取れること:

1. **DRAM 帯域律速ではない**。データを 1 回ずつ触れば済む量は 11.7 GB しかなく、
   実測 15.18s は 0.8 GB/s に相当する。**必要な traffic の 1000 倍近くを L1/L2 に投げている**。
2. **律速は「MAC 1 回あたりの命令数」**。1 MAC ごとに ①x の添字計算と load ②重みの
   `unpack2x16float` + `select` ③範囲検査の分岐、が走る。共有メモリもレジスタブロッキングも
   無いので、GEMM が持つ「5 ロードで 16 MAC」の密度が一切無い。
3. **512 の方が 2.2 倍効率が良い**のは L2 に載る作業集合の差（1024 は 96ch×1024×1024×4B =
   402MB/テンソルで L2 を完全に溢れる）。**解像度を上げるほど悪化する**性質で、
   1024px でこそ効く。
4. **上限の目安**: 同一マシンの GEMM 3,320 GFLOP/s にそのまま届けば 1024px で 1.29s、
   タイル量子化の無駄 +13.4%（§4.1）込みで 1.47s。conv は M が小さく（96〜1152）
   B タイル充填に gather と添字 decode が乗るぶん落ちるので、
   **現実的には 1,800〜3,000 GFLOP/s → 1.7〜3.0s（5〜9×）**と見積もる。
   512px は現在すでに 623 GFLOP/s なので伸びしろは 5.3× で、**0.4〜0.7s（2.5〜4×）**。

## 3. プロトタイプ側の conv 最適化の有無 — **無い**（確定）

- プロトタイプの conv2d は `src/kernels/indexing.ts`（プロトタイプ内） の
  `conv2dWgsl`（key `conv2d:{f32|wf16}:direct:v1`）1 本のみ。
  コメントに「**素朴実装 — 最適化は実測で必要になってから**」と明記され、
  1 スレッド = 1 出力要素・共有メモリなし・grid-stride で、Karume の現行実装と同型。
  むしろ Karume の方が広い（プロトタイプは B=1 / stride=1 / groups=1 / dilation=1 固定、
  i8 変種も未実装）。
- perf 記録にも「**VAE decode は 1.69 → 1.63 s とほぼ横ばい（conv2d が素朴実装のため）**」と
  あり、GEMM 置換の恩恵を受けない側として認識されたまま**着手されていない**。
- 設計ドキュメントに「conv 族: conv2d（im2col vs implicit GEMM）」という**検討予定の 1 行**が
  あるだけで、実装・実測・ベンチのいずれも存在しない。
- ⇒ **流用できる先行実装はゼロ**。流用できるのは GEMM 側の実測系譜（レジスタ 4×4 + vec4 =
  3.07×、8×8 はレジスタ溢れで劣化、subgroup-matrix は WebGPU に無い）だけで、
  それは既に ADR 0022 として Karume に取り込み済み。

## 4. 設計候補

前提として全候補が満たすべき制約:

- **full-write**（ADR 0014 / 0004⑤）: 出力の全バイトをちょうど 1 回書く。
- **決定性**（CLAUDE.md 横断不変条件）: 同一キー → バイト単位同一 WGSL。
- **fail loudly**: 未対応形は黙って近似せず落とす。
- 重み格納 3 変種（f32 / f16 / i8）を weight-storage.ts の 1 本で吸収する。
- ランタイム依存ゼロ・core WGSL のみ（`shader-f16` などの optional feature に依存しない）。

### 4.1 候補 (i) implicit GEMM — **推奨**

conv2d を **materialize しない GEMM** として解く:

```
C[Cout, N] = W[Cout, K] × Xcol[K, N]
  M = Cout                      … A（重み）の行
  N = B · Hout · Wout           … 出力ピクセル（NCHW の平面が連続）
  K = (Cin/groups) · Kh · Kw    … 縮約長
  Xcol[k][n] = x[b, ic, oy·sh − ph + kh·dh, ox·sw − pw + kw·dw]   （範囲外は 0）
      k → (ic, kh, kw) = (k / (Kh·Kw), (k % (Kh·Kw)) / Kw, k % Kw)
      n → (b, oy, ox)  = (n / (Hout·Wout), (n % (Hout·Wout)) / Wout, n % Wout)
```

#### 骨格の流用度

`src/kernels/gemm.ts` は 5 断片（header / bindings+loader / prologue / fillTiles / store）を
`skeleton` に差し込む形になっており、**そのまま使える部分が非常に多い**:

| 断片                                                                                                                                                              | conv2d implicit GEMM での扱い                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `skeleton` 本体（共有 `sa` 4KB + `sb` 4KB・16×16=256 スレッド・K タイル 16・`acc: array<vec4<f32>,4>`・内側の 5 ロード 16 MAC ループ・2 本の `workgroupBarrier`） | **無改造で流用**。ただし `struct Dims {m,n,k}` がハードコードなので、Dims をフラグメント化する小改修が要る                                                                                                                                                                          |
| `prologueA` / `fillA`（A タイル = `[m,k]` 行優先）                                                                                                                | **ほぼそのまま**。重み `[Cout, Cin/g, Kh, Kw]` は**平坦化すると `[M, K]` 行優先そのもの**なので reshape 不要。ただし読みは `weightRead` / `weightRead4` 経由に差し替える（現状 `fillA` は素の配列読み・`fillBLinear` の側が weight-storage 経由なので、両者を合成した新断片が要る） |
| `prologueBDense` / `fillBDense`（B タイル = `[k,n]` 行優先の vec4 読み）                                                                                          | **ここだけが新規**。`b[brow·n4 + bc4]` を x の暗黙 gather へ差し替える                                                                                                                                                                                                              |
| `store`（`c[orow·n4 + ocq]`）                                                                                                                                     | **無改造で流用**（`bias=false` 版）。M=Cout 行 × N=HW 列の行優先 = **NCHW の `[1,Cout,Hout,Wout]` そのもの**                                                                                                                                                                        |
| bias                                                                                                                                                              | `store` では足さず、**`acc[i]` の初期値を `vec4<f32>(bias[orow0+i])` にする**（= 現行の bias-first をそのまま再現。§5.3）                                                                                                                                                           |
| i8 の scale                                                                                                                                                       | 出力チャネル = **行**なので `weightScaleWgsl(weight, "arow", …)` を prologueA 側で束縛。ADR 0019 の「要素ごと dequant」は `dequant4` の `vec4 * scalar` で維持（ADR 0022 §4 と同じ）                                                                                                |

新規に書くのは実質「B タイル充填 15 行程度 + Dims + params + dispatch 計算」で、
**内積ループの正本は 1 箇所のまま**（gemm.ts の MUST を守れる）。

#### B タイル充填（新規部分）の設計

`fillBDense` の担当割り（`bk = tid/16` が k 行・`bcq = tid%16` が列 quad）を維持する。

```wgsl
let brow = t * 16u + bk;                       // K タイル内の k
var bv4 = vec4<f32>(0.0);
if (brow < dims.k && bc4 < n4) {
  // k → (ic, kh, kw)
  let khw  = dims.kernel_h * dims.kernel_w;
  let ic   = ic_base + brow / khw;             // ic_base はグループ帯（groups=1 なら 0）
  let r    = brow % khw;
  let kh   = r / dims.kernel_w;
  let kw   = r % dims.kernel_w;
  // n（quad の先頭列） → (b, oy, ox)
  let n0    = bc4 * 4u;
  let plane = dims.height_out * dims.width_out;
  let b     = n0 / plane;
  let rest  = n0 % plane;
  let oy    = rest / dims.width_out;
  let ox0   = rest % dims.width_out;
  let iy    = i32(oy * dims.stride_h) - i32(dims.padding_h) + i32(kh * dims.dilation_h);
  if (iy >= 0 && u32(iy) < dims.height_in) {
    let row_base = (b * dims.channels_in + ic) * dims.height_in * dims.width_in
                 + u32(iy) * dims.width_in;
    let ix0 = i32(ox0 * dims.stride_w) - i32(dims.padding_w) + i32(kw * dims.dilation_w);
    // v4 経路: 4 列は同じ出力行の連続 ox なので x 側も連続（stride_w == 1 が条件）
    if (ix0 >= 0 && u32(ix0 + 3) < dims.width_in) {
      bv4 = vec4<f32>(x[row_base + u32(ix0)],     x[row_base + u32(ix0) + 1u],
                      x[row_base + u32(ix0) + 2u], x[row_base + u32(ix0) + 3u]);
    } else {
      // 行端の 2 quad だけがここに来る。範囲外は **0 を書く**（クランプ読みは厳禁）
      … 成分ごとに境界検査 …
    }
  }
}
sb[bk * 16u + bcq] = bv4;
```

MUST になる点:

- **範囲外は 0 を書く。決してクランプした添字で読まない**（読むと実在する別ピクセルの値が
  混入し、例外なしの誤値になる）。
- **`bc4 < n4` の門を通ってから decode する**。門の外で `n0 / plane` を計算しても害は無いが、
  x を読むのは必ず門の内側。
- **4 列が同じ出力行に収まる条件は `Wout % 4 == 0`**。`N % 4 == 0`（= B·Hout·Wout）では
  **不十分**（例: Hout=Wout=2 → N=4 は N%4==0 だが quad が行をまたぐ）。
  → v4 判定は必ず `Wout % 4` で書く。**これは実測形（Wout はすべて 4 の倍数）では絶対に
  露見しない取り違え**なので、検出器を先に用意する（§6）。

#### vec4 化の条件

```ts
conv2dUsesVec4 = (kFlat % 4 === 0) && // A 側: 重みの quad 読み（f16 の dequant4 は平坦添字 %4 前提）
  (widthOut % 4 === 0) && // B 側: quad が出力行をまたがない ＋ store 側の n%4
  (strideW === 1); // B 側: 4 列の x アドレスが連続
```

- `kFlat = (Cin/groups)·Kh·Kw`。**`Cin % 4` ではない** — 例えば Cin=2, K=3×3 なら kFlat=18 で
  条件を満たさない。census では 14 形状すべて成立（144〜3456）。
- 条件を外れた形は **同じレジスタ構造のスカラ変種**へ落ちる（ADR 0022 決定 2 と同じ語彙）。
  キーが形状の関数になるが、形状 → 1 ビットの写像なので決定性は崩れない。
- f16 の `dequant4` は「平坦添字が 4 の倍数」に依存する。行頭 = `arow · kFlat` なので
  `kFlat % 4 == 0` がその十分条件（ADR 0022 決定 4 と同じ議論）。i8 の `unpack4xI8` も同じ。
- f32 の quad は重みバッファを `array<vec4<f32>>` で束縛する（`weightArrayType(f32, true)`）。
  既に linear v4 で実績がある経路。

#### groups の扱い

64 行の m タイルが**複数グループにまたがると、同じ B タイルを共有できない**
（行ごとに読むべき ic 帯が違う）。census では groups>1 の conv2d は 0 本なので:

- **implicit GEMM は `groups == 1` 専用**とし、**`groups > 1` は現行の直接カーネルを残して
  そちらへ流す**。キーで踏み分ける。
- 副産物として、**直接カーネルが恒久的な差分オラクル**になる（§6 の A/B ビット比較）。
- 将来 groups>1 が要るときの拡張余地: m タイルをグループ内に閉じ込める
  （`wid.y` を `(group, group 内 m タイル)` に分解し、dispatch は `ceil((Cout/g)/64) · g`）。
  depthwise（Cout/g = 1）では 64 行中 1 行しか使わず 98% が無駄になるので、
  **その時は専用カーネルを別に立てる**のが正しい。

#### dispatch とタイル幾何

`workgroups = [ceil(N/64), ceil(M/64), 1]`、`tiledWorkgroups` で **上限超過は fail loudly**
（grid-stride 縮退は禁止 — タイルが欠落して full-write が黙って壊れる。gemm.ts の MUST と同じ）。

1024 系列の実際の値（M 無駄 = `ceil(M/64)·64 / M`）:

| M(=Cout) |         N |     K | m タイル | n タイル |  総 WG | K タイル数 |    M 無駄 | MAC 比 |
| -------: | --------: | ----: | -------: | -------: | -----: | ---------: | --------: | -----: |
|      192 |   262,144 | 1,728 |        3 |    4,096 | 12,288 |        108 |      1.00 |  24.3% |
|       96 | 1,048,576 |   864 |        2 |   16,384 | 32,768 |         54 |  **1.33** |  24.3% |
|      384 |    65,536 | 3,456 |        6 |    1,024 |  6,144 |        216 |      1.00 |  20.2% |
|      384 |    16,384 | 3,456 |        6 |      256 |  1,536 |        216 |      1.00 |  10.1% |
|     1152 |    16,384 |   384 |       18 |      256 |  4,608 |         24 |      1.00 |   0.3% |
|        3 | 1,048,576 |   864 |        1 |   16,384 | 16,384 |         54 | **21.33** |   0.1% |
|       16 |    16,384 |    16 |        1 |      256 |    256 |          1 |  **4.00** |   0.0% |

- **タイル量子化の無駄は合計 +13.4%**（実 MAC 2,149.0G → 実効 2,436.2G）。512 系列も同率。
  内訳は Cout=96 の 6+1 本（+231.9G）と Cout=3 の 1 本（+55.2G）でほぼ全部。
- **n タイル最大 16,384 ≪ 65,535** で余裕。ただし **2048px では n = 4,194,304 → 65,536 で
  上限 65,535 を 1 だけ超える**。fail loudly になるので沈黙誤値にはならないが、
  動的解像度 recon の「③固定タイル VAE」を採るなら実質問題にならない（要記録）。
- 共有メモリは GEMM と同じ 8,192 B/WG。occupancy も同じ。
- K は全形状で 16 の倍数（端数 0 埋めが 1 度も発動しない = **K 端数経路の検出器が実 E2E に
  無い**。ADR 0022 の「検出限界①」と同型なので、ユニットテストで端数 K を必ず 1 本持つ）。

#### 期待性能

- 共有メモリ帯域あたりの演算密度は GEMM と**同一**（5 ロード 16 MAC）。
- グローバル側は、x が k 方向（ic·kh·kw）に 9 回重複して読まれるが、
  同じ出力行の ±1 行 ±1 列なので L1 に完全に載る。重みは 1 層あたり最大 2.6 MB（f16）で L2 常駐。
- 見積もり **1,800〜3,000 GFLOP/s → 1024px で 1.7〜3.0s（5〜9×）**（タイル無駄 +13.4% 込み）。
  同一マシンの linear/bmm が 3,320 GFLOP/s なので、その 55〜90% に届くかが判定点。
  下限を割ったら M=96 用の 32 行タイル変種を検討する（§4.2 の利点はそこで効く）。

### 4.2 候補 (ii) 共有メモリ直接タイル（入力タイル + halo 共有）

1 workgroup が出力の `(TC 出力チャネル) × (TH × TW ピクセル)` を担当し、
入力タイル `(TH + (Kh−1)·dh) × (TW + (Kw−1)·dw)` を halo 込みで共有メモリに載せ、
重みも共有に載せ、1 スレッドが `4 チャネル × 4 ピクセル` のレジスタブロックを持つ。

- **縮約順序**: `ic → kh → kw` の三重ループを維持すれば現行と一致させられる（可能）。
- **共有メモリ**: TH=TW=16, Kh=Kw=3 なら入力タイル 18×18×4B = 1.3 KB/ic、
  重み TC=16 なら 16×9×4B = 0.6 KB。`ic` を数チャネルずつ回す構造なら十分収まる。
- **演算密度**: 1 スレッドが 4ch × 4pix を持つと、(kh,kw) の 1 ステップで
  共有ロード 4（x）+ 4（w）= 8 に対し 16 MAC。**2 MAC/ロード**で、
  GEMM の 3.2 MAC/ロード（16 MAC / 5 ロード）に劣る。
- **利点**: M タイル量子化の無駄が無い（TC=16 なら Cout=96 も 16 も端数ゼロ）。
  halo の再利用が L1 頼みでなく共有メモリで明示される。
- **欠点（採らない理由）**:
  1. **内積ループの正本が 2 本になる**。gemm.ts の MUST「縮約順序の正本 1 箇所化」が
     conv2d では効かなくなり、「GEMM 3 op と conv2d の縮約順序が同じ」を機械的に守れない。
  2. 生成パラメータが多い（TH / TW / TC / halo / 端タイル / stride / dilation の組合せ）。
     codegen の分岐と故障注入の面積が (i) の数倍になる。
  3. 端タイル（画像端・チャネル端）の処理が (i) の `store` ガード 1 本より遥かに複雑で、
     **full-write を壊す形の誤りが入りやすい**。
- **位置づけ**: (i) が期待を下回った場合の次点。特に Cout=96 のタイル無駄が実測で効いていた
  場合の第 1 候補。

### 4.3 候補 (iii) im2col 実体化 — **却下**

Xcol を実バッファに書き出してから既存 GEMM を呼ぶ。

- **単一バッファサイズが致命的**: Cout=96 層（1024px）は
  `K × N × 4B = 864 × 1,048,576 × 4 = 3.62 GB`。384ch/256² 層でも 906 MB。
  WebGPU 仕様の `maxStorageBufferBindingSize` 既定は 128 MiB で、
  アダプタ申告値もプロトタイプ実測（Chrome）で **2,147,483,644 B = 2 GiB**。
  Karume はアダプタ値を要求する（`src/gpu/device.ts`）が、
  **3.62 GB は一般的な 2 GiB 上限を超える**。
  ※ 本機（RTX 3080 Ti / wgpu）の実申告値は本 recon では未確認 — 断定はしない。
- 総確保の天井 **7,280 MiB**（limitations.md）とも真っ向から衝突する
  （重み + 活性が既に載っている上に 3.62 GB を要求することになる）。
- n 方向にチャンク分割すれば収まるが、**その形は (i) の implicit GEMM を
  「余計な往復書き込み付きで」やっているのと同じ**。追加 traffic は全層合計で
  書き 45 GB + 読み 45 GB ≈ 90 GB（1024px）で、時間としては 0.1s 級なので致命的ではないが、
  IR に無い中間バッファをアリーナ／プールに持ち込む設計変更が必要になる。
- **利点がゼロではない点**: 「im2col + 既存 GEMM」は (i) の**独立実装オラクル**として
  価値がある。ただし CPU 参照実装（`src/reference/ops.ts` の conv2d）が既に同じ役割を
  果たしているので、**わざわざ作る必要は無い**。

### 4.4 候補 (iv) Winograd — **却下（理由付き）**

3×3 stride=1 dilation=1 に対し F(2×2,3×3) で MAC 2.25×削減、F(4×4,3×3) で 4×削減。
census の 34/37 ノード（MAC の 99.5%）が適用条件を満たすので、**適用範囲だけは理想的**。

却下理由:

1. **算術そのものが変わる**。並べ替えではなく別のアルゴリズムなので、
   ADR 0022 決定 3 の「縮約順序を変える変種は tolerance 再導出とセット」を超えて、
   VAE golden（atol 8e-5 / f16 1e-4 / 1024 1.2e-4）・段③（4e-5 / 5e-5）・turbo 画像（2e-1）を
   **全部採り直す**ことになる。さらに **PNG sha256 ビット一致という最強の回帰検出器を
   恒久的に失う**（ADR 0022 が確立した受け入れゲートが使えなくなる）。
   F(4,3) は f32 で 1〜2 桁の精度低下が知られており、10 step の反復累積
   （実測 1.75×/step）と組むと影響が読めない。
2. **重み格納の設計と衝突する**。変換済み重み `G g Gᵀ` は (Kh+m−1)² = 16 要素/(Cout,Cin) で
   元の 9 要素比 16/9 に膨らみ、しかも f32 でしか持てない。
   ADR 0018/0019 の「重みスロットは f16/i8 のまま GPU 常駐」が丸ごと崩れ、
   ロード時変換パスという新しいライフサイクルが要る。
3. **費用対効果**。ベースラインが**同一マシンの同一骨格 GEMM の 8.5%** という段階で、
   まず (i) が算術を一切変えずに 5〜9× を取れる。Winograd の上積みは
   (i) が演算律速になって初めて意味を持つ（現状その状態にすら達していない）。
4. 4 カーネル（入力変換 / 重み変換 / バッチ GEMM / 出力変換）または 1 本の巨大融合が要り、
   codegen 決定性・full-write・故障注入の面積が (i) の数倍。

**再検討の条件**: (i) 実装後に conv2d が明確に演算律速（実効 6,000 GFLOP/s 以上）へ達し、
かつ VAE が依然ボトルネックである場合のみ。

## 5. 推奨案の横断論点

### 5.1 パイプラインキーと変種

```
conv2d:v2:f32:igemm64x64[v4]:wg16x16{:wf16|:wi8}   … groups == 1
conv2d:v1:f32:direct:wg256{:wf16|:wi8}             … groups > 1（現行のまま・キー据え置き）
```

- 変種数は igemm 側 **3 格納 × 2（v4/スカラ）= 6 本**。WGSL スナップショット
  （`tests/fixtures/wgsl/`）を 6 本追加する。
- 直接カーネルのキーは **v1 のまま動かさない**（生成バイト列を 1 バイトも変えない）。
  weight-storage の `quad` 既定 false がこれを担保する（ADR 0022 決定 4 の不変条件を継続）。
- 決定性: v4 ビットは形状 → 1 ビットの写像。「同一キー ⇔ 同一 WGSL バイト列」は保たれる。

### 5.2 full-write と tiledWorkgroups

- igemm は **1 workgroup = 1 出力タイル**で、`ceil(M/64) × ceil(N/64)` が出力全域を
  ちょうど 1 回ずつ覆う。**grid-stride 縮退は禁止** — `tiledWorkgroups` で fail loudly。
- したがって conv2d の igemm 変種は **`tests/gpu_gridstride_test.ts` の対象外**
  （GEMM と同じカテゴリ判断）。ただし **直接カーネルは groups>1 用に残るので、
  現行の conv2d 縮退ケースはそのまま維持する**（削除しない）。
- **`tests/gpu_full_write_test.ts` に igemm 変種を追加**（毒値注入）。既存の conv2d ケース 1 本を
  6 変種へ拡張する。タイル系カーネルの安全網はここと `tiledWorkgroups` の 2 本しかない。

### 5.3 縮約順序・tolerance・ビット一致

**主張: implicit GEMM は現行カーネルと縮約順序が厳密に一致し、tolerance は 1 つも動かない。**

根拠を 4 点に分解する:

1. **k の走査順**: 現行は `ic → kh → kw` の三重昇順 = 平坦 k 添字の昇順。
   igemm は K タイル `t` 昇順 × タイル内 `kk` 昇順 = 同じく平坦 k 昇順。**一致**。
2. **bias の位置**: 現行は `acc = bias[oc]` から始める。igemm も `acc[i]` を
   `vec4<f32>(bias[orow0 + i])` で初期化すれば**同じ位置**（GEMM の「最後に足す」形は使わない）。
   M=Cout が**行**なので bias は行ごとのスカラ splat になり、これが成立する。
   ※ この一点を GEMM の `store` から流用してしまうと `(Σ) + bias` になり、
   丸めが変わって tolerance 議論が全部やり直しになる。**最重要の設計上の分岐点**。
3. **padding の扱い**: 現行は「加算せずに読み飛ばす」、igemm は「0 を掛けて足す」。
   IEEE754 で `a + 0.0 == a`（`a` が有限なら）なので値は同一。
4. **K タイル端数の 0 埋め**: 同上（census では K が全部 16 の倍数なので実 E2E では発生しない）。

**唯一の差分（明示すべき caveat）**: **符号付きゼロ**。
部分和がちょうど `−0.0` の瞬間に padding 由来の `+0.0` を足すと `+0.0` に転ぶ
（`−0.0 + 0.0 = +0.0`）。現行は足さないので `−0.0` のまま残る。

- 実害の評価: 出力が厳密に 0 になる要素でのみ起こる。bias が 0 でない限り到達しない。
- 既存のゲートは壊れない: `allclose` は `|−0 − 0| = 0`、PNG は u8 量子化後なので同一。
- **ただし「ビット一致」と書くときは "符号付きゼロを除き" を明記する**（言い切ると嘘になる）。

**受け入れゲート（ADR 0022 の前例をそのまま踏襲）**:

- Anima デモの PNG sha256 が **512px/wf16 と 1024px/wi8 の 2 系列とも置換前と一致**。
- 全 E2E の atol=rtol=0 実測 maxAbs が記録値と一致（tolerance 無変更）。

### 5.4 重み格納変種との合成

|     | A タイル充填での読み                                                                     | 条件                                                 |
| --- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| f32 | v4: `w[(idx)>>2]`（`array<vec4<f32>>` 束縛） / スカラ: `w[idx]`                          | v4 は kFlat%4==0                                     |
| f16 | v4: `dequant4(idx)` = `unpack2x16float` 2 語 / スカラ: `dequant(idx)` の偶奇選択         | v4 は **平坦添字が 4 の倍数** ⇐ kFlat%4==0           |
| i8  | v4: `dequant4(idx, wscale_v)` = `vec4<f32>(unpack4xI8(w))·s` / スカラ: `dequant(idx, s)` | 同上。scale は **行（出力チャネル = `arow`）**で束縛 |

- i8 の scale 軸は conv2d では **0（出力チャネル）**（ADR 0019）。implicit GEMM では
  行 = 出力チャネルなので `weightScaleWgsl(weight, "arow", …)` を prologue で 1 度だけ束縛する。
  **`wcol`（linear 側の名前）をそのまま持ってくると列＝ピクセルの scale を引くという
  沈黙誤値になる** — ADR 0022 の「検出限界③」と同型の罠なので、
  **m タイルが 2 枚以上ある形**のテストが唯一の検出器。
- 「scale は要素ごと dequant」（GPU / CPU 展開のビット一致）は `vec4 * scalar` で維持される
  （ADR 0019 の改訂は不要 — ADR 0022 決定 4 と同じ結論）。
- VAE decoder は現在 f32 / f16 の 2 系列しか実測が無い（i8 は transformer のみ）。
  **i8 の conv2d は unit テストのみが検出器**である点を記録しておく
  （ADR 0022 の「カバレッジの穴」と同型）。

### 5.5 隣接（本タスクの範囲外・報告のみ）

conv2d が 7× 速くなると 1024px VAE の内訳は次のように変わる（推定）:

|                                                                   |     現在 | conv2d 7× 後（推定） |    比率 |
| ----------------------------------------------------------------- | -------: | -------------------: | ------: |
| conv2d                                                            | 15.180 s |               ~2.2 s |     77% |
| `strided`（permute 78 disp）                                      |  0.303 s |              0.303 s | **11%** |
| group norm 相当（reduce+mul+div+sigmoid+sqrt+clamp_min 286 disp） |  0.207 s |              0.207 s |      7% |
| bmm / softmax                                                     |  0.143 s |              0.143 s |      5% |

- **`strided` が次のボトルネック**になる（ADR 0011 のレイアウト実行最適化が VAE 側でも効く）。
- group_norm 融合 op（現在 6 op に分解されている）も候補。ADR「カスタムカーネル機構 = C 案
  （ランタイム内蔵の融合 op を足す）」の裁定に素直に乗る形。
- どちらも本設計のスコープ外。次タスク候補として起票を推奨。

**計測の穴（記録）**: ADR 0021 の診断は**パイプラインキー単位の集計**なので、
37 ノードの内訳は取れない。形状別の実測が要るなら「キーに形状判別子を一時的に足す」か
「1 形状だけのマイクログラフを回す」しかない。本設計の見積もりは
**IR からの机上 MAC 集計**（§1.2）に依っており、この点は実測ではない。

## 6. 検証計画（実装波に渡す前提）

段はプロジェクトの既存規律に合わせる。

1. **CPU 参照との単体一致**（`tests/gpu_ops_test.ts`）— 非対称形を必ず含む:
   - `Cin ≠ Cout`・`Kh ≠ Kw`・`stride` / `padding` / `dilation` の H≠W
   - **`kFlat % 4 ≠ 0`**（スカラ変種を踏む。例 Cin=2, K=3×3 → 18）
   - **`K % 16 ≠ 0`**（K タイル端数 0 埋めを踏む。実 E2E では 1 度も踏まない）
   - **`Wout % 4 ≠ 0` かつ `N % 4 == 0`**（例: B=1, Hout=2, Wout=2）
     — §4.1 の判定取り違えの唯一の検出器
   - **m タイル 2 枚以上（Cout ≥ 65）× i8**（scale 軸取り違えの唯一の検出器）
   - `groups > 1`（直接カーネル側へ流れることの確認）
2. **A/B ビット比較（新設・恒久）**: 同一入力に対し直接カーネルと igemm を両方走らせ
   **atol=rtol=0 で一致**を確かめる。直接カーネルが groups>1 用に残るので、
   これは「捨てる予定の比較」ではなく**恒久的な差分オラクル**になる。
   符号付きゼロだけは `−0.0 == +0.0` として扱う（§5.3 の caveat をテストのコメントに明記）。
3. **WGSL スナップショット** 6 本（決定性の固定）。既存 4 op の生成物が
   1 バイトも動かないことを既存 fixture が引き続き検出する。
4. **full-write 毒値注入** を igemm 6 変種へ拡張（`tests/gpu_full_write_test.ts`）。
5. **`tiledWorkgroups` の fail loudly**（`tests/codegen_dispatch_test.ts`）— n タイルが
   上限を超える形で例外が出ること。
6. **故障注入（最低 8 件・赤→復元を実測）**:
   ① v4 判定を `N%4` で書く（quad が行をまたぐ）
   ② 範囲外 x をクランプ添字で読む（0 を書かない）
   ③ `k → (kh, kw)` の Kh/Kw 取り違え
   ④ bias を `store` 側で足す（丸めが変わる — 検出器は A/B ビット比較のみ）
   ⑤ i8 scale を `arow` でなく列で引く
   ⑥ f16 `dequant4` の 2 語目オフセット
   ⑦ `iy` の境界検査を `<=` にする
   ⑧ n タイル端の `bc4 < n4` ガード欠落
7. **E2E**: Anima VAE golden（512 f32 / 512 f16 / 1024 f16 / 1024 i8）+ 通しチェーン段③。
8. **受け入れゲート**: PNG sha256 の 2 系列一致（§5.3）+ 全 E2E の atol=0 実測 maxAbs 不変。
9. **性能実測**: `gpuTimingByGraph` の conv2d キーで前後比較。
   **熱状態を揃えるか ms×MHz で正規化**する（recon の「per-step 時間の伸び = GPU クロック低下」）。

## 7. 期待値と工数の見立て

|                                   |    現在 |                                   推奨案の期待 |
| --------------------------------- | ------: | ---------------------------------------------: |
| conv2d GPU 時間（1024px）         | 15.18 s |                        **1.7〜3.0 s（5〜9×）** |
| VAE 壁時計（1024px）              | 16.26 s |                                     2.5〜3.8 s |
| 総壁時計（1024px・turbo 10 step） |  85.9 s |                       **73〜74 s（−14〜15%）** |
| conv2d GPU 時間（512px）          |  1.73 s |                                     0.4〜0.7 s |
| 総壁時計（512px）                 |  26.1 s |                                   25.0〜25.3 s |
| 実効 GFLOP/s（1024px）            |     283 | 1,800〜3,000（同一マシンの GEMM 実測は 3,320） |

- 工数感: **M**（gemm.ts の Dims フラグメント化 + conv2d 側の新規 2 断片 + params/dispatch +
  テスト一式）。ADR 0022 が敷いた道の上を歩くので、設計の未知は B タイル充填の
  境界処理に集中している。
- **順序の材料**: 1024px の壁時計内訳は DiT 74% / VAE 19%。
  conv2d 単独の上限効果は −15% で、DiT 側（融合 attention / DP4a）より小さい。
  一方で **512px では −4% にしかならない**ので、この作業の価値は 1024px 以上の解像度に強く
  依存する。順序は主に「1024px を主戦場と見るか」で決まる。

## 8. 要判断（メイン裁定・閉じた選択肢）

1. **`groups > 1` の扱い** —
   (a) implicit GEMM は groups==1 専用とし、**直接カーネルを残して groups>1 を流す**
   （＝ 2 系統・直接カーネルが恒久の差分オラクルになる）**［推奨］** /
   (b) igemm にグループ別 m タイルを入れて 1 系統に畳む（depthwise で 98% 無駄・実測需要ゼロ） /
   (c) groups>1 を fail loudly（機能後退なので不可）。
2. **`gemm.ts` の骨格に 4 番目の消費者を入れるか** —
   (a) `skeleton` の `struct Dims` をフラグメント化して **conv2d と共有**（内積ループの正本が
   1 箇所のまま）**［推奨］** /
   (b) conv2d 側へ骨格を写経（縮約順序の正本が 2 箇所に割れる — gemm.ts の MUST に反する）。
3. **受け入れゲート** —
   (a) **PNG sha256 の 2 系列ビット一致を必須**にする（ADR 0022 の前例。§5.3 の
   「符号付きゼロを除く」を doc に明記）**［推奨］** /
   (b) tolerance 内一致で可とする（−0.0 の議論を回避できるが、検出力が大きく落ちる）。
4. **小 Cout（96 / 3 / 16）の M タイル量子化 +13.4%** —
   (a) 初手は 64 行タイル一本で実装し、**実測してから**判断**［推奨］** /
   (b) 最初から 32 行タイル変種（または候補 (ii)）を併走させる。
5. **着手順** — perf-a（融合 attention・DiT 74%）と perf-b（conv2d・VAE 19%）のどちらを先に。
   1024px 主戦場なら a → b、VAE 単体デコードの体感（decode だけ回すユースケース）を
   重く見るなら b 先行。

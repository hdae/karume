> 採否と復活条件の台帳は [perf-ledger](../perf-ledger.md) K-20、前回の採算実測（E-0〜E-3・BF16 target の
> E[a]）は [research 2026-09-07 §7](2026-09-07-codex-perf-review-followup.md)。生データと台本の写しは

## 0. 目的と結論

MTP（公式 drafter による投機的デコード — perf-ledger K-20）の復活条件 ③「i4 target で受理数 E[a] を再実測し、
長文脈の抽出的要約で E[a] ≥ 2 が立つか」を測った。E-1 は BF16 target 上の値で、i4 と BF16 の次 token 一致率が
75〜84% だったことから「i4 target では E[a] がさらに下がる」と見ていた。

- **i4 target の代理**（karume の i4 配布と同値の重み + f32 演算）は、karume が実際に出した token 列と
  **7 条件・1,319 位置すべてで argmax が一致**した（§2）。以下の E[a] は karume の挙動そのものと読んでよい。
- **復活条件 ③ は成立**: 抽出的な長文脈 3 条件（4.4K / 7.6K / 14.9K token・逐語列挙）で
  **k=3 で 2.26〜2.55・k=6 で 3.83〜5.03・k=8 で 4.38〜5.63**（§3）。抽象的要約は 1.5〜2.2、自由文 0.6、
  対話 2 ターン目 0.8〜0.95。
- **i4 で下がる、は外れ**: 同じ演算精度で BF16 重みと並べると同等（k=3 で c2 2.46 vs 2.55・d 2.55 vs 2.41・
  e 2.26 vs 2.44 — 差は ±0.2 で条件により上下）。E-1 の一致率 75〜84% は「i4 と BF16 が別の道に入る」ことを示していただけで、drafter に
  とっての当てやすさは道が変わっても変わらない。
- **演算精度の影響**: f32 では 84 record すべてで投機ありの出力が非投機 greedy と一致（E-1 §4 の「M 行まとめ
  の argmax 反転」は bf16 の産物）。bf16 演算では e の k=2〜4 で 8 token 目に EOS が立って生成が終わる事故が
  出た。karume の verify は M 行でも M=1 と u32 完全一致なので f32 側の挙動に当たる。
- **採算式の更新**（§4 — K-21 / H-15 後の T(M)・E-3 の未最適化 D）: 抽出的な長文脈で **Deno 1.8〜2.6× /
  ブラウザ相当 1.9〜2.4×**（k=3〜8）、抽象的要約 1.2〜1.5×、自由文は k ≤ 3 で 0.9〜1.0×・k=8 で 0.6×。
  k は条件で最適が動く（自由文は小さく・抽出は大きく）。**次 = ④ 設計**（perf-ledger K-20）。

## 1. 方法

### 1.1 i4 target の代理（torch 上に karume と同値の重みを組む）

karume の i4 配布（`models/karume-gemma4` e2b — linear を group 32 の int4・埋め込み表を int8）は
shard の tensor 名がハッシュなので HF のパラメタ名へ機械的に写せない。代わりに exporter が export の
**前**に torch 上で掛ける丸め（fake-quant — `tools/exporter/src/karume/quantize.py`）を、HF の
`Gemma4ForConditionalGeneration` へ gemma4 recipe（`tools/export-recipes/gemma4/export.py`
`quantize_wrapper`）と**同じ対象・同じ順序**で掛けた。格納の逆変換がこの丸め値とビット一致する保証は
ADR [0069](../decisions/0069-packed-w4-storage.md) 決定 4。

| recipe（ラッパの FQN）                             | 丸め                                     | HF 側の対応                                                                |
| -------------------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------- |
| `model.model.embed_tokens`                         | i8（token 行ごと・1536 要素で amax/127） | `model.language_model.embed_tokens`                                        |
| `per_layer.0 … 34`（PLE を 35 表 [V, 256] へ割る） | i8（行ごと・256 要素）                   | `embed_tokens_per_layer` [V, 8960] を `[V·35, 256]` の view に畳んで行ごと |
| `nn.Linear` 全部（tied `lm_head` を除く）          | i4 g32（scale = group の amax/7）        | `model.language_model.*` の nn.Linear 276 本（1,876,819,968 要素）         |

丸めの同値性は毎 run 機械検証して raw に焼いた（11 項目 — probe 7 本の linear と埋め込み 8 行 × (主 + PLE 35 表)
を丸め前のコピーから exporter の関数で再計算して `torch.equal`・対象本数と要素数を config から解析的に組んだ
期待値と突合・tied 実体が i4 対象に混ざっていないことを storage で検査・i8 の行数計測・置き場）。

置き場: f32 の PLE（9.4 GB）は VRAM に載らないので CPU に置き、text 本体と主 embedding（= tied `lm_head`）を
GPU へ（重み 8.5 GB）。vision / audio 塔は text 生成で使わないので外した。TF32 は切った（karume は f32 演算）。

### 1.2 軸 — 重み × 演算精度

| 札             | 重み                 | 演算 | 意味                                                                                                                                                                                                |
| -------------- | -------------------- | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bf16-bf16`    | 配布 BF16 checkpoint | bf16 | E-1 と同じ対照                                                                                                                                                                                      |
| `i4proxy-bf16` | 上の丸め             | bf16 | i4 重みの効果（対照と同じ演算精度）。ただし bf16 化で重みが第 2 の丸めを受ける（i4 の格納値 `q·s` は bf16 で表せない — 1 LSB の 2%・i8 埋め込みは 35〜42%・`embed_scale = √1536` が 39.19 → 39.25） |
| `i4proxy-fp32` | 上の丸め             | f32  | karume に最も近い形（重み同値・f32 演算）。**本命**。長文脈は活性が 12 GB に載らない（d は MLP・e は PLE projection で OOM）ので prefill を分割した（§1.5）                                         |
| `bf16-fp32`    | 配布 BF16 checkpoint | f32  | 演算精度の効果を切り分けるための対照（同じく分割 prefill）                                                                                                                                          |

### 1.3 ワークロード（7 条件・greedy・200 token・drafter は配布どおり）

| 条件 | P（token） | 文書                 | 指示                            | 性格                                                                 |
| ---- | ---------: | -------------------- | ------------------------------- | -------------------------------------------------------------------- |
| a    |         33 | —                    | 300 語の創作                    | 自由文（E-1 と同一）                                                 |
| b    |        461 | —                    | a の続き（要約 + 語彙）         | 対話 2 ターン目（E-1 と同一・1 ターン目の返答も E-1 のものを再利用） |
| c    |      4,414 | README 3 本          | 10 項目の要約                   | 長文脈・抽象的（E-1 と同一）                                         |
| c2   |      4,419 | README 3 本          | shell コマンドを逐語で列挙      | 長文脈・抽出的                                                       |

centroid 疎 softmax（`ordered`）だけ（E-1 で `plain` と受理数が全条件同一）。受理数の記録は E-1 と同じフック
（`update_candidate_strategy` — transformers 5.14.1 `generation/utils.py:3819`）。karume 側は同じ会話を
`gemma4ChatPrompt` でトークナイズし（HF の chat template と token 単位で同一）、capacity 16384 で greedy 生成。

### 1.4 代理の妥当性の測り方

karume（実資産・Deno・WebGPU）が実際に出した「prompt + 生成列」を各 target へ teacher forcing（prompt を 2048 token
ずつ KV cache へ流してから生成列を流す — 全長 1 回 forward と argmax 列が一致することを確認済み）し、各位置で
target の argmax が karume の選んだ token と一致する率を数える（E-1 probe3 と同じ測り方）。

### 1.5 f32 の長文脈 — prefill の分割

HF の `generate` は prompt 全長を 1 回の forward に流すので、f32 では 7.6K token から活性（MLP と PLE projection の
中間）が 12 GB に載らない。「prefill 済み cache を `generate` に渡す」形は assisted generation では成立しない
（`_assisted_decoding` が 1 周目に全長を流し直して cache が二重に伸びる — 実測で棄却）ので、target の forward を
instance で包み、長い入力を同じ cache へ 2048 token ずつ流す形にした（logits・cache・共有 KV は最後の chunk の
ものが全長ぶん・drafter が読む最終層 hidden だけ chunk を跨いで連結）。全長 1 回で載る a / b / c / c2 で、
基準 greedy の token 列・投機の token 列・ラウンドごとの受理数列が分割の有無で**完全一致**することを確かめた
（4 条件 × 6 k + 基準 4 本）。7.6K / 14.9K の 3 条件は全長 1 回の参照が原理的に無いので、同値は 4.4K までの
実測からの外挿（teacher forcing の分割が 15K で全長と一致することが傍証）。ピークは 10.29 GB。

- E[a] は「1 ラウンドで受理された draft 数の平均」。1 ラウンドで進む token 数は E[a]+1。
- 抽出的な条件（c2 / d / e）は k を伸ばすほど伸び続け（位置 1 の受理率 0.88〜0.97）、抽象的要約（c / e2）は

## 4. 採算式の更新

予測倍率 = (E[a] + 1)·T(1) / (T(k+1) + D(k))（E-0 の式 — T と D の壁はフェンス床 F を含む）。入力は K-21 / H-15 後の
実測から組む（[research 2026-09-07-gemv-rows-k21](2026-09-07-gemv-rows-k21.md) §8.2・[E-2 / E-3](2026-09-07-codex-perf-review-followup.md)）:

| 量                         | 値（P ≈ 14.7K〜16K）                   | 出どころ                                                                        |
| -------------------------- | -------------------------------------- | ------------------------------------------------------------------------------- |
| T(1) GPU                   | 21.5 ms                                | E-2 §7.2                                                                        |
| T(M) GPU（M = 4 / 8 / 16） | 27.6 / 37.2 / 38.6 ms                  | E-2 の GPU から A の linear を引き K-21 後の linear（10.9 / 12.9 / 19.0）を足す |
| D(k) GPU                   | 2.73 ms × k                            | E-3 §7.3（P=16K・未最適化 — attention の skinny GEMM 50%・argmax 19%）          |
| F（フェンス床）            | Deno 12 ms / ブラウザ相当 0.5 ms       | E-0                                                                             |
| verify の行数              | k+1 を測った M（4 / 8 / 16）へ切り上げ | M=2〜8 の linear は同じ・M=8 は谷の底                                           |

- 自由文は k=2 で 0.9〜1.0×（損も得もない）・k を伸ばすと損。抽出は k=6〜8 で最良。**k は条件で最適が動く**
  ので、実装では k を動的に選ぶ（受理率の移動平均で k を上下する — transformers の
  `num_assistant_tokens_schedule="heuristic"` 相当）のが筋。
- D は未最適化の値。attention の skinny GEMM（D の 50%）と argmax（19%）を詰めれば分母の 2.73·k が縮む
  （例: 半減で c2 k=8 が Deno 2.30× → 2.6×）。

## 5. 測っていないもの（境界）

- **karume 上で drafter を回した受理数**（真の i4 target）— drafter の移植が ④ の実装そのもの。ここでは
  「重み同値 + f32」の代理で全位置 argmax 一致を確かめたうえでの値。karume の verify（M 行の GEMV 行ブロック）は
  M=1 と u32 完全一致なので、HF bf16 で見えた「M 行まとめの argmax 反転」（E-1 §4・本実験の `i4proxy-bf16` e
  k=2〜4 で 8 token 目に EOS が立った例）は karume では起きない見込み。
- **sampling（temperature > 0）の受理率** — greedy のみ。配布既定の sampler（temperature 1・top-k 64・top-p 0.95）
  では drafter と target の乱数列が別なので greedy より下がる（参照実装の注記）。
- **drafter の時間 D の最適化後の値** — 採算表の D は E-3 の未最適化値（attention の skinny GEMM 50%・argmax 19%）。
- **k > 8 と、条件ごとに k を変える運用** — E[a] は抽出的条件で k=8 まで伸び続けているので、k の上限は
  T(k+1) と D(k) との釣り合いで決まる（採算表）。
- **Metal / ブラウザ実機の T(M)・D** — 採算表のブラウザ側は F だけ差し替えた見込み。

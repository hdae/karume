## §1 何を決めるための実測か

anima の既定 quant `w8a8-s16` は **linear の i8a8**（`linearCompute`）を使う。i8a8 経路の述語は
**i8 常駐を必要条件に含む**ので（`packages/runtime/src/runtime/recipe-builder.ts` —
`linearCompute === "i8a8" && weightStorage === "i8" && …`）、i4 常駐の linear は fail loudly
せず通常の f32 計算経路へ流れる。attention 側の 2 ノブ（`attentionCompute` /
`attentionScoreStorage`）は重みスロットを見ないので i4 でもそのまま効く。

したがって i4 席は「**取得量を減らす代わりに linear の i8a8 を失う**」形になる。**その損得の
実測**が本記録の目的で、既定を動かすか / opt-in に留めるか / w4a8 カーネル（i4 重み × per-token
i8 活性）を起こすかの分岐がここに掛かる。

## §2 測定条件

- RTX 3080 Ti（12GiB）・1024×1024・turbo 8 step・cfg 1・seed 42・**GPU 時間計測 off**（ADR 0032）
- run 前にクールダウン（アイドル 35°C + 5°C = **40°C 以下**へ待機）・各席 2 周
- 台本はセッション scratchpad（`AnimaPipeline.fromAssets` + `onEvent` で段と step を分解）—
  揮発。本表が恒久記録
- 取得量 = その quant が実際に読むファイルの合計（`resolveFiles` の解決集合 = HF からの DL 量）
- **`probe-a8-s16` は席ではない** — manifest をメモリ上だけで拡張して測った計測専用の構成
  （i8 重み + attention ノブのみ）。配布物は 1 バイトも触っていない

| ------------------------ | ----------- | ---------- | --------------------------- | ------------ | --------------------- |
| `i8`                     | f32         | f32        | 1,850 / 1,923               | 17.4 / 18.1s | 3.48 GB               |
| `probe-a8-s16`（計測用） | f32         | i8a8 + s16 | 1,625 / 1,662               | 15.6 / 16.0s | 3.48 GB               |
| **`w4`**                 | f32         | f32        | **1,888 / 1,944**           | 17.6 / 18.1s | **2.74 GB（−21.2%）** |
| **`w4-a8-s16`**          | f32         | i8a8 + s16 | **1,646 / 1,700**           | 15.7 / 16.2s | **2.74 GB（−21.2%）** |
| `w8a8-s16`（既定）       | **i8a8**    | i8a8 + s16 | **822 / 833**               | 9.25 / 9.43s | 3.48 GB               |

- 取得量の実測: 3,481,952,402 B → **2,743,186,466 B**。transformer 単体は
  1,962,502,636 → **1,223,736,700 B（−37.7%）**
- 系列の中身: i4 group32 が **453 本 / 1,956,249,600 要素**、i8 per-channel が **1 本 /

## §4 読み取り

1. **i4 の in-kernel dequant はほぼ無料**（f32 計算どうしの比較で +2%: 1,850 → 1,888・
   1,625 → 1,646）。重み読みの帯域が半減しても速くならないのは、1024² の DiT が**重み帯域
   律速ではない**ため（2026-08-05 の「i8 格納だけでは f16 と同時間」と同じ現象）。SBV2 で
   w4 が w8 より速かったのは向こうが帯域律速だったからで、DiT には移らない。
2. **linear i8a8 の効きは −49%**（1,646 → 833）。2026-08-05 の分解（4,231 → 2,153 = −49%）と
   同率で、カーネル波を経た今日でも構造は変わっていない。
3. **`w4-a8-s16` は既定の約 2.0 倍遅い**（1,646〜1,700 vs 822〜833 ms/step）。生成壁で
   9.3s → 15.9s（**+70%**）。得るのは取得量 −21.2%。
4. attention ノブ単体の効きは **−12%**（1,850 → 1,625）で、i4 席でも同じだけ効く
   （1,888 → 1,646）。重み格納と独立という設計どおり。
5. 素の RTN の画（seed 42・8 step）は**崩壊しないが明確に劣化**する — 髪色が黒 → 茶へ寄り、
   瞳の青が抜け、輪郭と背景が眠くなる。波 I の「絵柄の大きい変化・輪郭ぼやけ」の再現で、
   GPTQ（PSNR 12.26 → 22.73 dB・視認裁定「f32 とほぼ同一」）で解消される想定。

## §5 送り（この時点の見立て — §6 以降で更新された）

- **速度の結論**: i4 席は「サイズの席」であって速度の席ではない。既定 `w8a8-s16` は動かせない。
- **w4a8（i4 重み × per-token i8 活性）の価値がここで確定した** — 実装できれば 822ms/step 級を
  保ったまま取得量 −21.2% になる。gemm の i8a8 変種で k を group 長ごとに部分縮約して group
  scale を f32 累積する形（runtime の中核工事・ADR 級）。
- GPTQ 結線（校正コーパスの新設込み）は品質側の話で、速度の結論には影響しない。

## §6 GPTQ 結線後の実測と視認裁定（同日・追記）

校正付き export（4 プロンプト × 8 step・512²・g32・gptq × rtn）で i4 系列を採り直した。block
内 448 本が GPTQ・block 外 5 本が素の RTN・patchify 入口 1 本が i8。**ファイルサイズは
1,223,736,700 B で RTN 版と 1 バイトも変わらない**（格子が同じで丸め値だけが変わる）。export
所要 2,287 秒。

| 構成               | DiT ms/step | 生成壁 |  取得量 |
| ------------------ | ----------: | -----: | ------: |
| `f16`              |       1,915 |  18.2s | 5.43 GB |
| `w8a8-s16`（既定） |         823 |   9.3s | 3.48 GB |
| `i4` RTN           |       1,645 |  15.6s | 2.74 GB |
| `i4` GPTQ          |       1,640 |  15.6s | 2.74 GB |
| `i4` GPTQ + w4a8   |     **955** |  10.2s | 2.74 GB |

- **速度は丸め値に依存しないことの実測**: RTN 1,645 / GPTQ 1,640 ms/step（同条件）。速度
  スパイクを素の RTN で先に回した判断が正しかったことの裏取りでもある。
- **視認裁定（ユーザー・1024²/8 step/seed 42 の 5 枚）**: f16 = 品質重視の席 / `w8a8-s16` =
  安定（速度重視・既定据え置き）/ i4 RTN = 全体的にぼやけた印象 / **i4 GPTQ = 高品質を維持**
  （コントラストが少しハッキリ）→ **低 VRAM 席として採用** / **i4 GPTQ + w4a8 = 細部に破綻・
  線がラフ** → 席には載せない（ADR [0076](../decisions/0076-w4a8-linear-execution.md) 決定 6）。

## §7 「校正と実行の条件の食い違い」仮説 — 棄却（同日）

仮説: GPTQ は f32 活性で `H = Σ XᵀX` を積んでいるのに、w4a8 の実行時は活性が per-token i8。
この食い違いが w4a8 の劣化の主因ではないか。

- **噛み合わせは成立する（core 変更ゼロ）**: forward_pre_hook は登録順に走り、非 None を返した
  hook の結果が後続へ渡る。`attach_act_quant` を `calibrate_stages` より**先に**張れば、
  `_observe_stage` が後から張る観測フックは量子化後の活性を見る（torch 2.13.0 で実機確認）。
- **しかし取り分が無い**: リポ自身の `gptq_quantize_rows` / `GridSpec(rtn, 32)` を使った合成
  実験で、層出力の相対誤差 0.0642 → 0.0641（外れチャネル ×10: 0.0679 → 0.0675 / ×40:
  0.0772 → **0.0774 = 悪化**）。6 層の逐次伝播込みで **+0.20%**。活性を粗くしても
  levels 127 → +0.20% / 63 → +0.29% / 31 → +0.64% / 15 → +1.26% / 7 → +1.13%。
- 機序: **‖H_q − H‖/‖H‖ ≈ 5e-3** で H がほとんど動かない。GPTQ は `x̂Ŵ ≈ x̂W` を合わせられる
  だけで、活性量子化そのものの誤差 `(x − x̂)W` には構造的に手が届かない。
- **したがって仮説は棄却**。w4a8 の劣化の主因は活性量子化そのもので、重みの丸め方では
  回収できない。

## §8 未検証（可能性として残っているもの）

MUST: **ここに挙げたものは「試してダメだった」ではなく「試していない」**。後から可能性が
黙って消えないよう、棄却（§7）と分けて置く。

1. **視認裁定の標本が薄い** — §6 は 1 プロンプト・seed 42・1024²・8 step の 1 枚ずつ。§9 で
   `f16` / `w8a8-s16` / i4 GPTQ 修正前 / 修正後の 4 席だけ **5 ケース**（人物 2 / 人物なし 2 +
   §6 の 1 枚）へ広げたが、**i4 素の RTN と w4a8 は 1 点のまま**。いずれも統計ではない。
2. **§7 は合成実験**で、anima 実モデルの測定ではない。計測リグでの実測は可能（`--w4-screen` の
   参照周回を `attach_act_quant` で挟む・core 変更ゼロ・recipe 30〜60 行・1 構成 ≈ 930 秒 CPU）。
3. **もう 1 つの劣化機序が未検証**（推測）: GPTQ の誤差補償が層出力の振幅を上げ、下流の
   per-token amax が上がって活性 scale が粗くなる。正しければ **w4a8 には素の RTN 重みの方が
   合う**。判別は `i4` RTN + w4a8 を 1 枚描くだけ（コード変更ゼロ・GPU 5 分）。
4. **w4a8 の専用幾何は未試行** — `I8a8GemmOp` に `linear_w4a8` を足して regM を落とし、
   accumulator（i32 16 本 + f32 16 本）を半減させる案。残る +16% の一部は取れる可能性。
5. **g 軸は未試行**（g32 → g16）。重み忠実度は上がり、取得量は 1.22GB → 約 1.47GB の見込み。
   J-3 の軸そのもの。
6. **校正量の上振れは未測定**（プロンプト 4 → 12 / 24・step 数・解像度）。既定 4 本は「J-2 の
   根拠を下回らない下限」であって最適点ではない。
7. **校正は 512² 固定** — 1024² の活性分布は校正に入っていない（S 形 golden の 1024px ケースも
   自分の解像度では校正されていない）。
8. **w4a8 の VRAM は未測定** — 重み常駐は i4 席と同じだが、活性量子化の一時領域（xq / xs）が
   増える。
9. **irodori での w4a8 は未測定** — 既定が `w8a8` なので同じ構図（i4 席が dp4a を失う）が
   効くはず。
10. **GPTQ 版 i4 の汎化は評価 5 本ぶんしか見ていない**（校正 4 本・評価は §9 で 1 → 5 本へ。
    校正コーパスとは分離されているが、5 本は統計ではない）。

### 差分は機序どおりの範囲に閉じた

全 1,029 テンソルを突合すると、変化は **block 内 linear 448 本のうち丁度半分（28 block × 8 本）**。

| 変化した（28/28 block）                                                             | 変化しなかった（0/28 block）                           |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `attn1.to_q/k/v/out.0`・`attn2.to_q`・`attn2.to_out.0`・`ff.net.0.proj`・`ff.net.2` | `attn2.to_k`・`attn2.to_v`・`norm{1,2,3}.linear_{1,2}` |

変わったのは**入力活性が latent 経路（= `patch_embed.proj` の下流）から来る** linear だけ。
`attn2` の K/V は `encoder_hidden_states`、AdaLN の 6 本は `temb` を受けるので patchify 入口の
丸めに触れない。block 外の 5 本・i8 の 1 本・折り畳み定数は全てバイト一致。変化量は異なる
nibble 16.79%・平均 |Δlevel| 0.500。

**副産物 — export のビット再現性**: 変わらなかった 224 本は**独立した 2 回の GPTQ 実行**が
生んだ結果でバイト一致している。GPTQ 経路は入力が同じならビット再現し、今回の差分は全量が
順序変更に帰属する。

### 数値の忠実度（golden 突合 — 軌道発散が無い）

各系列の `io.<case>.safetensors`（同一の乱数プローブ入力に対する torch CPU 出力・入力の
バイト一致を検査済み）を f32 系列 `anima-turbo-f32-dyn` と突き合わせた相対 RMS。

| 系列                   |    s01024（512² 相当） | s04096（**1024² = 出荷解像度**） |
| ---------------------- | ---------------------: | -------------------------------: |
| `f16`                  |     4.280e-4 (67.4 dB) |               2.692e-4 (71.4 dB) |
| `i8`                   |     2.396e-2 (32.4 dB) |               2.019e-2 (33.9 dB) |
| i4 素の RTN            |     1.817e-1 (14.8 dB) |               1.808e-1 (14.9 dB) |
| i4 GPTQ **順序修正前** |     1.857e-1 (14.6 dB) |               1.423e-1 (16.9 dB) |
| i4 GPTQ **順序修正後** | **1.712e-1 (15.3 dB)** |           **1.382e-1 (17.2 dB)** |

- **2 ケースとも修正後が f32 に近い**（+0.71 dB / +0.25 dB）。
- 修正前は **s01024 で素の RTN より悪かった**（0.1857 vs 0.1817）。順序修正でこれが解消した。
  校正が 512² 固定（§8-7）なので、校正解像度そのもののケースで GPTQ が負けていたのは
  「校正入力が配布条件とずれている」症状として辻褄が合う。
- 留保: golden の入力は `torch.randn` のプローブで**出荷時の活性分布ではない**。系列間の相対
  比較としては妥当だが、絶対値を品質と読まないこと。

### 画素距離は品質の指標にならない（記録）

拡散のサンプリング軌道は重みの微小変化で発散するので、修正前後の PSNR は 13.9〜16.0 dB・
異なる画素 99.9% になる。物差しとして §6 で判定が割れた RTN vs GPTQ が 13.18 dB、i4 vs f16 が
13.95 dB — **同じ桁**。参照席との距離（平均 |Δ|）も 5 ケースで 2 勝 2 敗 1 分で向きが出ない。
**良し悪しは視認でしか決まらない。**

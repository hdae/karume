# DiT linear i8a8 + attention の変種スイープ実測（A 波）

> NOTE: 時点スナップショット。数値は 2026-08-10 の実測（RTX 3080 Ti / Linux / Vulkan /
> Deno 2.9.4・main `187b986`）。**比（ABBA 対計測）のみが有効**で、絶対 ms を別日の測定と
> 直接比較してはならない（§5 の理由）。op 別内訳の前提は
> [2026-08-10-op-timing-stats.md](2026-08-10-op-timing-stats.md)。

統計波で「桁を動かせるのは linear + attention のカーネルだけ（GPU の 63.3%）」と確定した
のを受け、codegen パラメタ（レジスタブロック・workgroup 形・タイル辺・K 幅）の変種を
**実形状**で系統的にスイープした。production は無変更・**全変種の出力を production カーネルと
バイト単位で突合**（i8a8 は整数縮約が順序非依存なので幾何を変えてもビットが動かない — 全
ログで不一致 0 件）。

**結論を先に**:

1. **codegen パラメタの変更だけで linear i8a8 ×1.45〜1.50・attention QK ×1.85〜2.12 /
   PV ×1.73〜1.78・stats ×1.67**（すべてビット同一）。全部入りで **DiT step 1,087 →
   772ms（×1.41）／壁時計 13.9 → 約 11.4s（×1.22）**の見積り — 台帳 4 件の合計（7% 台）の
   約 3 倍が 1 手で出る。
2. 律速は **LDS（共有メモリ）帯域 × 発行**であって dp4a 発行でも DRAM 帯域でもない。効く
   パラメタは**レジスタブロック（1 スレッドの出力数）が第一**、workgroup スレッド数
   （≤128 が有利・256 は一律劣位）が第二、tileK は第三（K64 は退行）。
3. **「attention_stats の起動幾何（3.67M workgroup/step）が律速」仮説は反証**。self 側は
   既に帯域の 83% に達しており、grid を減らすと**遅くなる**。唯一のビット同一の利得は
   「S を 2 回読む」→「1 回読んでレジスタ保持」（×1.672）。
4. **最安の発見: attention i8a8 に accumulator 静的展開（C1・`4b15ec2`）が未適用**。幾何も
   キーも変えず `acc[i]` を名前付き変数へ展開するだけで **QK ×1.41 / PV ×1.45**
   （`attention-i8a8.ts` の QK/PV 縮約ループ）。linear だけに入れた最適化の取りこぼし。
5. **PV だけ最適タイルが違う**（N=D=128 の 1 タイル化が勝つ）— 「1 本の最良幾何」は存在
   せず、形状バケット別の既定（案 B）を支える一次証拠。

## 1. 実形状（DiT 1024・S=4096・1 predict）

linear 454 本 / attention 56 本（既存記録と一致）。m=1 の 169 本は GFLOP の 0.003% で
最適化対象外。

| 形状 | m×n×k          | 本数 | linear 内 GFLOP 比 |
| ---- | -------------- | ---: | -----------------: |
| L1   | 4096×2048×2048 |  168 |              42.5% |
| L2   | 4096×8192×2048 |   28 |              28.3% |
| L3   | 4096×2048×8192 |   28 |              28.3% |
| L4   | 512×2048×1024  |   56 |               0.9% |

attention: self（batch16 M4096 N4096 D128）28 本 / cross（N=512）28 本。
`attention_stats` の 65,535 workgroup/ノードは `gridStrideWorkgroups(batch·M, 1, limit)` の
実装どおり（仮説の数値を追認した上で反証）。

ハーネスと in-situ（統計波）の突合: linear +4.6% / QK +5.7% / stats −1.3% — **6% 以内で
実運用を再現**（PV のみ +23% はスロットル巡回・比のみ使用）。

## 2. linear i8a8（現行 `reg64x64v4:dp4a` = r4×4 / wg16×16 / K16）

確認計測（ABBA×2 巡・再現性 ±0.2%）:

| 形状 | 最良変種                    |         比 | TOP/s（現行 → 最良）            |
| ---- | --------------------------- | ---------: | ------------------------------- |
| L1   | M128N64 **r8×8 wg8×16** K16 | **×1.452** | 24.1 → 34.7（達成率 35% → 51%） |
| L1   | 同 K32 + swizzle            |     ×1.496 | —（絶対値では K16 に劣後）      |
| L2   | M128N64 r16×8 wg8×8         | **×1.556** | 22.3 → 32.8                     |
| L3   | M128N64 r8×8 wg8×16         | **×1.388** | 16.1 → 27.4                     |

- **M128N64 r8×8 wg8×16 K16 が 3 形状すべてで ×1.39〜1.47 を出す唯一の変種**。
- 広域スイープ（37 変種）の傾向: regM×regN が支配的（4×4 = ×1.03 → 8×8 = ×1.39〜1.45）・
  threads 256 は一律劣位・M 側を伸ばすのが有利（B タイルの LDS 読みだけがバンク衝突を持つ）・
  bSwizzle / wideLoad は ±5% 以下・**dp4a → エミュは 2.6 倍遅い**。
- 律速モデル: r4×4 では「LDS 8 語 / 16 dp4a」が Ampere の LDS 帯域と dp4a スループットの
  比とちょうど拮抗する。r8×8 で 0.25 語/dp4a になり拮抗が解ける — 実測順位と整合。
- 帯域律速ではない: L1 最良で 305 GB/s = 帯域の 33%（重み 4MB は L2 に収まる）。

## 3. attention

### 3.1 stats（`attention_stats:v1:f32:lastdim:safe:wg256:s16`）

| 変種                                   | self（dim=4096）                  | cross（dim=512）   |
| -------------------------------------- | --------------------------------- | ------------------ |
| production                             | 1.4233ms・**754 GB/s = 帯域 83%** | 0.6692ms・201 GB/s |
| grid 640（8/SM）                       | ×0.762（**退行**）                | ×0.858（退行）     |
| **regcache（S 1 回読み・ビット同一）** | **×1.672**                        | ×1.115             |
| wg64〔数値非同一〕                     | ×0.725                            | ×2.170             |
| wide vec4〔数値非同一〕                | ×2.400（帯域 97%）                | —                  |

- self は完全に帯域律速 — 起動幾何を「改善」する方向は全て退行。
- regcache は要素→スレッド割当・縮約順とも不変（範囲外は `acc + 0.0`）で、**PNG 門を
  割らずに取れる唯一の大きな利得**。dim 依存の生成（`epc` がキー軸に増える — DiT は
  2 種のみ）。
- wg 幅を変える変種は全て数値非同一（maxRel ≈ 2.4e-7・ADR 0023 の逐語一致が壊れる）。
  cross の ×2.17 は tolerance 全面再導出とセットでのみ検討可。

### 3.2 QK / PV（i8a8・s16）

| -------- | ------------------------- | --------------------------------------------------------- |
| QK self  | **×1.408**                | M128N64 r8×8 wg8×16 = ×1.921（K32 併用 ×2.169）           |
| QK cross | —                         | M128N64 r16×8 wg8×8 swz = ×2.161                          |
| PV self  | **×1.451**                | **M64N128 r8×8 wg16×8 = ×1.738**（N=D=128 の 1 タイル化） |

## 4. 最良組での見積り（保守側の適用比）

| op              | 現行 ms/step |           適用後 |     差 |
| --------------- | -----------: | ---------------: | -----: |
| linear i8a8     |        568.9 |            392.4 | −176.6 |
| attention_qk    |        129.5 |             68.9 |  −60.6 |
| attention_pv    |        141.5 |             81.6 |  −59.9 |
| attention_stats |         59.4 |             41.7 |  −17.7 |
| **DiT 計**      |    **1,087** | **772（×1.41）** |   −315 |

壁時計 13.945 → **約 11.43s（×1.22）**。VAE conv2d（全体の 19.1%）は同じ GEMM 骨格を
共有しており、f32/f16 への横展開が成立すれば同型の利得が見込める（§6-1）。

## 5. マイクロベンチの計測規約（E2E 用の規約をそのまま使ってはいけない）

このカードはアイドルで SM 210MHz / メモリ 405MHz まで落ちる。E2E 用の「アイドル +5°C まで
待つ」を数 ms のマイクロベンチに適用すると**メモリクロック 1/23 の状態で測る**ことになる
（同一変種が 2 倍揺れた）。採った規約:

1. 1 タイムドパス ~80ms になるよう同一 dispatch を積む（duty cycle 維持）
2. 対の前にメモリクロックが張り付くまで空回し（`nvidia-smi` ポーリングは対の外で 1 回 —
   毎回叩くと起動 30ms の間に P8 へ落ちる）
3. **ABBA 対計測**で熱ドリフト相殺・代表値は min
4. 長時間スイープでは SM 1845→1290MHz まで落ちる — **絶対 ms の変種間比較は不可・比のみ**

この規約で A/B 再現性 ±0.2%（規約なしでは ±100%）。timestamp は 1 pass に reps 積みの
begin/end 差（pass 内の暗黙バリアで per-dispatch 実コストが出る）。

## 6. オートチューン布石の所見（実装せず・設計材料）

- 意味のある変種空間は **regM(3) × regN(2) × threads(2) × tileK(2) = 24 → 枝刈りで
  8〜12 変種**。1 変種の計測コストは生成 ~0.4ms + 実走 ~7ms → **12 変種 × 3 形状 ≈ 0.27s**
  （初回 predict の重みアップロード +287ms と同オーダー）。
- **数値の前提: オートチューンが成立するのは i8a8 系のみ**（整数縮約は順序非依存 — 本波の
  100+ 変種全てがバイト一致した実証）。f32/f16 は縮約順が数値契約（ADR 0022）。
- **`adapterInfo` は Deno/wgpu で空 `{}`** — adapter 名をキャッシュ鍵にする設計は成立しない。
  Web 標準の永続層も Deno に IndexedDB が無く非対称。プロセス内キャッシュのみ（毎 Session
  0.27s）が最も制約と衝突しない。
- キーの決定性は「キーに幾何を載せる」で保たれる（`gemmUsesVec4` の v4 フラグと同じ語彙）。

## 7. 未検証・次波への申し送り

1. **f32/f16 への横展開**（= VAE conv2d 19.1% が対象になるか）: ADR 0022 は「タイル形は
   担当割りだけを決め、K 縮約順は不変」と明言しており、正しければ regM/regN/wg 変更は
   f32 でもビット同一のはず。ただし backend の fma 縮約判断の留保があり、**PNG 門で
   確かめる以外に事前保証は無い** — 次波の最初の実測にすべき。
2. **Metal（Apple M2）A/B 未実施**。Linux 既定の切り替えは Metal で退行しうる
   （採用条件の裁定が要る）。r8×8 = 64 レジスタ/スレッドは spill の懸念。
3. flash-attention 形（S 非実体化・self 1 ノード ~2.1GB の往復が消える）は測っていない —
   ADR 0023 のビット同一を根本から失うため別の設計判断。
4. stats cross の wg64（×2.17）は tolerance 再導出とセット。
5. L4（linear の 0.9%）の確認計測は未了（見積りへの影響は誤差）。

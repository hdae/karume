# Wan2.2 の DiT のパスの切れ目の計測（perf-ledger H-37 段 1）

> 時点スナップショット（2026-10-15）— 2 機（Deno の RTX 3080 Ti・Chrome の RTX 5070 Ti）で各 1 回測った値。切れ目の見積もりは最大でも
> 1 step の約 1.3% で、kill 線（5%）の下 → [perf-ledger](../perf-ledger.md) H-37 は ❌。

## 問い

Wan2.2 TI2V-5B の DiT の 1 step は uncond → cond の逐次 2 パス（CFG）で、パスごとに入力を上げて出力を読み戻し、ホストで
unpatchify → CFG → UniPC → 有限性の検査 → patchify を行う（`packages/models/src/wan/dit-loop.ts` の `runWanDenoise`）。この間 GPU は
DiT の計算をしていない（上げと読み戻しの間は転送だけが動く）。この「切れ目」が 1 step のどれだけを占めるかを測り、H-37 の候補（① uncond / cond を続けて積み読み戻しを 1 回に ② 文脈・RoPE を
常駐 ③ CFG / UniPC を GPU へ）を採るかを決める。kill 線（perf-ledger H-37）= 切れ目の合計が 1 step の 5% 未満なら閉じる。

## 計測の方法

### 生成の中の区間

step の印（denoise-step のイベント）と、transformer の run の完了の印（`onRunDiagnostics` の callback の先頭）で、1 step を 3 区間に分ける。
定義の正本は `tools/gpu-lab/browser/wan-plan.ts` の `WanSeamStep` の doc。

| 区間 | 始まり → 終わり                        | 中身                                                                        |
| ---- | -------------------------------------- | --------------------------------------------------------------------------- |
| segA | 前の step の完了 → 1 本目の run の完了 | patchify と 1 本目の run（uncond — 入力の上げ・GPU の実行・出力の読み戻し） |
| segB | 1 本目 → 2 本目の run の完了           | unpatchify と 2 本目の run（cond — 同上）                                   |
| segC | 2 本目の run の完了 → step の完了      | unpatchify + CFG + UniPC + 有限性の検査（ホストだけ）                       |

区間と step の所要の中央値は step 2〜5 で取る（step 1 は Session の構築〈重みの転送〉を含む）。segA / segB は GPU の実行を含むので、
その中の上げと読み戻しは生成の中では分けられない。VAE の段は、最後のタイルの印 → 段の終わり（タイルの貼り合わせ・Session と cache の
破棄・フレームの仕上げ）を貼り合わせの区間として採る。

### 下見（生成とは別のマイクロベンチ）

`tools/gpu-lab/browser/wan-seam-probe.ts` の `probeWanSeams`。Deno の CLI と gpu-lab のタブが同じモジュールを使う。

- ホストの処理: 製品の関数（`packages/models/src/wan/`）を実寸の配列で回す。
- 転送: DiT 1 パスと同じ本数・バイト数で、上げ = 入力 7 本の `writeBuffer` + 空の submit の完了待ち、読み戻し = 出力と同じバイト数の
  copy → `mapAsync`。入力は 33 フレームで 21.6 MiB・121 フレームで 54.7 MiB、出力は 5.8 / 20.0 MiB。
- 見積もり（T2V の 1 step）= ホスト（patchify + unpatchify × 2 + CFG + UniPC + 有限性の検査 + timesteps_proj）+ 2 ×（上げ + 読み戻し）。

### 入力の照合

生成の後に、DiT の Session が実際に所有した入力のバイト数（`SessionDiagnostics` の `planBacking.inputBytes`）と下見の入力の合計を照合する。
全 4 ケースでバイト単位で一致した（33 フレーム 22,614,976 B・121 フレーム 57,385,536 B）→ 下見の転送は実物と同じ量を動かしている。

### 生成の中の補正

生成の中の segC は、下見の同じ関数（unpatchify + CFG + UniPC + 有限性の検査）の和より大きい（生成の中ではイベントの発行や GC などが乗ると見ている — 差の内訳は測っていない）。
その差を下見の見積もりに足したものを「生成の中の補正後」とする。差は Deno 33f +8.8・121f +10.5・Chrome 33f +8.7 ms。

## 判定

切れ目の合計の見積もりは 1 step の 0.34〜1.30%（生成の中の補正後 — 補正前は 0.33〜1.16%・Chrome 121 フレームは換算で 0.72%）で、全ケースで kill 線の 5% を大きく下回る → **H-37 は ❌
（不採用・記録として保持）**。VAE の貼り合わせも VAE の段の 0.76〜1.14% に留まる。

候補を採らない理由:

- どの候補も切れ目の一部を消すだけで、3 候補を全部入れても取れるのは切れ目の合計まで（最大でも 1 step の約 1.3% — 見積もり）。③ は GPU の側に
  計算の時間が残るので、実際の利得は上限より小さい。
- ③ は丸めが変わり、sha 行の焼き直しを伴う（参照層に入れるなら ADR [0110](../decisions/0110-practical-tier-numerics-contract.md) の裁定も
  要る）。約 1.3% 以下の利得に見合わない。

## 注意

1. run の印は `session.run` が settle し、`session.diagnostics()` を作った直後に採る。その構築の時間は run 側（segA / segB）に入るので、
   segC はわずかに小さく出る。大きさは測っていない。
2. segA は前の step の完了の直後から始まり、前の step のイベント処理・中断の検査・timesteps_proj も含む。
3. 転送の下見は runtime の run の経路そのものではなく、同じ本数・バイト数の素の WebGPU の操作による目安。上げは runtime の run が待たない
   フェンス（空の submit の完了待ち）を含み、runtime の側の束縛や計画の費用は含まないので、偏りの向きは決まっていない。
4. Chrome の 121 フレームは下見が無く、33 フレームからの換算（過大側）。
5. 各ケース 1 回の計測。ただし最大の 1.30% でも kill 線の 5% と約 4 倍の差があり、ばらつきで判定が変わる幅ではない。Deno の step は
   33 フレームで 7,864 → 8,180 ms と僅かに伸び、121 フレームで 70,718 → 63,955 ms と単調に縮んだ（step 2〜5 — 原因は調べていない）。
6. VAE のタイルごとの読み戻しはタイルの区間に含まれ、分けて測っていない（判定に使ったのは貼り合わせの区間だけ）。バイト数からの見積もり
   （推定）: タイルは潜在 16・出力 256 px 角（ADR 0121 決定 6 — 1280×704 で 28 枚）で、1 タイルの出力は 3 チャネル × フレーム数 × 256 × 256 の f32 = 33 フレーム
   24.75 MiB・121 フレーム 90.75 MiB。Deno の下見の読み戻しの遅い側の率（121 フレームの 20.0 MiB を 21.05 ms）で伸ばすと約 26 / 95 ms で、
   1 タイルの所要（Chrome の中央値で約 5.0 / 17.8 s）の約 0.5%。
7. 起票のきっかけの観察（タスクマネージャの GPU グラフで使用率が周期的に 0 まで落ちる — perf-ledger の H-37 の節）と、この区間の値の
   対応は取っていない。判定は時間の割合で行った。

## 副次の観察

- 1 step はほぼ全部が 2 回の run（forward）の時間。segA ≈ segB で、segA + segB は step の中央値の 99.3〜99.9%（中央値どうしの比）。
  run の時間は壁時計で、GPU の実行のほか run の中のホスト処理・submit の待ち・上げと読み戻しを含む（GPU だけの時間は分けて測って
  いない — Wan の家族 admission は GPU の timestamp の計測を拒む）。速くする余地は forward の側（attention / GEMM）にあると見ており（推定）、別件の Wan2.2 の attention の高速化の調査（git 追跡外のメモ
  `.claude/reviews/2026-10-11_wan-attention-recon/NOTES.md`・backlog は未起票）が扱う。
- step 1（Session の構築を含む）は Deno 33f 15,893.0 ms・Chrome 33f 56,785.0 ms で、生成 1 回の固定費。切れ目ではなく本件の対象外。
- `vae_decoder_first` の `overBudgetChunks`（推定時間が submit の予算を超えたまま出したチャンクの数）783（33 フレーム）/ 3,645（121 フレーム）
  は両機で同じ値が出た。ADR 0121 追記「段 9d の結果」の Chrome の I2V の項はこれ（と `maxWindowMeanMs`）を H-37 の材料と書いたが、
  どちらも run の中の submit の区切り方の指標で、run と run の間の切れ目ではないので、本件の判定には使っていない。

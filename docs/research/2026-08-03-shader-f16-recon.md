## 0. 要旨（先に結論）

1. **本機（RTX 3080 Ti / GA102）の f16 演算スループットは f32 と 1:1**（FP16 34.10 TFLOPS =
   FP32 34.10 TFLOPS — 事実・出典 §1.4）。つまり **f16 化による ALU 利得はゼロ**。得られるのは
   「共有メモリ / レジスタ / DRAM の**バイト数**が半分になること」だけ。#29 の期待利得は
   全てこの 1 本の機序に乗る。
2. **プロトタイプの「f16 計算 1.44×」は設計判断に使えない数値**（§2）。基準が旧 16×16 カーネル
   （現行 GEMM 比では **0.47×**）であるうえ、その f16 変種は ①vec4 グローバル読みが無い
   ②MAC ごとに f16→f32 変換が入る ③入力バッファが**全バイト 0x01 = f16 の subnormal**
   ④出力の検算が無い、と交絡が 4 つある。**「f16 は本命でない」という結論の向きは本機でも
   おそらく正しいが、根拠として引ける実測ではない**（ADR 0018 / gemm-design.md / ACTIVE_DESIGN
   の該当記述は出典の但し書きが要る — §7 隣接①）。
3. **Karume 自身の実測が f16 の見込みを最もよく縛る**: 同じ 64×64 骨格で、`linear` は
   f32 計算 3,318 GFLOP/s → i8a8 + dp4a **13,273 GFLOP/s（4.0×）**（§3.2 の試算）。dp4a は
   「共有バイト 1/4 × 1 命令 4 MAC」で 4×。f16 は「共有バイト 1/2 × 1 命令 1 MAC（ALU は 1:1）」
   なので、**同じタイル形のままなら期待値は 1.0〜1.5× の範囲**（推測・機序ベース）。
   4× のような桁は構造的に出ない。
4. **1024px の支配項 attention 46%（1,110ms / DiT GPU 2,415ms）に対し、f16 で確実に取れるのは
   時間ではなくメモリ**（S transient 1,073.7MB → 536.9MB）。S の DRAM 往復は 1 step 101.5GB と
   試算でき、**理論帯域比では attention 時間の 10% 相当**しかない（§3.3）。時間の主因は DRAM でも
   ALU でもなく**内側ループの共有ロード / 命令発行**であり、そこを f16 が動かせるかは
   **マイクロベンチでしか決まらない**。
5. したがって推奨は **Q0（マイクロベンチ）を門にした段階投入**（#28 の「実測で勝った場合のみ
   配線」の先例をそのまま踏襲）。第 1 波の候補は「案 α: feature 配線 + attention の f16 タイル
   変種（別キー・opt-in）」、勝てなければ**配線せず変種だけ残して報告**。
6. **w8a16 は「速度の案」ではなく「品質の案」**（§4.4）。w8a8 より確実に遅く（dp4a を捨てる）、
   w8+f32 計算より速い保証も本機には無い。価値は「w8a8 が品質で不合格なモデルの中間点」。

## 1. feature 配線（shader-f16 を M0.1 全廃方針の下でどう戻すか）

### 1.1 事実 — 本機では既に列挙されている

- `adapter.features` の実測列挙に **`shader-f16` は入っている**
  （`docs/research/2026-08-03-dp4a-w8a8-design.md:98-101`。M0 期の実測も
  `docs/research/2026-08-01-prototype-recon.md:28` で `shader-f16` ✅ / `timestamp-query` ✅ /
  subgroups ❌）。Deno 2.9.4 / Linux / wgpu-Vulkan / RTX 3080 Ti。
- 現状の Karume は **無条件要求 feature ゼロ**（`src/gpu/device.ts:122-131` の
  `REQUIRED_FEATURES = []`）。唯一の条件付きが `timestamp-query`（ADR 0021 の三値 —
  `src/gpu/device.ts:149-163` の `planTimestampFeature` / `:203-220` の `AcquireGpuOptions` /
  `:404-435` の `acquireGpu`）。
- ADR 0021 決定 4 が全廃方針を「**既定では**何も要求しない」に読み替え済みで、同じ文の中で
  「`enable f16` などシェーダ側の feature 依存ゼロは不変」と書いている
  （`docs/decisions/0021-gpu-timing-diagnostics.md:26-29`）。**#29 はこの後半を意図的に破る
  タスク**なので、ADR 0021 の当該文の改訂（または新 ADR での上書き明記）が要る。

### 1.2 最小の形（ADR 0021 の三値を先例にするが、**既定は auto にしてはいけない**）

```
AcquireGpuOptions.shaderF16?: boolean   // undefined = 要求しない / true = 必須（無ければ GpuFeatureError） / false = 明示的に要求しない
```

- **timestamp-query との決定的な違い**: 計測は「有っても無くても数値が変わらない」ので
  `undefined = 自動判定`が安全だった。**shader-f16 は数値を変える**ので、auto にすると
  「機械が変わると黙って出力が変わる」= ADR 0002（互換重視）と ADR 0006（fail loudly）の両方に
  反する。したがって **`undefined` は「要求しない」**（二値＋将来の拡張余地として三値の形だけ
  合わせる、が素直）。
- 判定は `planTimestampFeature` と同型の**純関数**に切り出す（`planShaderF16Feature`）。理由も
  同じ — 「feature あり × 要求 true」以外の分岐は実機では作れないので、単体テストの継ぎ目が要る
  （`src/gpu/device.ts:145-148` の doc がその理屈を既に書いている）。
- `GpuContext` 側は **`features` から導出**する（`shaderF16Enabled` を要求値の複製にしない —
  ADR 0021 の MUST・`src/gpu/device.ts:307-316` と同じ規律）。
- Session 側のノブ（§4.3）が f16 変種を要求したのに `features.has("shader-f16")` が false なら
  **Session 構築時に fail loudly**（「`acquireGpu({shaderF16:true})` を渡せ」まで書く）。
  黙って f32 経路へ落とすのは ADR 0025 決定 1 と同じ理由で禁止（既定経路と opt-in の区別が
  診断で見えなくなる）。

### 1.3 WGSL 側の制約（コード生成に直接効く点だけ）

- `enable f16;` は**モジュール先頭・全ての global 宣言より前**の directive。現行の骨格は
  `skeleton()` が `header` を先頭に置く形（`src/kernels/gemm.ts:478-529`）なので、
  **`enable` 行は skeleton が f16 変種のときだけ最初に差し込む**のが自然。
  MUST（既存規律の継承）: 既定変種の生成物は 1 バイトも動かさない
  （`src/kernels/gemm.ts:25-26` / `weight-storage.ts:20-23`。検出器は
  `tests/fixtures/wgsl/*.wgsl` のスナップショット）。
- 現行テストが **「f16 格納の WGSL に `enable f16` が入らないこと」を assert している**
  （`tests/codegen_wgsl_test.ts:1358`）。#29 は**格納 f16（ADR 0018 の unpack2x16float 形）とは
  別の変種**を足す話なので、この assert は**触らないのが正しい**（格納経路は据え置き）。
  同名の混同を避けるため、キーの語彙は格納 `:wf16` に対して**計算側は別語**にする
  （例 `:c16` / `:f16math`）。§4.3 参照。
- 型と整列: `f16` align 2 / `vec2<f16>` 4 / `vec4<f16>` 8。**storage / workgroup では自由に使える**
  が、**uniform は触らない**のが安全（uniform の配列要素は 16B 整列の縛りがあり、現行の
  `Dims`（3〜16 語の f32/u32）を f16 にする理由が無い）。
- 変換は `f16(x)` / `f32(h)`。**MAC ごとに変換を挟む形は避ける**（プロトタイプの交絡の 1 つ —
  §2.2）。
- **subgroups は本機で列挙されない**（プロトタイプ recon `docs/research/2026-08-01-m6-perf-recon.md:53`
  の Blackwell では列挙されるが、Karume 実測では ❌）。`subgroup-matrix` 系はプロトタイプの
  Blackwell でも無く、**WebGPU からテンソルコアには届かない**（同 :53-55）。f16 に期待できるのは
  あくまで CUDA コアの範囲。

## 2. プロトタイプの「f16 計算 1.44×」の解剖（一次ソースまで降りた）

### 2.1 数値そのもの

`docs/research/2026-08-01-m6-perf-recon.md:31-49`（実 Chrome / Blackwell RTX 5070 Ti・
M=4096 N=2048 K=2048・20 反復）:

| カーネル                                       |    GFLOP/s | 旧 16×16 比 | **現行 Karume 相当（vec4 f32）比** |
| ---------------------------------------------- | ---------: | ----------: | ---------------------------------: |
| 旧 16×16（1 スレッド 1 出力・f32）             |      3,506 |       1.00× |                              0.33× |
| レジスタ 4×4                                   |      8,754 |       2.50× |                              0.81× |
| レジスタ 8×8                                   |      3,867 |       1.10× |              0.36×（レジスタ溢れ） |
| **レジスタ 4×4 + vec4（= 現行 Karume）**       | **10,754** |       3.07× |                          **1.00×** |
| **レジスタ 4×4・f16 計算（スカラ・累積 f32）** |  **5,057** |   **1.44×** |                          **0.47×** |
| DP4a（i8）                                     |     16,599 |       4.73× |                             1.543× |

同 recon 自身が「**f16 計算は本命ではない**（1.44×）。スカラ f16 は NVIDIA では FP32 と同レートで、
効くのは共有メモリ/帯域の側だけ。vec4 化した f32（3.07×）の方が速い」と書いている（`:44-45`）。
**基準の読み替えは ADR 0025 が DP4a について既にやったのと同型**
（`docs/decisions/0025-w8a8-linear-execution.md:8-9`、設計書 §3.2）。

### 2.2 何を測った数値なのか（ベンチ実体を読んだ結果）

実体は `apps/playground/public/models/gemm-bench.js` の `REGTILE4_F16`（`:302-352`）と
`bench3()`（`:404-437`）。**交絡が 4 つある**:

1. **vec4 グローバル読みが無い**。`a: array<f16>` / `b: array<f16>` を**スカラで**読む
   （`:322` `:329`）。比較対象の 10,754 は vec4 読み。→ 「f16 かどうか」ではなく
   「vec4 かどうか」の差が混ざる。
2. **MAC ごとに f16→f32 変換**: `acc[i*4+j] = acc[i*4+j] + f32(av[i] * bv[j])`（`:338`）。
   1 FFMA で済む f32 版に対し、f16 乗算 → 変換 → f32 加算の 3 命令。しかも **NVIDIA の
   スカラ f16 乗算は f32 と同レート**なので、増えた変換ぶんだけ純損。
3. **入力データが違う**。f32 側の `bench2` は実データ相当
   （`(i%13)*0.01-0.06` — `:267-268`）だが、`bench3` は **`new Uint8Array(...).fill(1)`**
   （`:426`）= f16 のビット列 `0x0101` で**subnormal**（≈1.5e-5）。subnormal 一色の入力は
   ハードウェア / ドライバの遅い経路を踏みうる（推測・未検証）。
4. **検算が無い**。`bench2` にある先頭 4 要素の突合が `bench3` には無い（`:437` 付近。
   Karume 側でも `docs/research/2026-08-03-dp4a-w8a8-design.md:190-199` が同じ指摘をしている）。
   加えて `bench2` と `bench3` は**別 device セッション**なので熱状態も揃っていない。

**結論（事実）**: 1.44× は「純スループット・数値未検証・交絡あり」の値で、
**「f16 計算の価値」を測った実験ではない**。読み取れるのは
「**素朴な f16 移植（スカラ読み + MAC ごと変換）は現行 vec4 f32 の半分の速度になる**」という
**負の教訓**だけ。これは #29 の実装で踏んではいけない形の一覧としてはむしろ有用。

### 2.3 プロトタイプの「wf16」は計算 f16 ではない（用語の罠）

プロトタイプ本体（`src/kernels/gemm.ts（プロトタイプ内）:16-18` / `:271-275`）の `wf16` は
**重み格納のみ f16**（`enable f16` + `array<f16>` 直読み・計算は常に f32）。dtype ポリシーも
「計算 = f32 / f16（feature 検出、非対応時は f32 フォールバック）」と書きつつ
（`DESIGN.md:113-117`）、**実装された f16 計算は本体には無い**（ベンチのみ）。
→ **プロトタイプに「f16 計算の実装・実測・実モデル適用」は存在しない**。Karume が #29 で
負う部分は全て新規（w8a8 のときと同じ構図）。

## 3. どこに入れると 1024px の支配項が動くか

### 3.1 現状の内訳（実測・出典付き）

1024px・turbo・`--dit i8 --linear-compute i8a8`（`examples/anima/README.md:139-150` の NOTE /
ADR 0025 実測節）:

| 項目                              |                           実測 |
| --------------------------------- | -----------------------------: |
| 全体                              |                          36.5s |
| DiT 1 step（壁時計 / GPU 実時間） |          2,805ms / **2,415ms** |
| — `attention`（qk + stats + pv）  | **1,110ms（46%）← 次の支配項** |
| — `linear`（i8a8 / dp4a）         |                 1,024ms（42%） |
| VAE decode                        |                           2.1s |

512px 同条件は DiT GPU 370ms/step・linear 234ms（63%）で、**attention の内訳は記録されていない**
（融合直後の 512px/wf16 実測は `attention_qk 35 + pv 43 = 78ms / DiT GPU 929ms`
— `docs/decisions/0023-fused-attention.md:90-92`。w8a8 下では相対比が上がるはずだが未実測）。

### 3.2 何が律速か（試算 — ここが設計の分かれ目）

FLOP は設計書に実測ベースの表がある（`docs/research/2026-08-03-attention-design.md:175-190`）:
1024px の attention = **4,329.3 GFLOP / forward**（QK 2,164.7 + PV 2,164.7）。turbo は CFG=1 で
1 step = 1 forward。

| 指標                                          |                            値 | 出所                                                                                  |
| --------------------------------------------- | ----------------------------: | ------------------------------------------------------------------------------------- |
| attention 実効                                |             **3,900 GFLOP/s** | 4,329.3 / 1.110s（**私の試算**）                                                      |
| linear（i8a8 dp4a）実効                       |            **13,273 GFLOP/s** | 13,592 GFLOP（`dp4a-w8a8-design.md:72-73`）/ 1.024s（**試算**）                       |
| linear（f32 計算・wi8）実効                   |                 3,318 GFLOP/s | `dp4a-w8a8-design.md:72-73`（実測換算）                                               |
| 本機 FP32 ピーク（定格 / 熱制限下の実効推定） |      34.1 TFLOPS / ≈19 TFLOPS | 定格は仕様・熱制限は README の SM クロック実測（1,665→約 900-1,000MHz）からの**試算** |
| 本機 FP16 ピーク                              | **34.1 TFLOPS（f32 と 1:1）** | 仕様（§1.4 の Web 出典）                                                              |
| 本機メモリ帯域                                |     912 GB/s（GDDR6X 384bit） | 仕様                                                                                  |

**attention の DRAM トラフィック試算**（1024px・1 step）:
S = `[B·H, M, N]` = 16×4096×4096 = 268.4M 要素 = **1,073.7MB**（ADR 0023 の実測値と一致）。
① QK が S を書く → ② stats が S を読む → ③ PV が S を読む = **3.22GB / self-attn 層**。
self 28 層で 90.2GB、cross（N=512）28 層で 11.3GB → **合計 101.5GB / step**。
q/k/v/o は合計 3.8GB で誤差。

- 演算強度 = 4,329 GFLOP / 101.5 GB = **42.6 FLOP/B**。本機の均衡点（19 TFLOPS / 912 GB/s）は
  20.8 FLOP/B なので **DRAM 律速ではない**。
- 実際の達成は **ALU ピークの約 20%・DRAM ピークの約 10%**（101.5GB / 1.11s = 91 GB/s）。
  → **どちらのピークも当たっていない**。律速は**内側ループの共有メモリ帯域 / 命令発行**である
  （推測だが、下の dp4a の実測がこの読みを強く支持する）。
- 内側ループ（`src/kernels/gemm.ts:519-524`）は **共有ロード 5 回（B の vec4 1 + A のスカラ 4）で
  16 MAC** = 32B / 16 MAC = **2 B/MAC**。Ampere の共有メモリは 32 バンク × 4B/clk = 128 B/clk/SM に対し
  FMA は 128/clk/SM なので、**2 B/MAC は共有帯域を 2 倍超過**する（試算）。
- **dp4a が 4.0× 出た事実**（3,318 → 13,273 GFLOP/s・同じ 64×64 骨格・タイル幾何も同一 —
  ADR 0025 決定 3）は、「オペランド幅を詰めると比例して速くなる」という読みの直接の裏付け。
  dp4a は **バイト 1/4 かつ 1 命令 4 MAC** の二重取り。

**f16 の期待値（推測・機序ベース）**:

- 同じタイル形のまま f16 タイルにすると **バイトは 1/2、命令数は不変、ALU は 1:1**。
  共有帯域が真の律速なら最大 2×、命令発行（LSU 発行数）が律速なら **1.0×（利得ゼロ）**。
  実際はその中間 = **1.0〜1.5×** と読むのが妥当。
- **より確実な使い道は「浮いた共有メモリでタイルを大きくする」**（1 共有ロードあたりの MAC を
  増やす）。ただし 8×8 レジスタ化は**プロトタイプ実測でレジスタ溢れにより劣化**（3,867 GFLOP/s）
  なので、方向は「K タイル拡大」「n タイル拡大 + f16」等に限られ、**どれも机上では決まらない**。
- **f16 での桁違いの勝ちは構造的に無い**（ALU 1:1・テンソルコア到達不能）。
  「attention 46% を半分にする」級の期待は持てない。

### 3.3 変種ごとの期待利得（試算・要マイクロベンチ）

| 変種                                                                      | 機序                                    | 期待（1024px・DiT GPU 比）                                                                                                                  | 確度                         |
| ------------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| (a) attention の **f16 タイル計算**（qk/pv の共有タイルを f16・累積 f32） | 共有バイト 1/2                          | attention 1,110ms → 740〜1,110ms（**0〜15% の DiT 短縮**）                                                                                  | 低（要実測）                 |
| (b) **S を f16 で受け渡し**（qk が書く / stats・pv が読む）               | DRAM 1/2・**transient 1,073.7→536.9MB** | 時間 −3〜5%・**メモリは確実に半減**                                                                                                         | 中（メモリは確実・時間は小） |
| (c) **w8a16 linear**（i8 重み × f16 活性）                                | 共有バイト 1/2（dp4a を捨てる）         | **w8a8 より遅い**。w8+f32 比では 1.0〜1.5×                                                                                                  | 低・§4.4                     |
| (d) 活性 f16 の全面伝播（中間バッファを f16 に）                          | 全 op の DRAM 1/2                       | 非 GEMM 系（strided / elementwise）は帯域律速なので**ここが一番効く可能性**（DiT の strided 実効 680 GB/s — `attention-design.md:705-706`） | 中・ただし工事は最大         |
| (e) f16 で浮いた共有メモリをタイル拡大に回す                              | 1 共有ロードあたり MAC 増               | 不明                                                                                                                                        | 低（設計自由度が大きい）     |

> **注意（事実）**: (b) は **shader-f16 を必要としない**。`pack2x16float` / `unpack2x16float` は
> core WGSL で、ADR 0018 が重み格納で既に使っている（`src/kernels/weight-storage.ts:84-103`）。
> つまり **#29 の中で最も安全な部分は feature 配線と独立に実行できる**。

## 4. 数値設計と tolerance

### 4.1 何が壊れるか（範囲を正確に）

- ADR 0022 決定 3 が明文で「**縮約順序を変える将来の変種（DP4a・shader-f16 等）は tolerance
  再導出とセットでしか入れない**」（`docs/decisions/0022-gemm-register-blocking.md:23-24`）。
  ACTIVE_DESIGN の #29 エントリも同じ（確定済み前提）。
- f16 変種はどれも **ビット同一が原理的に不可能**（f16 丸めが縮約の途中に入る）。したがって:
  - **PNG sha256 門は f16 変種には掛からない**。w8a8 と同じく**出力名で分離**し
    （`-w8a8` の先例 — `examples/anima/main.ts:286`）、**既定経路の PNG は不変が MUST**。
  - `tests/gpu_attention_parity_test.ts`（分解経路との Uint32 完全一致）は **f32 変種専用のまま**。
    f16 変種には**別の門**が要る（§4.5）。
- 誤差の目安（試算）: f16 の相対 eps は 4.88e-4（仮数 10bit）。
  - **(a) タイル f16・累積 f32**: 各積が f16 精度に丸まる → 内積の相対誤差はおよそ
    `4.88e-4 × O(√k)`。k=2048 なら ≈2e-2 …ではなく、**入力を f16 に丸める**ぶんが支配的で
    相対 1e-3 級。**現行 E2E の 1e-5〜1e-4 級とは 1〜2 桁違う** → tolerance は「実測から素で
    再導出」が必須（w8 / w8a8 系列と同じ流儀）。
  - **(b) S の f16 格納**: S の絶対値が大きい行（ADR 0023 の golden は logit −195 の域を持つ）で
    `exp(S−m)` の指数に絶対誤差 `|S|·4.88e-4` が乗る。|S|≈10 でも 0.005 → P に 0.5% の誤差。
    **w8a8（PSNR 13.28dB）よりはるかに良いが、現行の 1e-5 級からは大きく離れる**。
    → **Q0 相当の品質ゲート（torch 側での事前見積もり）を ADR 0025 と同じ形で置くべき**。
- **fake-quant 正の原則（ADR 0006）との関係**: 格納 f16 は「エクスポータが f16 に丸めた重みで
  参照を作る」で成立していたが、**計算 f16 は参照側で再現できない**（torch の f16 計算は
  縮約順序も異なる）。→ **参照は f32 のまま置き、E2E は「判別帯」で検出力を作る**
  （ADR 0025 決定 6 の設計をそのまま縮約）。ここは w8a8 で一度通った道なので前例がある。

### 4.2 どの系列に新 tolerance が要るか（opt-in 前提での本数）

**既定 f32 不変を守る限り、既存系列は 1 本も動かない**（w8a8 のときの実績 —
ADR 0025「既存 tolerance 変更ゼロ」）。新規に要るのは:

| 層                | 追加するもの                                                                       |              本数 |
| ----------------- | ---------------------------------------------------------------------------------- | ----------------: |
| カーネル単体      | f16 変種 vs f32 参照の**理論由来 tolerance**（atol=0 は取れない）+ 変種間の一致    |        1 ファイル |
| 恒久の門          | パイプラインキー検査（f16 変種が実際に走ったか / f32 変種が 0 本か）               | 既存テストへ 1 節 |
| E2E               | Anima 系列 1 本（`e2e_anima_f16compute_test.ts` 相当・step1 の判別帯 + 最終画像）  |        1 ファイル |
| 縮退 / full-write | 新カーネル族を `gpu_gridstride_test.ts` / `gpu_full_write_test.ts` へ（族の MUST） |           各 1 本 |

対して **既定を f16 に倒す設計**を採ると、再導出は Anima 4 ファイル + DeBERTa 2 + SBV2 1 +
golden 1 の **8 ファイル・数十 tolerance** に膨れる（`tests/*_test.ts` の TOLERANCE 定数は
現状 **41 個**）。**opt-in 一択**と考える。

### 4.3 ノブの形（compute 精度という第 2 軸）

現状は 1 軸だけ（`src/runtime/executor.ts:242-256`）:

```ts
readonly linearCompute?: "f32" | "i8a8";
```

候補:

- **(A) 直交ノブ**: `computePrecision?: "f32" | "f16"` を 1 本足し、既存 `linearCompute` と直交させる。
  - 長所: 語彙が最小。短所: `linearCompute:"i8a8"` × `computePrecision:"f16"` という
    **無意味な組み合わせが型で作れてしまう**（実行時 fail loudly が要る）。
- **(B) 統合列挙**: `compute?: "f32" | "i8a8" | "f16" | "w8a16"` の 1 本に畳む。
  - 長所: 排他が型で表現される。短所: **attention と linear で別々に選べない**
    （1024px は attention 46% / linear 42% で、片方だけ f16 にしたい場面が実際にある）。
- **(C) 族ごとの軸（推奨）**:
  ```ts
  readonly linearCompute?: "f32" | "i8a8" | "w8a16";   // 同一 op 内は排他 → 列挙が自然
  readonly attentionCompute?: "f32" | "f16";           // 別の op 族 → 別の軸
  ```
  - 長所: **排他は列挙で・独立は別軸で**表現でき、無意味な組み合わせが作れない。
    段階投入（attention だけ f16）とそのまま噛み合う。診断もキー別に分かれて見える。
  - 短所: ノブが増える（が、`SessionOptions` は既に「族ごとの opt-in」の形をしている）。
  - **命名の注意**: 格納 f16（ADR 0018）と計算 f16 は**別物**。ノブ名・キー名・診断名は
    `wf16`（格納）と衝突しない語にする（例: キー `linear:v4:w8a16:reg64x64v4` /
    `attention_qk:v2:f16:reg64x64v4`）。

### 4.4 w8a16 の位置づけ（数式レベル）

- 定義: 重みは既存 i8 資産（`unpack4xI8` + per-channel scale）、活性を f16 にして f16 で内積、
  累積 f32。**dp4a は使えない**（整数内積ではない）。
- 期待: 共有タイルのバイトが半分（f32 → f16）だけ。**ALU 1:1 なので理論上限も 2× に届かない**。
  **w8a8（実測 3.25×）より確実に遅い**。
- では何のためか: **品質**。w8a8 は「別の絵になる」ことをユーザー目視で受理した経路
  （ADR 0025）で、DeBERTa では hidden SNR 20.7〜23.3dB（ADR 0026）。
  **f16 活性は業界標準の推論精度**で、劣化はほぼ無視できる。
  → **w8a8 が品質で不合格なモデル／用途の中間点**という位置づけなら価値がある。
  「速度のための w8a16」は本機では成立しない（推測ではなく ALU 1:1 という事実から）。

### 4.5 検出器の設計（w8a8 の教訓の再利用）

- **f16 変種 vs f32 変種の atol=0 は原理的に取れない**（w8a8 は整数縮約だから取れた）。代わりに:
  1. **TS 参照側に f16 丸めを持つ**（`Math.fround` の f16 版 = `Float16Array` があれば素直。
     無ければビット演算で書く）。「GPU の f16 演算」と「TS の f16 模倣」は**縮約順序を揃えれば
     厳密一致しうる**（f16 の乗算・加算は IEEE 754 binary16 で一意）。**ここは atol=0 を狙える**
     — ただし WGSL 実装が f16 演算を f32 で行って最後に丸める（"promote" 実装）ことが許される
     かはドライバ依存なので、**atol=0 を契約にする前に実測で確かめる**（推測・要検証）。
  2. **恒真化しない判別帯**（ADR 0025 決定 6）: 「f32 経路に静かに落ちたら赤」になる下限を実測で
     決める。
  3. **キー検査**: f16 変種のキー本数と f32 変種 0 本（ADR 0026 の DeBERTa 検出力の形）。
- **故障注入の重点**（過去の検出限界の類型から）: ①`enable f16` の欠落（コンパイル失敗なので loud）
  ②累積を f16 にする変異（**k=2048 で桁落ち — 実測形でも値に出るはず**）③f16 → f32 変換位置の
  ずらし ④タイル充填時だけ f32 のまま（利得ゼロだが値は正しい = **時間でしか検出できない**
  → ADR 0024 追補の「述語の誤りは数値テストで検出不能」と同型の穴。検出器はキーと
  マイクロベンチのみ、と記録すべき）。

## 5. 段階分割の候補（3 案）

### 案 α（推奨）— 「Q0 マイクロベンチ → attention だけ f16 タイル」

1. **Q0（GPU 空き時に実施・実装 0 行）**: 実形状（1024px の `B·H=16, M=N=4096, D=128` と
   linear の `M=4096,N=2048,K=2048`）で 3 変種を同一 submit 内交互で計測
   — (i) 現行 f32 vec4 (ii) f16 タイル・累積 f32 (iii) 共有だけ packed f16（`unpack2x16float`・
   演算 f32／feature 不要）。**#28 の「マイクロベンチで勝った場合のみ配線」を踏襲**。
2. 勝てば **feature 配線（§1.2）+ `attentionCompute:"f16"`**（別キー・opt-in・既定不変）。
3. tolerance は新規 1 系列のみ（§4.2）。

- 期待利得: **DiT GPU の 0〜15%（1024px）**・512px はより小さい。
- 検証コスト: 小（既存系列ゼロ + 新規 1 系列 + 単体 1 ファイル）。
- リスク: **Q0 で負ける確率が実質的にある**（ALU 1:1 という事実から。負けたら変種は残して
  述語を結ばない = #28 の裁定形をそのまま使える）。

### 案 β — 「S の半精度受け渡し（feature 不要）＋ 案 α」

- ① QK が S を packed f16 で書き、② stats と ③ PV が unpack して読む。
  **shader-f16 を一切使わない**（core WGSL の `pack2x16float` / `unpack2x16float`）。
- 期待利得: 時間 −3〜5%（試算）だが、**1024px の DiT transient が 1,073.7MB → 536.9MB**。
  1024px の VRAM ピーク（i8 系列 6,725MiB）に対して意味のある削減で、
  **2048px / VAE tiling（`docs/research/2026-08-03-dynres-vae-tiling.md`）の前提を緩める**。
- 検証コスト: 中（S の丸めは全 attention ノードの数値に効くので E2E tolerance 再導出が要る。
  Q0 相当の品質見積もり推奨）。
- リスク: **時間の利得は小さい**（DRAM は律速でない — §3.2）。「メモリのための案」と割り切る。

### 案 γ — 「活性 f16 の全面伝播（中間バッファ f16 化）」

- 意味論を変えずに中間テンソルの**格納**を f16 にする（ADR 0006 が明示的に不採用としてきた軸）。
- 期待利得: 非 GEMM 系（strided / elementwise / layout）は帯域律速なので、ここが最大の未収穫。
  DiT の strided 実効 680 GB/s（`attention-design.md:705-706`）に対し VAE は 86 GB/s。
- 検証コスト: **最大**（全 op × 全系列。ADR 0006 / 0011 / 0018 の前提に触る）。
- リスク: 大。**#29 の枠を超える**（別マイルストーン相当）。今回は**候補として記録するだけ**を推奨。

## 6. openQuestions（メイン裁定・閉じた選択肢）

1. **着手の門**: (a) Q0 マイクロベンチ先行で、勝った場合のみ配線（#28 の先例・推奨） /
   (b) Q0 なしで案 α を実装して実測で判断 / (c) 本機では ALU 1:1 なので **#29 は
   「feature 配線 + 変種を持てる形」までで止め、時間の勝ちは狙わない**。
2. **feature の既定**: (a) `shaderF16` は **`undefined` = 要求しない**（数値が変わるため auto 禁止・推奨） /
   (b) ADR 0021 と同型の三値 auto（feature があれば要求する）。
3. **第 1 波のスコープ**: (a) attention だけ（案 α） / (b) attention + S の半精度受け渡し（案 α+β） /
   (c) linear の w8a16 も同波（品質フォールバック枠）。
4. **ノブの形**: (a) 族ごとの軸 `linearCompute` 拡張 + `attentionCompute` 新設（推奨） /
   (b) 直交ノブ `computePrecision` 1 本 / (c) 統合列挙 `compute` 1 本。
5. **w8a16 の扱い**: (a) 品質フォールバックとして実装する（速度は主張しない） /
   (b) 実装せず「shader-f16 と合流」の予告（ADR 0025 参照節）を**却下側へ更新** /
   (c) 保留（Q0 の結果次第）。
6. **数値契約の狙い**: (a) TS 参照に f16 模倣を置いて **atol=0 を狙う**（成立するか要実測） /
   (b) 最初から理論由来 tolerance で運用し、atol=0 は狙わない。
7. **記録先**: (a) 新 ADR 0027 を起こす（feature 方針の変更 = ADR 0021 決定 4 の改訂を含むため推奨） /
   (b) ADR 0018 の「upgrade path」節への追補。

## 7. 隣接（本タスクのスコープ外・報告のみ）

1. **「f16 計算 1.44×」を引いている記述が 4 箇所あり、いずれも但し書きが無い**:
   `.claude/ACTIVE_DESIGN.md`（#29 の動機）/ `docs/decisions/0018-f16-weight-execution.md:42-44` /
   `docs/research/2026-08-03-gemm-design.md:26`・`:458` /
   `docs/research/2026-08-03-demo-w8-perf-recon.md:20`。**基準が旧カーネル**（現行比 0.47×）で
   あることと**交絡 4 点**（§2.2）は ADR 0025 が DP4a に対して行った訂正と同型の扱いが要る。
2. **attention は linear の 1/3.4 のスループットしか出ていない**（3,900 vs 13,273 GFLOP/s・試算）。
   f16 とは独立に、**attention の a8 化（q/k を per-token i8 にして QK を dp4a）**が
   桁の大きいレバーになりうる（PV 側は P が [0,1] なので量子化しやすい）。品質ゲートは w8a8 と同型。
3. **Deno の shader-f16 沈黙故障報告（denoland/deno#23125・open）**は #29 に限らず
   「optional feature を使うときは必ず実走の門を置く」という一般則の材料。
4. **ADR 0021 決定 4 の「`enable f16` などシェーダ側の feature 依存ゼロは不変」は #29 で破れる** —
   ADR 側の文言更新が必要（黙って破らない）。
5. `src/gpu/device.ts:122-131` の `REQUIRED_FEATURES` doc も同様に更新対象
   （「無条件に要求する feature は無い」は維持できるが、理由の記述が変わる）。

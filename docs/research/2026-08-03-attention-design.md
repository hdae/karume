## 0. 結論サマリ（先に読むところ）

1. **形は極めて単純で一様**。DiT の attention は **28 層 × 2（self / cross）= 56 本**、
   全て **マスク無し・causal 無し・B=1・H=16・D=128**。scale は
   `const 0.2973017692565918 = 128^-0.25` を **q と k^T の両方に掛ける** torch SDPA
   math decomp そのもの。間に挟まるのは `permute`(K^T) / 恒等 `expand`×3 / `reshape`(別名) だけ。
2. **時間の頭打ちは思ったより低い**。融合で消せるのは
   **512px 106.7ms / 968.3ms = 11.0%**、**1024px 1,587.9ms / 5,871.0ms = 27.0%**（DiT の GPU 実時間）。
   ただし融合カーネル自身が同じ FLOP（512: 360.8 GFLOP / 1024: 4,329.3 GFLOP）を払う。
3. **⚠ プロトタイプ実測では融合は時間を悪化させた**（1024px **+12.5%** / 512px +3.1%）。
   融合カーネル 5,498 GFLOP/s に対し同機の GEMM は 10,754 GFLOP/s で、**flash 型は
   FLOP あたり約 2 倍遅い**。Karume でも素直に移植すれば
   **1024px で +19%・512px で +6% の悪化**が見積もられる（§2.4）。
   **融合 attention は「時間」ではなく「メモリ」の施策**と読み替えるべき。
4. **メモリの効きは絶大**。1024px の S と P が **1,073.7MB × 2 = 2,147.5MB** 同時生存で、
   これが denoise 中の VRAM（実測 6,725MiB − 常駐 3,732MiB = 2,993MiB）の主成分。
   完全融合で **33.6MB** まで落ちる。VAE decoder も同型（1024px で S/P 各 1,073.7MB）で、
   **1024 チェーンの床（6,725MiB）を決めているのは VAE のこの 1 本**。
5. **時間だけを見るなら、融合より先にやるべき「数値不変の掃除」がある**（§2.5）。
   恒等 `expand` **224 本**と恒等になる `permute` ペア **280 組（560 本）**が、
   1024px で **strided 全体 172.2ms のうち 152.4ms（88.5%）**と
   **dispatch 3,137 本のうち 784 本（25.0%）**を占めている。**数値は 1 ビットも動かない**。
6. 推奨は **案 B（段階融合）**: `attention` op を 1 個新設し、executor はそれを
   **3 dispatch（QK gemm → 行統計 → 正規化読みつき PV gemm）**でエンコードする。
   S は実体化するが **P は実体化しない**。既存 GEMM 骨格の縮約順序を温存できるので
   **ビット同一（PNG sha256 一致）を狙える**唯一の案で、時間は悪化しない。
   flash 完全融合（案 A）は **同じ op 契約のままキー変種として後段**に置く。

## 1. 実グラフの attention 部分グラフ（形の確定）

### 1.1 DiT（`models/anima-f16/transformer` / `models/anima-f16-1024/transformer`）

両者 **ノード数 3,904 で完全に同型**。違うのは `latents` が `[1,16,64,64]` か `[1,16,128,128]` かだけ。
op 内訳（両解像度で同一）:

| op      | 本数 |   | op          |    本数 |
| ------- | ---: | - | ----------- | ------: |
| reshape |  824 |   | expand      |     224 |
| permute |  736 |   | rms_norm    |     113 |
| linear  |  454 |   | **bmm**     | **112** |
| mul     |  395 |   | layer_norm  |      85 |
| add     |  395 |   | cat         |      57 |
| slice   |  367 |   | **softmax** |  **56** |
|         |      |   | neg         |      56 |
|         |      |   | gelu        |      28 |
|         |      |   | sigmoid     |       2 |

**self-attention（`attn1`・28 本）の完全な形**（512px・node 番号は 0 層目）:

```
#29-31 linear ×3  q/k/v : [1,1024,2048]            (attn1_to_{q,k,v}_weight [2048,2048])
#32-37 reshape+permute   : [1,1024,16,128] → [1,16,1024,128]
#38-39 rms_norm q,k      : eps=1e-5, weight [128]   (QK-norm)
#40-46 RoPE q            : slice/slice/neg/cat/mul/mul/add   ← neg 56 本の出所
#47-53 RoPE k            : 同上
--------- ここから下が torch SDPA の math decomp -------------------------------
#54-56 permute [0,2,1,3] : [1,16,1024,128] → [1,1024,16,128]   ← 対合の往復（前半）
#57-59 permute [0,2,1,3] : [1,1024,16,128] → [1,16,1024,128]   ← 対合の往復（後半）
#60    mul  q  × const_6953fe58410d6c34[1] = 0.2973017692565918
#61    permute [0,1,3,2] : k → k^T [1,16,128,1024]
#62    mul  k^T × 同じ const
#63,65 expand（恒等）    : [1,16,1024,128] / [1,16,128,1024]
#64,66 reshape（別名）   : [16,1024,128] / [16,128,1024]
#67    bmm               : [16,1024,128]·[16,128,1024] → S[16,1024,1024]
#68    reshape（別名）   : [1,16,1024,1024]
#69    softmax dim=3     : P[1,16,1024,1024]
#70    expand（恒等）    : P のフルコピー ★
#71    reshape（別名）
#72,73 expand（恒等）+reshape : v
#74    bmm               : [16,1024,1024]·[16,1024,128] → O[16,1024,128]
#75    reshape（別名）
#76,77 permute [2,0,1,3]→[1,2,0,3] : 合成が恒等の往復
--------- ここまで -----------------------------------------------------------
#78    permute [0,2,1,3] : [1,1024,16,128]
#79    reshape（別名）   : [1,1024,2048]
#80    linear            : attn1_to_out_0_weight
```

**cross-attention（`attn2`・28 本）**は RoPE が無く、k/v が `encoder_hidden_states[1,512,1024]`
由来（`attn2_to_k_weight [2048,1024]`）である点だけが違う。`rms_norm` の QK-norm は両方にある。

**確定した事実（すべて実測）**:

- **mask は 1 本も無い**。`masked_fill` / mask の `add` / `where` は attention 経路に不出現。
  causal も無い（`softmax` の入力は `reshape(bmm)` 直結）。
- **scale の位置**: `mul` が **q 側と k^T 側の 2 本**。定数は両方とも同一テンソル
  `const.6953fe58410d6c34` = **0.2973017692565918**（= f32(√(1/√128)) = `128^-0.25`）。
  これは `aten::_scaled_dot_product_attention_math` の
  `q *= √scale_factor; k *= √scale_factor` そのもの。
- **`expand` は 224 本すべてが恒等**（入力 shape = 出力 shape）。内訳は
  q/k^T 側 112・P 側 56・v 側 56 で、**全部が SDPA decomp 由来**。
- **`permute` 736 本のうち 560 本（280 対）が「合成すると恒等」の隣接ペア**。
- 記号次元なし（`symbols: []`）。**shape は完全静的**。

| --------------------- | ----- | -------------: | -: | --: | -----------------: | ---------: | ------: | ---------------------- |
| DiT 512px             | self  |             28 |  1 |  16 |              1,024 |      1,024 |     128 | 無                     |

| text_encoder          | self  |             28 |  1 | 16※ |            T(≤512) |          T |     128 | **−inf 加算・因果**    |

### 1.3 スコープ判定（融合可否）

| 対象                          | 判定                     | 理由                                                                                                                                                                                                    |
| ----------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DiT self / cross（56 本）** | **○ 本命**               | マスク無し・D=128・完全静的。時間もメモリもここが支配項                                                                                                                                                 |
| **text_conditioner（12 本）** | ○ 付随                   | 同型で D=64。ただし GPU 時間 0.10ms/18.7ms で**効果は測定限界以下**                                                                                                                                     |
| **VAE decoder（1 本）**       | △ **メモリのみ**で価値大 | D=384。時間は 143ms/15,833ms（0.9%）だが **S/P で 2,147MB** を食い、**1024 チェーンの床そのもの**。ただし D=384 は共有メモリに載らず**別タイル構成が要る**（§4.3）                                      |
| **text_encoder（28 本）**     | ✕ v1 では除外            | −inf 折り込み因果マスクが要る（arity 4 か attrs `causal`）。GPU 時間は **72.2ms/step 相当ではなく 1 回きりの 72.2ms** で、全体 26s の 0.3%。契約を広げるコストに見合わない                              |
| **SBV2 front / flow / voice** | ✕ **構造的に不可**       | ① 相対位置バイアスを `gather` して score に加算 ② `masked_fill(−10000)` ③ **softmax 出力が 2 回消費される**（`bmm(·V)` と `pad→gather→bmm`（相対位置 value 側））。P を実体化しない融合は定義上できない |

### 2.2 融合で「消える」時間の内訳

`strided` と `ew:mul` は要素数按分で attention 由来分を切り出した（IR から算出した要素数と
実測 workgroup 数が **grid-stride 上限 65,535 のクランプまで含めて完全一致**することを確認済み —
512px: 計算 9,523,220 = 実測 9,523,220 / 1024px: 計算 27,650,184 = 実測 27,650,184）。

| 消える対象                                 | 512px (ms) |  1024px (ms) | dispatch |
| ------------------------------------------ | ---------: | -----------: | -------: |
| `bmm` ×112（QK^T と ·V）                   |      79.99 |     1,302.36 |      112 |
| `softmax` ×56                              |      10.75 |       160.22 |       56 |
| 恒等 `expand`（q/k^T 112・**P 56**・v 56） |      12.31 |       111.54 |      224 |
| `permute`（k^T）×56                        |       1.09 |         3.12 |       56 |
| `mul`（scale）×112                         |       2.55 |        10.63 |      112 |
| **合計（除去可能）**                       | **106.67** | **1,587.87** |  **560** |
| DiT GPU 実時間に対する比                   | **11.02%** |   **27.05%** |    17.9% |

新たに増える dispatch は 56 本なので、**正味 −504 本 / 3,137 本 = −16.1%**。

### 2.4 ⚠ 純利得のシナリオ表 — 「素直な flash 移植は遅くなる」

融合カーネルの実効スループットを変数にした純利得（+ は悪化）:

**512px（除去可能 106.67ms / DiT 合計 968.32ms）**

| 融合カーネルの想定                    | GFLOP/s | 融合後の時間 |      純利得 |        DiT GPU 比 |
| ------------------------------------- | ------: | -----------: | ----------: | ----------------: |
| **プロトタイプ比（現 bmm の 0.48×）** |   2,165 |      166.6ms | **+59.9ms** | **+6.2%（悪化）** |
| 現 bmm と同等                         |   4,511 |       80.0ms |     −26.7ms |             −2.8% |
| 現 bmm の 1.5×                        |   6,767 |       53.3ms |     −53.4ms |             −5.5% |
| 現 bmm の 2×                          |   9,022 |       40.0ms |     −66.7ms |             −6.9% |

**1024px（除去可能 1,587.87ms / DiT 合計 5,870.98ms）**

| 融合カーネルの想定                    | GFLOP/s | 融合後の時間 |         純利得 |         DiT GPU 比 |
| ------------------------------------- | ------: | -----------: | -------------: | -----------------: |
| **プロトタイプ比（現 bmm の 0.48×）** |   1,596 |    2,713.5ms | **+1,125.6ms** | **+19.2%（悪化）** |
| 現 bmm と同等                         |   3,324 |    1,302.4ms |       −285.5ms |              −4.9% |
| 現 bmm の 1.5×                        |   4,986 |      868.3ms |       −719.6ms |             −12.3% |
| 現 bmm の 2×                          |   6,648 |      651.2ms |       −936.7ms |             −16.0% |

**「0.48×」の根拠（プロトタイプの実測から復元）**:

- プロトタイプの融合 attention（T3b）は実形状 B16 M4096 N4096 D128 で **5,498 GFLOP/s**、
  同機の GEMM ベンチ（M4096 N=K=2048）は **10,754 GFLOP/s**（比 0.51）。
- プロトタイプの 1024px step 実測は **融合なし 3.864 s/step → 融合あり 4.346 s/step（+12.5%）**。
  512px は 0.979 → 1.009（+3.1%）。同じモデル・同じ解像度で、**融合は時間の損だった**。
  この比較の baseline は既に恒等 expand の別名化（T0-a）と permute 連鎖畳み込み（T0-b）を
  含むので、Karume の現状より有利な baseline である点に注意（＝ Karume では
  §2.2 の 125ms（1024px）ぶんだけ融合側に追い風がある）。
- この step 時間差から逆算すると、プロトタイプの **未融合 bmm ペアは約 11,468 GFLOP/s**
  （softmax の帯域律速ぶん ≈338ms を分離した推定）。**融合/未融合 = 0.48**。

**結論**: プロトタイプのタイル構成をそのまま持ってくると、Karume でも
**1024px で +19% / 512px で +6% の悪化**が既定路線。時間で勝つには「現 bmm と同等以上」の
スループットが要る。§4.3 で述べるとおり、**D=128 かつ共有メモリ 32KB の制約下では
プロトタイプの構成がほぼ拘束された最適**なので、**flash 型で時間の勝ちを設計目標に置くのは
危険**である。

### 2.5 ⚠ 融合より先にやるべき「数値不変の掃除」（重要）

IR 実測で判明した、**1 ビットも値を変えずに消せる**コピー:

| 掃除                                   |            本数 | 512px 要素数 | 1024px 要素数 |  512px 時間 |  1024px 時間 |
| -------------------------------------- | --------------: | -----------: | ------------: | ----------: | -----------: |
| 恒等 `expand`（in shape == out shape） |             224 |       998.2M |      9,454.0M |     12.31ms |     111.54ms |
| 合成が恒等の隣接 `permute` ペア        | 280 対 = 560 本 |       998.2M |      3,464.5M |     12.30ms |      40.88ms |
| **合計**                               |      **784 本** | **1,996.4M** | **12,918.5M** | **24.61ms** | **152.42ms** |
| `strided` 全体に占める比               |           59.1% |        81.9% |         88.5% |       81.9% |        88.5% |
| dispatch 3,137 に占める比              |       **25.0%** |              |               |             |              |

- **恒等 expand 224 本は全数が SDPA decomp 由来**（`_drop_identity_repeat` / `_drop_identity_add`
  と同じ族の normalize パス 1 本、または executor の `reshape` 別名化を
  「out shape == in shape の expand」へ広げるだけで消える）。
- **恒等 permute ペア 280 組**は `[0,2,1,3]`（対合）や `[2,0,1,3]→[1,2,0,3]` の往復。
  プロトタイプの `foldPermuteChains`（T0-b）に相当。
- GPU 時間の効きは 512px 2.5% / 1024px 2.6% と控えめだが、**dispatch −25%** は
  壁時計側の固定費に効く（512px は 1 step 壁 1,452ms 対 GPU 968ms = 固定費 484ms、
  1024px は 6,390ms 対 5,871ms = 519ms。dispatch 比例と仮定すると 512px −121ms/step（−8.3%）・
  1024px −129ms/step（−2.0%））。
- **恒等 expand の除去は、そのまま P の 1 枚ぶん（1024px で 1,073.7MB）の peak 削減でもある。**

この掃除は **融合 attention の実装によっても同じ範囲が消える**（§2.2 に内包）。したがって
「融合をやらない／後回しにする」判断をしても掃除だけは独立に取れる、という関係にある。

### 2.6 メモリ（融合の本命）

|                    |  S = QK^T | P = softmax(S) | E = 恒等 expand(P) |  同時生存の峰 | 融合後 |
| ------------------ | --------: | -------------: | -----------------: | ------------: | -----: |
| DiT 512px（1 本）  |    67.1MB |         67.1MB |             67.1MB |   **134.2MB** |  8.4MB |
| DiT 1024px（1 本） | 1,073.7MB |      1,073.7MB |          1,073.7MB | **2,147.5MB** | 33.6MB |
| VAE 1024px（1 本） | 1,073.7MB |      1,073.7MB |          1,073.7MB | **2,147.5MB** | 25.2MB |

（生存解析: `bmm→S`、`softmax` が S を読み P を書く瞬間に S+P が同時 → S 解放 →
`expand` が P を読み E を書く瞬間に P+E が同時。どちらの局面も 2 枚ぶん。）

実測との突合: 1024px denoise 中の VRAM 中央値は f16 **6,725MiB**（常駐 3,732MiB）/
i8 **4,677MiB**（常駐 1,871MiB）で、差は 2,993 / 2,806MiB。**S+P の 2,048MiB がその主成分**。
VAE decode の 1024px ピーク 6,725MiB も同じ 2,048MiB を含み、
`examples/anima/README.md` の「**1024 チェーンの下限を決めているのは DiT ではなく VAE**」は
このバッファのことを指している。

**したがって融合の第一目的はメモリで、その効きは（時間と違って）疑いようがない。**
本機の GPUBuffer 天井 7,280MiB（`docs/known-issues.md`）に対しても、
DiT と VAE の両方を融合できれば 1024 チェーンの床が **約 2.1GB 下がる**。

## 3. プロトタイプの融合 attention（T3b 系譜）の読解

### 3.1 カーネル構造

- **タイル**: 1 workgroup が Q の **BR=32 行**を担当し、K/V を **BC=16 列**ずつ流す
  （online softmax で走査中に行の max と総和を更新）。**T=128 スレッド**。
- **スレッド割当**: `rg = t/8`, `cg = t%8`。1 スレッドが **S の 2×2** と
  **出力 2 行 × D/8 チャンネル**（D=128 なら 16 ch = 32 個の acc）を持つ。
  行 `{rg, rg+16}`・列 `{cg, cg+8}` の「飛ばし」割当で、共有メモリのバンクと
  `out` への書き込みの両方を散らす。
- **共有メモリ（D=128 で 27,232 B）**: `qs` 16.5KB + `kv` 8.25KB + `ps` 2KB + 行統計 384B。
  **行 stride は D ではなく D+1**（D=128 は 32 バンクの倍数なので、そのままだと
  `kv[c*D+dd]` が列 c によらず同じバンクに落ちて 16-way 衝突）。
  仕様既定の 16,384 B では載らないので **`maxComputeWorkgroupStorageSize` の明示要求が前提**
  （Karume は `src/gpu/device.ts` でアダプタ値をそのまま要求済み — 追加要求は不要）。
- **online softmax**: `mOld/mNew/corr = exp(mOld-mNew)` を行ごとに 1 スレッドで更新し、
  acc をブロックごとに `corr` 倍して補正。最後に `1/rowSum` を掛けて書き出す。
- **−∞ の扱い**: 行 max の初期値に `-3.0e38`（f32 最小有限値ではない）を使う。
  「−inf 同士の減算が NaN になる」ため、**指数が確実に 0 へ潰れる有限値**を選んでいる。
- **スケールは融合していない**（K^T 側の `mul` で既に掛かっている前提）。
- **マスクも扱わない**。融合するかどうかの判定側（`fuseAttention`）が
  「bmm→softmax→bmm の鎖に他の消費者が居ないこと」で担保。

### 3.2 ベンチ条件とタイル構成スイープ（プロトタイプの実測表）

実 Chrome / RTX 5070 Ti・**B16 M4096 N4096 D128**（= Anima 1024px の self-attention 実形状）。
全変種を CPU 参照（端数形状 m=70 n=37 d=128 / m=33 n=16 d=64）で検算済み。

| 構成（BR×BC・スレッド数・1 スレッドの S タイル） |   GFLOP/s |
| ------------------------------------------------ | --------: |
| 32×16・T512・1×1（初版）                         |     2,365 |
| 32×16・T256・2×1                                 |     4,042 |
| 32×16・T128・1×4                                 |     4,308 |
| 32×16・T64・4×2                                  |     5,086 |
| 32×16・T128・4×1                                 |     5,186 |
| **32×16・T128・2×2（採用）**                     | **5,498** |

### 3.3 記録された落とし穴（そのまま Karume にも効く）

1. **共有メモリの行 stride を D ちょうどにすると 16-way バンク衝突**（→ `D+1`）。
2. **出力チャンネルの担当を連続塊にすると** PV 積の共有読みが 4-way 衝突・
   `out` への書き込みも coalesce しない（→ `cg + k*COL_GROUPS` の飛ばし割当）。
3. **K^T は `[D,N]` レイアウトなのに連続 tid を D 方向へ割り当てると**
   1 要素ごとに N ワード飛び、transaction がスレッド 1 本ずつになる（→ tid を N 方向へ）。
   この 3 点の修正だけで **1024px の悪化が +130% → +12.5% に縮んだ**。
4. **行ごとに `m`（範囲）を判定する MUST**。1 スレッドが複数行を持つので、
   先頭行だけ見ると末尾 workgroup が範囲外へ書き、**別バッチの領域を壊す**
   （プロトタイプが実際に踏んだ）。
5. **ヘッド次元の上限**: `BR·(D+1) + BC·(D+1) + BR·BC + 3·BR ≤ 8,192 word ⇒ D ≤ 152`。
   VAE の **D=384 は載らない**ので融合対象外だった。
6. **「1 スレッド 1 要素」にすると共有 2 ロード / 1 FMA にしかならない**（2,365 GFLOP/s）。
   2×2 で 4 ロード / 4 FMA（5,498）。演算順序が変わらないので出力はビット不変。
7. `subgroup-matrix` 系は WebGPU に無く、テンソルコアには届かない。

## 4. 設計論点

### 4.1 (i) op 契約 — `attention` の arity / attrs / 出力 shape / 契約 4 点セット

**提案する契約**:

| 項目               | 内容                                                                              |
| ------------------ | --------------------------------------------------------------------------------- |
| op 名              | `attention`                                                                       |
| kind               | `attention`（`OpContract` の判別可能ユニオンに 1 本追加）                         |
| arity              | **3 固定**（q, k, v）。可変アリティは `cat` のみという既存規律を崩さない          |
| 入力 shape         | q `[B,H,M,D]` / k `[B,H,N,D]` / v `[B,H,N,D]` — **rank 4 固定・head-first・連続** |
| 出力 shape         | `[B,H,M,D]`                                                                       |
| dtype              | uniform `f32` のみ（`bmm` / `softmax` と同じ）                                    |
| attrs              | **`scale`（f32・宣言必須・既定値補完なし）**                                      |
| 数式（契約の正本） | `out = softmax_lastdim((q·scale) @ (k·scale)^T) @ v`                              |

**attrs `scale` を「q と k の両方に掛ける半スケール」と定義することの是非**は最大の分岐点。

- **(α) 半スケール**（`scale = 128^-0.25 = 0.2973017692565918`）:
  torch の math decomp と**同じ丸め列**になるので、**現行出力とのビット同一が狙える**。
  ADR 0022 が使った「PNG sha256 一致」の門をそのまま再利用できる。
  代償は「契約の数式が `√` を含む見慣れない形」。
- **(β) 全スケール**（`scale = 1/√128`・内積後に 1 回掛ける）:
  数式が自然で、torch の**融合**実装（flash）とも整合。
  代償は**丸めが変わる**ので tolerance を全系列で採り直し、ビット同一の門を失う。
  なお `f32(√(f32(1/√128)))` が `f32(√(f64(1/√128)))` と一致する保証は無い（最終 ulp）ので、
  「(β) の attr から (α) の値をカーネル内で導く」逃げ道は**取れない**。

→ **推奨は (α)**。契約 doc に「`scale` は q と k の両方に掛かる（torch SDPA の
`√scale_factor` と同義）」と MUST で書けば曖昧さは残らない。エクスポータは
SDPA の `scale` 引数（既定 `1/√D`）から `f32(math.sqrt(scale))` を計算して attrs に載せる。

**契約 4 点セットへの載せ方**（既存 op と完全に同じ 4 箇所）:

| 面             | 追加内容                                                                                                                                                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 契約表       | `src/ops.ts` に `ATTENTION_OP` / `kind: "attention"` / `ATTENTION_ATTRS`（`scale`）/ 出力 shape 計算。`tools/exporter/karume/ops.py` に同内容。適合表 `tests/fixtures/op-contracts.json` に op エントリ + attr 値域 + shape ケース（**両実装が同じ表を読む** — `tests/ops_conformance_test.ts` / `tools/exporter/tests/test_ops_conformance.py`） |
| ② WGSL         | `src/kernels/attention.ts`（案 B なら `src/kernels/gemm.ts` の 5 断片テンプレートの拡張 + 行統計カーネル 1 本）。スナップショットを `tests/fixtures/wgsl/attention*.wgsl` に                                                                                                                                                                      |
| ③ CPU 参照     | `src/reference/ops.ts` に `referenceAttention`（§4.4）                                                                                                                                                                                                                                                                                            |
| ④ エクスポータ | `PRESERVED_OP_PREFIXES` に 1 行 + `_h_attention` ハンドラ（§4.2）                                                                                                                                                                                                                                                                                 |

加えて **op 語彙台帳** `docs/op-vocabulary.md` の「分解禁止 11 op → 12 op」更新
（`attention` が Core ATen 160 に含まれないことは台帳 L17 が既に明記済み）と
`docs/ir-v1.md` の改訂履歴 1 行、ADR 1 本（0023 想定）。

### 4.2 (ii) エクスポータ側の融合検出

**実測で確定した事実**（本 recon 内で torch 2.13.0+cpu を使って確認）:

```
default_decompositions() に含まれる SDPA 関連エントリ:
  aten._scaled_dot_product_flash_attention_for_cpu.default
  aten._scaled_dot_product_attention_math.default
  aten.scaled_dot_product_attention.default        ← これを表から抜けば保存される

export 直後（decompose 前）の target: ['aten.scaled_dot_product_attention.default']
"aten.scaled_dot_product_attention." を preserved に足した decomp 後: 同上（保存成功）
足さない場合: ['aten._softmax', 'aten.any.dim', 'aten.bmm', 'aten.clone', 'aten.eq.Scalar',
              'aten.expand', 'aten.full_like', 'aten.logical_not', 'aten.mul.Scalar',
              'aten.permute', 'aten.view', 'aten.where.self']
引数形: (q, k, v, attn_mask=None, dropout_p=0.0, is_causal=False, scale=None, enable_gqa=False)
  - is_causal=True   → args に 'True' が乗る
  - attn_mask 指定   → args[3] が Node
  - enable_gqa=True  → kwargs に乗る
```

したがって **`PRESERVED_OP_PREFIXES` に `"aten.scaled_dot_product_attention."` を
1 行足すだけで融合検出が完成する**（既存 11 op と完全に同じ機構 — `convert.py:243` / `:1887`）。
normalize のパターンマッチ（`_fold_rms_norm` 型）は**不要**。

**2 つの選択肢**:

| 案                                  | 内容                                           | 長所                                                                                                                                   | 短所                                                                                                                                                                                       |
| ----------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **(ii-A) PRESERVED に足す**         | `curated_decompositions()` の既定表を 12 op へ | 実装は 1 行 + ハンドラ 1 本。パターンの脆さがゼロ。恒等 expand / scale mul / k^T permute / 対合往復の**decomp 由来ノードが全部消える** | **表がグローバル**なので text_encoder（mask 付き）/ SBV2（そもそも SDPA を通っていない）も保存対象になる。未対応形はハンドラで fail loudly になり、**text_encoder が export できなくなる** |
| **(ii-B) normalize のパターン照合** | `_fold_attention` で `bmm→softmax→bmm` を畳む  | ノード単位で「畳める形だけ畳む」判断が自然。scale の `mul` を op の外に残せば**ビット同一が自明**                                      | 照合対象が torch の実装詳細（decomp 形は safe-softmax ガードの有無で既に 1 度変化している）。コード量が大きい。ADR 0016 のガード除去パスと干渉する                                         |

**(ii-A) の短所の解き方（推奨）**: `curated_decompositions(preserved=…)` は**既に引数化済み**
（`convert.py:1887`）。`pipeline.export_module` に `preserved` キーワードを通し、
**ターゲット別に preserved 集合を選ぶ**。DiT / VAE / conditioner は SDPA 保存、
text_encoder は従来どおり分解（＝ ADR 0016 の safe-softmax ガード除去パスがそのまま効き続ける）。
`_h_attention` は mask / causal / dropout≠0 / GQA / rank≠4 を**全件列挙して fail loudly**。

**既存資産の再 emit**: IR の JSON（`__metadata__.karume_ir`）が変わるので、
**DiT を含む全系列の再 emit が必要**。対象は
`models/anima{,-f16,-f16-1024,-i8,-turbo-f16,-turbo-f16-1024,-turbo-i8,-turbo-i8-1024}/transformer`、
`.../vae_decoder`（VAE も融合するなら）、`models/anima-pipeline*`、
tiny golden の `attention_block`（`goldens.py:845`）。重みテンソル自体は 1 バイトも変わらないが
`write_model` はファイルを作り直すので、**約 10GiB の再書き出し**になる（波5 で
`conv1d` の attrs 追加時に同じことをやった前例あり）。

### 4.3 (iii) カーネル設計

#### 4.3.1 共有メモリ制約からの逆算（重要な現実確認）

flash 型は「Q タイルを共有に常駐させ、K/V を流す」構造なので、
`shared = (BR + BC)·(D+1)·4 + BR·BC·4 + 行統計` が **32,768 B**（本機のアダプタ値）に収まる必要がある。

|   D | BR | BC | 共有メモリ | 可否                  |
| --: | -: | -: | ---------: | --------------------- |
| 128 | 32 | 16 |   27,232 B | ○（プロトタイプ採用） |
| 128 | 48 | 16 |   33,024 B | ✕                     |
| 128 | 64 | 16 |   41,984 B | ✕                     |
|  64 | 64 | 16 |   24,832 B | ○                     |
| 384 | 32 | 16 |   76,928 B | ✕✕                    |

→ **D=128 では BR=32 / BC=16 が事実上唯一**。S タイルは 32×16 = 512 要素しかなく、
1 スレッド 4×4 のレジスタブロッキングを入れると **32 スレッドしか使えない**。
プロトタイプ recon の「残る +49% はレジスタブロッキングが無いこと」という自己診断は
**共有メモリ上限を勘定に入れると成立しない**（＝ ここを直せば GEMM 並みになる、
という期待は持てない）。**これは本 recon による反証**として記録する。

Q を共有に常駐させない構造（K タイルごとに Q を global から読み直す）は、
1024px で Q の再読みが 57GB/step になり、消したはずのトラフィックが戻ってくるので不可。

#### 4.3.2 案 B（段階融合）のカーネル構成 — 推奨

`attention` **1 ノード = 3 dispatch**（`cat` が入力ごとに複数 dispatch を出すのと同じ扱い。
full-write は**ノードの出力 O について**成立する）:

```
① QK dispatch : S[b,h,m,n] = (q·scale) @ (k·scale)^T
                gemm.ts の linear 変種と同じ「B を k 連続で読み共有で転置」構造
                （k は [N,D] のまま読める = permute(k^T) が不要）
                縮約は K 昇順・K タイル 16 → 現行 bmm と 1 ビット違わない
② 行統計       : m[row] = amax_n S, l[row] = Σ_n exp(S - m)
                現行 softmax.ts のパス①②をそのまま切り出す（同じ 256 幅ツリー縮約）
                出力は [B·H·M] の 2 本（または [B·H·M, 2]）— 数 MB
③ PV dispatch : O = P @ v,  P は A タイル読み込み時に exp(S - m[row]) * (1/l[row]) で生成
                gemm.ts の dense 変種の fillA を差し替えるだけ。縮約は現行 bmm と同一
```

**この構成の要点**:

- **P を実体化しない**（1024px で −1,073.7MB・−111.5ms の恒等 expand も同時に消える）。
- **S は実体化する**（peak は 2,147.5MB → 1,073.7MB の**半減**。完全融合の 33.6MB には届かない）。
- **数値**: ① は現行 `bmm` と同一の縮約順序・同一入力 → **ビット同一**。
  ② は現行 `softmax` のパス①②と同一 → `m` と `l` はビット同一。
  ③ の A 要素は `exp(S-m)*inv` を f32 で評価した値で、
  **現行 softmax がパス③で f32 に丸めて書き出す値とビット同一**（同じ式・同じ演算順）。
  以降の縮約も同一 → **出力全体がビット同一**。
  → **ADR 0022 と同じ「PNG sha256 一致」の門が使える**。
- **時間**: `softmax` の 3 読み 1 書き → **1 読み**（②）に減る（1024px で 160.2 → ≈40ms）。
  ③ で `exp` を追加評価する（A タイルは `ceil(D/64)` = 2 回読まれるので
  1024px で ≈16.9G exp/step。SFU 4/clk × 80SM × 1.7GHz ≈ 544 G exp/s として ≈31ms）。
  恒等 expand・scale mul・k^T permute は消える。

  |        | softmax 削減 | expand 削減 | permute+mul 削減 | exp 追加 |            **純利得** |
  | ------ | -----------: | ----------: | ---------------: | -------: | --------------------: |
  | 512px  |         −8.1 |       −12.3 |             −3.6 |     +2.6 |  **−21.4ms（−2.2%）** |
  | 1024px |       −120.2 |      −111.5 |            −13.7 |    +31.1 | **−214.3ms（−3.7%）** |

  **悪化リスクはほぼ無い**（`bmm` 2 本の時間はそのまま持ち越すため、最悪でも現行と同じ）。
  `exp` の SFU 見積りは**唯一の未実測項**で、ここが 5 倍外れると 1024px の純利得が消える
  （§9 のリスク）。
- **D の上限が無い**（gemm 骨格は D を K 次元として流すだけ）。**VAE の D=384 もそのまま通る**
  → 1024 チェーンの床が VAE 側でも 1,073.7MB 下がる。
- **`tiledWorkgroups`**: ① は `[ceil(N/64), ceil(M/64), B·H]`、③ は `[ceil(D/64), ceil(M/64), B·H]`。
  1024px self で ① は `[64, 64, 16]` — 上限 65,535 に対し余裕。**縮退させてはいけない**
  （タイル欠落＝未書き込み）ので既存どおり `tiledWorkgroups` で fail loudly。
  ② は行方向 grid-stride（`gpu_gridstride_test.ts` に 1 本追加する対象）。

#### 4.3.3 案 A（flash 完全融合）のカーネル構成 — 後段の変種

プロトタイプ T3b を移植（BR=32 / BC=16 / T=128 / S タイル 2×2 / 行 stride D+1 /
飛ばし割当 / `-3.0e38` 初期値）。**D ≤ 152 の制約**が付くので VAE は対象外。
online softmax により **S も実体化しない**（peak 33.6MB）。
**数値はビット同一にならない**（縮約順序が根本的に違う）。

#### 4.3.4 codegen 決定性

- WGSL は D で完全展開されるので **キーに D を載せる**（`elementwiseKey` の `r${rank}` /
  `gemmUsesVec4` の `v4` と同じ「形状 → キー」の語彙で、
  「同一キー ⇔ 同一バイト列」は保たれる）。
- **MUST: 縮約順序をキーで固定する**。案 B は「K 昇順・タイル 16」で ADR 0022 決定 3 と同一、
  案 A は online softmax の別順序なので**別キー・別 tolerance**（ADR 0022 の MUST
  「縮約順序を変える変種は tolerance 再導出とセットでしか入れない」がそのまま適用）。

### 4.4 (iv) CPU 参照実装の数値規律

**方針**: CPU 参照は「契約のオラクル」であって GPU の鏡像ではない
（`referenceBmm` は f64 で積んで最後に 1 度だけ f32 へ丸めており、既に GPU とビット同一ではない）。
したがって `referenceAttention` も**素直な 3 段**で書く:

```ts
S[b,h,m,n] = Σ_d (q*scale)[b,h,m,d] * (k*scale)[b,h,n,d]     // f64 累積 → f32 丸め 1 回
P = safe-softmax(S)   // amax を引く形 MUST（referenceSoftmax と同じ規律）
O = Σ_n P[..,n] * v[b,h,n,d]                                  // f64 累積 → f32 丸め 1 回
```

- **online 順にはしない**。オラクルが GPU と同じ壊れ方をすると突合が違反を検出できなくなる
  （`referenceSoftmax` の MUST と同じ理由）。案 A（online softmax）を入れたときも
  参照は据え置きで、**差は tolerance で吸収する**。
- `scale` を q と k の両方へ掛ける（契約 (α) をそのまま実装）。

**tolerance 再導出の段取り**:

1. **案 B を入れる波**: 出力がビット同一になる設計なので、
   **① 全 E2E の `atol=rtol=0` 実測 maxAbs が置換前の記録値と一致すること**
   **② デモの PNG sha256 が 2 系列（512px/wf16・1024px/wi8）とも一致すること**
   を門にする（ADR 0022 と同じ手順）。**tolerance は 1 つも変えない**のが期待値で、
   変わったら設計の前提（縮約順序の同一性）が破れている合図。
2. **案 A を入れる波**: ビット同一は原理的に得られない。
   - `atol=rtol=0` で maxAbs を系列別（tiny golden / DeBERTa / SBV2 / Anima f32・f16・i8・
     1024・turbo）に実測 → **5〜10 倍**を取って新 tolerance にする
     （既存の tolerance がすべてこの手順で決まっている）。
   - **turbo の反復累積（約 1.75×/step・9 step で 160 倍）**があるので、
     step 1 の裸の誤差と step N の到達点を**別 tolerance で**採る
     （`tests/e2e_anima_turbo_test.ts` の既存の 2 段構えをそのまま使う）。
   - **段②（通しチェーン）を必ず完走で採る**。少 step からの外挿は
     ACTIVE_DESIGN の落とし穴どおり禁止。
   - 画像は `TURBO_IMAGE_TOLERANCE` を採り直し。**PNG sha256 の門は案 A では使えない**ので、
     代わりに「参照画像との maxAbs」を門にする。

### 4.5 (v) パイプラインキー命名

既存の語彙（`op:vN:dtype:変種:wgN` / 重み格納は末尾 `:w{f16,i8}`）に合わせる:

| 実装          | キー案                                      | 備考                               |
| ------------- | ------------------------------------------- | ---------------------------------- |
| 案 B ① QK     | `attention_qk:v1:f32:reg64x64{v4}`          | `gemmKeyPart` を再利用             |
| 案 B ② 行統計 | `attention_stats:v1:f32:lastdim:safe:wg256` | `softmax` と同じ語彙               |
| 案 B ③ PV     | `attention_pv:v1:f32:reg64x64{v4}`          | `gemmKeyPart` を再利用             |
| 案 A          | `attention:v1:f32:flash:br32bc16t128d${D}`  | D は WGSL に展開されるのでキー必須 |

- 3 dispatch 構成のキーを 3 本に分けるのは、**ADR 0021 の診断（キー別 GPU 時間集計）で
  内訳が見える**ようにするため。1 本にまとめると「どの段が支配的か」が測れなくなる。
- 変種選択（案 B / 案 A）は**形状の関数**にする（例: `M·N·4 > しきい値` なら flash）と
  決定性は保たれるが、**しきい値がキーに載る = 設計裁定が必要**（§6 の openQuestion）。

## 5. 設計案と推奨

前提として共通なのは **§4.1 の op 契約**と **§4.2 (ii-A) のターゲット別 SDPA 保存**。
分かれるのは**カーネル実装戦略**である。

### 案 A — flash 完全融合（プロトタイプ T3b の移植）

- S も P も実体化しない。1024px の DiT peak transient **2,147.5MB → 33.6MB**。
- **時間は悪化見込み（1024px +19% / 512px +6%）**。§2.4 のシナリオ表と
  プロトタイプ実測（+12.5% / +3.1%）が根拠。
- D ≤ 152 の制約で **VAE（D=384）は対象外**。
- ビット同一は原理的に取れない → tolerance 全面再導出。

### 案 B — 段階融合（S 実体化・P 非実体化）★ 推奨

- `attention` 1 ノード = 3 dispatch（QK gemm → 行統計 → 正規化読みつき PV gemm）。
- 1024px の DiT peak transient **2,147.5MB → 1,073.7MB**（半減）。
- **時間は改善（512px −2.2% / 1024px −3.7% の見積り）で、悪化しない**。
- **出力がビット同一**になる設計 → ADR 0022 と同じ PNG sha256 の門が使える。
- **D の上限が無い** → VAE（D=384）もそのまま対象になり、1024 チェーンの床が両方で下がる。

### 案 C — 融合しない（恒等コピーの掃除だけ）

- 恒等 `expand` 224 本 + 恒等 `permute` ペア 280 組を消す（normalize パス 2 本、
  または executor の別名化 1 箇所）。
- **1024px −152.4ms（−2.6%）/ dispatch −784 本（−25.0%）/ peak −1,073.7MB**、
  **数値は 1 ビットも動かない**。
- 新 op ゼロ・再 emit の要否は実装場所次第（executor 側なら再 emit 不要）。
- ACTIVE_DESIGN の「C = 融合 op を足す」路線そのものは前に進まない。

### 推奨 — **案 B**（案 C を先行波として内包し、案 A は後段のキー変種）

**根拠 1 — 「時間で勝つ」という前提が実測で否定されている。**
プロトタイプは同じモデル・同じ解像度で **融合により 1024px +12.5% / 512px +3.1% 遅くなった**
（`docs/research/2026-08-01-m6-perf-recon.md` 相当の実測表）。融合カーネル 5,498 GFLOP/s に対し
同機の GEMM は 10,754 GFLOP/s で **FLOP あたり約 2 倍遅い**。しかも §4.3.1 で示したとおり、
**D=128 と共有メモリ 32KB の制約下ではプロトタイプのタイル構成がほぼ拘束された最適**であり、
「レジスタブロッキングを入れれば GEMM 並みになる」というプロトタイプ側の期待は成立しない。
案 B は**既存 GEMM 骨格をそのまま使う**ので、この落とし穴を構造的に回避する。

**根拠 2 — ビット同一の門を維持できる唯一の案。**
ADR 0022 の置換が安全に着地できた最大の理由は「PNG sha256 が 2 系列とも一致」という
**tolerance に依存しない門**を持てたことにある。案 B は ① QK の縮約順序 ② 行統計の縮約順序
③ P の値（`exp(S-m)*inv` の f32 評価）④ PV の縮約順序 のすべてを現行と一致させられるので、
同じ門をそのまま再利用できる。案 A は online softmax なので原理的に不可能で、
**7 系列ぶんの tolerance 再導出**（+ 反復累積の 2 段構え）を丸ごと背負う。

**根拠 3 — 効果が「時間・メモリ・dispatch」の 3 面で正の方向にしか動かない。**
案 B は現行 `bmm` を 2 本ともそのまま使い続けるので、**最悪でも現行と同じ時間**になる。
そのうえで `softmax` の 3 パス → 1 パス化（1024px −120ms）、恒等 `expand` 224 本の消滅
（−111.5ms・−1,073.7MB）、scale `mul` と k^T `permute` の消滅（−13.7ms）、
dispatch −504 本が確実に乗る。**下方リスクが無い**のは案 A と決定的に違う。

**根拠 4 — D の上限が無いので VAE まで届く。**
1024 チェーンの床は VAE decode の 6,725MiB で、その 2,048MiB が VAE mid-block の S/P である。
案 A は D=384 が共有メモリに載らないので**この床には触れない**。案 B は gemm 骨格が
D を K 次元として流すだけなので、**同じ op・同じキーで VAE も対象になる**。

**根拠 5 — 案 A への移行パスが残る。**
op 契約（arity 3・attrs `scale`・出力 shape）は案 A と案 B で同一なので、
案 A は**executor のエンコード実装を差し替えるだけのキー変種**として後から入る。
IR も再 emit も不要で、「メモリ最優先の局面（2048px / VAE tiling）でだけ flash を選ぶ」
という選択も後付けできる。

## 7. 隣接（本タスクのスコープ外・報告のみ）

1. **恒等 `permute` ペア 280 組（560 本）**: §2.5。案 C／波0 で扱う想定だが、
   融合 attention とは独立に価値がある（DiT の `permute` 736 本の 76%）。
2. **cross-attention の K/V が毎 step 再計算されている**。`encoder_hidden_states` は
   step をまたいで不変なのに、28 層 × 2 本の `linear`（`[1,512,1024] → [1,512,2048]`）が
   毎 forward 走る。512px で 120.3 GFLOP/step = `linear` 全体の 3.4%。
   グラフを跨ぐキャッシュはランタイム契約の外なので、**エクスポータ側でグラフを割る**話になる。
3. **1024px では `softmax` の全 56 ノードが grid-stride の上限（65,535）をクランプしている**
   （行数 65,536 → 65,535）。ACTIVE_DESIGN の落とし穴節にある
   「実運用で本当に上限を超えるのは今のところ pad だけ」という記述は、
   **1024px の実測で更新が要る**（縮退経路は本番で常時踏まれている）。
4. **VAE の `conv2d` が 1024px で 15,180ms / 15,833ms（95.9%）**。perf-b の対象で、
   融合 attention をどう転んでも 1024px の壁時計の支配項はこちらのまま。
5. **`strided` の実効帯域**: DiT で 0.0118 ms/M要素（≈680 GB/s 相当）に対し
   VAE は 0.0926 ms/M要素（≈86 GB/s 相当）と 8 倍の開き。VAE の `permute` は
   channel-last ↔ channel-first の 4 次元転置で局所性が悪い。
   プロトタイプの「座標デコード律速の疑い」と併せて perf の別題材。

## 8. メイン裁定が要る点（閉じた選択肢）

§9 の openQuestions に同内容を再掲する。

1. **カーネル戦略**: 案 B（段階融合・ビット同一・時間 −3%・メモリ半減）/ 案 A（flash・
   tolerance 再導出・時間 +19% 見込み・メモリ 64 分の 1）/ 案 C（融合せず掃除のみ）。
2. **`scale` の契約**: (α) 半スケール（ビット同一が取れる）/ (β) 全スケール（数式が自然・
   tolerance 再導出）。
3. **v1 のスコープ**: DiT のみ / DiT + VAE（案 B なら追加コストほぼゼロ）/
   DiT + VAE + conditioner / text_encoder まで（mask 契約の拡張が要る）。
4. **恒等コピー掃除（波0）の実装場所**: executor 別名化（再 emit 不要・IR は据え置き）/
   エクスポータ normalize（IR が綺麗になるが約 10GiB 再 emit）/ 両方。
5. **波0 を融合より先に単独で入れるか**（数値不変・dispatch −25% で、融合の可否と独立）。
6. **再 emit 10GiB のタイミング**: 融合と同じ波でまとめて 1 回 / 波0 とあわせて 2 回。

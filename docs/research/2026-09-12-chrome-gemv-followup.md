# ChromeでのGEMV追試と大語彙INT8の担当列数

> 2026-09-12の調査・実測スナップショット。RTXの結果であり、M2の検収とは区別する。

RoPE融合の後、語彙出力の形状選択、submitの上限、K方向の並列加算を調べた。
数値の正本は[保存JSON](2026-09-12-chrome-gemv-followup-results.json)。
基点は`ecc3801`。比較用bundleは同じRoPE融合を含み、語彙INT8の担当列数だけを切り替えた。
既定の生成経路・計測境界は[前の調査](2026-09-12-chrome-gemma-optimization.md)と同じ。

## 採用: 大語彙INT8の32→16列/workgroup

対象はM=1・INT8・N=262,144・K=1,536。通常版Gemma 4 E2Bの語彙出力に一致する。
カーネルの加算順、逆量子化、bias、保存形式、公開APIを変更せず、担当列数だけを選ぶ。
追加メモリは不要。既存のキー形式で`c16u4`と識別し、行ブロック・他形状は従来の選択を保つ。
選択点は`defaultLinearGemvVariant(shape)`、shapeの供給はM=1のrecipe構築時だけ。
[ADR 0082追記10](../decisions/0082-linear-gemv-decode.md)へ記録した。

実際の語彙INT8重みを使った単体比較では、約1.21→0.82 ms、約1.47倍になった。
3種類の入力で全262,144要素がu32一致し、非同期GPUエラーも無かった。
モデル全体は同じChromeの2ページへA/Bを読み込み、GPU実行を1ページずつ交替した。
各ページ3×256tokenの暖機後、ABBAを4組。次にページ作成順と実行順を逆にしてBAABを4組測った。

| 比較 | 各組のB/A倍率                     | 倍率中央値 |
| ---- | --------------------------------- | ---------: |
| ABBA | 0.9991 / 1.0186 / 1.0303 / 1.0450 |     1.0244 |
| BAAB | 1.0045 / 1.0141 / 1.0233 / 1.0426 |     1.0187 |

暖機後の通常版はA約57.2〜60.2、B約59.7〜60.7 tok/s（各組の平均）。
**計32走行すべてで全256token・文章・停止理由が一致**した。
最初の組はほぼ同速で、時刻による変動もあるため、約1.9〜2.4％の改善として扱う。
2ページ常駐・同じpromptのPLE行キャッシュが暖まった条件であり、初回やM2の速度は主張しない。

重点検証は95 passed（2 steps）/ 0 failed。実際の語彙形を選ぶ門に加え、
同じWGSLを使う端の列・端の先読み語でc32とのu32一致と独立CPU参照を検査した。
従来のWGSL snapshotを更新せず、c16との差が担当列数の記載とworkgroupサイズだけであることも検査する。

統合後の`deno task verify`は**2,946 passed（773 steps）/ 0 failed / 5 ignored、25分3秒**。
ログは`outputs/bench/karume/2026-09-12_head16-verify-6iecb046/verify.log`。
Gemmaのlogits・参照token・MTPの一致検査も通過した。

## 不採用: submitの最大dispatch数1024→2048

初期値16、時間予算100 ms、余裕係数0.5、適応的な増加、error scope、map待ちは維持し、最大値だけを変えた。
通常/QATそれぞれ4組のABBA、計32走行でID・文章・停止理由が一致したが、速度は全組で低下した。
倍率中央値はQAT **0.9267（約7.3％低下）**、通常 **0.9783（約2.2％低下）**。
製品のsubmit policyは変更しない。大きい投入単位が有利とは仮定しない。
GPU/CPUの重なりやdriverのスケジュールへの帰属は、この比較だけでは未確定。

## 未統合: K方向の並列加算

いずれも独立実装した隔離カーネル。圧縮重み・f32入力を使うが、加算順が既定と異なる。
ビット一致の門を緩めず、既定とは別の数値契約として調査した。

最初の実装は1要素ずつKを8/16/32laneへ分け、256threadのworkgroup内で部分和を合算した。
INT2/4/8×7形状を測り、長いKの一部は約1.4倍になる一方、大きなNでは遅くなった。
実語彙INT8も32laneは約1.44 msで、既定の約1.21 msより遅い。
実語彙の3入力でargmaxは一致したが、多数の要素の下位bitが変わった。語彙全体の品質保証とはしない。

次は圧縮語1本をまとめて展開してからKを32laneへ分けた。
1 workgroupが1出力行を担当し、subgroupAddと通常のworkgroup内木縮約を比較した。
前者は`subgroups`機能を要求し、実機のsubgroup幅が32であることを確認する隔離版。
23形状にはQATのgroup 512/2048も含めた。

| INT4形状（N×K、group） | subgroup / 既定 | workgroup / 既定 |
| ---------------------- | --------------: | ---------------: |
| 256×1536、32           |          3.55倍 |           3.33倍 |
| 6144×1536、32          |          0.79倍 |           0.76倍 |
| 12288×1536、32         |          0.90倍 |           0.85倍 |
| 1536×6144、32          |          2.36倍 |           2.32倍 |
| 1536×12288、32         |          2.92倍 |           2.98倍 |
| 1536×2048、512         |          1.60倍 |           1.52倍 |
| 1536×2048、2048        |          1.59倍 |           1.52倍 |

倍率は各試行で既定時間/候補時間を取り、その中央値。合成重み・入力・biasを使った単体値である。
各試料は暖機用GPU処理の後に64dispatchを同じpass内で計時し、6回の順序交替を行った。
大きな出力幅にも一律適用すると逆効果になる。次はworkgroup内に複数の出力行を持たせる幾何と、
モデル全体での速度・生成列・品質の比較を行う。

### 数値差の評価

各形状・3入力分布につき128出力行を等間隔に選び、f32の入力と逆量子化値からFP64で積和した参照も求めた。
並列2方式の参照に対するRMSE（平方平均二乗誤差）は、既定に対する比の中央値が約0.229。
この範囲では多くのケースで参照へ近づいた。最大の比は約1.0000005。
ただし、これは量子化済み行列積の算術誤差であり、生成モデルの品質スコアではない。
既定とbitが異なる事実も変わらず、モデル全体での比較と、数値モード・対応機能の設計が必要。
subgroupの加算は[WGSL §17.12.1](https://www.w3.org/TR/2026/CRD-WGSL-20260831/#subgroupadd-builtin)に従う。
local invocation IDとsubgroup IDの対応は仮定していない。

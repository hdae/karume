## 0. 3 行まとめ

1. **DP4a は使える**（本機 Deno で `packed_4x8_integer_dot_product` が列挙され、`dot4I8Packed` を
   含む提案カーネルが `createComputePipeline` まで通った）。**エミュレーション経路は整数演算なので
   数値が完全一致**し、拡張の有無は速度だけになる — fail loudly も tolerance 分岐も要らない。
2. **期待利得は 4.73× ではなく約 1.54×**。プロトタイプの 4.73× は**旧 16×16 カーネル比**で、
   Karume は ADR 0022 でその 3.07× 相当を取得済み。残差は 16,599 / 10,754 = **1.543×**
   （プロトタイプ自身も表 T2 で「さらに 1.5×」と書いている）。1024px 生成の GPU 実時間で
   **74.65s → 60.57s（−18.9%）**・壁時計 85.9s → 約 71.9s（−16.4%）の見積り。
3. **SBV2 は w8a8 の検証対象として成立しない**。SBV2 全 5 ターゲットは **conv1d が FLOP の
   86〜90%**、linear は front 2 本 / voice 4 本で **0.00 GFLOP**（実測 census）。linear だけの
   DP4a では SBV2 の速度は 1% も動かない。「他モデルでも検証」の受け皿は
   **DeBERTa full-24layer（linear 86.8%）と Anima text_encoder（88.2%）/ text_conditioner（89.0%）**。

| ---------------- | ----------: | ----------------------------------------- | ---------: |

| vae_decoder      | **15.8334** | `conv2d:v1:f32:direct:wg256:wf16` 15.1802 |  **95.9%** |
| text_encoder     |      0.0807 | `linear:…:wf16` 0.0745                    |      92.3% |

`turbo-f16-512-seed42.json`（512px・DiT は wf16）: transformer 0.9683s のうち

DiT 1024px 1 forward: linear 454 本 **13,591.88 GFLOP** / bmm 112 本 4,329.33 GFLOP。
DiT 512px: linear **3,488.46 GFLOP** / bmm 360.78 GFLOP。

linear の形（1024px・m は先行次元の積）:

| m                      | k    | n    | 本数 | 備考                    |
| ---------------------- | ---- | ---- | ---: | ----------------------- |
| 4096                   | 2048 | 2048 |  168 | attention 投影（qkv/o） |
| 4096                   | 2048 | 8192 |   28 | FFN up                  |
| 4096                   | 8192 | 2048 |   28 | FFN down                |
| 512                    | 1024 | 2048 |   56 | cross-attn の text 側   |

| 1                      | 256  | 6144 |   84 | modulation（m=1）       |
| その他 5 形（各 1 本） |      |      |      | 入口 / 出口             |

**全ての k が 4 の倍数**（2048 / 8192 / 1024 / 256 / 68 / 2048）。DP4a の適格条件（後述 §4.1）を

**達成 GFLOP/s の実測換算**: 1024/wi8 = 13,591.88 / 4.0966 = **3,318 GFLOP/s**、

### 1.3 i8 重み dequant のコスト（既存経路の実測）

GEMM 置換**前**の 1024px 実測（`turbo-*-1024-seed20260803.json`・同日 08:2x）:
i8 `ditMs` 271,100 ms vs f16 265,591 ms = **i8 が 2.1% 遅い**。
→ 現行の「要素ごと dequant（`vec4<f32>(unpack4xI8(w)) * s`）」の追加コストは 2% 程度で、
**w8a8 の利得の主因は dequant 除去ではなく内積そのものの置換**である（§3.3）。

### 2.1 仕様上の位置づけ（設計に効く 3 点）

1. **WGSL 言語拡張であって device feature ではない**。`requiredFeatures` に載せる対象ではなく、
   `navigator.gpu.wgslLanguageFeatures` に列挙されるかどうかで決まる。したがって
   **device 作成時に決める必要がない**（`acquireGpu` の三値ノブと違い、Session 単位・
   ノード単位で自由に選べる）。
2. **ディレクティブ不要**。列挙されていれば `enable` / `requires` なしで `dot4I8Packed` が使える
   （本機実測: `requires` を書いても書かなくても通る）。`enable f16` と対照的。
3. **列挙 = 速いとは限らない**。列挙はコンパイルが通ることの保証であって、ドライバが
   ネイティブ DP4A 命令へ落とすかソフトウェア展開するかは別。既存の
   `src/gpu/device.ts` の `readWgslLanguageFeatures` docstring が
   「参考情報であり機能検出には使わない（ハードウェア対応と無関係に列挙されるため）」と
   書いているのはこの意味で正しい。**本設計では「数値が同一なので誤った選択でも壊れない」
   ことを根拠に、経路選択にだけ使う**（§4.4）。

### Chrome / ブラウザ側の状況（既知情報からの整理・**本 recon では未実測**）

- `packed_4x8_integer_dot_product` は WebGPU 仕様の WGSL language feature として定義されており、
  Chrome（Dawn/Tint）でも `navigator.gpu.wgslLanguageFeatures` に載る形で提供される系統の機能。
- ネイティブ対応: NVIDIA は Pascal（sm_61）以降の `IDP4A`、AMD は Vega 以降の `V_DOT4_I32_I8`、
  Intel は Gen11 以降の DP4A が対応。非対応 HW では Tint / naga がエミュレーション展開する。
- **速報値・断定は避ける**。ブラウザ側の実測（列挙の有無・dp4a 版とエミュ版の速度差）は
  実装波の受け入れハーネス（`examples/`）で取ること。設計上はこれが**速度にしか効かない**ので、
  未実測でも設計は確定できる。

## 3. プロトタイプの DP4a 実験の読み解き

一次ソースは先行実験プロジェクトの perf recon（2026-08-01）と、そのベンチ実体
（`gemm-bench.js` の `DP4A` カーネル + `bench3()`）。

### 3.1 実測条件と数値

- 形状 M=4096, N=2048, K=2048、20 反復、実 Chrome / Blackwell、`timestamp-query` ではなく
  `performance.now()` + `onSubmittedWorkDone()`（2 回ウォームアップ → 本計測）。
- **16×16 単純タイル 3,506 / レジスタ 4×4 8,754 / レジスタ 4×4+vec4 10,754 /
  f16 計算 5,057 / DP4a 16,599 GFLOP/s**。

### 3.2 「4.73×」の正しい読み方（**最重要の訂正点**）

4.73× は **16×16 単純タイル比**。Karume は ADR 0022 でレジスタ 4×4+vec4（同表 3.07×）を
既に採っているので、**DP4a の残余利得は 16,599 / 10,754 = 1.543×**。
プロトタイプ自身も高速化の段の表で `T2: W8A8 + DP4a → GEMM をさらに 1.5×
（実測 10754 → 16599 GFLOP/s）` と正しく書いている。ADR 0019 の代替案節の
「プロトタイプ実測 4.73×」は**基準が旧カーネルのままの記述**で、GEMM 置換後は誤解を招く。

### 3.3 カーネル形（`DP4A` 定数の実体）

```
A: array<u32>  [M, K/4]（i8 を 4 詰め）
B: array<u32>  [N, K/4]（転置格納 = linear の W レイアウトそのもの）
C: array<f32>  [M, N]
共有: sa[64*4] u32（64 行 × 4 パック）/ sb[64*4] u32 → 計 2KB（現行 f32 版の 8KB の 1/4）
workgroup 16×16 = 256・1 スレッド 4×4 出力・acc: array<i32,16>
K タイル 16（= 4 パック）・内側は p=0..3 で 16 回の dot4I8Packed
```

**設計にそのまま効く 3 点**:

- **B は `[N, K/4]` = linear の W `[n,k]` と同じ並び**。現行 f32 linear カーネルが共有メモリで
  やっている転置（`fillBLinear` の `sb[sb_base][wsl]`）が **DP4a では不要**になる。
  i8 ペイロードは ADR 0019 の**平坦添字 4 詰め**なので、`k % 4 == 0` なら行頭が語境界に来て
  そのまま `[n, k/4]` の u32 配列として読める（**既存 i8 資産のバイトを 1 つも変えずに使える**）。
- 共有メモリが 8KB → 2KB で occupancy が上がる（副次的な利得。プロトタイプの 1.543× に既に含む）。
- **`sb` の共有レイアウトに 8-way バンク衝突がある**（プロトタイプの弱点）:
  読み出しが `sb[(lid.x*4 + j)*4 + p]` = `16*lid.x + 4j + p` で、warp 内の 16 スレッドが
  **語ストライド 16 → バンク 2 種**にしか当たらない。`sb[p*64 + col]`（パック優先）へ組み替えれば
  ストライド 4 → バンク 8 種で **4 倍改善**。→ **1.543× は天井ではなく床**と読むべき。

### 3.4 プロトタイプが**やっていないこと**（Karume が新規に負う部分）

| 項目                    | プロトタイプの状態                                                          |
| ----------------------- | --------------------------------------------------------------------------- |
| 活性の動的量子化        | **無し**。ベンチは A/B とも全バイト `1` 埋めのダミー                        |
| dequant                 | **無し**。出力は `f32(acc) * 0.001` という固定ダミー係数                    |
| 数値検証                | **無し**。`bench2` にある先頭 4 要素の突合が `bench3`（f16 / dp4a）には無い |
| 品質実測（W8A8 の精度） | **無し**。表 T2 は「精度ゲート先行」のまま未着手                            |
| 実モデルへの適用        | **無し**                                                                    |

→ **16,599 GFLOP/s は「純スループット・数値未検証」の値**。移植できるのはカーネル形と
桁感だけで、**per-token 量子化の方式・scale の扱い・品質ゲートは全て Karume の新規設計**。
「per-token 動的か」という問いへの答え: **プロトタイプには活性量子化が存在しないので前例が無い**。

## 4. w8a8 linear 変種の設計

### 4.1 適格条件（fail loudly ではなく「静かに f32 経路へ落ちる」ではない — 明示 opt-in）

| 条件                                 | 理由                                                                      |
| ------------------------------------ | ------------------------------------------------------------------------- |
| 重みが **i8 で GPU 常駐**            | `weightStorages.get(w) === "i8"`（既存判定をそのまま使う）                |
| **`k % 4 == 0`**                     | i8 ペイロードは平坦添字 4 詰め。k が 4 の倍数のときだけ行頭が語境界に来る |
| **`k <= 131072`**                    | i32 縮約のオーバフロー門（§4.3）                                          |
| Session が w8a8 モードで作られている | opt-in（§4.5）。既定では 1 バイトも挙動が変わらない                       |

DiT 454 本は全て通る（k ∈ {2048, 8192, 1024, 256, 68, 2048}）。
`n % 4 == 0` は**出力 vec4 書き出しの条件**で、現行 `gemmUsesVec4` と同じ 1 ビット。
i8a8 では **k 条件と n 条件を分離**する（k は必須・n はスカラ書き出し変種へ落ちるだけ）。
opt-in なのに適格 0 本なら**診断で見える**ようにする（キーが 1 本も出ない = 気づける）。

### 4.2 (i) 活性量子化カーネル `quantize_rows` — 追加 dispatch とバッファ

**形**: 1 行 = 1 workgroup（256 スレッド）・行方向を grid-stride で回す（`reduce` 族と同型）。

```
入力  x  : array<f32>  [m, k]     （既存の中間バッファをそのまま読む）
出力  xq : array<u32>  [m, k/4]   （i8 を 4 詰め）        … m*k バイト
出力  xs : array<f32>  [m]        （per-token scale）     … m*4 バイト
```

1. **パス 1**: 各スレッドが行を 256 ストライドで舐めて局所 absmax → 共有メモリ木構造で
   workgroup reduce。**NaN はビット列判定で伝播**（ADR 0020 の流儀。`max` の NaN 挙動に頼らない）。
2. `s = amax == NaN ? NaN : max(amax / 127.0, f32 tiny)` を `xs[row]` へ書き、共有変数で全員に配る。
3. **パス 2**: 各スレッドが 4 連続要素（quad）を担当し
   `q = clamp(round(x / s), -127, 127)` → `pack4xI8(vec4<i32>)` を `xq[row*k4 + q]` へ書く。
   行を**もう一度グローバルから読む**（行は最大 32KB で L2 に乗る）。

**MUST 級の設計点**:

- **`±127` に閉じる**（−128 を使わない）。ADR 0019 の重み側と同じ規約で、絶対値最大の要素が
  厳密に復元され fake-quant が冪等になる。`pack4xI8Clamp`（[−128,127] へ飽和）には**頼らない**
  — 明示 `clamp(±127)` の後に `pack4xI8` を使う。
- **全ゼロ行**は `amax == 0` → `s = tiny` → `q = 0` → 出力 `0*tiny = 0` で厳密。
- **NaN 伝播は「行 scale 経由」で成立する**（§4.6）。
- **丸めの同点規則**は GPU / TS 参照 / torch の 3 者で一致させる。WGSL `round` の同点規則
  （偶数丸め / 0 から離れる方向）は**実測で確定させる**（実装波の最初の 1 テスト。
  `round(0.5)` / `round(1.5)` / `round(-0.5)` の 3 点で足りる）。torch は偶数丸め、
  JS `Math.round` は上方向 — **3 者を揃える正本を 1 箇所に置く**。

**コストの見積り（1024px・1 step）**: linear の x 読み総量は census で **10,487.7 MB**。
2 パス再読み + `xq` 書き出しで 2×10,488 + 2,622 ≈ **23.6 GB/step**。
本機の elementwise 実効帯域は実測 `ew:v2:mul:f32>f32:r4`（1.674e9 要素 / 24.22 ms・12 B/要素）
= **829 GB/s**。控えめに 700 GB/s とすると **33.7 ms/step**。
→ **linear 4,096.6 ms/step の 0.82%**。10 step で 0.34 s。**無視できる。**

**dispatch 数**: +454/forward（現行 3,137 → 3,591、+14.5%）。GPU 時間支配なので submit 側は問題なし。

**同じ x を複数の linear が食う重複量子化について**: qkv 投影などで同一入力が 2〜3 本に入る。
上の見積り（0.82%）は**重複を含んだ総量**なので、**重複排除は不要**（Simplicity first）。
IR 側で CSE する案（活性量子化を op 語彙へ入れる）は §5 案 C で却下。

**バッファプールとの整合**:

- `xq` / `xs` は `arena.allocStorage` から取り、`retain(buf, 1)` → GEMM の dispatch を
  エンコード → `release(buf)`。**両 dispatch は同じノードのエンコード内**なので、
  ADR 0004 の「解放はノード境界」と衝突しない（ノード内で閉じた一時領域）。
  **実装波で `RunArena` の retain/release 契約を実コードで再確認すること**（本 recon は
  executor の `#encodeLinear` を読んだのみで、arena の細目までは追っていない）。
- **full-write**: `quantize_rows` は `xq` の全語 + `xs` の全要素を書く（k%4==0 なので端数なし）。
  `tests/gpu_full_write_test.ts` に毒値注入で 1 本追加する。
- **grid-stride 縮退**: 行方向 grid-stride なので **`tests/gpu_gridstride_test.ts` に必ず 1 本足す**
  （ACTIVE_DESIGN の落とし穴 — 実測形では縮退経路を 1 度も踏まない）。
- **ピークメモリ**: `xq`（x の 1/4）+ `xs`（無視）が x と同時生存する。1024px の最大 x は
  m=4096,k=8192 = 128 MB → xq 32 MB。現行 DiT のピーク（softmax の入出力対）に対して小さい。

### 4.3 (ii) 整数 GEMM の縮約と dequant

```
acc[i32] = Σ_k  xq[m,k] · wq[n,k]          （厳密な整数・丸め 0 回）
out       = f32(acc) · (xs[row] · wscale[col]) + bias[col]
```

**オーバフロー門**: |acc| ≤ k · 127 · 127 = k · 16129。
i32 上限 2,147,483,647 → **k ≤ 133,142**。安全側で **k ≤ 131,072（2^17）を門**にする
（k=131,072 で 2.114e9 < 2.147e9）。DiT の最大 k = 8,192 に対し余裕 16.2 倍。
門を超える k は fail loudly（黙って壊れると i32 の巻き戻りで符号ごと化ける）。

**数値契約 — ADR 0019 の「scale は要素ごと」との関係**:

- ADR 0019 は `(Σ x·q)·s` 形を**却下**した。理由は「GPU の dequant と CPU 展開のビット一致を失う」。
- **w8a8 では逆になる**。整数縮約は**順序に依存しない厳密値**なので、`(Σ xq·wq)` は
  どんな実装でも同じ 1 つの整数になる。したがって `(Σ)·s` 形でも
  **GPU と CPU 参照がビット一致する** — ADR 0019 が守ろうとした性質が、むしろ**強化される**。
  現行 f32 GEMM は縮約順序に依存するので、**w8a8 の方が数値契約が強い**。
- ただし **f32 変換の丸めが 1 回だけ入る**: |acc| は最大 1.3e8 > 2^24 なので `f32(acc)` は丸まる。
  丸めは IEEE round-to-nearest-even で決定的 → GPU（WGSL `f32(i32)`）と TS（`Math.fround`）と
  torch（`.float()`）で一致する。**乗算の順序を codegen で固定する MUST**:
  `(xs[row] * wscale[col])` を先に 1 つの f32 に畳んでから `f32(acc)` に掛け、最後に bias を足す。
  順序を変えると 1ulp ずれて参照とのビット一致が崩れる。
- ADR 0022 の決定 3「縮約順序を変える変種は tolerance 再導出とセット」は満たされる
  （GPU 側の順序依存は消えるが、**値そのものが量子化で変わる**ので tolerance は必ず取り直す）。

**カーネル骨格（本機でコンパイル + パイプライン生成まで確認済み）**:

```
共有  sa: array<u32, 4*64>   // [pack][row]  ← プロトタイプの [row][pack] から組み替え
      sb: array<u32, 4*64>   // [pack][col]  ← バンク衝突 8-way → 2-way
acc   array<vec4<i32>, 4>    // 4×4 出力・vec4 で 4 列ぶん
内側  for p in 0..3 { bq = sb[p*64 + lid.x*4 + 0..3];
                      for i in 0..3 { a = sa[p*64 + lid.y*4+i];
                                      acc[i] += vec4<i32>(idot(a,bq.x), …, idot(a,bq.w)); } }
書出  if (n%4==0) { out[…] = vec4<f32>(acc[i]) * (ws * xs[row]) + biasv; }  // v4
      else        { スカラ 4 本（現行 store() のスカラ変種と同型） }
```

K タイルは 16 要素（4 パック）で ADR 0022 と同じ刻み。K 端数（k4 が 4 の倍数でない）は
**0 埋めで厳密**（`dot4I8Packed(0, x) == 0`）。ADR 0022 の検出限界①（A/B 片側だけの
0 埋め退行が相殺で見えない）はそのまま引き継ぐ。

**束縛**（linear の現行 0..5 の後ろに 1 本追加）:
`0 uniform dims / 1 xq / 2 w / 3 bias / 4 out / 5 wscale / 6 xscale`。
`LINEAR_SCALE_BINDING = 5` は据え置き、`LINEAR_ACT_SCALE_BINDING = 6` を新設し
`weight-storage.ts` ではなく **i8a8 変種側**に置く（活性 scale は重み格納の概念ではない）。

### 4.4 (iii) 拡張無し環境の fallback — **数値完全一致が成立する**

```wgsl
fn idot(a: u32, b: u32) -> i32 {
  return dot4I8Packed(a, b);                    // 拡張あり
  // return dot(unpack4xI8(a), unpack4xI8(b));  // 拡張なし
}
```

**両者は同じ整数を返す**:

- `unpack4xI8` は core WGSL（feature 依存ゼロ・ADR 0019 で既に使用中）。
- `dot(vec4<i32>, vec4<i32>)` は WGSL の整数 `dot`。整数加算は結合的かつ厳密で、
  中間値も最大 4×16129 = 64,516 なので巻き戻りが起こりえない。**総和の順序に関係なく同値**。
- したがって **`dot4I8Packed` の定義（i8 4 組の積和）と 1 ビットも違わない**。

**帰結（設計として重要）**:

1. **fail loudly は不要**。拡張が無くても正しく動く。ADR 0002 の「Web 標準 API のみ」とも整合。
2. **tolerance は 1 本**。環境で数値が変わらないので、E2E の期待値は環境非依存。
3. **経路選択の誤りが壊れない**。§2.1-3 の「列挙 = 速いとは限らない」問題は
   **速度にしか影響しない**ので、`wgslLanguageFeatures.has(...)` で選んでよい。
   `device.ts` の「機能検出には使わない」docstring には
   「**数値が同一な変種の選択にだけ使う**」という但し書きを足す。
4. **検出器**: 実装波では**エミュ経路を強制するテスト専用ノブ**を置き、
   拡張のある本機で dp4a 版とエミュ版の出力を **atol=0 で突合**する。これが
   「エミュは数値同一」という主張の唯一の機械的な検出器になる。
5. パイプラインキーに `:dp4a` / `:dp4aEmu` を載せる（診断でどちらが走ったか見える）。
   キーが device 由来になるのは新しいが、`PipelineCache` は device ごとなので衝突は起きず、
   決定性（同一キー ⇔ 同一バイト列）は保たれる。

### 4.5 (v) opt-in の面・パイプラインキー・診断

**opt-in は `Session` のノブ**（`acquireGpu` ではない）。理由:

- DP4a は **device feature ではない**ので device 作成時に決める必要がない（§2.1-1）。
- 活性量子化の可否は**モデル/資産ごと**の判断（品質ゲートを通ったターゲットだけ有効にしたい）。
  同一 device 上で「DiT は w8a8・text は f32」を同時に走らせられる形が要る。

```ts
export type SessionOptions = {
  readonly submitPolicy?: SubmitPolicy;
  /** linear の実行形（既定 "f32" = 従来どおり）。"i8a8" は i8 常駐重みの linear だけに効く。 */
  readonly linearCompute?: "f32" | "i8a8";
};
```

**MUST: 既定は `"f32"`**。i8 資産を自動で w8a8 実行にすると、既存の
`models/anima-i8/` 系列の数値（と PNG sha256・E2E tolerance）が黙って変わる。
ADR 0022 が確立した「置換前後で PNG がビット同一」という検証資産を壊さないため、
**opt-in 以外はあり得ない**。

**パイプラインキー**: `linear:v3:i8a8:reg64x64{v4}:dp4a{Emu}`
（`v2` の重み格納判別子 `:wi8` は i8a8 では意味が重複するので `i8a8` に畳む）。

**診断**:

- `gpuTimingByGraph` に上記キーが出る → 何本・何 ns 走ったかが自動で見える（ADR 0021）。
- `quantize_rows:v1:wg256` も別キーで出る → 活性量子化の実コストが実測で分離できる。
- opt-in なのに `i8a8` キーが 0 本 = 適格判定で全部落ちている、が観測できる（ADR 0006 の流儀）。
- `SessionDiagnostics.storage` に「w8a8 で実行した linear 本数 / f32 へ落ちた本数」を足すかは
  **不要と判断**（キー別 `dispatchCount` が同じ情報を持つ）。

### 4.6 NaN / Inf の扱い（ADR 0020 との整合）

整数経路には NaN が無い。しかし **NaN は行 scale 経由で伝播する**:

- `quantize_rows` が行内の NaN をビット列判定で拾い、`xs[row] = NaN` を書く。
- 整数側は `clamp(round(NaN/NaN))` で不定値になるが、
  `out = f32(acc) * (xs[row] * wscale[col]) + bias` の `xs[row]` が NaN なので **出力行は全て NaN**。
- **f32 linear と同じ粒度**である（f32 でも行内に 1 つ NaN があれば、その行の出力は
  全 k を縮約するので全列が NaN になる）。**伝播粒度は劣化しない。**

Inf: `amax = Inf → s = Inf → x/s ∈ {0, NaN}` → 整数は不定 → 出力は `f32(acc)*Inf` で ±Inf / NaN。
f32 経路も Inf / NaN を出すので**符号が変わりうる**点だけ差が残る。
→ **`docs/limitations.md` に「i8a8 経路では非有限値の伝播は行単位で保たれるが、
Inf の符号は f32 経路と一致しない」を記載**する。ADR 0020 の不変条件は
「NaN が黙って消えない」なので満たすが、明文化しないと後から不変条件破れに見える。

## 5. 設計案 3 つ

### 案 A — 実行時ノブ + 既存 i8 資産の再利用（**推奨**）

`models/anima-i8/` を**バイト単位でそのまま**使い、`SessionOptions.linearCompute: "i8a8"` で
実行形だけを切り替える。活性量子化は executor 内の追加 dispatch。参照は TS 側に
`linear_i8a8` を実装（GPU とビット一致）、torch 側は活性量子化を鏡像実装した forward hook で
golden / fixture を採り直す。

### 案 B — 資産系列で分離（`models/anima-i8a8/`）

コンテナ metadata に実行モードを宣言し、系列ごとに 1 つの数値を持たせる。
資産と数値が 1:1 になり fixture の対応が明快。
**欠点**: 重みバイトは w8 と完全に同一なので、**純粋な重複**（transformer 1.87GiB）。
emit と保管と再生成の手間が増え、SBV2 / DeBERTa へ広げるたびに系列が倍増する。

### 案 C — IR の op 語彙へ入れる（`quantize_rows` + `linear_i8a8` ノードをエクスポータが吐く）

契約 4 点セットに乗り、CSE で重複量子化が自動的に消え、CPU 参照も既存の仕組みに乗る。
**欠点**: ADR 0006 の「量子化は格納と重みスロットの概念であり、グラフ意味論に入らない」を破る。
IR v1 の語彙が量子化方式ごとに増殖し（w4 が来たら再増殖）、同じモデルの IR が
量子化方式ごとに別物になる。**却下**。

### 推奨: **案 A**（根拠 5 つ）

1. **資産追加ゼロ**。w8a8 の重み側は per-channel scale まで含めて w8 と完全同一なので、
   既に緑になっている `models/anima-i8/`（DiT 1,872.8MiB・--verify ビット一致）で
   **今日から実験できる**。SBV2 / DeBERTa へ広げるときも「i8 資産を作る」1 手で足りる。
2. **数値契約がむしろ強くなる**。整数縮約は順序非依存の厳密値なので、ADR 0019 が
   `(Σ x·q)·s` 形を却下した理由（GPU/CPU 展開のビット不一致）が w8a8 では**消える**。
   参照との atol=0 突合が成立し、E2E は実装誤差だけを測れる（ADR 0006 の規律を維持）。
3. **拡張の有無が速度だけ**（§4.4）。fail loudly も環境別 tolerance も要らず、
   ADR 0002（Web 標準のみ・feature 依存最小）と正面から整合する。
4. **既存の検証資産を 1 バイトも壊さない**。opt-in なので ADR 0022 の
   「PNG sha256 が置換前とビット同一」も、既存 tolerance 表も全て有効なまま残る。
5. **公開面の増分が 1 プロパティ**。ADR 0008 の「薄い面」に収まる。案 B は配布形式の設計
   （後回しと裁定済みのタスク #21）を先取りしてしまう。

## 6. (iv) 品質ゲートの段取り

活性量子化は**非可逆**で、fake-quant 方法論（ADR 0006）では**エクスポータ側で先に丸められない**
（活性は実行時に決まる）。したがって「量子化誤差」と「実装誤差」の分離をどう保つかが要になる。

### 6.1 参照の作り方（2 択・裁定要 → openQuestion）

- **(a) 鏡像参照**: torch 側と TS 参照側に per-token 活性量子化を**同じ式で**実装し、
  golden / fixture を採り直す。E2E は従来どおり**実装誤差だけ**を測る。工数が増えるが
  ADR 0005/0006 の規律が保たれる。**推奨**。
  - 既知のほころび: 上流の 1ulp 差が `amax` を動かすと `s` が 1ulp 動き、丸め境界近傍の
    要素が ±1 段飛ぶ。**厳密なビット一致は E2E 全体では成立しない**（GPU 単体 vs TS 参照の
    同一入力比較では成立する）。tolerance は実測導出。
- **(b) 近似モードと割り切る**: 参照は f32 のまま、w8a8 専用の緩い tolerance + 品質ゲートで運用。
  安いが、実装バグが tolerance に埋もれる（ADR 0005 が排したもの）。

### 6.2 品質指標の段（ADR 0019 の品質ゲートを w8a8 用に拡張）

1. **Python 先行の直交分解**（GPU コード 0 行で go/no-go が取れる）:
   torch 上で「重み i8 fake-quant のみ」vs「+ 活性 per-token i8」を DiT に当て、
   ① latent の relRMS / SNR（step ごと）② 最終画像の PSNR / LPIPS 相当 ③ 目視。
   **ADR 0019 の計測台本（`measure_quant_anima.py` 相当）は Karume へ未移植**
   （リポジトリ内に PSNR を計算するコードは無い — grep で確認）。
   w8a8 ではこの台本が**必須**になるので、ここで作る。
2. **層別の外れ値調査**: DiT の活性は modulation（scale-shift）と GELU 後で外れ値が出やすい。
   per-token symmetric だけで足りるか、SmoothQuant 相当の平滑化 or 一部層の f32 残置が
   要るかを ①の副産物として出す（層別 relRMS の表）。
3. **デモ目視裁定**: `examples/anima/` で w8 画像と w8a8 画像を同一 seed で生成して並べる
   （ADR 0019 の②と同じ形。拡散は軌道が変わるので数値だけでは決められない）。
4. **SBV2**: 音声は SNR で悲観的に出るが聴感が正本 — ただし **§7 の通り SBV2 に w8a8 の
   出番はほぼ無い**。

## 7. 「SBV2 や他モデルでも検証」への回答（**purpose fit の反証**）

### 7.1 SBV2 は linear をほぼ持たない（実測 census）

各ターゲットの FLOP 内訳（P=512 で解決した静的 census・本 recon 実施）:

| ターゲット | ノード数 | 総 GFLOP | conv1d           | bmm         | conv_transpose1d | linear              |
| ---------- | -------: | -------: | ---------------- | ----------- | ---------------- | ------------------- |
| front      |      911 |     8.75 | 75 本 **86.0%**  | 24 本 14.0% | —                | **2 本 0.00 GFLOP** |
| flow       |     1589 |    44.93 | 152 本 **89.1%** | 96 本 10.9% | —                | **4 本 0.00 GFLOP** |
| dec        |      246 |    13.35 | 93 本 **89.7%**  | —           | 5 本 10.3%       | **0 本**            |
| voice      |     1836 |    58.28 | 245 本 **89.2%** | 96 本 8.4%  | 5 本 2.4%        | **4 本 0.00 GFLOP** |
| dp         |       17 |     0.35 | 4 本 **100%**    | —           | —                | **0 本**            |

→ **linear だけを DP4a 化しても SBV2 の速度は測定限界以下**。
SBV2 で w8a8 を「試す」意味があるのは**正しさの確認**（数本の tiny linear が通ること）だけで、
それは tiny golden とユニットテストで既に賄える。**SBV2 の真の perf レバーは conv1d**。

### 7.2 SBV2 の i8 資産は「無い」どころか **f16 資産も無い**

`tools/exporter/export_sbv2.py` には **`--dtype` オプションが存在しない**（`--target` /
`--sym-max` / `--verify` のみ）。`models/sbv2/` は全ターゲット f32 格納。
一方 `karume/emit.py` の `emit(weight_dtype=…)` と
`karume/quantize.py` の `fake_quant_int8(model)` は**モデル非依存に書かれている**ので、
SBV2 の i8 化は**配線作業**で足りる:

1. `export_sbv2.py` に `--dtype {f32,f16,i8}` を追加。
2. `fake_quant_int8` を **`remove_weight_norm` / パッチ適用の後・参照と golden の採取の前**に呼ぶ
   （順序 MUST は `export_sbv2.py:699` に既にコメントで予告されている）。
3. `emit(..., weight_dtype, weight_scales=report.scales)` へ渡す。
4. 資産系列 `models/sbv2-i8/`（5 ターゲット）を生成。
5. **`tests/e2e_sbv2_test.ts` の 5 系列 tolerance を i8 で再導出**（front atol 1e-4 / flow 2e-5 /
   dec 3e-5 / voice 1e-5 は f32 の実測値。i8 では音声 SNR 12.8〜24.2dB 相当の誤差になるので
   全面的に取り直し）。
6. conv1d / conv_transpose1d / embedding の wi8 カーネルは**既に存在する**（ADR 0019 で
   WEIGHT_SLOTS 全 5 op が適格）ので、ランタイム側の新規実装は 0。

**工数は中（波 1 本）だが、これは w8 の話であって w8a8 とは独立**。

### 7.3 「他モデル」の正しい受け皿

| 候補                            |          linear 比 | 資産の現状            | w8a8 の意味                       |
| ------------------------------- | -----------------: | --------------------- | --------------------------------- |
| **Anima text_encoder**（Qwen3） |          **88.2%** | f16 のみ（i8 未生成） | 速度 + 品質の両方。DiT と独立の軸 |
| **Anima text_conditioner**      |          **89.0%** | f16 のみ              | 同上（小さいので回しやすい）      |
| **DeBERTa full-24layer**        |          **86.8%** | f32 のみ              | 既存 E2E 8 ケースがそのまま回帰網 |
| Anima vae_decoder               | 0%（conv2d 97.7%） | f16                   | 対象外（perf-b の領分）           |
| SBV2 全 5 系列                  |                ≈0% | f32 のみ              | **速度の意味なし**（§7.1）        |

→ **「他モデルでも試して検証」の実体は DeBERTa + Anima text 系**とするのが、
指示の意図（一般性の確認）を最小コストで満たす形。SBV2 を含めたい場合は
「w8（i8 格納）の対応を SBV2 へ広げる」という**別タスク**として切り出すのが正直。

**前提と不確実性**:

- 1.543× はプロトタイプの **Blackwell 実測 / 数値未検証 / バンク衝突ありのカーネル**由来。
  本機は Ampere（GA102）で INT パイプ幅が FP32 の半分（**この点は仕様理解からの推測**）だが、
  1.543× は ALU 律速ではなく**共有帯域の 4 分の 1 化**が主因と読めるため、
  アーキテクチャ非依存に近い。§3.3 のバンク衝突修正で**上振れ余地**がある。
- 本機の現行 linear は 3,318 GFLOP/s（FP32 ピークの約 10%）。**ALU 律速ではない**ので、
  DP4a の理論倍率（Ampere 2× / Blackwell 4×）は達成できない。1.543× が現実的な期待値。

**perf 他段との比較（同じ 1024px・GPU 74.647 s に対する削減余地）**:

| 段                 |               対象時間 |         仮に 2× |     仮に 4× | 数値リスク                           |
| ------------------ | ---------------------: | --------------: | ----------: | ------------------------------------ |
| **C: w8a8 linear** |                40.97 s | — (実測 1.543×) | **−14.4 s** | **大**（活性が非可逆・新 tolerance） |
| A: 融合 attention  | 14.63 s（bmm+softmax） |          −7.3 s |     −11.0 s | 中（縮約順序変更・tolerance 再導出） |
| B: conv2d（VAE）   |                15.18 s |          −7.6 s |     −11.4 s | **小**（f32 のまま・順序のみ）       |

→ **削減量はほぼ同格で、数値リスクは C が最大**。順序は既にユーザー裁定済み
（③GEMM → ④融合 attention → 以降は実測次第・DP4a は後段）なので本 recon は順序を提案しないが、
**「C を先に着手するか」を再確認する価値はある**（openQuestion 5）。

## 10. 本 recon で確定した事実 / 未確定のまま残るもの

**確定（一次データあり）**:

- 本機 Deno 2.9.4 で `packed_4x8_integer_dot_product` が列挙され、`dot4I8Packed` を含む
  提案カーネル 3 本が `createComputePipeline` まで通る（陰性対照つき）。
- linear は DiT GPU の 69.8%（1024/wi8）/ 84.2%（512/wf16）。1 生成の GPU 合計 74.647 s の 54.9%。
- DiT の linear 454 本は k が全て 4 の倍数（DP4a 適格）。
- プロトタイプの 4.73× は旧 16×16 比。現行比は **1.543×**。
- プロトタイプの DP4a ベンチは**数値未検証・活性量子化なし・dequant はダミー定数**。
- SBV2 は conv1d が 86〜90%・linear は実質 0 GFLOP。`export_sbv2.py` に `--dtype` は無い。
- Karume に PSNR / 品質計測の台本は存在しない（ADR 0019 の品質ゲート①は未移植）。

- `RunArena` の retain/release がノード内一時バッファ 2 本を素直に扱えるか（細目未確認）。

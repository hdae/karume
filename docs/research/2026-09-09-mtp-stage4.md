## 0. 目的と結論

段 3 で着地した投機ループ（k=3・公式 drafter）が**実用でどれだけ速いか**を、同一プロセス・同一 prompt で
非投機（plain）と投機（speculative）を交互に回して測った（暖機 2 + A B B A × 3・中央値・
[`tools/mtp-bench`](../../tools/mtp-bench/README.md)）。段 3 の「1.18×」は生文書の継続 1 条件の単発値で、
chat 形式の実用 4 条件 × sampler 2 種はこれが初めての実測。

- **取り分は課題で決まる**（decode 相の ms/token・greedy）: 抽出 **1.81×** / 要約 **1.41×** / 対話 **1.18×** /
  自由文 **0.96×**（§2 表 1）。ターン全体（prefill 込み）では長文脈 1.22〜1.27×・対話 1.17×・自由文 0.96×。
- **採算式は 4 点とも 2% 以内で成立**: 倍率 = A / A\*（A = 確定 token / cycle・A\* = cycle 壁 / decode 壁）。
  この機では **A\* = 1.72（短文脈）〜 1.88（長文脈 4.8K）**。A がこれを下回る課題（自由文 1.66）は投機が負ける。
  閾値は文脈長 P ではなく**受理率**で決まる（対話 P=230 の A=2.03 は勝ち・自由文 P=33 の 1.66 は負け）→ 4-B ④ の
  on / off ゲートは P ではなく受理の移動平均で切る（§5）。
- **温度 1.0（配布推奨 sampler）でも受理率は greedy と同じ**（抽出は 168 cycle のヒストグラムまで一致・他は ±2%）。
  段 3 で見込んだ「greedy の 0.75〜0.9×」は外れ。token 列も plain / speculative で一致（seed 固定・8 走行すべて）。
  推奨 sampler の費用はホスト側の抽選（top-k / top-p・語彙 262K）で **+1.4 ms/cycle**（§3）。
- **cycle の内訳（壁）**: draft 15〜16 ms + verify 30.5（P=33）〜38.8（P=4.8K）+ ホスト 1〜1.3 ms。draft の GPU は
  5.5〜6.6 ms しかなく、残り ≈9.5 ms は Deno の round trip の床（F ≈ 11 ms・§3）。verify − decode は短文脈 +4 ms・
  長文脈 +8〜10 ms。
- **長文脈の verify 超過は attention**（timing ON の内訳・§4）: P≈4.8K で verify − decode = +6.25 ms のうち
  attention ①（prefill 形 M=4）対 ①′（decode 形）が **+5.7 ms**、本体の linear は M=4 でも M=1 と同コスト（+0.1）。
  4-B ⑤（①′ / ③′ の行タイル化）の着手条件「attention ≥ 5 ms/cycle」は長文脈で成立。短文脈の内訳は timing ON の
  膨張が壁の差（+4 ms）を超えるので帰属できない（§4 注意）。
- **4-B の順序（§6）**: ④ on / off ゲート（負ける側を守る・閾値 A\* ≈ 1.8）→ ⑤ 行タイル化（長文脈 −5 ms/cycle ≈ −9%）
  → ③ argmax 2 相化（Deno では F の陰に隠れ、ブラウザで効く）→ ⑥ k=7（抽出は 75% の cycle が 3/3 受理で k=3 が
  飽和 — ④ の動的 k が前提）。⑦ GPU 出口は不採用（ホスト + readback は cycle の 2〜5%）。

## 1. 方法

- 条件: `--workload {extract, summarize, dialogue, freeform} × --sampler {greedy, recommended}`（8 プロセス）、
  k=3・`--new-tokens 200`・`--capacity 8192`・PLE 全量常駐・`--rounds 3`。素材はリポ内の git 追跡下の文書
  （`tools/exporter/README.md` を 20,000 字で段落境界切り = 4,840〜4,845 token）と定数の対話・自由文
  （[`workloads.ts`](../../tools/mtp-bench/workloads.ts)）。抽出は 94 token で `eos`（自然長）、他は 200 token で
  `max-tokens`。
- 壁: `Session.prototype.run` を tool が包んで run 1 本の壁を採り、種別（prefill / decode / draft / verify）は
  `onRunDiagnostics` の phase で名乗る（production 無改変）。`msPerToken = generationMs / (tokens − 1)`（最初の
  token は prefill run が出す）。中央値は暖機を除く plain 6 / speculative 6 ターン。
- GPU 内訳: 別プロセス（`--gpu-timing --rounds 1`・greedy のみ）。**timing ON は 1 dispatch = 1 pass で壁が伸びる**
  ので、内訳は同じ種別の run の中の相対値として読み、壁の差と突き合わせて使う（§4）。
- 掃引は各プロセスの前に GPU 温度 ≤ 55 ℃ を待つ（`scripts/sweep.sh`）。実装レッグの誤りで runtime の estimate
  テストが 1 回（約 0.16 s）GPU に触れた窓が掃引中にある — 該当ターンは中央値に埋もれる長さで、表の値は動かない。

## 3. cycle の内訳（壁）

| 部位                    | 短文脈（P=33） | 長文脈（P≈4.8K） | 備考                                                           |
| ----------------------- | -------------: | ---------------: | -------------------------------------------------------------- |
| draft run（3 段 1 run） |        15.1 ms |          15.8 ms | GPU は 5.5〜6.6 ms（§4）— 差 ≈9.5 ms は round trip の床        |
| verify run（M=4）       |        30.5 ms |          36.6 ms | decode + 4.1（短）/ +7.8（長）                                 |
| ホスト（run の外）      |         1.0 ms |           1.3 ms | 受理判定 + 配送 + PLE gather。推奨 sampler で +0.7〜1.4        |
| **cycle**               |    **46.5 ms** |      **53.7 ms** |                                                                |
| decode run（比較）      |        26.4 ms |          28.8 ms | plain のホストは 0.44〜0.66 ms/token（推奨 sampler で ≈ +0.5） |

- **draft の壁は GPU ではなく round trip で決まる**。drafter の GPU 仕事は 5.5〜6.6 ms（lm_head i8 gemv 3 段 +
  argmax 3 段 + readonly attention）だが壁は 15 ms で、差 ≈9.5 ms は Deno の fence + readback の床
  （[research 2026-09-07 §7](2026-09-07-codex-perf-review-followup.md): B ≈ 11 ms・Chrome は 0.3〜0.5 ms）と整合する
  （**推測** — 直接は測っていない）。decode / verify（GPU 25〜35 ms）では床が GPU 時間の陰に入る。
- 1 cycle は run 2 本（draft の id をホストが読み、PLE の gather を経て verify を組む）が下限で、ADR 0096 帰結の
  「fence 1 本化」は成立しない（4-C で訂正）。
- 推奨 sampler のホスト費用 +1.4 ms/cycle（表 1 の host 列: 1.0〜1.3 → 1.7〜2.7）は cycle の 3〜5%。確定 token 1 個に
  つき 1 回の抽選（語彙 262K の top-k 64 / top-p 0.95）で、plain 側でも +0.5 ms/token 乗っている。

### 表 4 — verify − decode の差の帰属（extract・P=4845・ms/run）

| 部位                         | decode（M=1） | verify（M=4）           |         Δ |
| ---------------------------- | ------------: | ----------------------- | --------: |
| linear gemv i4（本体）       |         13.71 | r1 11.27 + r2 2.52      |     +0.08 |
| lm_head i8                   |          1.49 | r4 1.98                 |     +0.49 |
| attention full（qk + pv）    |   1.29 + 1.21 | 3.32 + 3.22（① wg16x4） | **+4.04** |
| attention sliding（qk + pv） |   0.59 + 0.83 | 1.87 + 1.21             | **+1.66** |
| rms_norm / strided / ew ほか |             — | —                       |     ≈ 0.0 |

- **長文脈では超過のほぼ全部（5.7 / 6.25 ms）が attention**: verify は prefill 形 ①（`wg16x4`・M=4）で、decode 形
  ①′（`wg16x16 par`・M=1）より遅い。本体の linear は M=4 でも帯域律速のまま（K-21 の row-block 変種 r1 / r2）。
  → 4-B ⑤（①′ / ③′ を M ≤ 8 の行タイルへ）の着手条件を満たす。効き代 ≈ −5 ms/cycle（長文脈の cycle 53.7 の 9%・
  既定席で u32 同一が付随）。
- **短文脈の内訳は帰属できない**（注意）: timing ON の Δ（+9.8〜+11.0 ms）が timing OFF の壁の Δ（+4.1〜+4.2 ms）を
  超えている。1 dispatch = 1 pass の膨張が dispatch 数の多い verify（1,477 本）に厚く乗るためで、キー別の差
  （linear r1 / r2 +3.9〜+5.1・lm_head r4 +1.4・sliding ① +1.8）は膨張込みの値。壁で読める事実は「verify は decode
  より +4 ms（M=4 の linear と lm_head の余分 — K-21 表 A1 の M=4 は M=1 の ×1.09）」まで。
- draft の GPU: lm_head i8 gemv 1.8〜2.6 ms（3 段）・argmax 1.5〜2.1 ms（3 段・1 行 = 1 workgroup）・readonly
  attention 0.2〜0.7 ms。4-B ③（argmax の 2 相化・−1.5 ms）は Deno では round trip の床の陰に入り壁に出ない
  （ブラウザでは cycle の 4%）。

## 5. 採算式と閾値

倍率 = A / A\*・A = 確定 token / cycle = `(accepted + cycles) / cycles`・A\* = cycle 壁 / decode 相の ms/token
（run 2 本 + ホストを decode 1 本 + ホストで割った値）。

| 条件           |  A\* | A（k=3） | 予測 A / A\* |  実測 |
| -------------- | ---: | -------: | -----------: | ----: |
| extract 4.8K   | 1.84 |     3.39 |        1.84× | 1.81× |
| summarize 4.8K | 1.88 |     2.65 |        1.41× | 1.41× |
| dialogue 230   | 1.72 |     2.03 |        1.18× | 1.18× |
| freeform 33    | 1.72 |     1.66 |        0.97× | 0.96× |

- **閾値は A\* ≈ 1.7〜1.9（この機・Deno）**。P の寄与は verify の attention 分（A\* で +0.1〜0.15）だけで、勝ち負けは
  課題の受理率が決める。ゲートの物差しは受理の移動平均（4-B ④）。
- **ブラウザ相当の推定**（F を 11 → 0.5 ms に差し替え・draft 壁 ≈ GPU + 1 ms・decode / verify は −2 ms と仮定・
  **未実測**）: A\* ≈ 1.5（短）〜 1.65（長）→ 抽出 ≈2.1× / 要約 ≈1.6× / 対話 ≈1.35× / 自由文 ≈1.1×。段 3 の見込み
  「ブラウザ相当 ≈1.3×（対話相当）」と同程度。実測はリリース後（裁定 2026-09-08）。
- **M2（Deno / Metal）**: 同じコマンドで壁だけ採る（`--gpu-timing` は device lost）。帯域律速の gemv が支配的なら
  T(M=4)/T(1) → 1 に近づき A\* が下がる（**推測**）。

## 6. 4-B への含意

| # | 項目                          | 数字の根拠                                                                                                   | 裁定              |
| - | ----------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------- |
| ④ | 投機の on / off ゲート        | 自由文 0.96×（A 1.66 < A\* 1.72）。閾値 A\* ≈ 1.8・受理の EWMA で k′ ∈ {0, k}・探索を混ぜる                  | **先頭**          |
| ⑤ | ①′ / ③′ の行タイル化（M ≤ 8） | 長文脈の verify 超過 +5.7 ms が attention（表 4）。−5 ms/cycle ≈ 抽出 1.81 → ≈2.0×。既定席で u32 同一が付随  | **④ の次**        |
| ③ | argmax の 2 相化              | drafter GPU −1.5 ms だが Deno では round trip の床の陰。ブラウザで cycle −4%                                 | ⑤ の後            |
| ⑥ | k=7 drafter + 動的 k          | 抽出は 75% の cycle が 3/3 受理（k=3 飽和）→ E-4 の k=6 で E[a] 3.8〜5.0。自由文 / 対話は k=7 固定だと負ける | ④ の動的 k が前提 |
| ⑦ | GPU argmax / topk 出口        | ホスト + readback は cycle の 2〜5%（閾値 10% 未満）                                                         | 不採用            |

- ADR 0096 帰結「fence 1 本化」は不成立（cycle = run 2 本が下限）→ 4-C で訂正。draft の壁 ≈9.5 ms は Deno の床で、
  ブラウザでは消える見込み。
- 事前プローブ（2026-09-08・生文書の継続・A 2.15・1.18×）は表 1 の対話条件と同じ位置にある。

## 7. 未検証・落とし穴

- 短文脈の GPU 内訳（§4 注意）。timing ON の壁は速度として読まない（tool の README・ADR 0021）。
- plain のベースラインは drafter 常駐の device で測っている（drafter 無しの配布形より遅ければ倍率は過大 —
  drafter は 76 MB で影響は小さい見込み・未測定）。
- 抽出は 94 token で自然停止するため標本が 168 cycle（他は 444〜720）。
- 掃引ごとの絶対値は 20〜25% 動く（K-21 §7）。採否は同じプロセス内の倍率で読む（この tool の設計理由）。
- M2 / ブラウザは未実測。温度 1.0 の受理率は seed 42 の 1 系列。

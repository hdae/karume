## 0. 要旨（先に結論）

1. **案 γ は「時間の案」ではなく「メモリの案」である**。1024px turbo w8a8+attn-a8 の DiT GPU
   1,331.24ms のうち、案 γ が触れる帯域律速 op 群（stats / elementwise / quantize_rows /
   layout / norm）は **285.96ms = 21.48%** しかなく、支配項の GEMM 1,045.28ms = 78.52% には
   **原理的に 1ms も効かない**（活性は既に i8 で読まれている — §3.4 ①）。
2. **f16 格納の実利得は「バイト半減 = 2×」ではない**。本プロジェクト唯一の実測アンカーは
   ADR 0028 の `attention_stats` **1.45〜1.58×**（帯域律速カーネルで S を f16 化した実測）。
   本 doc の期待値は全てこの倍率で割り引いてある。
3. **期待利得（試算）**: 中間バッファ f16 のみで DiT GPU **−3.9〜4.9%**、S の f16 受け渡しも
   同時に成立させて **−6.7〜9.6%**、VAE GPU **−2.8〜4.7%**。壁時計（1024px turbo 全体 27.4s）
   では **−3.3〜4.7%**、512px は**測定限界以下**。
4. **確実なのは transient メモリ**（本日実測）: DiT 1024px **1,224.5MiB**・VAE 1024px
   **1,536.0MiB** が、それぞれ約半分になる。1024px チェーンの VRAM ピークを決めているのは
   VAE decode（README 実測 6,725MiB）なので、**2048px / VAE tiling / GPUBuffer 天井
   7,280MiB の前提を緩める**のが案 γ の本体価値。
5. **非 GPU 固定費には 1ms も効かない**（§3.4 ③）。本日実測で非 GPU は
   **1024px 695ms/step・512px 704ms/step** と**解像度非依存** = データ量ではなく dispatch
   数 × CPU エンコードが支配。案 γ は変換 dispatch を足す方向なので**悪化のリスクだけがある**。
6. **`pack2x16float` は「無料」ではない**（§4.2）。ADR 0018 の重み f16 が feature 非依存で
   済んだのは**読み専用**だったから。中間バッファは**書き側**を持つので、u32 パックは
   「1 スレッドが偶数境界の 2 要素を書く」制約を全カーネルに強制する（端数・奇数長で
   read-modify-write ハザード）。**`array<f16>`（shader-f16 必須）か、書き側制約を飲むかの
   二択**が案 γ 最大の設計分岐。
7. 推奨は **案 (ii-b) = 「値の格納 dtype」を第 2 軸として executor が伝播させ、対象族を
   段階的に広げる opt-in**。工事は (i) 全面伝播と同じ構造だが、**波ごとに独立リリース可能**で、
   途中で止めても縮退点が成立する（§7）。**波 1 = S の f16 受け渡しを i8a8 と直交化**
   （既存 ADR 0028 実装の大半を流用でき、単独で 536.9MB + stats 1.45〜1.58× を取る）。

### 1.2 数値の読み方（ADR 0030 実測節の流儀を継承）

- `gpuTimingByGraph` の `entries` は**直近 run = DiT 1 step ぶん**（steps で割らない）。
- 熱でクロックが振れるので、**絶対 ms ではなく同一 run 内の比**で読む。本日の run の
  linear 時計プロキシは **1024px: DiT GPU / linear = 1,331.24 / 782.52 = 1.7013**、
  **512px: 383.90 / 274.24 = 1.3999**。ADR 0030 の実測（1024px の DiT GPU = 1.651·linear）
  とは attention 系の熱状態ぶんズレるが、**比率の構造は一致**している。
- `workgroupCount` は grid-stride の 65,535 クランプを受けるので、**要素数の代用にできるのは
  クランプに掛かっていない族だけ**（DiT の ew/strided は掛かっていない、gelu・rms_norm・VAE の
  ew/strided は掛かっている）。**帯域モデルの分子は IR 由来の要素数（実測 B）を正**とする。

### 1.3 IR 要素数と実測 dispatch の突合（分子の妥当性）

DiT 1024px・1 forward。`workgroupCount × 256` と IR の write 要素数が**完全一致**した族:

| 族                    |   実測 `wg × 256` |             IR write 要素数 | 判定           |
| --------------------- | ----------------: | --------------------------: | -------------- |
| `ew:add`（3 rank 計） |     1,888,131,072 |               1,888,131,072 | 一致           |
| `ew:mul`（3 rank 計） |     2,357,202,944 |               2,357,202,944 | 一致           |
| `ew:neg`              |       234,881,024 |                 234,881,024 | 一致           |
| `strided_write`(cat)  |       470,040,576 |                 470,040,576 | 一致           |
| `strided`             | **4,201,168,896** | permute+slice 3,936,927,744 | 差 264,241,152 |

最後の差 **264,241,152 要素**は、IR に存在しない**ランタイム挿入の Vᵀ**
（attention i8a8 の V 転置 — ADR 0030 決定 3）で、解析値
`28 層 × (16·4096·128 + 16·512·128) = 264,241,152` と**厳密一致**した。
→ **`strided` キーの 6.29%（1024px）/ 7.31%（512px）が量子化系の Vᵀ** と確定（時間換算
2.99ms / 1.27ms）。以降の分類はこの分割を使う。

## 3. 帯域モデル

### 3.1 族別の read/write バイトと実効帯域（f32 現状・DiT 1 step）

分子は §1.3 の IR 要素数、分母は §2.1 の実測 ms。**本機のスペック帯域は 912 GB/s**
（GDDR6X 384bit）。read/write の数え方は各カーネルの実装（走査回数）に合わせた。

| 族 / カーネル            | バイト式（1 要素あたり）                          | 1024px トラフィック |     ms | **実効 GB/s** | 飽和？              |
| ------------------------ | ------------------------------------------------- | ------------------: | -----: | ------------: | ------------------- |
| `strided`（Vᵀ 込）       | read 4 + write 4                                  |            33.61 GB |  47.52 |       **707** | ほぼ飽和            |
| `strided_write`          | read 4 + write 4                                  |             3.76 GB |   5.10 |       **737** | ほぼ飽和            |
| `ew`（mul/add/gelu/neg） | read 4 + write 4（他方は broadcast の小テンソル） |            43.36 GB |  64.43 |       **673** | 飽和寄り            |
| `layer_norm`             | read 4 + write 4（2 パス目は L2 命中）            |             5.70 GB |   8.63 |       **661** | 飽和寄り            |
| `rms_norm`               | 同上                                              |             5.87 GB |  27.35 |       **215** | **非飽和**          |
| `quantize_rows`          | read 4 ×2 パス + write 1（i8）                    |            32.58 GB |  54.97 |       **593** | 飽和寄り            |
| `attention_stats`        | S を read 4（write は m/l のみ）                  |            33.82 GB |  77.96 |       **434** | 中間                |
| `attention_qk`           | S を write 4（+ q/k は i8）                       |            33.82 GB | 126.86 |           267 | 非飽和（整数 GEMM） |
| `attention_pv`           | S を read 4（+ Vᵀ は i8）                         |            33.82 GB | 135.90 |           249 | 非飽和（整数 GEMM） |
| `linear`（w8a8）         | act i8 + w i8 + out f32                           |    15.19 GB（下限） | 782.52 |            19 | **完全に非飽和**    |

VAE decoder（1024px）:

| 族           | トラフィック |     ms | **実効 GB/s** | 判定                           |
| ------------ | -----------: | -----: | ------------: | ------------------------------ |
| `ew`         |     74.70 GB |  85.00 |       **879** | **ほぼピーク（完全飽和）**     |
| `strided`    |     23.71 GB | 188.63 |       **126** | **非飽和（非コアレス）**       |
| `reduce:sum` |      4.89 GB |  39.39 |       **124** | **非飽和（dim=128 の行縮約）** |

> **同じ `strided` キーでも DiT 707 GB/s と VAE 126 GB/s で 5.6 倍開く**（旧 recon の
> 「DiT 680 / VAE 86 GB/s」— [attention-design](2026-08-03-attention-design.md):705-706 —
> と同じ構造で、conv2d igemm 化後も残っている）。**推測（機序）**: DiT の permute は
> `[B,M,H,D] → [B,H,M,D]` で最内 D=128（512B）が連続 = コアレス。VAE の permute は
> `[1,C,H,W]` のチャネル軸を最終軸へ持ち上げる形で、読みの stride が H·W·4 バイト =
> **1 要素ごとに別セクタ**。→ **f16 化しても VAE の読みは 32B セクタ数が変わらないので
> 削減されず、halve するのは書き側だけ**。案 γ の VAE strided への期待は 2× ではなく
> 1.1〜1.2× と読むべき（**推測** — マイクロベンチでしか確定しない）。

### 3.2 S（attention スコア）のトラフィック — 案 γ と隣接する最大の単一項

S の要素数 = `28 層 × (16·4096·4096 + 16·4096·512)` = **8,455,716,864 要素 = 33.82GB（f32）/ step**
（512px は 704,643,072 要素 = 2.82GB）。①QK が書き ②stats が読み ③PV が読むので、
**S の DRAM 往復は 101.47GB / step**（旧 recon §3.2 の試算 101.5GB と一致）。
DiT の全 DRAM トラフィックの過半がここに集中している。

### 3.3 f16 化した場合の削減率と理論上限（族別）

| ------------------------------------------ | ---------------------------: | -------------: |

かつ変換 dispatch を足せばここが増える（§3.4 ③）。
**512px は帯域そのものが飽和していない**（strided 554 / ew 593 GB/s）ため利得はさらに小さく、
壁時計では**測定限界以下**（全体 15.6s に対し −0.2s 級）。

### 3.4 タスクが名指しで確定を求めた 3 点

#### ① linear w8a8 経路で活性を読むのは誰か（f16 化の効き先）

**確定（コード読解 + 実測）**: `linearCompute: "i8a8"` の 1 ノードは
**`quantize_rows` → i8a8 GEMM** の 2 dispatch（executor.ts:1392-1478）。活性 f32 を読むのは
**`quantize_rows` だけ**で、GEMM 本体（`linear:v3:i8a8:…:dp4a`）が読むのは
`xq`（i8 パック済み・executor.ts:1423）と `xs`（per-token scale）である。

- したがって **f16 格納の利得は `quantize_rows` の読み（2 パス × 4B → 2 パス × 2B）だけ**。
  1 要素あたり 9B → 5B（**−44.4%**）で、**GEMM 本体には 1 ビットも効かない**。
- 実測での上限: `quantize_rows` 54.97ms（DiT GPU の 4.13%）→ 期待 −13.7〜16.3ms。
- **既定経路（`linearCompute: "f32"`）は話が違う**: GEMM が活性 A タイルを直接 f32 で読み、
  A は `ceil(N/64)` 回再読される（1024px の代表形 M4096/K2048/N2048 で 32 回 = 1.07GB/ノード）。
  ここは f16 化でバイトが半減するが、**ADR 0028 の実測で GEMM は f16 タイルで 0.91〜0.92×
  = 遅くなる**（律速は共有帯域でなく命令発行）。**推測**: 格納 f16 + f32 計算（ロード時
  `unpack2x16float`）でも展開命令が増えるので **1.0× 前後**、勝ち筋は薄い。

#### ② attention i8a8 との共存制約の**正確な機序**

ADR 0030 Consequences の「S 格納形の互換が無く i8a8 と組めない」は、**独立した 2 つの障害**の
合成である。

1. **型の障害（API）**: `ComputePrecision = "f32" | "f16" | "i8a8"` は**単一 enum の相互排他 3 値**
   （executor.ts:257-267 の MUST）。`#encodeAttention` は
   `const compute: GemmCompute = attentionCompute === "f16" ? "f16" : "f32"`（executor.ts:1612）で
   計算精度を導き、**S のバイト幅もこの 1 変数で決まる**
   （`allocStorage(batch*rows*cols*(compute === "f16" ? 2 : 4))` — executor.ts:1624）。
   → `i8a8` を選んだ瞬間、S は必ず f32。**「S の格納形」という軸が存在しない**のが 1 つ目の機序。
2. **エンコードの障害（feature）**: 現行の S f16 は **`array<f16>` + `enable f16`**
   （attention.ts:80,86 / gemm.ts:579 の `outF16` 経路 gemm.ts:487-522）で、**shader-f16 feature を
   要求する**。一方 ADR 0030 決定 1 は「**`i8a8` は `shader-f16` を要求しない**」を MUST に
   している。素直に組むと i8a8 が feature 依存になり、決定 1 が壊れる。

**共存可能な形（設計として成立する）**:

- **(A) 軸を割る**: `attentionCompute`（計算形）と `attentionScoreStorage?: "f32" | "f16"`
  （S の格納形）を**別ノブ**にする。`i8a8 × S f16` は意味のある組で、直積が存在する
  （ADR 0028 が「直積は存在しない」と書いたのは q/k/v が全て活性だからで、**S は中間バッファ
  なので格納軸を持ちうる** — ここが読み替え点）。
- **(B) エンコードを feature 非依存にする**: S を `array<u32>` + `pack2x16float` /
  `unpack2x16float` へ。書き手は attention_qk の 1 箇所だけで、v4 経路（`n % 4 == 0`）なら
  4 連続列 = 2 語ちょうどなので**ハザードが出ない**（§4.2 の一般の危険は S には掛からない）。
  ただし丸め列は現行 `:c16` と別物になるので、ADR 0028 の atol=0 オラクルは**別に取り直す**。
- **(C) 妥協**: 組み合わせたときだけ shader-f16 を要求する（決定 1 の MUST を「i8a8 単独では
  要求しない」に緩める。ADR 0030 の改訂が要る）。

**i8a8 側の追加要件**: ③PV の i8a8 変種は S から `qP = round(127·exp(S−m))` を作る
（ADR 0030 決定 3）。S が f16 なら `exp` の引数が f16 丸め済みになるので、
**qP が ±1 段ずれる行が増える**（現行の門「不一致率 < 2%」— ADR 0030 検出限界 2 — の
再導出が必須）。品質への効きは Q0 シムで先に測るべき（§6.3）。

#### ③ 非 GPU 固定費 ~350ms/step に案 γ が触れる余地はあるか

**確定（本日実測）: 無い。**

| 解像度 | 最終 step 壁時計 | 同 step GPU | **非 GPU** | dispatch/step |
| ------ | ---------------: | ----------: | ---------: | ------------: |
| 1024px |          2,026ms |     1,331ms |  **695ms** |         3,311 |
| 512px  |          1,088ms |       384ms |  **704ms** |         3,311 |

- **非 GPU が解像度に依らずほぼ同一（695 対 704ms・差 1.3%）** で、dispatch 数も同一 3,311。
  → 非 GPU 固定費は**データ量ではなく dispatch 数 × ホスト側エンコード**（bind group 生成・
  params の writeBuffer・JS の await 連鎖）で決まっている。
- readback は DiT 出力の latent 1 本のみ（1024px で `[1,16,128,128]` = 1.0MiB / step）で、
  **f16 化しても最大 0.5MiB しか減らない = 測定限界以下**。入力アップロードも同様
  （グラフ入力は f32 固定 — executor.ts:796）。
- **むしろ案 γ が境界に変換 dispatch を挿入する形（§5 の (ii-a)）を採ると、この 695ms が増える**。
  境界変換は**専用 dispatch ではなく既存カーネルのキー変種**に畳むのが必須条件になる。
- なお ADR 0030 が記録した「~350ms/step」より本日の実測が大きいのは、あちらが 512px の
  A/B/A/B 排他実測時の値であるのに対し、本 run が単発（プロセス起動直後・GPU 冷機）である
  ためと**推測**する。**桁と性質（解像度非依存）は一致**しており、結論は動かない。

### 3.5 transient メモリ（本日実測 — 案 γ の本体価値）

`RunArena` の実績（`session.diagnostics().lastRun`・実測 C）:

| 構成                                        | alloc 回数 | 再利用 | createBuffer 計 | **peakTransient** |
| ------------------------------------------- | ---------: | -----: | --------------: | ----------------: |
| DiT 1024px turbo i8（`i8a8` + `attn i8a8`） |      3,356 |  3,835 |      1,557.7MiB |    **1,224.5MiB** |
| DiT 1024px turbo i8（`i8a8` + attn f32）    |      3,128 |  3,447 |      1,549.1MiB |    **1,184.5MiB** |
| DiT 512px turbo i8（`i8a8` + `attn i8a8`）  |      3,356 |  3,835 |        197.6MiB |      **114.2MiB** |
| VAE decoder 1024px                          |        432 |    360 |      4,935.8MiB |    **1,536.0MiB** |

- DiT 1024px の peak 1,224.5MiB のうち **S が 1,024.0MiB**（`16·4096·4096·4B`）= **83.6%**。
  → **S を f16 にするだけで DiT transient は 1,224.5 → 712.5MiB**。中間バッファも全て f16 に
  すれば **≈612MiB（−50%）**。
- **VAE の 1,536.0MiB が 1024px チェーンの VRAM ピーク（README 実測 6,725MiB @VAE decode）を
  決めている**。VAE の中間を f16 にすれば **≈768MiB（−768MiB）**。
  → GPUBuffer 天井 7,280MiB（known-issues）と 2048px / VAE tiling
  （[dynres-vae-tiling](2026-08-03-dynres-vae-tiling.md)）の前提が実際に動く。
- **これは推測ではなく設計値**（バッファサイズは shape の関数）。時間の期待値と違い、
  **マイクロベンチ待ちにならない唯一の利得**である。

## 4. 実装制約（実コード読解）

### 4.1 中間バッファの確保点は 1 箇所（良い知らせ）

```ts
// src/runtime/executor.ts:817-819
const out = step.contract.kind === "reshape"
  ? inputs[0]
  : arena.allocStorage(numel(step.outputShape) * 4);
```

**全ノードの出力はこの 1 行で確保される**（`* 4` がハードコード）。例外は
①`reshape` の別名化（ADR 0011）②各カーネルが自前で取る一時バッファ
（`xq`/`xs`:1423-1425、`scores`/`stats`:1624-1626、`qq`/`qs`/`kq`/`ks`:1769-1775、
`vt`/`vq`/`vs`:1888-1892）。**「値 → 格納バイト幅」の写像を 1 つ足せば、確保側の工事は
この 1 行 + 一時バッファ 12 箇所で閉じる**。

### 4.2 格納エンコードの二択と、**書き側の read-modify-write ハザード**

| 形                                     | 要求                                           | 読み                                                        | 書き                                                    | 端数                                  |
| -------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------- |
| **(α) `array<f16>`**                   | **shader-f16 feature**（+ 16bit storage）      | 2B 粒度で自然                                               | **2B 粒度で自然**                                       | 制約なし                              |
| **(β) `array<u32>` + `pack2x16float`** | **core WGSL・feature 不要**（ADR 0018 の先例） | `unpack2x16float(w[i>>1])[i&1]`（weight-storage.ts:98-102） | **1 スレッドが偶数境界の 2 要素を同時に書く必要がある** | **奇数長・端数タイルで RMW ハザード** |

**ADR 0018 の「feature 非依存」が案 γ に継承できない理由**（本 recon の重要な発見）:
重み f16 は**読み専用**だったので `unpack2x16float` が無料だった。中間バッファは**書き側**を
持つ。u32 に 2 要素を詰めると、隣接 2 要素を**別スレッドが書く**現行のカーネル形
（elementwise の grid-stride は 1 スレッド 1 要素、`strided` も
`out[i] = src[src_index]` — strided.ts:86）では、同じ u32 語への非アトミックな
read-modify-write が**データ競合**になる。回避には全カーネルを「1 スレッド 2 要素・
偶数境界」へ書き換える必要があり、**奇数要素数のテンソル・端タイルの部分書き**が
そのまま特別扱いになる（full-write 不変条件 — ADR 0004 ⑤ / 0014 — の再証明が要る）。

- **S だけは (β) が安全**: 書き手は `attention_qk` の 1 箇所で、v4 経路なら 1 スレッドが
  4 連続列 = 2 語ちょうどを書く（gemm.ts:509-518）。スカラ経路（`n % 4 != 0`）は
  `if (ocol + k < dims.n)` で部分書きするので**そこだけ RMW になる**（gemm.ts:524-540）。
  → **(β) を採るなら適格判定に `n % 4 == 0` を足して非適格は f32 へ縮退**（linear の `k % 4`・
  ADR 0030 決定 5 と同じ流儀）。
- **サイズクラスと full-write**: `toSizeClass` は 4 バイト整列（arena.ts:49-54）。f16 で
  奇数要素のバッファは 2 バイトの余りが**どのカーネルにも書かれない**。値としては無害だが、
  「全カーネルが出力の**全バイト**を書く」という ADR 0004 ⑤ の字義は破れる
  → **不変条件の文言側を「宣言要素ぶんの全バイト」へ明確化するか、確保を 4B 倍数へ切り上げる**
  かの裁定が要る（切り上げると `arrayLength()` が 1 増えるので、要素数を params で持つ現行の
  規律〔arena.ts:44-48 の MUST〕は維持できる）。
- **プールの分裂**: サイズクラスは「4 バイト整列した実バイト数そのもの」なので、同じ論理形の
  テンソルが f32 と f16 で**別クラス**になる。混在期間中は再利用率が落ち、peak が理論値どおりに
  半減しない可能性がある（**推測** — 実測 C の `reuseCount` を波ごとに見るのが検出器）。

### 4.3 codegen 決定性への影響

- 全キーは**生成入力の関数**（`elementwiseKey` = `ew:v2:<op>:<from>><to>:r<rank>:wg256`
  — elementwise.ts:360-362、`stridedKey` = `strided:v1:<dtype>:r4:wg256` — strided.ts:55）。
  **格納 dtype をキーに載せれば決定性は保たれる**（形状 → 1 ビットの写像である `v4` フラグの
  先例 — gemm.ts:36-41）。
- **キーの語彙は 3 本目の軸になる**: 格納重み `:wf16`（ADR 0018）/ 計算 `:c16`（ADR 0028）/
  **活性格納（案 γ）は第 3 の語**が要る（例 `:a16` / `:s16`）。3 語が同時に立つ組み合わせが
  実在する（例 `linear:v4:wf16:a16`）ので、語の並び順を**キー生成の 1 箇所**で固定しないと
  同一構成が 2 通りのキーを持つ。
- スナップショット（`tests/fixtures/wgsl/` = **93 本**）は「既定変種のバイト列不変」で守られる。
  既定 f32 を 1 バイトも動かさない限り既存 93 本は無傷、新変種ぶんが増える。

## 5. 設計空間（3 案）

### 案 (i) — 全域伝播（executor がグラフ全体の格納 dtype を決め、全カーネルが f16 変種を持つ）

- **形**: 値ごとに `storage: "f32" | "f16"` を計画段階で決め（グラフ入出力は f32 固定 —
  executor.ts:796 と `#readOutputs`）、全カーネル族が「入力スロットごとの格納形 × 出力の格納形」
  の変種を持つ。
- **変種本数（試算）**: 現行のキー関数は **28 本**（`src/kernels/*.ts` + `src/codegen/*.ts`）。
  そのうち活性を触るのは elementwise / strided / strided_write / reduce / softmax / layer_norm /
  rms_norm / gemm 5 種（linear/matmul/bmm/attention_qk/attention_pv）/ conv 3 種 /
  attention_stats / embedding / gather / masked_fill / pad / flip / cumsum / quantize_rows
  ≒ **22 族**。二項 op は入力 2 × 出力 1 で **2³ = 8 通り**、単項は 4 通り。
  素朴に全直積を取ると**数百変種** = ADR 0006 の「却下案 (a) 組合せ爆発」そのもの。
  現実には「全入力を f16 に揃える」正規化で **族あたり 2 通り**（全 f32 / 全 f16）へ落とせるが、
  それでも**全 22 族 × 2 + 混在境界の変換**になる。
- **codegen 決定性**: キーに 1 語足すだけで保たれる（§4.3）。
- **アリーナ**: サイズクラス分裂（§4.2）。peak は理論どおり半減。
- **格納形**: 書き側が全族にあるので **(β) `pack2x16float` は事実上不可**
  （全 22 族を 2 要素/スレッドへ書き換え）。→ **(α) `array<f16>` = shader-f16 必須**。
- **評価**: 工事最大。**shader-f16 が無い環境で案 γ が丸ごと無効**になるのが致命的
  （ブラウザ・Qualcomm 系の除外 — shader-f16-recon §1.4）。**非推奨**。

### 案 (ii) — 帯域律速 op 族に絞った opt-in【推奨】

対象を「実効帯域が飽和している族」に限る（§3.1 の実測が選定基準）:
**DiT: `strided` / `ew` / `layer_norm` / `quantize_rows` の入力 / S**、
**VAE: `ew`（879 GB/s = ほぼピーク）**。除外: `rms_norm`（215 GB/s）・
VAE `strided`（126 GB/s）・VAE `reduce`（124 GB/s）・全 GEMM。

境界の扱いに 2 つの下位案がある。

- **(ii-a) 変換 dispatch を挿入する**
  - 長所: カーネル変種が「全 f16」の 1 種で済む。
  - 短所: **却下すべき**。変換 dispatch 1 本は read 4B + write 2B = 元の op と同等の
    トラフィックで、**利得を丸ごと食う**。さらに dispatch 数が増えて非 GPU 固定費
    695ms/step（§3.4 ③）が悪化する。
- **(ii-b) 変換込みのキー変種にする**【推奨】
  - 消費側カーネルが「入力 i を f16 で読む」ビットを持ち（`unpack2x16float` か
    `array<f16>`）、生産側が「出力を f16 で書く」ビットを持つ。**境界の変換は既存
    dispatch のロード / ストアに畳まれ、追加 dispatch はゼロ**。
  - これは **`weight-storage.ts` が重みに対してやっていることの活性版**で、部品構成
    （`weightArrayType` / `weightLoaderWgsl` / `weightRead`）をそのまま鏡像化できる。
  - 変種本数: 対象 4 族（ew / strided / strided_write / layer_norm）+ 消費側の読みビット
    （gemm の A タイル・quantize_rows・reduce）。**族あたり 2〜4 変種・計 15〜20 変種**。
  - 格納形: **対象族の書き手が「1 スレッド 1 要素」なので (β) は要素対の再設計が要る**。
    現実解は **①S は (β) で feature 非依存**（v4 経路のみ適格）**②それ以外は (α)**、
    あるいは**全部 (α)** の二択（openQuestion 3）。

### 案 (iii) — 「格納 dtype は値の属性」+ 適格集合を波で広げる（(ii-b) の一般形）【本命の骨格】

(ii-b) を「対象族の列挙」ではなく **「値ごとの格納 dtype を planGraph が決め、executor が
伝播する」**構造で実装し、**適格集合（どの値を f16 にするか）を波ごとに広げる**。

- **利点**: 波 1 の工事がそのまま波 2・3 の土台になる（案 (i) と同じ構造を、適格集合という
  1 つのつまみで段階制御する）。**途中で止めても、そこまでの適格集合で成立する**。
- 適格判定の述語は**形状と op の関数**（`v4` フラグの先例）なので決定性は保たれる。
- **不適格の縮退は「沈黙」にしない**: ADR 0030 決定 5 の教訓（沈黙縮退の検出器はキー本数
  検査ただ 1 本）を先取りし、**適格集合を診断に出す**（`StorageDiagnostics` の活性版）。

## 6. 数値契約・検証設計

### 6.1 atol=0 が狙える範囲

**狙える**。ADR 0028 決定 5 のオラクル「**f16 変種 ≡ 入力を f16 に丸めた f32 変種**」は、
案 γ ではむしろ**より素直に成立する**:

- 案 γ は**格納だけ**を f16 にし、**演算は f32 のまま**（ADR 0006 の骨格を維持）。したがって
  「f16 格納変種の出力 ≡ 入力を f16 に丸めた f32 変種の出力」は**定義上の恒等式**で、
  縮約順序も丸め列も 1 段も動かない。ADR 0028 の f16 **タイル計算**（共有タイルで丸める =
  内積の途中に丸めが入る）より契約が強い。
- **例外は「出力も f16 に丸める」段**。生産側が f16 で書く場合、出力は
  `f16(f32 の計算結果)` になる。オラクルは「f32 変種の出力をホストで `Math.f16round` した値」と
  ビット一致すべき（ADR 0028 決定 5 と同じ合成 — ホストは丸めだけを担う）。
  **`Math.f16round` とビット実装の二重丸め問題**（ADR 0028 知見）はここでも同じ罠。
- **MUST（ADR 0028 知見の継承）**: レジスタ上の `f32→f16→f32` 往復はコンパイラに消される。
  **丸めは必ず「格納」を経由させる** — 案 γ はまさに格納で丸めるので、この性質に自然に乗る。
  ただし**「書きだけ f16 にして読み側が f32 のまま」という半端な変異は数値に出ない**
  （読み手が同じバッファを f16 として解釈しない限り値が壊れるので、これは loud）。
  一方**「f16 で書くべき所を f32 で書いたが、読み手も f32 で読む」= 変種が丸ごと効いていない**
  形は**数値でも時間でも検出しにくい**（ADR 0024 追補・0030 決定 5 と同型）→ **検出器は
  パイプラインキー検査**。

### 6.2 E2E の型（opt-in 沈黙失効の検出器）

ADR 0028 の 3 層（上限 + **下限の床** + キー検査）をそのまま使える。ただし **ADR 0030 と同型の
限界が出る**:

- **単独適用（`--linear-compute f32 --attention-compute f32` + 活性 f16 のみ）**なら、f32 対照との
  判別帯が広く取れ**床が置ける**見込み（**推測** — f16 格納の相対 eps 4.88e-4 は、ADR 0028 が
  実測した f16 タイル計算の step1 noise 4.943e-3 と同桁になるはず）。
- **実運用形（w8a8 + attn-a8 と併用）では床が構造的に置けない可能性が高い**。ADR 0030 の実測
  （attention a8 単独は f32 対照と 1,969 倍離れるが、w8a8 併用では 1.35 倍しか離れない）と
  同じ構造で、**先に効いている量子化のノイズに埋もれる**。→ **実運用形の opt-in 検出は
  キー本数検査 1 本**になると予告しておくべき（ADR 0030 の「検出限界」の再演）。
- **キー検査の設計**: 「f16 格納変種のキーが所定本数走る」+「対応する f32 キーが 0 本」。
  §2.1 の census（`strided` 991・`ew:add:r3` 254 …）がそのまま期待本数の正本になる。
  **適格判定が形状の関数**（§5 案 iii）なので、期待本数は解像度ごとに固定する。

### 6.3 品質ゲート（Q0 torch シム）

- **既存の受け皿は拡張できる**: `tools/exporter/measure_quant_anima.py` の
  `Config` dataclass（`weight_i8` / `linear_act` / `attn` / `stats_quantized` / `measure_pt`）に
  **`act_f16: bool` を 1 つ足す**形で構成表に載る（`CONFIGS` は 8 構成・`BASELINE = "w8a8"`）。
- **粒度はランタイム実装粒度と厳密一致 MUST**（ADR 0030 決定 6）。案 γ の実装粒度は
  「**Karume の IR ノードの出力バッファ**」なので、torch 側は
  **`TorchDispatchMode` で aten op の出力を `.half().float()` する**のが唯一整合する形。
  ADR 0029 の知見「**パッチ層は functional を直接呼ぶためモジュールフックは沈黙で取り逃す
  — op 粒度が唯一安全**」がここにも効く（モジュールフックは不可）。
- **粒度のズレが残る**（正直に開示）: IR ノード ≠ aten op（エクスポータの分解・融合を経る）。
  特に **融合 attention（1 IR ノード = SDPA 1 本）**と **rms_norm / layer_norm**（torch では
  1 op、Karume でも 1 カーネル = 一致）で扱いが変わる。**シムは「上界の見積もり」であって
  厳密鏡像ではない**と明記して使うべき（ADR 0030 の Q0 も相対比較で使っている）。
- **門の形（提案）**: 基準は **f32 ではなく受理済みの w8a8 + attn-a8**（ADR 0030 の流儀）。
  latent relRMS 倍率 ≤ 1.5× と最終画像のユーザー目視。

### 6.4 tolerance 再導出の範囲

**既定 f32 不変なら既存系列は 0 本**（確認済み）。根拠:

- `tests/*_test.ts` のトップレベル `*TOLERANCE*` 定数は現状 **59 本**
  （`grep -rhoE "^(const|export const) [A-Z_0-9]*TOLERANCE[A-Z_0-9]*" tests/*.ts | sort -u | wc -l`
  の実測。ADR 0028 執筆時の 41 から SBV2 f16 / i8 系列・DeBERTa i8 系列・attention a8 で増えた）。
  WGSL スナップショットは **93 本**（ADR 0028 時点の 74 から増加）。
- 先例 3 件がいずれも「既定不変 → 既存 tolerance 変更ゼロ」を実証している
  （ADR 0025 w8a8 / 0028 f16 計算 / 0030 attention a8）。
- 新規に要るのは **① カーネル単体の atol=0 テスト 1 ファイル ② E2E 1 ファイル（判別帯 +
  可能なら床 + キー検査）③ `gpu_gridstride_test.ts` / `gpu_full_write_test.ts` へ新変種を
  各 1 本**（族の MUST）。

## 8. プロトタイプの先行事例

**結論: 実装も実測も断念記録も無い。** 記録は「未計画」の 1 行だけ。

- プロトタイプの量子化台帳（`docs/quantization.md` の方式一覧）に
  **「活性 f16 / 中間バッファも F16 / 帯域 1/2 / `shader-f16` / **未計画**（数値検証の
  切り分けが濁る — 0006 の却下案 (b)）」** の行がある。
- プロトタイプの決定記録 0006（f16 は重み格納のみ）の却下案に
  **「(b) 活性値も f16（数値検証の切り分けが濁る。**性能目的の活性 f16 は量子化
  マイルストーン M4 で改めて**）」** とあり、その M4 は f16 重み格納 / w8 / w4 の実測で
  埋まって**活性 f16 には到達していない**（`docs/quantization.md` の実測記録節）。
- 全文検索でも活性 / 中間バッファの f16 化に関する実装・ベンチ・断念の記録は出てこない。
- **Karume の ADR 0006「活性 f16: 不採用（検証の切り分けが濁る）」は、この行の直接の継承**
  である。つまり **案 γ は「プロトタイプで試して駄目だった案」ではなく、「両プロジェクトとも
  一度も測っていない案」**。w8a8・attention a8 と同じ構図（先行実測なしで Karume が初手を打つ）。

## 9. openQuestions（メイン裁定・閉じた選択肢 + 推奨）

1. **着手するか / 何を目的に据えるか**
   (a) **メモリ目的で着手する**（時間の勝ちは −3〜5% と正直に見積もり、transient −50% =
   DiT 612MiB / VAE 768MiB を主目的に据える）/ (b) 時間目的で着手し、波 0 の
   マイクロベンチで勝てなければ閉じる / (c) 着手せず、2048px / tiling が現実の要求に
   なるまで記録で閉じる。
   → **推奨 (a)**。時間の期待値は §3.3 のとおり控えめだが、**transient は設計値で確実**で、
   1024px の VRAM ピーク（VAE decode 6,725MiB）と GPUBuffer 天井 7,280MiB の距離を
   実際に動かす唯一の手だから。

2. **スコープの切り方**
   (a) 案 (i) 全域伝播 / (b) **案 (iii) = 値の格納 dtype を伝播させる骨格 + 適格集合を波で
   広げる**（(ii-b) の一般形）/ (c) 案 (ii-b) の「対象族を列挙で固定」。
   → **推奨 (b)**。(c) は列挙が増えるたびに配線が散り、(a) は shader-f16 非対応環境で
   丸ごと無効になる。(b) なら**適格集合というつまみ 1 つ**で (c) にも (a) にも寄せられ、
   波の途中で止めても成立する。

3. **格納エンコード**
   (a) **`array<f16>`（shader-f16 必須）で統一** / (b) `pack2x16float`（core WGSL）で統一 /
   (c) **S だけ (b)・それ以外 (a)**。
   → **推奨 (a)**。(b) は §4.2 のとおり**書き側の RMW ハザード**で全カーネルを
   「1 スレッド 2 要素・偶数境界」へ書き換える羽目になり、端数と full-write の再証明が
   波ごとに発生する。(c) は魅力的だが**同じ機能に 2 つのエンコードが並存**し、
   「S は feature 無しで動くのに ew は動かない」という説明のつかない非対称を生む。
   ただし **(a) は ADR 0030 決定 1（i8a8 は shader-f16 を要求しない）の改訂を伴う** —
   そこを飲めるかがこの問いの実質。

4. **波 1（S の直交化）の API 形**
   (a) **`attentionScoreStorage?: "f32" | "f16"` を新設**して `attentionCompute` と直交させる /
   (b) `attentionCompute` に `"i8a8+s16"` のような複合値を足す / (c) 既定で i8a8 のとき
   自動的に S を f16 にする。
   → **推奨 (a)**。(c) は「機械や設定で黙って数値が変わる」= ADR 0028 決定 1 が auto を
   禁じた理由に真っ向から反する。(b) は enum が組み合わせ爆発する。
   なお ADR 0028 の「直積は存在しない」は **q/k/v が全て活性である**ことの帰結であり、
   **S は中間バッファなので格納軸を持ちうる** — この読み替えを ADR 側に明記すべき。

5. **数値契約の狙い**
   (a) **atol=0 を契約にする**（「f16 格納変種 ≡ 入力を f16 に丸めた f32 変種」— 演算は
   f32 のままなので定義上の恒等式）/ (b) 理論由来 tolerance で運用する。
   → **推奨 (a)**。ADR 0028 の f16 **タイル計算**より契約が強く、オラクル（ホストは
   `Math.f16round` だけを担い f32 縮約は既存カーネルに任せる合成）もそのまま流用できる。

6. **E2E の opt-in 検出器**
   (a) **判別帯 + 床 + キー検査の 3 層**（ADR 0028 と同型。実運用形〔w8a8 + attn-a8 併用〕では
   床が置けないことを**あらかじめ ADR に書く**）/ (b) 最初からキー検査 1 本に割り切る /
   (c) 単独適用専用の E2E を別ファイルで持ち、実運用形はキー検査のみ。
   → **推奨 (c)**。ADR 0030 の実測（単独 1,969 倍 / 併用 1.35 倍）が「単独なら床が置ける・
   併用では置けない」を既に示している。両方を 1 ファイルに混ぜると床が恒真化する。

7. **品質ゲート Q0 の粒度**
   (a) **`TorchDispatchMode` で aten op 出力を f16 丸め**（op 粒度 — ADR 0029 の知見に整合。
   IR ノードとのズレは「上界の見積もり」と開示）/ (b) モジュールフック（**不可** — ADR 0029 で
   FFN conv 60 本を沈黙で取り逃した実績）/ (c) Q0 を省き、実 GPU の E2E と目視だけで裁定。
   → **推奨 (a)**。(c) は工事が大きすぎて「作ってから品質不合格」のリスクを取れない。

8. **ADR の起こし方**
   (a) **新 ADR 1 本**（ADR 0006 の「活性 f16 不採用」を上書きし、0028 の S 軸・0030 決定 1 の
   feature 規律・0004 ⑤ の端数語を同時に改訂）/ (b) ADR 0006 への追補 / (c) 波ごとに ADR。
   → **推奨 (a)**。**ADR 0006 の中核的決定を覆す**変更なので、追補では読み手が
   「不採用」の記述に先に当たってしまう。0004 / 0011 / 0018 / 0028 / 0030 への波及は
   新 ADR の「改訂する決定」節で一覧にする。

9. **`rms_norm` と VAE `strided` / `reduce` の扱い**
   (a) **入れない**（実効 215 / 126 / 124 GB/s で非飽和 = f16 化しても利得が出ない）/
   (b) 一様性のために入れる / (c) **先にこれらの非飽和そのものを直す**（rms_norm は
   dim=128 に対し 256 スレッド = 半分遊休、VAE strided は非コアレス、VAE reduce は
   dim=128 の行縮約）。
   → **推奨 (a) を採り、(c) を別タスク候補として起票**。(c) は案 γ より小さい工事で
   VAE の 188.63 + 39.39 = **228.02ms（VAE GPU の 17.8%）**に効く可能性があり、
   **案 γ より費用対効果が良い隣接**である。

## 10. 隣接（本タスクのスコープ外・報告のみ）

1. **VAE の `strided` 126 GB/s と `reduce:sum` 124 GB/s は、案 γ より安い手で改善しうる**
   （openQuestion 9 (c)）。合計 228.02ms = VAE GPU の 17.8%。group_norm の縮約軸を
   permute で最終次元へ持ち上げる現行形（ADR 0011 案 B）が原因なので、
   **「reduce に軸指定を持たせて permute を消す」**が筋。ADR 0011 が予告した
   「消費側カーネルへ strided 読みを融合してコピーを消す最適化」の具体例そのもの。
2. **非 GPU 固定費 695〜704ms/step（1024px で全体の 34%・512px で 65%）は現在の最大の未収穫**。
   dispatch 数 3,311/step に比例し、解像度に依らない。bind group のキャッシュ・
   params バッファの再利用・`await` 連鎖の削減が候補（**未調査**）。
3. **ADR 0030 の記録「非 GPU 固定費 ~350ms/step」は本日の実測 695〜704ms と 2 倍違う**。
   測定条件の違い（A/B/A/B 排他 512px 対 単発 1024px 冷機）と**推測**するが、
   どちらかの数値に但し書きが要る。
4. `attention_stats` の `dispatchCount` は 56 だが `workgroupCount` は 3,669,960 =
   `56 × 65,535` で**全ノードが grid-stride のクランプを踏んでいる**（Pitfalls index の
   「1024px の DiT では softmax 全 56 ノードが常時クランプ」と同じ現象が融合 attention の
   行統計でも起きている）。縮退経路が本番経路であることの追加の実測証拠。

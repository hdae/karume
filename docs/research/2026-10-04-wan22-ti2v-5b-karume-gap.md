# Wan2.2 TI2V-5B を Karume へ移植するときの差分（Karume 側の部品・容量・時間・段の案）

> 時点スナップショット（2026-10-04）— Wan2.2 TI2V-5B の ADR を起こすための、Karume 側の差分分析（部品の再利用 / 変更 / 新規・容量と時間の外挿・段の案）。裁定は含まない。

手法: 上流の構造は [2026-10-04 の上流調査](2026-10-04-wan22-ti2v-5b-upstream.md)（以下「上流調査 §n」）を正とし、調べ直していない。
Karume 側は ADR [0118](../decisions/0118-wan21-video-generation.md) / [0119](../decisions/0119-wan-umt5-gpu-text-encoder.md) /
[0120](../decisions/0120-wan-dit-w8a8-seat.md) の記録と、`packages/models/src/wan/`・`tools/export-recipes/wan/`・exporter core・runtime の
コードを読んだ。数値の外挿は `node calc.mjs`、ビット一致の前提の確認は torch CPU の小実験で行った（§11）。GPU は使っていない。

記法:

- 「事実」= コード（`file:line`）・ADR の検収欄の実測・こちらで実行した結果。「推測」= 外挿と設計案。各節で 2 つを分ける。
- 用語は ADR 0118 / 0120 のまま使う。**S** = DiT のトークン数。**1 パス** = DiT の 1 forward（50 ステップ × CFG 2 本で 100 パス）。
  **diag** = 診断が出す確保量（重み + backing）。**backing** = Session の中間テンソルの置き場（アリーナ）。**参照席** = 同じ重みで
  `session` が空の席（ADR 0120 の `f16+dit8`）。**実用席** = `f16+dit8-a8-attn8-s16`。
- B570 の天井 = Deno の総確保の天井 9,600 MiB = 9.375 GiB（[research 2026-10-02](2026-10-02-b570-vram-budget.md) §3-2）。

## 0. 要約

- **新しい IR op は要らない**。VAE 2.2 の新しい演算（DupUp3D・AvgDown3D・patchify / unpatchify・非対称ゼロ詰め）は、全て rank 4 以下の
  reshape / permute / expand / slice / pad / sum / mul で書ける（§2）。DiT は 2.1 と同じ語彙。
- **T2V は 2.1 と同じ DiT グラフの形で上流とビット一致する**。全トークンの t が同じなら、diffusers の `[B,S,6,C]` 経路と
  `[B,6,C]` 経路は要素ごとに同じ演算になる（`transformer_wan.py:469-485`・`704-711` を読んだ）。ただし diffusers のパイプラインが
  渡す 2 次元の timestep（M = S の Linear）は、torch CPU で M = 1 と最終ビットが違う（実験で観測 — §6.1）。
- **f16 席は B570 に載らない**。重みだけで 9.31 GiB あり、天井 9.375 GiB と同じ大きさ。参照層の門は **i8 の参照席**（重み i8・計算 f32）で
  持つのが現実的（§3）。
- **B570 で入るのは 832×480・81 フレーム（S = 8,190）まで**の見込み（diag 7.2〜7.6 GiB）。公式の既定 1280×704・121 フレーム
  （S = 27,280）は diag 9.2〜11.4 GiB で B570 に入らず、RTX 5070 Ti（16 GB 級）の Chrome でだけ届く見込み（§3）。
- **1 パスの時間**（B570・実用席）は 832×480×81 で約 11 s（2.1 の 81 フレーム 34.0 s の約 1/3）。生成 1 本は DiT 約 18 分 + VAE 約
  11 分の見込み。VAE 2.2 は 2.1 の 2 倍強重く、生成の約 4 割を VAE が占める（§4）。
- **export**: i8 系列は ADR 0119 段 10b の「meta で trace + 行の塊ごとに i8 + `fixed_weights`」で core を変えずに書ける見込み。
  **f64 参照は全体を f64 にすると 37.25 GiB で 31 GiB 機に載らない** ので、層逐次の参照に書き直す必要がある（§5）。
- **I2V** は DiT に「条件フレーム用の時刻入力」と「トークン選択のマスク」を足すだけで書ける（`where` が 3 者 broadcast を持つ）。
  **DiT のグラフは最初から I2V の入力を持たせて 1 本にし、T2V を先に通す**のを推奨する（5B の再 export と golden の撮り直しを避ける）（§6）。
- **VAE のタイル decode は diffusers と順序が違う**。2.2 の diffusers は 12 チャネルの patchify 空間でブレンドしてから unpatchify する
  （`autoencoder_kl_wan.py:1355-1401`）。Karume も同じ順にする必要がある（§1・§9）。
- 利用者に仰ぐのは 3 点（受理する解像度・フレーム数／f16 席の要否／I2V の画像の縦横比の扱い）。他は推奨が明らか（§10）。

### 1.2 推測（規模の根拠）

- DiT・スケジューラ・text 段・RoPE はほぼそのまま使える。重いのは「VAE 2.2 のパッチと export」「I2V の encoder」「5B の export
  経路（meta trace と層逐次 f64 参照）」「パイプラインの世代の切り替え」の 4 つ。
- ホストの定数（チャネル 16・mean / std・タイルの重なり・出力 3 ch・受理集合・既定）は全部 2.1 の世代に結び付いている。2.2 を足すときは
  グラフ宣言から導けるもの（チャネル数・出力チャネル・タイル辺）は導き、導けないもの（mean / std・受理集合・既定・重なりの px）は世代の
  記述子（profile）に集めるのが自然（§7）。

## 2. op 語彙 — Karume に無い演算と書き方

### 2.1 事実

- exporter のハンドラは `gelu` … `scaled_dot_product_attention` の表（`tools/exporter/src/karume/aten_handlers.py:1429-1499`）。
  `sum.dim_IntList`（`:1437`）・`where.self`（`:1448`）はある。**`aten.mean.dim` はハンドラが無く**、rms_norm の畳み込みの部品としてだけ
  認識される（`normalize.py:253-260`）。
- `pad` は最終次元・定数 0 だけ（`aten_handlers.py:349-370`）。strided の rank 上限は 4（`tools/exporter/src/karume/ops.py:279`・
  runtime `ops/shapes.ts:109-112`）。
- `where` は条件・値の 3 者を右詰め broadcast する（`packages/runtime/src/ops/shapes.ts:309-313`）。
- 融合 attention の head 幅 D に上限の検査は見当たらない（`kernels/attention.ts` と `recipe-builders/attention.ts` を rg した範囲。
  見えるのは `D % 4` の適格判定だけ — `recipe-builders/attention.ts:192`・`240`）。VAE 2.2 の mid の D は decoder 1024 / encoder 640
  （上流調査 §3.1）。
- 2.1 の VAE パッチは、上流の rank 6 の時間インターリーブを rank 4 の reshape / permute へ書き直している（ADR 0118 決定 2）。

### 2.2 書き方（推測 — 全てデータ移動か要素ごとの演算なので、上流と値でビット一致する見込み）

テンソルは unbatched の `[C,T,H,W]`（ADR 0118 決定 2 と同じ）。

- `mean` の書き換え: torch CPU の `mean` は和を要素数で割る形だが、4 要素の和の順が Karume の `sum` と同じとは限らない（推測）。encoder は
  I2V の画像 1 枚だけに効くので、門は帯で受ける。

### 3.2 推測（式と外挿）

**backing の式**（2.1 の実測で係数を決めた）: `backing ≈ max( Sblk + k·A, 2·S·ffn·4 + 3·A )`

- `A = S·dim·4`（`[S,dim]` の f32 1 本）、`Sblk` = 行ブロック 1 枚のスコア（`planRowBlocks` の式・f32 か s16）。
- k は「attention の瞬間に生きている `[S,dim]` の本数」。2.1 の実測から `k_f16 = 9.24 / 8.14`（33 / 81 フレーム）、
  `k_実用席 = 15.22 / 11.37`（実用席は量子化の一時を含む）。5B は同じブロック構造なので k は同じ値の帯を使う。
- 第 2 項は FFN の瞬間（中間 `[S,ffn]` の f32 2 本 + `[S,dim]` 3 本）。5B の候補ではどれも第 1 項の方が大きかった。

**重み**: f16 9,999,575,424 B（9.31 GiB — 上流調査 §1.2）。i8 = Linear 4,997,382,144 要素（patch 埋め込みの 589,824 を含む）+ 行 scale

## 6. I2V のホスト処理とグラフ入力・T2V を先に通す段取り

### 6.1 事実

- 上流 DiT のブロックは `temb.ndim == 4`（トークンごと）と `== 3`（バッチごと）で分岐するが、式はどちらも `scale_shift_table + temb` を
  6 分割して `norm(x)·(1+scale)+shift` / `·gate` に使う（`transformer_wan.py:462-500`）。head も同じ（`transformer_wan.py:704-711`）。
  t が全トークンで同じなら、2 つの経路は要素ごとに同じ演算になる。
- **torch CPU の Linear は、同じ行を M 本並べたときと M = 1 のときで最終ビットが違う**（観測 — §11 の実験。K 256 → N 3072 と
  K 3072 → N 18432 の 2 形で、M = 2 / 64 / 390 / 8,190 のどれも M = 1 と不一致・最大差 3.6e-7〜1.9e-6・M 本の行どうしは一致。
  torch 2.13.0+cpu・6 スレッド）。diffusers の `WanPipeline(expand_timesteps=True)` は T2V でも `[1,S]` の timestep を渡す
  （上流調査 §7）ので、time MLP は M = S で走る。
- 2.1 の DiT の eager 同値の門は、上流を 1 次元の timestep（M = 1 の経路）で呼んでビット一致を見ている（`dit_patch.py:350-356` の
  ラッパは上流の `[B,6,C]` 経路の逐語）。
- I2V の条件づけ（上流調査 §2.3）: 先頭の潜在フレームだけ t = 0、モデル入力は各 step で `(1 − mask)·cond + mask·latents`、
  スケジューラは置き換えない潜在で進め、最後に 1 回置き換える（diffusers `pipeline_wan_i2v.py:760-767`・`816-817`）。
- 先頭フレームのトークンはトークン列の先頭に連続して並ぶ（トークン添字 `(f·H' + h)·W' + w` — `dit-tokens.ts:15`・`88`・`108`）。その数 P は
  832×480 で 390・1280×704 で 880（`(H/32)·(W/32)`）。
- 画像の前処理は公式（覆う側へ LANCZOS → 中央クロップ）と diffusers（指定寸法へ LANCZOS で直接 — クロップ無し）で違う（上流調査 §4.3）。

### 6.2 推測（グラフ入力の変え方）

**DiT のグラフ**: 時刻の入力を 2 本にし、トークンごとに選ぶ。

- 入力 `timesteps_proj [1,256]`（生成側の t — 2.1 と同じ）に加えて `timesteps_proj_condition [1,256]`（条件フレームの t = 0）と
  `condition_mask [1,S,1]`（先頭フレームのトークンで真）を足す。
- グラフの中で time MLP を **M = 1 で 2 回**回し（同じ重みの linear を 2 ノード）、6 成分の変調ベクトルと head の 2 成分を
  `where(condition_mask, 条件側, 生成側)` で `[1,S,C]` に選ぶ。`where` は選択なので値は上流のトークンごとの値と同じ。
- **M = 2 の 1 回にしない**: M = 1 と M = 2 で linear の縮約の経路が違えば（CPU では §6.1 で実際に違った・GPU の GEMV と GEMM の
  切り替えは未確認）、T2V の出力が「I2V 対応のグラフ」と「2.1 型のグラフ」で割れる。M = 1 を 2 回にしておけば、T2V（マスク全偽・
  2 本とも同じ t）の生成側の行は 2.1 型と同じ計算になる。
- 費用: 変調 8 か所 × `[S,C]` の where と生きている `[S,dim]` の増分（k が +2 程度）。S = 8,190 で backing +0.19 GiB、S = 27,280 で
  +0.62 GiB。時間は要素ごとの演算で、1 パスの 1% 程度（帯域から見た概算）。
- 代わりの案: ① ホストで `[S,256]` に展開してグラフの MLP を M = S で回す — `time_projection` だけで約 1.8 T MAC・`e0` が f32 1.87 GiB
  （上流調査 §2.4）。② 先頭 P トークンを slice / cat で分ける — S のほかに P の記号が要り、S 形グラフ（1 シンボル — ADR 0034）から外れる。

**ホストの処理**（I2V）:

1. 画像の前処理（RGB8 を受ける — decode は Karume の責務外 `preprocess.ts:6-9`）: 出力寸法を決め、LANCZOS でリサイズ（PIL 互換の
   分離型 — `preprocess.ts` に lanczos を足す）、縦横比の扱い（§10 の分岐点）、`[-1,1]` へ。
2. patchify（3 → 12 ch）をホストで → VAE encoder のグラフ（T = 1・cache 無し）→ 出力の前半 48 ch（mu）→ `(mu − mean)·(1/std)`（48 値）。
3. 各 step: モデル入力の先頭フレームを条件の潜在で置き換え（diffusers の式は `(1−m)·c + m·x` で、m が 0 / 1 なら符号付きゼロを除いて
   置き換えと同じ値）→ patchify → DiT（時刻 2 本 + マスク）→ unpatchify → CFG → UniPC（置き換えない潜在で進める）。
4. 最後に先頭フレームを置き換えて VAE decode。

**VAE encoder の寸法**: I2V の出力寸法は画像の縦横比で変わる（公式は `best_output_size` — 上流調査 §4.3）。encoder のグラフは
固定形なので、①寸法ごとのグラフ（受理寸法を絞る・ADR 0038 §4 の「資産は解像度から独立」に反する）②タイル encode（解像度から独立・
上流の非タイルとは近似の差）③conv の記号次元（runtime の shape 規則 `ops/shapes.ts:672-728` は数値の長さで式を立てる — 記号長の
conv2d / conv3d の可否は未確認）のどれか。1280×704 の画像 1 枚の encode は最大中間 36.2 M 要素（145 MB — 上流調査 §3.4）で、
タイルにしなくても容量は足りる。

**T2V を先に通せるか**: 通せる。T2V はマスク全偽・2 本とも同じ t で I2V 対応のグラフを使い、I2V のホスト処理・encoder・画像の前処理は
後の段に回せる。グラフの形を最初から I2V 対応にしておけば、5B の DiT の再 export（CPU 数時間・golden の撮り直し）が要らない。

## 7. 配布形と API

### 7.1 事実

- 配布リポは家族 1 つ・世代は別リポ（ADR 0092 決定 1 / 2）で、ADR 0118 決定 7 が Wan2.2 を `karume-wan2.2`・`WAN_SOURCES` のキー
  `wan2.2` と予告している。`WAN_SOURCES` は公開リポができるまで作らない（ADR 0118 追記「段 7 の結果」）。
- umT5 は別リポ `karume-umt5-xxl`（model `xxl`・pipeline `umt5-encoder/1`・quant `i8`）で、Wan2.1 の配布形が `weights.text_encoder` を
  越境参照する（ADR 0119 追記「段 10d の設計」A / D・「10d-1」）。出所は Wan2.1-T2V-1.3B-Diffusers の text_encoder（F32）。
- umT5 の重みは 2.1 と 2.2 で同じ（公式 .pth は sha 一致・Diffusers 版 2.2 の bf16 は 2.1 の f32 の RNE 丸めと抜き取りでビット一致 —

## 8. 数値の門と段の分割・w8a8

### 8.1 事実（既存の門の型）

- DiT: S = 192 は f32 参照に対する比・実寸は f64 参照と正規化比 r。帯 = 決定用 6 本の最悪 × 5、受入れ 2〜3 本は別 seed、故障注入
  （timestep +1 など）が帯の外（ADR 0118 決定 8・追記）。帯は S ごとに独立に導く。
- VAE: cache の正規化だけを当てた形が上流の非タイル `_decode` とビット一致、GPU の chunk 列は比の帯（ADR 0118 段 4）。タイルは縮退門が
  Uint32 一致（段 5）。
- 実用席: 参照席との自機 A/B 門（step 1 の relRMS・上限 = 実測 × 2・床 = ビット同一なら赤・census・決定性 — ADR 0120 決定 4）。
- 2.1 の実用席の step 1 relRMS は N = 14,040 で 1.07e-1、N = 32,760 で 2.10e-1（attention a8 が大半）。利用者の視認で「f16 と比べて明確な
  劣化は無く誤差の範囲」と裁定された（ADR 0120 裁定 2026-10-04）。

## 9. 推奨が明らかなもの（推奨と理由だけ）

- **新しい op を足さない**。§2 の書き換えは全てデータ移動か要素ごとの演算で、rank 4 以下に収まる。
- **VAE のタイルは潜在 16（256 px）・重なり 4 潜在（64 px）・12 ch の patchify 空間でブレンドしてから unpatchify**。diffusers の
  2.2 の既定（`tile_sample_min` 256 px・stride 192 px・ブレンドは patchify 後の寸法 — `autoencoder_kl_wan.py:1076-1081`・`1349-1401`）と
  同じ大きさと順序で、タイル 32 は B570 で VAE 段の余裕を消す（§3）。2.1 の重なりの定数（潜在 8）は px から導く形に変える。
- **DiT のグラフは最初から I2V の入力（時刻 2 本・マスク）を持つ 1 本にする**。5B の再 export と golden の撮り直しを避け、T2V の値は
  2.1 型の計算のまま保てる（§6.2）。
- **i8 系列は meta trace + `fixed_weights` で export し、f64 参照は層逐次に書き直す**。前者は core の変更なしの前例があり、後者は
  31 GiB 機で他に手が無い（§5）。
- **参照層の門は i8 の参照席で持つ**（f16 席は B570 に載らない — §3）。
- **umT5 は `karume-umt5-xxl` を越境参照し、再 export しない**（§7）。
- **eager 同値の門の相手は上流の 1 次元 timestep の経路**にする。diffusers のパイプラインの 2 次元 timestep の経路は、torch CPU の
  M = S の Linear で最終ビットが割れる（§6.1 の観測）。2 次元の経路との差は記録だけにする。

## 10. 利用者に仰ぐ分岐点

1. **受理する解像度とフレーム数**。公式の T2V は 1280×704 / 704×1280 の 2 つだけで既定 121 フレーム（上流調査 §4.1）。B570（開発機）で
   検収できるのは 832×480×81 まで（§3）。
   - a. 832×480 系（480p・4n+1 の ≤ 81）で始め、開発機で全部の門を持つ。1280×704 は後で RTX の Chrome の実走で足す。
   - b. 最初から 1280×704・121 を受理に入れる。開発機では回らず、検収は利用者の RTX の実走（DiT だけで 40〜80 分）に頼る。
   - 得失: a は門と sha 行を開発機で持てるが、公式が想定していない 480p の品質は未知（公式の I2V の docstring は「480p なら shift 3.0」と
     書くので、480p で回す使い方自体はある — 上流調査 §4.1）。b は公式どおりの品質だが、回帰を開発機で検出できない。
   - 推奨: a（そのうえで 832×480×121 が B570 に入るかを段 2 で測る）。
2. **f16 席を作るか**。f16 の DiT は 9.31 GiB で B570 に載らず、RTX 5070 Ti でも 1280×704×121 では境界（§3）。
   - a. 作らない（参照席 `f16+dit8` と実用席の 2 つ）。
   - b. VRAM の大きい機のために作る。開発機では一度も回らず、export も RAM の境界か core の変更が要る（§5）。
   - 推奨: a。元の重みに近い席は参照席（重み i8・計算 f32）が担う。
3. **I2V の画像の縦横比が出力と違うときの扱い**（I2V の段で決める）。
   - a. はみ出しを切る（公式 — 覆う側へリサイズして中央クロップ）。
   - b. 引き伸ばす（diffusers — 指定寸法へ直接リサイズ）。
   - 得失: a は縦横比を保つが端が欠ける。b は全体を残すが形が歪む。どちらも出力寸法の選び方（公式は縦横比から 32 の倍数を選ぶ）と組。
   - 推奨: a（公式の挙動）。参照は、ホストで切った画像を diffusers に渡して採る。

## 独立検証（2026-10-04）

別のレッグが、設計が依存する主張 14 個を一次ソースと再計測で確かめた。成り立つ（holds）が 13 個。

### 覆った・不確かな主張

- **refuted（影響 low）**: VAE 2.2（タイル 16）の最大の中間は [4,512,128,128] f32＝134,217,728 B（128 MiB） — meta 上で TorchFunctionMode を使い全テンソルを数えた。chunk 1 の最大は CausalConv3d の pad 後の入力 [1,512,6,130,130]＝51.9M 要素（f32 207.7 MB）で、次が cat [1,512,5,128,128] の 41.9M。見積りは約 70 MB 小さい。

### 本文が落としていた、設計に効く事実

- 2.2 の patchify 空間は潜在 1 あたり 8px（16/2）で、2.1 の sample 空間と同じ縮尺。既存の vae-tiles.ts のブレンドと貼り付けは、チャネル 12・重なり 4 潜在で流用できる可能性がある。逆に WAN_VAE_MIN_TILE_OVERLAP=8 のままだと出力 128px の重なりになる。
- 参照席 f16+dit8 の diag と backing は 2.1 で一度も測られていない。5B の参照席の容量は f16 席の k を借りた仮定にすぎない（ADR 0120 段4 の基準 68.5/17.1 s・6.17 GiB がどの席の値かも文書は区別していない）。
- 束縛上限を超える S の境界が 1 ずつずれている。FFN 中間は S≥37,450、cross の S は S≥43,691 が正しい（37,449×57,344 B も 43,690×49,152 B も上限の内）。設計への影響は無い。
- 5B の HF vae/config.json には diffusers 0.39.0 の **init** が受けない clip_output キーがある（meta で組むとき TypeError、from_pretrained では無視される）。export の台本で config を直接渡す場合は除く必要がある。
- VAE の最大中間は CausalConv3d の cache との cat と pad の後の入力（[512,6,130,130]＝207.7 MB）。Karume のグラフが cat を中に持つ形なら、VAE 段の中間の見積り（0.5〜0.8 GiB）の根拠を測り直す必要がある。
- torch の実験は M 本の行の一致を先頭 8 行しか見ていなかった（再実験では全行の一致を確認した）。スレッド数への依存は未確認（6 スレッドだけ）。

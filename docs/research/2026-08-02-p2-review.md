## 1. レビュー概要

対象は M1-P2 波 1〜5 の差分全体。3 レンズ（correctness / contract / tests）を並列実行し、
統合後 13 件（major 3・minor 6・info 4）。major 3 件は複製環境での実機再現を伴う敵対検証に
かけ、**いずれも holds**（指摘の核心は成立）と判定された一方、実害評価の結果は全て
**minor へ降格**した。

1. **gather の先行次元不一致 / embedding のスカラ添字**（`verify.py:508` ほか）—
   エクスポータ側に shape 契約の層が無く、torch が合法とする形（先行次元不一致の
   gather・0-dim 添字の embedding）が export・verify を素通りし、ランタイムの
   Session 構築（`planGraph`）で初めて落ちる「三面契約が割れる」典型形と確認。ただし
   落ち方は例外なしの沈黙誤値ではなく Session 構築時の fail loudly（`OpContractError`）
   に留まり、踏む形も torch 的には稀。実害はレイトフェイルどまりで minor に降格。

2. **grid-stride 境界ケースが実際には縮退しない**（`tests/gpu_ops_test.ts:564`）—
   `BOUNDARY_CASES` が謳う「grid-stride が効く経路」3 ケースは dispatch が縮退せず、
   M1-P2 で新設した strided/gather/embedding/conv1d/masked_fill/softmax/layer_norm の
   grid-stride ループは 1 本も行動テストで踏まれていないと確認。ただしセッション作業域で
   組んだプローブ（実機、repo 無変更）では現行カーネルは縮退時も正しく全域を書き、NG は
   0 件。「現に壊れている」defect ではなく被覆欠落 + 誤誘導コメントであり minor に降格。

3. **scalar_operands golden の出力が恒等的に 0**（`tools/exporter/karume/goldens.py:398`）—
   コミット済みフィクスチャを実測し、出力 24 要素が全て 0（逆順スカラの誤りが値に出ない）
   ことを確認。ただし exporter 側の正規化パスには独立の単体テストがあり、実行時側も
   int_cast golden が同種の被演算子順の誤りを別経路で捕捉するため、実害は「E2E 検出器が
   存在すると称する虚偽のコメント / README」に限定されると判明し minor に降格。

## 3. submit 根治の設計要点

DeBERTa 24 層 T=512 の実測で、1 回の submit が時間予算の 3.5 倍（352.1ms）に膨らむ問題を、
threshold の後付けや smoothing ではなく制御則そのものの作り直しで根治した。

不変条件は 3 つ:

1. **成長は実測の裏付けがある窓だけで行う** — 実測 0ms を「速い」と読んで無条件倍増する
   旧制御則の欠陥を排し、実測 0 は「情報なし」として推定を更新しない。
2. **切れ目は積む前に判定する** — 「この dispatch を足すと予算超過」を事前に見て先に
   チャンクを閉じ、超過してから縮めるのではなく超過そのものを起こさない。
3. **推定単位は workgroup 数**（dispatch 数ではない） — dispatch 数を単位にすると、
   系列長 T が変わった瞬間に推定が一度は必ず踏み越える。

計測の誤帰属（重なった submit の完了通知が一斉に届き、先頭 1 本に全時間が乗って見える現象）
は個別値を信用せず、**窓の合計時間 ÷ 窓内の合計 workgroup 数**で吸収する設計にした。

before/after 実測（T=512、2 回目 run）: 1 submit / 352.1ms（予算比 3.5 倍）→
10 submit / 窓合計 387.8ms（推定上限 50ms・平均 38.8ms）。wall clock は 496.6ms → 490.8ms で
実質不変。

## 4. 繰り延べ裁定（P3 へ）

構造的な対応が要るとして今回は見送った 2 件:

1. **TS ↔ Python 契約表の適合表化** — 現状 `src/ops.ts` の `OP_CONTRACTS` と
   `ops.py` の同名テーブルは独立した手書きで、両者の一致は人手の規律にのみ依存する。
   `tests/fixtures/dim-grammar.json` の前例に倣い、op 名 × arity × dtype 集合 ×
   attrs キー・値域を JSON 適合ケース表へ外出しし、両側のテストから読ませる構造が必要。
2. **Python 側 shape 層の構造的移植** — エクスポータには TS の `computeOutputShape` に
   相当する shape 規則の層が無く、ハンドラごとに個別の検査を書き写す運用になっている。
   今回は gather / embedding / sym_prefix_slice の個別穴を塞いだが、根治には TS 側の
   shape 規則を Python 側へ構造的に移植する必要がある。

残存の非対称メモ（実害小・P3 検討候補）:

- CPU 参照実装（`referencePermute` / `referenceExpand` / `referenceSymPrefixSlice`）は
  `computeOutputShape` を通らないため rank 5 を受理し続ける — テスト専用層に閉じており
  実害なし。
- `convert.py` の rank 検査（permute/expand は inline、sym_prefix_slice は
  `assert_strided_rank`）と契約層の rank 検査とで例外型が層ごとに異なる
  （`NotImplementedError` vs `OpContractError`）— 統一するなら例外設計の裁定が要る。
- per-chunk の真の実測時間には timestamp-query が要る（この実行環境では
  `onSubmittedWorkDone` の解決が flush の await まで遅延し、窓の先頭 1 本に全時間が
  乗ってしまうため）— 未提案。
- 初回 run は裏付けが run 終端でしか取れないため常に `initialChunkSize` で進む
  （DeBERTa で 56 submit）。wall clock 実害は無いが、run 中に意図的に drain して早期に
  推定を得る設計余地は残っている。

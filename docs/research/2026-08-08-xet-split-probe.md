# HF Xet でレイヤー分割は DL を速くするか — E1 実測

> NOTE: 時点スナップショット。数値は 2026-08-08 の実測（開発機 / 開発回線・`curl` 直叩き）に
> 基づく。HF 側の CDN・Xet backend の挙動は時間とともに変わりうるので、再現には §6 の手順で
> 測り直すこと。

配布形を「1 モデル = 1 safetensors」のままにするか、レイヤー単位に分割するかの裁定材料。
発端は公開済み `hdae/anima-turbo` の text_encoder（f32・1,194,225,572 B の単一 safetensors）が
**0.4〜0.8 MB/s** しか出ないという観測で、「分割すれば Xet 側の並列取得が効くのでは」という
仮説を実測で潰しに行った。

**結論を先に**: 分割はどの指標でも改善せず悪化する。速度を決めているのは**ストリーム数**
だけで、それは分割しなくても HTTP Range で得られる（resolve URL は 206 /
`accept-ranges: bytes` を返す）。**分割せず、単一ファイルに対する Range 4 並列**が正解。

## 1. 方法論

### 1.1 素材と摂動（CAS dedup の排除）

`models/anima-turbo/text_encoder/model.safetensors`（1,194,225,572 B）を**読み取り専用**で
使い、以下の 4 構成を作った。各構成の合計バイト数は元サイズと完全一致する。

| variant | 構成                       | ファイルサイズ                   |
| ------- | -------------------------- | -------------------------------- |
| A       | 単一 1 ファイル            | 1,194,225,572 B                  |
| B       | 8 分割                     | 149,278,196 B ×7 + 149,278,200 B |
| C       | 32 分割                    | 37,319,549 B ×31 + 37,319,553 B  |
| D       | 単一 1 ファイル（別 salt） | 1,194,225,572 B                  |

**摂動**: 4096 B ごとの先頭 8 B に、variant + shard 固有の 8 B salt を XOR（サイズ不変）。
salt は FNV-1a + xorshift32 でラベル（`A|0` / `B|3` / `C|17` / `D|0`）から決定的に生成し、
全バイト非ゼロを保証した（差分バイト数が厳密に予測できる）。

これは **Xet の CAS dedup を確実に外すため**である。Xet の CDC 最小チャンク（約 8 KiB）>
摂動間隔 4096 B なので、**どのチャンクも必ず摂動点を含む** — 公開リポとのチャンク一致は
原理的に起こり得ない。検証:

- 全 42 ファイルで size 一致かつ diffBytes == expectedDiff（`gen-report.txt`）。
- `cmp` による独立検証 — `c/shard-00` vs 元 `[0:37319549]` = 72,896 バイト差、
  `b/shard-00` vs 元 `[0:149278196]` = 291,560 バイト差。いずれも予測値と一致。
- **決定的証拠**: アップロード完了時の最終カウンタが **New Data Upload 3.58GB / 3.58GB**
  （dedup ゼロ）。cold 測定が「実は既存チャンクの再利用だった」という汚染は無い。

### 1.2 計測経路

`curl -sS -L -H "Authorization: Bearer <token>"` で **resolve URL を直叩き**した。これは
`@karume/hub` と同じ**素の HTTP 経路**であって、Xet クライアントの経路ではない
（hub は Web 標準 API のみ = ADR 0038 なので、この経路が実装に対応する）。リダイレクト先は
private の probe リポ・public の `hdae/anima-turbo` とも同一（`us.aws.cdn.hf.co`）で、
両者とも `x-xet-hash` を持つ Xet オブジェクトである。

**cold を無駄にしない排他設計**: cold は 1 オブジェクトにつき初回 GET の 1 回しか取れないので、
逐次と 4 並列を同じ shard で二度測ることはできない。B は shard 00-03 を逐次 / 04-07 を 4 並列、
C は 00-15 を逐次 / 16-31 を 4 並列（どちらも 597MB 相当）に割り、A は単一ファイルゆえ逐次のみ、
D は全域を 4 分割 Range の同時 4 本とした。

生ログ: `results-cold.txt` / `results-warm.txt` / `results-ranged.txt` /
`results-control.txt`、整形済み `tables.md`（いずれもスクラッチパッド）。

## 4. 結論

1. **分割は cold を悪化させる。** per-stream 純転送は 1.19GB 単一 10.75 > 149MB 分割 9.77 >
   37MB 分割 6.70 MB/s と、shard を小さくするほど単調に低下した。単一ストリームでモデル
   全体を取る時間は A 111.81s < B 約 127.6s < C 約 200.3s = **分割で 1.14〜1.79 倍遅い**。
2. **TTFB は 1 リクエストあたり約 0.67 秒の固定費**。全 phase を通じて中央値 0.663〜0.709s に
   収まり、ファイルサイズ（37MB / 149MB / 1.19GB）にも cold/warm にも Range / 全体 GET にも
   ほとんど依存しない。分割はこれをファイル数だけ積み増す（C 逐次 32 ファイルで TTFB 合計
   21.20s = 総時間 77.25s の **27%**）。
3. **Range 4 並列（分割なし）が全構成で最速** — cold **32.98 MB/s** / warm **84.09 MB/s**。
   分割で到達できた最高は 8 分割 4 並列の cold 27.91 / warm 70.31 MB/s で、届かなかった。
   **32 分割の 4 並列（warm 40.61）は、分割なしの単一ストリーム（64.88）より遅い。**
4. **並列は 4 で飽和する** — D-warm-range8 84.27 vs range4 84.09 MB/s（差 0.2%）。
   「並列を増やすために shard を増やす」動機も存在しない。
   > 適用範囲の限定（2026-08-09 追記）: これは**健全なオブジェクト（帯域律速）に限る**。
   > 再構成が断片化したオブジェクトでは 16 並列まで単調に伸びた（1.9 → 28.4 MB/s）。
   > [2026-08-09-xet-fragmentation.md](2026-08-09-xet-fragmentation.md) §2。
5. したがって **DL 性能を理由にレイヤー分割してはいけない**。分割が非ネットワーク要件
   （メモリ上限・部分ロード・バリアント差し替え等）で必要なら「その要件を満たす最大サイズ」を
   選ぶ。下限は 150 MiB 程度（149 MiB で単一 1.19GB 比 warm 純転送 65%、37 MiB では 33%）。
   **32 分割（約 36 MiB）は明確に不可**。なお 149 MiB と 1.19 GB の間に測定点が無いので、
   「256〜512 MiB が実用帯」は補間であって実測ではない。

## 5. anima-turbo の遅さはオブジェクト固有・永続

> **撤回（2026-08-09）**: 本節末の「配布形 v2 として再アップロードすれば治る公算が大きい」は
> 誤り。同一バイト列は dedup で同じ CAS オブジェクトに戻るため、別リポへ上げ直しても
> `x-xet-hash` は変わらず速度も変わらない（実証済み）。遅さの機序は再構成の断片化で、
> [2026-08-09-xet-fragmentation.md](2026-08-09-xet-fragmentation.md) に引き継ぐ。

本実験の cold は「**アップロード直後・未 DL**」であり、発端の 0.4〜0.8 MB/s は再現していない
（今回の cold は 10.68 MB/s）。一方、read-only の対照計測（既存 public リポ
`hdae/anima-turbo` に GET / HEAD のみ）では**今なお遅い**:

| 測定                   |     size(B) |     TTFB(s) | total(s)                      |      MB/s |
| ---------------------- | ----------: | ----------: | ----------------------------- | --------: |
| 全体 GET               |           — |           — | >720s で未完 → 中断           |       < 2 |
| 末尾 100MiB 単発 Range |   104857600 |       0.706 | 30.82                         |      3.40 |
| 中盤 50MiB × 4 並列    | 52428800 ×4 | 0.670-0.714 | 13.15 / 16.70 / 16.86 / 16.91 | 3.10-3.99 |
| 同 壁時計              |   209715200 |           — | 16.92                         | **12.39** |

- この 3.1〜4.0 MB/s は 2026-08-05 の記録（2 回目 3.6〜4.7 MB/s）とほぼ同じ値で、
  **あの遅さは cold/warm の区別ではなく、そのオブジェクト固有かつ永続的**である。
- 両リポとも同じ Xet backend・同じ CDN ホスト（`us.aws.cdn.hf.co`）なので、
  **「ストレージ backend の違い」仮説は反証された**。
- **同じバイト列の摂動版（probe リポ）は速い**（10.68 MB/s）ので、原因はリポ / オブジェクト
  単位の要因を強く示唆する — **配布形 v2 として再アップロードすれば治る公算が大きい**
  （推測。xorb 配置か CDN edge 側の事情という仮説の裏付けは無い）。
- 対照側でも 4 並列は 3.4 → 12.39 MB/s と約 4 倍にスケールした。**「per-stream 律速・並列は
  ほぼ線形」は速い領域でも遅い領域でも成立する**ので、結論 §4 は遅い領域へ外挿しても向きは
  変わらない。

## 6. probe リポの温存と再計測手順

**本実験が答えていない唯一の問い**は「長期間 CDN に触れられていないオブジェクトの真 cold」で
ある。今回の cold は 5 分前にアップロードしたばかりの状態だった。これを測るために
**`hdae/karume-probe`（model 型・private・42 ファイル・4,776,902,288 B = 4.449 GiB）を
消さずに残してある**。

| prefix | ファイル数 |    合計バイト | 内訳                               |
| ------ | ---------: | ------------: | ---------------------------------- |
| `a/`   |          1 | 1,194,225,572 | `a/model-a.bin`                    |
| `b/`   |          8 | 1,194,225,572 | `b/shard-00.bin` 〜 `shard-07.bin` |
| `c/`   |         32 | 1,194,225,572 | `c/shard-00.bin` 〜 `shard-31.bin` |
| `d/`   |          1 | 1,194,225,572 | `d/model-d.bin`                    |

commit: `736f3b067d259eda5900b309d6abdc99b9cdeb5e`（2026-08-08T19:13:08Z）/
先行 `c752f0f60d685d1d2ce6d33383202f47f4c36b95`（同 18:40:13Z）。

**再計測手順（数週間放置後の真 cold 検証）**:

1. 前回計測から**十分な期間（数週間）を空ける**。CDN edge から落ちていることが前提なので、
   間に一度でも GET すると cold が失われる。
2. 対象ファイルの resolve URL
   （`https://huggingface.co/hdae/karume-probe/resolve/main/<path>`）へ
   `curl -sS -L -H "Authorization: Bearer <token>"` を投げる。private リポなので Bearer
   token が要る。
3. **cold は初回 GET のみ**。1 オブジェクトにつき 1 回しか取れないので、逐次と並列を同じ
   shard で二度測らないこと（§1.2 の排他設計をそのまま使う）。variant D（`d/model-d.bin`）は
   Range 分割で複数の測り方ができるが、**Range も初回アクセスで warm 化する**点は同じ。
4. 比較先は本ドキュメントの §2（今回の「アップロード直後 cold」）。真 cold がここより
   明確に遅ければ、`hdae/anima-turbo` の 3〜4 MB/s は「放置による cold」で説明でき、
   §5 の「オブジェクト固有」という読みを**撤回**することになる。

削除する場合の対象はリポ全体（`hf repo delete hdae/karume-probe`）で、karume 本体には影響
しない。ただし**消すと上記の真 cold 検証はできなくなる**。

## 7. 未解決（openQuestions）

- 真 cold（長期放置後）は未測定 — §6 の手順で埋める。
- `hdae/anima-turbo` が遅い原因は未特定。切り分け候補: ①同リポ内の他ファイル（unet 等）も
  同様に遅いか ②別リージョン / 別回線から同じ値が出るか。③（同じバイト列を別リポへ再
  アップロードすると速くなるか）は今回の probe が肯定側の証拠を出している。
- 並列度 4 の飽和が**クライアント側（回線・CPU）の上限か HF 側の上限か**は切り分けていない。
  warm の 84 MB/s は回線帯域そのものに当たっている可能性がある（cold の 33 MB/s は明らかに
  別の律速）。回線実効帯域の独立測定が未実施。
- 計測は `curl` であって Deno / ブラウザの `fetch` ではない。`@karume/hub` の実装
  （`fetch` + `ReadableStream`・`@hdae/fetch-cache` 経由）で同じ数値が出るかは未検証 —
  **Range 並列を実装する際は `fetch` の挙動で再測定が要る**。

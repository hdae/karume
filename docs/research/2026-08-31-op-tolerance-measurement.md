# op 別 tolerance の実測 — 汎用 DEFAULT_TOLERANCE を置き換えるための測定（2026-08-31）

> 性格: **時点スナップショット**（HEAD `683d6a0` / RTX 3080 Ti・Vulkan / Deno 2.9.6）。
> OP 数値レビュー W-5（`.claude/reviews/2026-08-31_b35cf5c/SUMMARY.md` — git 追跡外）の
> 「DEFAULT_TOLERANCE は M1 の宿題のまま」に対する実測。**計測のみでリポは無変更**、
> 末尾の tolerance 表は提案（未実装・未裁定）。

## 1. 何を測ったか

`packages/runtime/tests/gpu_ops_test.ts` の `checkAll` と**同じ入力・同じ経路**（単一ノード
グラフ → `createSession` → `session.run`）で実 GPU 実行し、CPU 参照
（`applyReferenceOpOutputs`）との要素ごと誤差を op 単位に集計した。ケースは
`tests/helpers/gpu_op_cases.ts` の 18 群をそのまま使う（UNARY / BINARY / DTYPE / MATH /
MATMUL / BMM / ATTENTION / GATHER / REDUCE / ARGMAX / TOPK / LAYOUT / LAYOUT2 / FUSED /
UPSAMPLE / DEFORM / GRU_SCAN / BOUNDARY）。

- 規模: **58 op グループ / 179 ケース / f32 要素 2,476,945 + 整数要素 481**
- 指標: `maxAbs` / `maxRel`（`|期待| > 1e-6` の要素のみ）/ `p99.9(abs)` / 期待値 ULP 単位の
  誤差 / 既定 tolerance の**消費率** `abs / (1e-5 + 1e-3·|期待|)`（1 で赤）
- 整数（i32 / bool）出力は厳密一致で突合 — **481 要素すべて一致・不一致 0**。非有限の
  食い違いも 0（NaN / ±Inf の門は既存の専用テストの担当で、ここでは触れていない）

オラクルの性質（`src/reference/ops.ts` の冒頭方針）を明示しておく。**「f64 オラクル」は
一様ではない**:

- elementwise は演算ごとに `Math.fround` する = f32 逐次計算の写し
- 縮約（matmul / 行 reduce / 二乗和）は **f64 で積んで格納時に 1 回だけ丸める** = 実質の
  厳密値。ここで測っている誤差は「GPU の f32 累算誤差」そのもの
- `cumsum` だけは参照側も**1 項ごとに丸める**（カーネルの逐次累算に丸め経路を揃える意図が
  コメントに明記されている）。よって cumsum の一致は**構造的**で、丸め誤差の測定ではない

## 2. 結果 — 既存コーパスでは 58 op 中 43 op が誤差ゼロ

まず結論から。既存の入力生成器（`SIGNED` = 0.75 の倍数 / `POSITIVE` = 0.125 刻み /
`NONZERO` = 0.5 の倍数）は**すべて 2 進で厳密表現できる粗い格子**に載っており、GEMM・conv・
行 reduce の中間和も f32 の厳密整数域に収まる。したがって縮約系は**丸めが一度も起きず、
GPU と参照がビット単位で一致する**。

機械確認（縮約系 9 op = matmul / bmm / linear / conv1d / conv2d / conv_transpose1d / sum /
cumsum / deform_conv2d の全ケース）:

- 入力の最細格子 = **2^−3**（= 1/8 刻み）
- 期待出力の最細格子 = **2^−9**（= 1/512 刻み）
- 期待出力の最大 = **55,467 格子単位**（f32 が整数を厳密に持てる上限 2^24 = 16,777,216 の
  **1/302**）
- 格子から外れた値 = **0 件**

つまり全ての部分和が厳密表現可能で、**累算順序・FMA 契約・ベクトル化のいずれにも依存せず**
同じ値になる。既存コーパスにおける GEMM 系のビット一致は偶然ではなく、この構造の帰結である。

> **この事実の含意（W-5 の核心）**: 既存コーパスからは GEMM / reduce 系の tolerance を
> **導出できない**。実測値 0 に貼り付けて `atol=0` を置けば、入力生成器を少し変えた瞬間に
> 赤くなる帯を焼き込むことになる。逆に現行の `atol 1e-5 / rtol 1e-3` は、これらの op に対して
> **無限のスラック**を与えているだけで、門として一切効いていない。

## 3. 第 2 パス（摂動コーパス）— 丸めを起こす入力での実測

§2 の理由で、既存コーパスだけでは縮約系の丸め挙動が測れない。そこで**同じケース・同じ
shape・同じ値域**のまま、f32 入力に `±1%` の**非 2 進小数**の揺らぎを掛けた第 2 パスを走らせた
（符号・定義域（`POSITIVE ≥ 0.125` / `NONZERO ≥ 0.5`）・ちょうど 0・非有限・`−F32_MAX` は保存）。

> 本文の依頼は「入力域は既存ケースのまま」だが、**既存コーパスは縮約の丸め誤差を構造的に
> 測れない**ため、一次表（§2）は依頼どおり据え置いたうえで、K 依存の導出（指針 d）に必要な
> 第 2 パスを**追加**した（一次表の値は第 2 パスの影響を受けない）。判断の逸脱として §9 に
> 再掲する。

### 3.1 縮約長 K の依存則

摂動コーパスの `maxAbs` は **√K に比例**する（K を 4 倍すると誤差は約 2 倍）。

S = そのテンソルの期待値の最大絶対値。

| ケース                                    |       K |   maxAbs |     S | `maxAbs / (eps·√K·S)` |
| ----------------------------------------- | ------: | -------: | ----: | --------------------: |
| matmul K=16                               |      16 |  2.29e−5 | 155.2 |                 0.309 |
| matmul K=64                               |      64 |  5.72e−5 |  96.9 |                 0.619 |
| matmul K=256                              |     256 |  1.07e−4 | 153.9 |                 0.364 |
| matmul K=1024                             |    1024 |  1.83e−4 | 146.7 |                 0.327 |
| matmul K=4096                             |    4096 |  3.62e−4 |  90.7 |                 0.524 |
| sum K=256                                 |     256 |  4.29e−6 |  13.4 |                 0.168 |
| sum K=4096                                |    4096 |  9.42e−6 |   4.9 |                 0.253 |
| sum K=16384                               |   16384 |  1.67e−5 |  12.1 |                 0.090 |
| matmul v4 タイル境界                      |      20 |  3.05e−5 | 129.4 |                 0.442 |
| linear タイル端数                         |      40 |  3.05e−5 | 108.9 |                 0.372 |
| conv2d igemm v4                           |      72 |  9.16e−5 | 320.7 |                 0.282 |
| conv1d / bmm / deform / sum（既存ケース） | 19〜700 | ≤ 2.3e−5 | ≤ 102 |            0.28〜0.31 |

**実測則（eps = 2^−23 = 1.19e−7）**:

```
maxAbs ≈ C · eps · √K · max|期待|      C = 0.09 〜 0.62（中央 ≈ 0.3・上限 0.62）
```

3 桁の K レンジ（16〜16384）で係数が 1 桁未満に収まる。ランダムウォーク型の累積誤差モデル
（`√K·eps·項の大きさ`）と整合する。**tolerance を K から引く根拠はこの 1 本**で足りる。

### 3.2 縮約長が伸びても悪化しない op

- `softmax`: K=16 → 4096 で `maxAbs` は 2.98e−8 → **2.33e−10 と縮む**（出力が 1/K に縮む
  ため）。`maxRel` は 7e−7 で横ばい。**K 依存の帯は不要**
- `cumsum`: K=8192 でも**誤差ちょうど 0**。参照が逐次丸めを鏡写しにしているため（§1）で、
  丸め誤差を測っているのではない
- `attention`: N=8 → 2048 で `maxAbs` は 3.8e−6 → 9.6e−7 と**縮む**が、`maxRel` は
  2.4e−4 → **1.75e−2 へ発散**する（出力が 0 近傍へ寄る = 桁落ち）。**相対帯で切ってはいけない
  典型**

## 4. ULP 級で見た単発 op（指針 b / c の材料）

摂動コーパスでの期待値 ULP 単位の最悪値:

| op                         |                 実測 ULP | WGSL 仕様帯（W-5 G1-4 の引用）                     |
| -------------------------- | -----------------------: | -------------------------------------------------- |
| `add` / `sub` / `mul`      |      **0**（ビット一致） | 正しく丸められる（IEEE）                           |
| `div`                      |                        1 | 2.5 ULP                                            |
| `sqrt` / `tanh` / `log1p`  |                        1 | inverseSqrt 2 ULP / tanh は**絶対 1e−5**           |
| `exp` / `sigmoid`          |                        2 | exp は `3 + 2·abs(x)` ULP（abs(x) ≤ 4.5 → 12 ULP） |
| `log`                      | 5（既存コーパスでは 13） | —                                                  |
| `sin`                      |                        7 | —                                                  |
| `softmax` / `safe_softmax` |                       13 | （合成）                                           |
| `gelu` / `gelu_tanh`       |         71,415 / 103,754 | （合成 — **桁落ち位置**。§5）                      |

`add` / `sub` / `mul` の 0 は構造的である: 参照は f64 で計算して 1 回 `fround` するが、f32 の
2 値の和・積は f64 で厳密に表せるので、`fround` は正しく丸められた f32 演算と**必ず一致**する。
`div` だけは f64 除算の二重丸めが原理的に入りうるうえ、WGSL の保証も 2.5 ULP なので別枠。

> 仕様帯の数値（除算 2.5 ULP / inverseSqrt 2 ULP / exp `3+2·abs(x)` ULP / tanh 絶対 1e−5）は
> W-5 の `findings/verify-6-chatgpt-runtime.md` §G1-4 からの引用で、**本測定では WGSL 仕様の
> 原文を再確認していない**。表に採る前に一次確認すること。

## 5. 桁落ち位置（指針 e の材料）

相対誤差が跳ねる 4 か所は、いずれも**期待値が 0 近傍へ落ちる位置**で、絶対誤差はむしろ小さい。

| op               | 位置                              |            期待値 |    abs |     rel |
| ---------------- | --------------------------------- | ----------------: | -----: | ------: |
| `gelu_tanh`      | x = −4.5（負側テール）            |          −5.14e−6 | 4.1e−8 |  7.9e−3 |
| `gelu`           | x = −3.75（負側テール）           |          −3.32e−4 | 1.4e−7 |  4.1e−4 |
| `layer_norm`     | 正規化後が 0 近傍（x−μ の桁落ち） |           1.01e−2 | 5.3e−7 |  5.2e−5 |
| `attention`      | N が大きく出力が平均化される      | 8.98e−2（N=2048） | 9.6e−7 | 1.75e−2 |
| `matmul`（摂動） | 縮約が打ち消し合う要素            |          −6.72e−4 | 8.4e−7 | 1.25e−3 |

いずれも **abs は 1e−6 未満**。W-5 の既知見（gelu の x≈−3.4 で相対 ≈2.2e−4）とも整合する
（こちらはより深いテール x=−3.75 なので 4.1e−4 と大きい）。**相対帯で切ると偽陽性になり、
絶対帯で受ければ 1e−6 級の床で足りる**、が指針 e の実測根拠。

摂動コーパスの `matmul` 相対 1.25e−3 は**現行 rtol 1e−3 を単独では超えている**（合成帯の
atol 1e−5 に救われて緑）。「rtol だけ見る帯」が成り立たないことの実例でもある。

## 6. tolerance をどう引くか（導出方針）

以上から、帯は 5 クラスへ分かれる。**クラスごとに「基準値 → 4〜8 倍マージン」で引く**。

1. **厳密（atol=0 / rtol=0）** — 値を計算しない op（コピー・添字・選択・比較・整数）と、
   丸めが構造的に起きない単発演算（`add` / `sub` / `mul`）。実測でも両パスとも 0。
2. **ULP 級（rtol = 16·eps ≈ 2e−6）** — `div`。実測 1 ULP・仕様 2.5 ULP の 6.4 倍。
3. **超越（atol 2e−6 / rtol 8e−6 = 64·eps）** — 実測 ULP（最大 13）と仕様帯（exp で 12 ULP）の
   悪い方 ×5、加えて桁落ち用の絶対床。
4. **縮約 / GEMM（K 依存）** — §3.1 の則から `4·eps·√K·max|期待|`。ただし**要素ごとの誤差は
   その要素の累算スケールに比例し、`|期待|` には比例しない**（打ち消し合った要素でも誤差は
   大きいまま）ので、`rtol·|期待|` では表せない。**帯の主役は atol 側**になる。
5. **桁落ちを含む合成（atol 4e−6 = 8·eps·入力スケール 4.5）** — `gelu` 族 / `layer_norm` /
   `attention`。相対帯を上げて対処してはならない（`gelu_tanh` なら rtol 1e−2 が必要になり、
   同じテンソルの他の要素に対して門が消える）。

### 6.1 「実測 0 に貼り付けるか / 則から引くか」— この波の本質的な分岐

- **案 α（実測に貼る）**: 43 op に `atol=0`。検出力は最大だが、入力生成器を変えた瞬間に赤くなる。
- **案 β（則から引く）**: §3.1 の則で帯を作る。入力を変えても緑だが、GEMM の帯は現行より
  **20 倍ゆるく**なり（atol 1e−5 → 2e−4）、実測 0 の op に対して門がほぼ消える。
- **案 γ（両建て・推奨）**: 既定は β の帯。そのうえで、**現行コーパスでビット一致する op には
  「この入力ではビット同一」という別テスト 1 本**を置く。§2 の格子論証が「なぜ厳密なのか」の
  根拠になるので、これは偶然への依存ではなく**検証済みの不変条件**を門にする形になる。
  ドライバが f16 へ落とす / 精度を下げるといった事故は α と同じ強さで捕まる。

### 7.1 併せて置く「ビット同一」門（案 γ の後半）

上表で `atol=0` としていない op のうち、**現行コーパスでは実測 0 のもの** —
`matmul` / `bmm` / `linear` / `conv1d` / `conv2d` / `conv_transpose1d` / `deform_conv2d` /
`sum` / `upsample_bilinear2d` — について、「この入力・この shape ではビット同一である」ことを
**別テスト 1 本**で固定する。根拠は §2 の格子論証（機械確認済み）で、IEEE-754 f32 に従う
どの実装でも成り立つ。落ちる場合の意味は「ドライバが f32 未満の精度で計算している / 生成
WGSL が別の演算へ落ちた」で、**tolerance を緩める対象ではない**。

リスク: 既知の Metal 事例（GEMV エピローグの 1 ULP 差 — `docs/known-issues.md`）のように、
特定ドライバでこの門だけが割れる可能性がある。そのときは**帯へ緩めず、op 単位で門を外して
理由を記録**する（tanh 飽和カナリアと同じ運用）。

## 8. 実装形の推奨（`checkAll` と省略呼び 46 か所）

### 8.1 省略呼びの実測内訳（2026-08-31 時点・機械集計）

`compareTensors` 49 か所のうち第 3 引数なしが **26**、`allclose` 23 か所のうち **20** —
合計 **46**（W-5 の数と一致）。内訳:

| 置き場                                                      |      件数 | 性格                                                                                                |
| ----------------------------------------------------------- | --------: | --------------------------------------------------------------------------------------------------- |
| `tests/reference_ops_test.ts`                               |     5 + 6 | **`allclose` / `compareTensors` 自体の単体テスト**。既定値をそのまま検証している = 触ってはいけない |
| `tests/runtime_executor_test.ts`                            |    2 + 14 | フェイク device / 実行器の配線テスト（値は自明な小データ）                                          |
| `tests/gpu_ops_test.ts`                                     |         3 | `checkAll` 1 か所（= 全掃引の門）+ `sym_prefix_slice` / 記号軸 `cat` の 2 か所                      |
| `tests/gpu_{f16,i8,i4}_weights_test.ts`                     | 5 + 5 + 4 | 量子化重み経路の linear/GEMM 突合（GEMM クラス相当）                                                |
| `tests/gpu_gemm_skinny_test.ts` / `gpu_linear_gemv_test.ts` |     1 + 1 | GEMM 変種の突合（同上）                                                                             |

**46 か所を一括で変える必要はない**。門として効くのは `checkAll` の 1 か所と、GEMM 系
14 か所（量子化 + skinny + gemv）だけで、残り 27 か所は「既定値そのものの検証」か
「配線テスト」である。

### 8.2 実装形の候補

- **A 案（推奨）: テスト側に表を置く。`src` は無変更。**
  `tests/helpers/op-tolerance.ts` に `OP_TOLERANCE: Record<string, Tolerance>` を置き、
  `checkAll` が `testCase.op` で引く。**表に無い op は fail loudly**（既定へ落とさない —
  新 op を足したときに「黙って汎用帯で通る」形を塞ぐ）。ケース単位の例外は `OpCase` に
  `tolerance?: Tolerance` を足して上書き（悪条件ケース用の逃げ道）。
  GEMM 系 14 か所は同じ表から GEMM クラスの値を明示的に渡す。
  `DEFAULT_TOLERANCE` は `src` に残すが、**用途を「E2E golden の既定」に限定**して
  doc コメントを書き換える（`reference_ops_test.ts` の既定値検証はそのまま生きる）。
- **B 案: `allclose` に縮約スケール項を足す。**
  `band = atol + rtol·|期待| + κ·√K·max|期待|`（κ = 4·eps）。§6 の 4 で述べた「誤差は
  `|期待|` に比例しない」を素直に表せる唯一の形で、GEMM の帯を 2e−4 という固定値でなく
  ケースの K と実データから引ける。ただし**公開 API（`Tolerance` 型）の変更**で、E2E 側の
  既存 tolerance 全部に影響が及ぶ。A 案を入れたあとの改善として温存するのが妥当。
- **C 案: 現状維持 + doc 化。** 却下。§2.2 のとおり現行帯は最悪でも消費率 2.6e−2 で、
  「掃引の門」を名乗れる強度が無い。

推奨は **A 案 + §7.1 のビット同一門**（= 案 γ）。B 案は A 案を入れたあとの後続波として
`docs/backlog.md` へ起票する形が妥当。

## 9. 再現手順・限界

- 計測スクリプトはスクラッチ（`measure-op-tolerance.ts` / `validate-tolerance.ts` /
  `check-dyadic.ts`）で**リポには入れていない**。再現に必要な要素は 3 つだけ:
  ① `gpu_ops_test.ts` の `runOutputs` の写経 ② `applyReferenceOpOutputs` との要素ごと突合
  ③ 摂動パスは f32 入力に `v·(1 + 0.01·(2·hash(i) − 1))` を掛ける（0・非有限・`|v|>1e30` は保存）
- **1 機・1 ドライバの実測**（RTX 3080 Ti / Vulkan）。Metal / DXC では超越関数の ULP と
  §7.1 のビット同一が変わりうる。表を採るなら M2 実機で消費率だけ再測するのが望ましい
- 非有限（NaN / ±Inf）の扱いは既存の専用テスト群の担当で、本測定は触れていない
- 量子化重み経路（i4 / i8 / f16 格納）は本測定の対象外。GEMM クラス相当と見なしているが
  実測していない
- WGSL 仕様帯の数値（§4）は W-5 findings からの**引用で、原文未確認**
- **依頼からの逸脱（§3 再掲）**: 「入力域は既存ケースのまま」に対し、K 依存の導出のために
  ±1% 摂動の第 2 パスを追加した。§2 の一次表は依頼どおり既存入力のみで、第 2 パスは
  §3 以降の別コーパスとして分離してある
